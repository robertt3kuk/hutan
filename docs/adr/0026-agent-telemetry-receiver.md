# 0026. A loopback OTLP receiver for agents' own telemetry

- Status: accepted (2026-11-03; the user took the spike's § 6 decisions 1–4 as recommended: a receiver, off by default and enabled per agent; transcripts stay primary for Claude Code and Codex with OTLP as the opt-in live upgrade; automatic in Hutan's terminals for enabled agents and `--telemetry` for agents started elsewhere; a random persistent port in `daemon.toml`. Decision 5, an OSC 7501 `insight=` extension, is deferred)
- Date: 2026-11-03
- Milestone: M13 (agent and subagent monitor; agent insight) — slices TEL-1…TEL-4 of the spike
- Relates to: ADR 0001 (the daemon owns state), ADR 0003 (dependency direction), ADR 0008 (no secrets in logs, events, SQLite), ADR 0016 (agent control surface), ADR 0022 (remote access: SSH is the authentication, **no listener**), `docs/integrations.md` § Insight, `docs/protocol.md` § Agent insight
- Evidence: `docs/spikes/2026-11-03-agent-telemetry.md` (real binaries of eight agents run against a local mock API, prototype receiver, recorded payloads in `docs/spikes/2026-11-03-agent-telemetry/fixtures/`)

## Context
The user asked (2026-11-03) how other agents will give Hutan their stats — tokens, context, cost, tools, files — Claude Code and Codex first, then a generic channel. Hutan's channels today: OSC 7501 (state), hooks and the status-line tee, the OMP extension, `hutan agent report --insight-json` (all in `docs/integrations.md`), and, in progress, tails of Claude Code's and Codex's transcripts (INSIGHT-C). Eight agents export OpenTelemetry themselves (Claude Code, Codex, OMP, Gemini CLI, Qwen Code, Copilot CLI, Goose, OpenCode — all observed, spike § 2); Cursor CLI, Amp and Aider do not.

Facts that shape the decision (spike § 3, all observed unless marked):
- **`hutand` has no TCP listener today** (`grep` of `crates/*/src`; ADR 0022 chose "no listener" for remote access). An OTLP receiver is the first one: a new attack surface, hence this ADR.
- Wire formats are mixed: protobuf (Claude Code, Codex, OMP, Goose, Copilot), **JSON only** (Gemini, Qwen, OpenCode), chunked bodies with no `Content-Length` (OMP, Gemini, Qwen, OpenCode traces); nobody gzips; nobody needs gRPC.
- **Content leaks with "prompts off":** Codex's `tool_result` carries arguments and output; Gemini exports system instructions and the `-p` prompt in `process.command_args`; OpenCode exports `ai.prompt` ungated; Qwen exports `function_args`.
- **A receiver that does not answer slows the agents' exit** (Codex +33 s, Claude Code +2 s); a closed port costs ≤ 1.3 s.
- Enablement is not uniform: env vars suffice for seven agents, **not for Codex** (config file only; the endpoint cannot come from env, `${VAR}` is not expanded in config, per-signal headers and `OTEL_RESOURCE_ATTRIBUTES` can); Claude Code's own `~/.claude/settings.json` `env` overrides the terminal's environment. Standard `OTEL_*` names exported into every terminal would also capture the user's own instrumented programs.
- Transcripts remain richer for Claude Code and Codex (Codex's context window, Claude's `cost-state`, file edits) and need no listener.

## Options
| Option | Pros | Cons |
|---|---|---|
| A. Transcripts and `hutan agent report` only | no listener; INSIGHT-C is under way | one parser per format for every new agent (JSONL ×3, SQLite ×3); nothing live; no channel for agents without a file format Hutan reads; unavailable from inside Contain (unix socket refused) |
| B. OTLP receiver in `hutand`, per-agent opt-in (**chosen**) | one mapper per agent over one listener; live (≈ 1 s); standard, so future agents join without Hutan code; reachable from Contain with network on | first TCP listener; mapper upkeep per agent release; content to be filtered; the user's own OTel destination cannot be served at once |
| C. A separate collector process (OpenTelemetry Collector, Laminar's) | mature | a new dependency to install and supervise, outside the daemon's lifecycle and bounds; rejected in the Laminar spike § 6 |
| D. OTLP receiver always on, `OTEL_*` in every PTY | zero setup | hijacks the user's own OTel apps; ambient exposure; rejected |

## Decision
1. **The daemon hosts an OTLP/HTTP receiver** (protobuf and OTLP-JSON; no gRPC, no TLS). Decoding and the per-agent mappers live in a pure service crate (`crates/telemetry`, no sockets, no daemon types); the listener, the token registry and the settings live in `hutand` (`crates/daemon/src/telemetry/`). Dependencies point inward (ADR 0003): `hutan-core` knows nothing of OTLP. New dependency: `prost` (+ `prost-derive`) for a **hand-written subset** of the three Export requests, not `opentelemetry-proto` (which pulls `tonic`, `opentelemetry_sdk`, `futures`). HTTP is `hyper` (http1 server), already in `Cargo.lock` through `reqwest`.
2. **Off unless the user enables an agent.** No socket exists until `[telemetry.agents] <agent> = true` (`daemon.toml`, Settings → Integrations, `hutan telemetry enable <agent>`); it is a user-only setting like every `daemon.settings.set` (an agent over MCP or `hutan ui` cannot turn it on). The listener binds when the first agent is enabled and closes with the last. It binds **`127.0.0.1` only**, on `[telemetry] port` (`0` = pick once at random in the ephemeral range and persist it, because Codex's endpoint lives in a config file); a busy persisted port leaves the receiver down and visible (`hutan telemetry status`, `hutan integration status`), never re-bound elsewhere silently.
3. **A process reports only as its own session.** Each session gets a 128-bit random capability at spawn, held in memory only (never in SQLite, events, logs, argv, notifications or `hutan ps`); a new spawn gets a new one. It is accepted as the URL path prefix (`/s/<token>/v1/<signal>`) or the `x-hutan-token` / `Authorization: Bearer` header, compared in constant time; it selects the session. **Nothing inside a payload selects a session**: `session.id`, `conversation.id`, resource attributes are untrusted labels. Every refusal is the same answer.
4. **Allowlist, not denylist.** Each mapper names the attributes it reads; the decoder skips everything else without materialising it. Prompts, tool arguments and outputs, system instructions, command lines, file contents and e-mail addresses are on no list. Hutan also sets each agent's content gates off in the environment it injects, as defence in depth. Nothing is persisted beyond the in-memory insight record, raw payloads are dropped after mapping, **nothing is forwarded**, and Hutan never injects a non-loopback endpoint.
5. **Bounded everywhere** (ADR "bounded everything"): header block ≤ 8 KiB; body ≤ 1 MiB on the wire and ≤ 4 MiB inflated (gzip decoded under a limit); ≤ 2 000 records per request, ≤ 64 attributes per record read, strings cut at 256 characters; ≤ 16 connections, ≤ 4 per session; a token bucket per session; read timeout 2 s, idle keep-alive 30 s; a **bounded** channel (64 requests) to one mapper task, `429` + `Retry-After` when full. One reducer record per session, as for hooks.
6. **The receiver always answers at once and never blocks an agent.** Checks before the body is read: `POST`; `Host` ∈ {`127.0.0.1`, `localhost`} (421); `Content-Type` ∈ {protobuf, JSON} (415); path/header token (401); size (413). Accepted requests are answered `200` with the signal's empty `Export*ServiceResponse` **before** mapping.
7. **Telemetry carries no authority.** Its only output is an `InsightReport` with a new `source: otlp` (additive protocol minor, capability `agent.telemetry`, classified Read/Mutate in `router.rs` with golden fixtures). It cannot set an agent's state, approvals, tasks, notifications, grants or user hooks (those stay with OSC 7501 and hooks). Per block the existing **best-source rule** decides; counters from two sources are never added. Paths it might carry never go into notifications or hooks (as for every insight).
8. **Enablement is launch-scoped, never ambient.** `HUTAN_OTLP_ENDPOINT` and `HUTAN_OTLP_TOKEN` (non-standard names) are exported into a session's PTY only while telemetry is on. An agent's own export is switched on by the narrowest mechanism that works — a shell function from the shell integration that sets that agent's variables for that command only, or an explicit `hutan integration install <agent> --telemetry` (Claude Code: user settings `env` + `otelHeadersHelper`; Codex: `[otel]` with a log exporter only) — and **never overrides** an `OTEL_*` the user, a managed policy or the agent's settings already set: it is detected and `hutan integration status` says so.
9. **The contract is public** (`docs/integrations.md` § Report your agent's stats to Hutan): L0 recognised · L1 OSC 7501 state · L2 `hutan agent report --insight-json` · L3 OTLP with the OpenTelemetry GenAI semantic conventions plus optional `hutan.*` attributes (cost, context, files). Mappers are versioned per agent and tested on recorded payloads; an unmatched shape means "not reported", never zero.
10. **One listener for every OTLP consumer.** If the traces work of MW-7 (`docs/spikes/2026-10-20-laminar.md` § 6, TR-1) lands first it owns the listener and these limits and TEL-1 adds its sink; otherwise the reverse.

## Consequences
- `docs/integrations.md` gains the public contract and each agent's recipe; `docs/protocol.md` gains `agent.telemetry` (version bump + `just update-golden`); `docs/architecture.md` gains the first listener in `hutand`; `docs/shell-integration.md` gains the per-agent functions; `docs/packaging.md` the new `[telemetry]` settings. A Seatbelt profile with network on already lets a contained agent reach loopback TCP (`docs/agents.md` § Contain): the parser is exposed to it, hence the allowlist, bounds and no-authority rules above; with network off nothing reaches the port.
- Claude Code and Codex keep their transcripts as the primary insight source (INSIGHT-C); OTLP is the opt-in live upgrade. The generic channel pays for itself for Gemini, Qwen, Copilot, Goose, OMP and OpenCode.
- Costs accepted: a listener to defend and fuzz, a `prost` dependency, per-agent mapper maintenance, a user who already exports an agent's telemetry to their own collector gets Hutan's insight only if they point it elsewhere (forwarding is a later, separate decision).
- Not decided here: gRPC (no agent needs it), forwarding to another collector, storing traces (MW-7), an `insight=` extension of OSC 7501 for remote or containerised agents, enablement through a PATH shim.
- **Revisit when:** the transcripts prove enough for the agents users actually run (then drop the opt-in UI, keep L2); an agent drops OTel or stops allowing local endpoints; a decoder bug or abuse report; an agent needs gRPC or TLS; Hutan gains a restricted socket for contained agents (SANDBOX-2B), which would give them a channel without TCP.
