# 0015. Harness chat over ACP, accounts through harnesses, OMP first-class

- Status: accepted (2026-10-15, with the user)
- Milestone: M8 (pulled forward), M16 follow-up
- Amends: ADR 0005 (agent integration), ADR 0008 (credentials) — confirms its rule

## Context
- Users want to chat (and run the assistant) through the harnesses they already use and are logged in to: OMP (OAuth logins to Anthropic, OpenAI Codex, xAI, OpenCode, …), Claude Code, Codex. Measured here: `omp acp` (18.11.1) answers ACP `initialize` with `loadSession`, `sessionCapabilities {list, fork, resume, close}`, MCP over http/sse, embedded context and images, and one auth method `agent` ("use existing local credentials under ~/.omp"). `claude` 2.1.299 and `codex` 0.162.1 are installed; Codex already runs over `codex app-server` (M4).
- The user first asked for Hutan's own OAuth like OMP's; after weighing it (Anthropic blocks subscription OAuth outside Claude Code: we hit `403 OAuth authentication is currently not allowed` today; ADR 0008), the user chose **logins through harnesses**.

## Decision
- **Hutan never performs subscription OAuth and never reads, stores or forwards harness tokens.** ADR 0008 stands. API keys for direct providers stay in the Keychain (M5).
- **ACP client** in `crates/agents` (ACP v1 over stdio JSON-RPC, like the Codex adapter): sessions, prompt turns with streaming updates, tool calls, plans, permission requests (`session/request_permission` → Hutan approvals, enforced in the daemon), `session/load`/`resume`, model and mode selection where the agent offers them, MCP servers passed through. Mapped onto the existing `AgentEvent` model and chat journal, so the chat view, approvals, notifications, history index and tasks work unchanged.
- **Harnesses** (registry, `daemon.toml [harness.<id>]` with `bin`/`args`, detection on PATH):
  - `omp` — **first-class**: `omp acp`; models from OMP (`omp models --json`, or the ACP session config), OMP sessions resumable by id, OMP's own subagents shown in the agent tree.
  - `claude` — Claude Code over ACP through the Claude Code ACP adapter (`claude-agent-acp`, or the older `claude-code-acp`; Hutan points to it, does not bundle it); its login is Claude Code's.
  - `codex` — stays on `codex app-server` (M4); its login API (`account/read`, `account/login/start`) is used for the accounts view.
- **Accounts** view (daemon `account.list|login|logout`): per harness, which providers/accounts are logged in (OMP: providers with credentials from `omp models --json` / `omp usage`; Codex: `account/read`; Claude Code: its status command) — names and plan only, never tokens. *Log in* runs the harness's own flow: an interactive terminal session (`omp login <provider>`, `claude` `/login`, `codex login`) or the harness API when it has one (Codex `account/login/start` returns a URL the desktop opens). *Log out* likewise delegates.
- **Assistant backend per scope** (M16 follow-up): the global assistant and each project's assistant choose `omp` / `claude` / `codex` / a direct provider; the assistant is **optional** (`assistant.enabled`, default on; off hides the panel and ⌥Space). Harness assistants run with tools restricted to read-only (or none) where the harness allows it; attachments (M16) are sent as ACP embedded context.
- **Tools**: MCP servers configured in Hutan (`[mcp.<name>]`) are passed to ACP sessions; Hutan as an MCP server is M8 later.

## Consequences
- One chat UI for every harness; no token handling in Hutan; harness version ranges are pinned and fixture-tested like Codex.
- Features depend on what each harness exposes over ACP (models, modes, subagents); gaps are shown, not faked.

## Amendment (2026-10-25): several accounts per harness

- Status: accepted for implementation (slice ACCOUNTS-MULTI; reviewed at merge). Protocol 0.50.

### Context
People hold two subscriptions (work and personal) and want one harness to run as either, per project or per session: Claude Code [#18435](https://github.com/anthropics/claude-code/issues/18435) (1 183 👍) and [#36151](https://github.com/anthropics/claude-code/issues/36151) (1 065 👍), Codex [#4432](https://github.com/openai/codex/issues/4432) (`--auth-profile`). Until now Hutan had one login per harness, the one the harness finds in its own home. The harnesses already isolate logins by **configuration home**, selected by an environment variable; that is the only mechanism this amendment uses.

### Decision
1. **An account is a named configuration home of one harness that Hutan creates and the harness fills.** Its identity is `(harness, name)`. The home is `<data dir>/accounts/<harness>/<name>/` (created empty, mode 0700, at its canonical path), and a session of that account starts the harness with the harness's own environment variable pointing at it (table below). The name is 1 to 32 lowercase letters, digits, `-`, `_`, starting with a letter or digit; `system` is reserved for the harness's own login (no variable: what the harness uses when started in a terminal, the only account until now).
2. **Hutan never opens the contents of a home.** It creates the directory, checks that it is a directory, and deletes the tree on *Remove*; it lists, launches and logs in through the harness (`claude auth status --json` with the variable set, `account/read`, `omp models --json`: the commands ADR 0015 already uses). No file inside a home is read, copied, parsed, watched or listed — not `auth.json`, not `agent.db`, not `.credentials.json`, not settings. The *allowlist of what Hutan reads in an account home is empty*; tests make the credential files unreadable and assert that nothing fails. Hutan never touches the Keychain: Claude Code and Codex may keep a home's secret there, keyed by the home's path, and only the harness's own login/logout command reads or removes it.
3. **Login is the harness's own login command, with the variable set, in a visible terminal session** (`omp login`, `claude auth login`, `codex login`), exactly as in § Decision above; Hutan sees the session end and lists the account again.
4. **Remove asks first** (the desktop confirms, `hutan account remove` asks `[y/N]` or takes `--yes`), refuses while a live session runs on the account, runs the harness's own non-interactive logout with the variable set where one exists (`claude auth logout`, `codex logout`: so a Keychain item and the provider-side login go with it), then deletes the home. Where the logout could not run the answer says so and names the command to run by hand.
5. **Defaults.** Precedence for a new session, first that names an account: the session's own choice (`chat.create.account`, `hutan new --account`, the Start sheet) > the project's default > the harness's default > the harness's own login. A default is stored in the account registry (`account.default`); `[harness.<id>] account` / `[codex] account` in `daemon.toml` is the harness default of a user who keeps their settings in a file, used when the registry has none. The account a session started with is stored in its record: restarts and restores keep it whatever the defaults say now.
6. **The registry holds no secret**: name, harness, label, home path, creation time, and the defaults. It is a file beside the homes (`accounts/registry.json`), written atomically.
7. **Limits are per account.** A usage window is attributed to the account whose session or probe reported it; the summary lists each account's windows (§ Usage in `docs/agents.md`).

OMP also has `--profile <name>` (`~/.omp/profiles/<name>/agent`); Hutan does not use it, because the profile directory lives in the user's own home and a profile is not Hutan's to delete. Claude Code's *Console sign-in without an API key* is stored outside the config directory ("separate directories don't keep two Claude Console sign-ins apart"): two such accounts are not isolated; subscription (claude.ai) logins are.

### Consequences
- A fresh home has none of the user's own harness settings (models, MCP servers, skills, `config.toml`): an account starts as a first run of the harness. Hutan does not copy settings in (it would have to read them); the `env` and `args` of `[harness.<id>]` still apply.
- Credential variables of the user's login environment that outrank a stored login still win. For Claude Code, `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and `CLAUDE_CODE_OAUTH_TOKEN` outrank a `/login` credential ([authentication precedence](https://code.claude.com/docs/en/authentication#authentication-precedence)), so Hutan removes those three from the environment of a Claude Code process that runs as an account; for the others the account page says the variable would win.
- Keychain items of Claude Code and Codex accumulate per home until the harness's logout removes them; Remove runs it (decision 4).
- The ADR's invariants hold: no token is read, stored or forwarded; an account's only footprint in Hutan is a name, a label and a path.
