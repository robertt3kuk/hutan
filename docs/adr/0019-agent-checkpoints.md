# 0019. Per-turn checkpoints of agent edits (hidden git refs, path-scoped undoable restore)

- Status: **accepted** 2026-10-21 with the user; storage in hidden refs of the user's repository and the retention numbers below as proposed; default **on** for agent chats in git checkouts (the user first chose off, then asked to follow the community research, which contradicts off: `docs/spikes/2026-10-21-community-opinions.md`)
- Date: 2026-10-21
- Milestone: UX (slice family CK-1…CK-7; card `UX-CHECKPOINT`)
- Builds on: ADR 0001 (daemon owns state), ADR 0002 (additive protocol minor + capability), ADR 0012 amendment 2026-10-21 (file I/O and `fs.changed` origin through the daemon), ADR 0016 (one control surface; agent-originated requests)
- Evidence: `docs/spikes/2026-10-21-checkpoints.md` (measurements on a 10 k-file temporary repository, harness capabilities, slice plan)

## Context
Hutan can reopen a session but cannot take back what an agent did to files. Undo of agent edits is the most-reacted gap in the competitor research: Codex [#9203](https://github.com/openai/codex/issues/9203) (+538) and [#11626](https://github.com/openai/codex/issues/11626) (+229), Claude Code [#64615](https://github.com/anthropics/claude-code/issues/64615) (destructive default, no preview) and [#8763](https://github.com/anthropics/claude-code/issues/8763), Zed [#28676](https://github.com/zed-industries/zed/issues/28676) (restore must itself be undoable) (`docs/spikes/2026-10-21-ux-plan.md`, T6, card #23).

Facts that shape the decision:
- The three harnesses' own rewinds are not usable by Hutan: Claude Code's `/rewind` tracks only its edit tools (not Bash or subagents) and no ACP v1 method drives it; Codex's app-server `thread/revert` "does not revert local file changes" and `thread/rollback` was removed; OMP's `/rewind` is an interactive branch of messages. ACP v1 has no rewind/truncate method (`session/fork` is a Draft RFD). Hutan offers harnesses no `fs`/`terminal` (`docs/agents.md:148`), so it sees edits only as `FileDiff` events, which miss Bash-driven changes.
- Codex's own snapshot undo (temporary `GIT_INDEX_FILE` + `git add`) failed in public: `git add -A` over a home directory and cancelled captures left 200 GB / 774 GiB of `tmp_pack_*` ([#19588](https://github.com/openai/codex/issues/19588), [#50920](https://github.com/openai/codex/issues/50920)). The failure modes are known and must be designed out.
- Measured with plain git 2.54 (spike §4): a snapshot of an unchanged 10 k-file tree costs ≈ 0.1 s, scales with changed bytes, never touches the user's index/HEAD/stash/refs/worktree, never reads ignored files; unbounded first-time hashing (6.7 s, 64 MiB for 10 k untracked files) and big files (120 MiB: 3.5 s, +129 MiB) are the expensive cases; 20 000 loose refs slow `git branch` to 0.7 s; `git push --mirror` pushes `refs/hutan/*`; `gc --prune=now` keeps objects reachable from those refs.

## Options
| Option | Pros | Cons |
|---|---|---|
| **A. Hidden refs in the user's repository, snapshots through a private index with plumbing (chosen)** | exact tree per turn incl. Bash edits and untracked files; dedupes against existing objects; objects safe from `gc`; worktrees share the store; no new storage format; measured ≈ 0.1 s | needs git; refs visible to `log --all` and `push --mirror`; ref count must be bounded; filter/LFS corner cases need explicit handling |
| B. Private bare repository under `HUTAN_HOME` (shadow store) | no ref clutter or push risk; our own gc | every new blob stored twice; `alternates` unsafe against the source repo's `gc` **[INFERENCE]**; one more store to reconcile |
| C. APFS `clonefile` copies of the tree per turn | no git; fast copies | whole-tree copy needed to get pre-images (the agent's edits are unknown in advance) which captures ignored files (privacy rule), no dedupe/retention story **[INFERENCE]** |
| D. Rely on each harness's rewind | no storage | none is drivable over ACP / app-server; coverage differs (Claude Code skips Bash and subagents) |
| E. `git stash create` / commits on a branch | no plumbing | no untracked files without extra steps, touches or pollutes user-visible history |
| F. Do nothing | free | leaves the top user-reported gap open |

## Decision
1. **Checkpoints are daemon state** (ADR 0001): the daemon snapshots, stores, lists, previews and restores; clients render and ask. New requests are an additive protocol minor with capability `checkpoint` (ADR 0002).
2. **Scope v1:** chat sessions with a harness (Codex, OMP, Claude Code) whose working directory is inside a git checkout. Not git, git missing, `$HOME`, `/` or volume roots, or more than `max_untracked_files` untracked files → state `unsupported` with a stated reason and no snapshot. Terminal agents and direct model chats are out of v1.
3. **Snapshot = a tree commit in a hidden ref** `refs/hutan/checkpoints/<session>/<turn>` (the end commit's parent is the start commit; restore checkpoints use `-r<n>` refs), taken before the prompt reaches the agent and when the turn ends, with commit trailers `Hutan-Session`, `Hutan-Turn`, `Hutan-Kind`. No end ref is written for a turn that changed nothing. Metadata is in SQLite (`checkpoints` table) and is rebuildable from the trailers.
4. **Never the user's state:** every git call uses a **private index** (`GIT_INDEX_FILE` under `HUTAN_HOME`, seeded from the user's index, else `HEAD`), `GIT_OPTIONAL_LOCKS=0`, `GIT_NO_LAZY_FETCH`, `-c core.hooksPath=/dev/null`, a fixed identity, and plumbing only (`update-index --refresh`, `ls-files -o --exclude-standard`, `diff-files`, `hash-object -w --no-filters`, `update-index --index-info`, `write-tree`, `commit-tree`, `update-ref`). The user's index, HEAD, stash, branches, reflogs and working tree are never written; reviewers check this by test.
5. **Privacy and content rules:** ignored files are never read; bytes are stored raw (no eol/ident/LFS filters); paths with a `filter=` attribute (LFS), gitlinks and nested repositories, non-regular files and a name denylist of likely secrets are skipped and *listed*; symlinks are stored as links and never restored by v1; staged state is not captured or restored.
6. **Bounds before writes** (defaults in `daemon.toml [checkpoints]`, per-project override, effective for the next snapshot): `max_file_bytes` 10 MiB, `snapshot_budget_bytes` 64 MiB, `max_files` 5 000 per snapshot, `max_untracked_files` 20 000. Candidates are `lstat`ed and over-budget files skipped **before** `hash-object` runs. A git write is never cancelled in flight. Three consecutive failures or less than 2 GiB free disk switch a checkout's checkpoints off with a visible reason.
7. **Retention** (numbers pending decision D2): per session the newest 100 turns, 30 days of inactivity, a recorded-bytes cap of 1 GiB per repository and at most 1 000 refs per repository; refs are packed with `pack-refs --include 'refs/hutan/*'`. Hutan deletes refs and rows and **never runs `gc` or `prune`**; unreachable objects age out under git's own settings. Checkpoints of a removed worktree stay until retention drops them.
8. **Restore is files only, path-scoped, previewed and undoable.** Per path, three-way: with start tree `S`, end tree `E` of the covered turns and the checkout now, a path that still equals `E` is rewritten to `S` (or deleted when `S` lacks it); a path that differs is a **conflict** (`after`, `gap`, or `during` with `fs.changed` attribution) left untouched unless named in `accept_conflicts`; paths not changed by the covered turns are never touched. A **preview** is always produced first and the apply request carries its `plan_digest` (a stale digest answers `conflict`). Before writing the daemon takes a `restore` checkpoint of the present state and afterwards another; the restore is a synthetic turn, so **Undo is the same algorithm** and undo-of-undo works. Writes are confined to the checkout, atomic, raw, announced through `fs.changed` with origin `restore`. A restore is refused while any agent in the checkout has a running turn.
9. **Conversation rewind is not promised.** No harness Hutan drives can rewind its conversation (spike §5.4). Every restore is labelled "files only — `<harness>` still remembers this turn", HEAD/branches/stash are not rewound, and the dialog offers to put a note in the composer. Real conversation rewind needs its own spike (CK-7) and, if feasible, an ADR amendment.
10. **Who may call it** (ADR 0016): `checkpoint.list`, `.diff`, `.preview` are reads (also MCP tools `checkpoint_list`, `checkpoint_diff`); `checkpoint.restore` is `UserOnly` — an agent-originated connection gets `forbidden` regardless of `[control]`; `checkpoint.remove` follows `[control]`.
11. **Surfaces:** `hutan checkpoint ls|diff|restore|undo|rm` (restore prints the preview, default answer No, `--yes` required without a terminal, conflicts need `--accept-conflicts`); desktop turn-footer *Rewind…* and `Restored — Undo`, a preview dialog whose default focus is *Cancel*, ⌘K commands, an Agents-page Checkpoints list, a Settings section; all gated on the capability.
12. **Default:** on for agent chat sessions in git checkouts, with the bounds above (`docs/spikes/2026-10-21-community-opinions.md`: Claude Code, Cursor and Copilot CLI ship checkpoints on; Codex's rewind request has +229). `[checkpoints] mode = "on" | "off"` globally and per project; the first restore dialog and the Settings section say "files only; edits made by shell commands outside the turn may be missed".

## Consequences
- The UX card's acceptance becomes testable: a turn editing three files including a new one → restore returns the exact tree, undoing the restore returns it again, a file edited after the turn is listed and needs acknowledgement.
- A `core` pure `restore_plan` and a guarded-write primitive are shared with editor E-10's per-hunk Reject; `fs.changed.origin` (E-3) gains `restore`.
- Costs: ≈ 0.1 s per turn on a warm 10 k-file repository, a few MB a day of objects (inference), one SQLite table and one migration, up to 1 000 refs per repository that `git log --all` shows and `git push --mirror` would push (docs say so; Hutan never pushes, `docs/orchestration.md:178`). Disk use trails retention by git's own prune expiry.
- Harder: filter/LFS repositories lose coverage of those paths (skipped and listed); edits outside the checkout, in submodules, or by Bash to other directories are not captured; the restore dialog must be honest about all of it.
- Revisit when: ACP stabilises a rewind/fork-at-message method or Codex's pinned range exposes `thread/revert` / `thread/fork {lastTurnId}` (conversation rewind); a shadow store (option B) if refs in the user's repository prove unacceptable in practice; retention numbers after real usage.
- Slices CK-1…CK-7 in the spike §7; CK-1 (engine, no protocol) can start as soon as this ADR is accepted.
