# 0021. Sandboxed agent runs: native sandboxes first, Hutan's Seatbelt where none exists, containers later

- Status: proposed
- Date: 2026-10-26
- Milestone: after M8 (agents); security track
- Relates to: ADR 0005 (agent integration), ADR 0008 and ADR 0015 (credentials: Hutan never touches harness tokens), ADR 0016 and ADR 0017 (control surface; "a stronger restricted endpoint + sandbox"), ADR 0019 (checkpoints), ADR 0020 (Finish is the user's)
- Evidence: `docs/spikes/2026-10-26-sandbox/README.md` (harness facts with links, a Seatbelt prototype measured on macOS 27.0.1 arm64, container survey)
- Number: draft; renumber on merge if another ADR took 0021.

## Context
- Users run agents unattended and ask for a boundary so that approvals are not the only guard (Orca #13665, Superset #3957 and #2419, agent-orchestrator #6663). What they want is **safe autonomy**: no prompts *because* damage is contained.
- Hutan today: approvals (harness-owned, answered in the daemon) and the `[control]` policy. Codex's `sandbox`/`approval_policy` are on the wire but no UI sets them; ACP harnesses accept a `mode` that no UI sets; `chat.create` refuses policy/sandbox for ACP harnesses.
- Harnesses differ: **Codex** has a Seatbelt/bubblewrap sandbox with three modes and a network switch; **Claude Code** has a Seatbelt/bubblewrap *Bash* sandbox (file tools, MCP servers, hooks stay outside it) plus permission modes, switchable per session; **OMP has no OS sandbox** (approval modes and a tool list only).
- macOS offers one unprivileged per-process-tree mechanism: Seatbelt (`sandbox-exec`, deprecated in its man page, used by Codex, Claude Code, `srt`, Homebrew). App Sandbox and Endpoint Security do not fit. **Seatbelt does not nest**: a process inside any non-trivial profile that calls `sandbox-exec` gets `sandbox_apply: Operation not permitted` (reproduced; openai/codex #45657).
- A prototype profile ("write only in the worktree and the repo's git dir") ran a PTY shell, git in a linked worktree, cargo, python and `omp acp` with no functional loss, ~9 ms once per process tree, and no measurable file-op overhead. A deny-by-default variant also blocked Keychain and network. Reads stay open unless denied; DNS leaks through any allowed unix socket; the harness itself needs network for its model API.
- Containers fit as a *placement* (PTY = `container exec -it`, ACP/Codex = stdio over `exec -i`), but need runtime detection, same-path mounts, a per-harness credential volume logged in *inside*, and a way to reach the daemon socket. No runtime is installed on the development machine; REMOTE-SPIKE solves the adjacent transport/authentication problem.

## Options
| Option | Pros | Cons |
|---|---|---|
| Do nothing (approvals only) | no work | `bypassPermissions`/`yolo` are one click away with no boundary; the demand stays unmet |
| Expose harness-native modes only | cheapest; maintained upstream; per-command network control (Codex, Claude) | OMP has nothing; Claude's file tools/MCP/hooks stay outside; policy-in-the-agent, not a boundary around it |
| Hutan Seatbelt around every session | one mechanism for all harnesses, covers file tools/MCP/hooks, makes the control-policy boundary real (per-session socket) | cannot nest with native sandboxes; whole-process network cannot be off without a proxy; profile maintenance; `sandbox-exec` deprecated; reads open by default |
| Containers only | strongest local boundary short of a VM; repeatable toolchains | runtime dependency, credentials-in-container flow, mount performance, path/socket plumbing, macOS-only tools unreachable |
| **Layered (chosen)** | each harness uses the best boundary it has; Hutan fills the OMP/terminal gap; containers added without redoing the UI | three code paths to test; the UI must say who enforces what |

## Decision
1. **One control, two parts: autonomy level and boundary, chosen together** as a *Safety* preset (*Ask*, *Contained*, *Read-only*, *Full access*) on the Start sheet for chats and terminal agents, with a project/global default. The daemon maps a preset to harness arguments per harness; a preset a harness cannot honour is disabled with the reason, never approximated. *Full access* (`danger-full-access`, `bypassPermissions`, `yolo`) keeps the existing "approves everything" warning styling. (`SANDBOX-1`)
2. **Native first.** Where a harness has an OS sandbox (Codex, Claude Code) *Contained* means that sandbox with the harness's own network and filesystem settings; Hutan passes it per session (Codex `sandbox`/`approval_policy`/network; Claude session mode + `_meta.claudeCode.options` `sandbox`/`settings` on `session/new`; terminal agents get flags) and shows the *effective* state read back from the harness, never only its own request. If the harness does not confirm (an adapter version that ignores the metadata), the UI says "not applied".
3. **Hutan's Seatbelt ("Contain") fills the gap**: for OMP chats, terminal agents and commands, and plain terminals on request. The daemon renders a profile per session from a typed policy (write roots = worktree + repo git dir without `hooks`/`config` + temp + a per-harness fragment; read-deny = credential directories and Hutan's data dir with a carve-out for `shell-integration/`; network on/off for commands, on for chat harnesses; unix sockets: only the session's own), wraps the spawn as `sandbox-exec -f … -D … -- argv` at the two existing choke points (terminal `command()`, `Transport::spawn_v2`), canonicalizes every root, and **fails closed**: if `sandbox-exec` or its self-test is unavailable the session does not start uncontained. `sandbox-exec` execs in place, so process trees, `hutan ps` and signals are unchanged. (`SANDBOX-2`)
4. **No stacking.** Contain and a harness's native sandbox are mutually exclusive per session (they cannot nest). Applying Contain to Codex or Claude is an explicit advanced option that turns their native sandbox off (`danger-full-access` / `externalSandbox`, `sandbox.enabled: false`) to cover file tools, MCP servers and hooks too; it is never the default.
5. **Per-session restricted daemon socket.** A contained session may connect only to `<HUTAN_HOME>/s/<session>.sock`; connections there are always agent-origin for that session and pass the `[control]` policy. This replaces trust in `HUTAN_SESSION_ID` for contained sessions and implements the "stronger restricted endpoint" ADR 0017 reserved. (`SANDBOX-2B`)
6. **Honest labelling.** The chip and the Start-sheet line name the boundary and its holes: *writes limited to this worktree · can read your files · network on*; *harness sandbox: workspace-write, network off*; never a bare "secure". Violations surface as the command's own `EPERM` output; no promise of a violation log.
7. **Containers are a placement, decided later.** `SANDBOX-3` adds `Placement::Container` (same abstraction as a remote host), mounts the worktree at the same absolute path, uses one credential volume per harness and account with the login run **inside** the container through the harness's own flow (ADR 0015 unchanged: Hutan never reads, stores or forwards a token; no API keys from the Keychain into a container env), and reaches the daemon through a published socket (Apple `container`) or REMOTE-SPIKE's authenticated relay. It starts only after REMOTE-SPIKE's transport decision, a user decision on the runtime dependency, and a runtime being available to test against.
8. **Protocol (additive, minor bumps with capabilities, ADR 0002):** `chat.safety` — `chat.create.safety?`, `ChatInfo.safety {preset, enforced_by: harness|hutan|none, network?}`, `chat.models` also returns `modes`, `TaskRun::Chat.safety?`; `sandbox` — `contain?` on `terminal.create`/`chat.create`/task runs, `SessionInfo.containment {kind: seatbelt|container, network, write_roots, applied, reason?}`, `daemon.toml [sandbox]`. Existing `approval_policy`/`sandbox` fields stay as Codex's expert pair; the refusal for ACP harnesses stays. No breaking change.

## Consequences
- Easier: users can run Codex/Claude with fewer prompts inside a boundary they can see; OMP and plain terminals can be contained; the "boundary is the user's sandbox" sentence in `docs/control.md` gets a mechanism.
- Harder: three enforcement paths and a per-harness profile fragment to test against real turns (OMP's writable `sessions/`/`logs` vs read-only `settings`/`extensions`/`hooks` is unmeasured); `sandbox-exec` may disappear (mitigation: the `Contain` trait, self-test, fail closed — Codex, Claude Code and `srt` break first); reads are open by default so Contain is damage containment, not confidentiality.
- Codex's approval-policy vocabulary is moving (`untrusted` documented as retired in the current docs while the adapter is pinned to 0.160–0.169 and its fixtures use it): `SANDBOX-1` verifies against the pinned versions before adding UI for it.
- Revisit when: Apple deprecates/removes `sandbox-exec` or ships a supported replacement; OMP adds a native sandbox (then it joins decision 2); a user reports needing a network allowlist for chat harnesses (proxy slice); REMOTE-SPIKE lands (start `SANDBOX-3`); Claude/Codex stop accepting the pass-through settings.
