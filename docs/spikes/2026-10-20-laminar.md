# Laminar and Hutan: observability without adopting another agent runtime

**Status:** Research and proposed integration design, not an implementation decision. Research snapshot: 2026-10-19. No code changes, deployment, paid inference, account creation, Keychain access, build, or runtime experiment was performed.

## Executive recommendation

Build **C: a small, daemon-owned local trace store and Traces page**, accept harness-native telemetry through a bounded local OTLP receiver (**D**), and offer **A: optional export to Laminar or another OTel backend**. Treat Laminar as an excellent external observability/evaluation workbench, not as Mawas's runtime or Hutan's source of truth. Do not make its Docker stack a Hutan dependency. Initially **detect/connect to a user-operated instance**, rather than install or manage it (**B**). Use its datasets/evaluations later for explicit, curated Mawas quality work (**E**).

The important distinction: **OTLP is a transport, not a promise of complete agent visibility, replay, safe content, or Laminar-specific rendering.** Current official Claude Code and OMP sources support real spans; Codex has a separate trace exporter as well as event-log export. None makes Hutan's own approvals, memory deliveries, shell blocks, or delegation observable unless Hutan instruments them. Conversely, exporting an enclosing Hutan turn does not reveal the harness's hidden model requests.

This direction implements ADR 0017's **MW-7**, rather than replacing it: daemon-owned bounded spans, OTel IDs/GenAI conventions, transcript content remaining in journals, safeguards and audit remaining authoritative in `hutand` (`docs/adr/0017-mawas-local-meta-harness.md:10-26`). It follows the existing trace design in `docs/spikes/2026-10-18-vault-traces.md:388-562`.

## 2. What Laminar is today

Laminar calls itself an **open-source observability platform purpose-built for AI agents**. Its core value is reading an agent execution as a conversation and a hierarchy, then querying, evaluating, and investigating many executions. It is not a general terminal host, IDE, or a replacement for a harness's model/tool loop (`/Users/workie/proj/lmnr-src/README.md:8-32`).

### Coding-agent and framework integrations

These are different integration surfaces, not interchangeable implementations:

- **[Claude Code plugin](https://laminar.sh/docs/integrations/claude-code.md):** documents one trace per prompt with LLM/tool/subagent activity, grouped by session. The installer uses a login/device flow and writes a project API key to `~/.config/lmnr/claude-code-plugin.json`; `LMNR_PROJECT_API_KEY`, `LMNR_BASE_URL`, and `LMNR_USER_ID` override configuration/identity. Self-host endpoints are supported.
- **[Codex plugin](https://laminar.sh/docs/integrations/codex.md):** analogous session/turn tracing and `~/.config/lmnr/codex-plugin.json`. The documented plugin is separate from Codex's native `[otel]` settings. The Laminar docs describe its output, but this research did not inspect the plugin implementation: its internal capture mechanism and exact coverage remain unverified. Do not assume it is a native OTLP exporter or transcript-free just because it produces spans.
- **[Claude Agent SDK](https://laminar.sh/docs/integrations/claude-agent-sdk.md):** Python auto-instrumentation; TypeScript wraps `query` with `Laminar.wrapClaudeAgentQuery`. Documents model turns, tools, usage/cost and nested `Agent` subagents. This requires embedding/instrumenting the SDK; it does not instrument an unrelated ACP process by importing a Rust dependency in Hutan.
- **[OpenAI Agents SDK](https://laminar.sh/docs/integrations/openai-agents-sdk.md):** Python/TS initialization integrates with SDK tracing, model calls, function tools, handoffs and agents-as-tools. This is **not** the Codex CLI/app-server integration.
- **[Pi integration](https://laminar.sh/docs/integrations/pi.md)** is listed, but Pi and **OMP/oh-my-pi are different projects**. No OMP-specific Laminar plugin was established here. OMP's own OTLP support is a better direct route; see §6.

**Hutan implication:** sending safe metadata gets a useful waterfall, session grouping, and usage view. Getting Laminar's full conversation previews, semantic Signals, playground reproduction, browser replay, or debugger replay requires additional content/instrumentation and explicit consent. Exporting metadata is not a covert way to grant those features access to journal contents.

## 3. Architecture, ingestion, deployment, and licensing

### 3.1 Services and state ownership

```text
instrumented application / harness / Hutan exporter
  ├─ OTLP/gRPC → Rust app-server :8001
  └─ OTLP/HTTP → Rust app-server :8000/v1/traces
                         │ project-key authentication + normalization
                         ├─ LITE: in-process Tokio message queues
                         └─ FULL: RabbitMQ (+ optional stream data plane)
                                      │ processing workers
                   ┌──────────────────┼──────────────────┐
                   ▼                  ▼                  ▼
            PostgreSQL           ClickHouse          Quickwit
          control/metadata   spans/content/analytics  full-text index
                   └──────────────────┼──────────────────┘
                                      ▼
                         Next.js / React frontend :5667
                         HTTP APIs + real-time updates
```

- **App-server:** Rust 2024, Actix Web HTTP server, tonic gRPC, Tokio, sqlx/Postgres, ClickHouse client, RabbitMQ clients. Evidence: `/Users/workie/proj/lmnr-src/app-server/Cargo.toml:1-13,29-30,45-67,81-100`.
- **Frontend:** TypeScript, Next.js 16/React 19, Drizzle/Postgres, ClickHouse client, better-auth, rrweb, SQL/editor/chart libraries; it also owns application API/actions and startup migrations, not only rendering. Evidence: `/Users/workie/proj/lmnr-src/frontend/package.json:33-64,97-143`; `/Users/workie/proj/lmnr-src/frontend/instrumentation.ts:6-18`.

[Evaluation storage](https://laminar.sh/docs/evaluations/concepts.md#what-gets-stored-where).
- **Quickwit** supplies search. It is included in both Compose stacks despite the lite file's opening comment claiming only four services. Count the actual services: lite has **five**, full has **seven** including RabbitMQ and **Valkey**, not an additional Redis server. ### 3.2 Ingestion and authentication

| Interface | Cloud | Default self-host | Meaning |
|---|---|---|---|
| OTLP/HTTP protobuf | `https://api.lmnr.ai/v1/traces` | `http://localhost:8000/v1/traces` | `ExportTraceServiceRequest`, `Content-Type: application/x-protobuf` |
| OTLP/HTTP JSON | Same URL | Same URL | Actual OTLP JSON, `Content-Type: application/json`; not arbitrary JSON span objects |
| OTLP/gRPC | `https://api.lmnr.ai:8443` | `http://localhost:8001` | Standard `opentelemetry.proto.collector.trace.v1.TraceService/Export`; authorization in gRPC metadata |
| Laminar JSON spans | `POST /v1/spans` | App-server API origin | Laminar's own JSON batch format, not OTLP JSON |
| OTLP logs | `POST /v1/logs` | App-server API origin | Limited log ingestion, queryable in SQL; not a universal metrics backend |
| Browser/debugger/dataset/eval APIs | Separate `/v1/...` routes | App-server API origin | Needed for those richer workflows; not encoded merely by naming an OTLP span |

Protocol evidence: [OTel guide](https://laminar.sh/docs/tracing/otel.md), [HTTP ingestion](https://laminar.sh/docs/api-reference/ingestion/ingest-opentelemetry-traces.md), [JSON spans](https://laminar.sh/docs/api-reference/ingestion/create-spans.md). Source independently confirms HTTP content-type dispatch and the real gRPC service: `/Users/workie/proj/lmnr-src/app-server/src/api/v1/traces.rs:52-64,130-148`; `/Users/workie/proj/lmnr-src/app-server/src/traces/grpc_service.rs:50-59,94-108`.

**gRPC caveat:** the docs use SDK URLs containing `/v1/traces` and describe path-appending behavior. For Rust, use the exporter's gRPC **origin/port** configuration and standard generated RPC; do not manually POST to `/v1/traces` on the gRPC port. HTTP requires the trace path. The standard tonic implementation above is stronger evidence than a language-specific URL shorthand.

Authentication is **`Authorization: Bearer <project API key>`**, or lowercase `authorization` gRPC metadata. The project is derived from the validated key, not a client-supplied `project_id` attribute. Source permits **ingest-only keys** for ingestion and rejects them on ordinary project APIs: `/Users/workie/proj/lmnr-src/app-server/src/auth/mod.rs:34-105,108-122`. Prefer an ingest-only project key for Hutan export; evaluation/query access should be a separate, explicitly granted connector.

Laminar accepts OTel IDs but represents trace IDs and zero-padded span IDs internally as UUID-like values. Hutan should keep canonical **16-byte trace IDs and 8-byte span IDs**, not copy that internal storage quirk. Laminar's span model has parent, name, attributes, content, type, timestamps, events and status: `/Users/workie/proj/lmnr-src/app-server/src/db/spans.rs:20-34,71-91`; [OTel representation](https://laminar.sh/docs/tracing/otel.md#span-object).

### 3.3 Standard conventions versus Laminar conventions

The wire format is OTel, but its UI reads both standard-ish `gen_ai.*` fields and proprietary **`lmnr.*`** fields. Some cost fields under `gen_ai.*` are **not OTel standards**. Source explicitly documents that distinction (`/Users/workie/proj/lmnr-src/app-server/src/traces/span_attributes.rs:8-32,62-118`).

Use current pinned GenAI conventions for Hutan's canonical model, and a **destination mapping** for Laminar. Do not define the SQLite schema in terms of whichever exporter currently recognizes a spelling. In particular, retain modern `gen_ai.provider.name` canonically where applicable, and emit Laminar's documented `gen_ai.system` alias at its export boundary. Convention stability/version caveats already exist in `docs/spikes/2026-10-18-vault-traces.md:390-399`.

Two source/docs discrepancies affect integration correctness:

1. The [attribute reference](https://laminar.sh/docs/tracing/structure/span-attribute-reference.md) says `lmnr.span.type="LLM"` is required for LLM UI/cost. The inspected server also **infers** LLM/tool types from `gen_ai.operation.name`, model/provider keys and tool-call attributes (`/Users/workie/proj/lmnr-src/app-server/src/traces/spans.rs:458-500`). Set the explicit type when exporting to Laminar anyway, and set enclosing turns explicitly to `DEFAULT` so adding a model attribute does not misclassify a container as an extra inference.
2. The reference describes resource attributes as available, but this checkout's producer walks `resource_spans → scope_spans → spans` and passes only each span onward; `from_otel_span` receives no resource/scope (`/Users/workie/proj/lmnr-src/app-server/src/traces/producer.rs:324-348`; `/Users/workie/proj/lmnr-src/app-server/src/traces/spans.rs:739-778`). Emit standard resources for interoperability, but do not rely on resource-only fields for critical Laminar session/coverage metadata on this self-host version. Preserve resource/scope/link data in Hutan even if this backend does not retain it.

### 3.4 Self-host requirements and realistic footprint

**Observed requirements:** a Docker-compatible Linux container engine and Compose; on macOS that normally means a Linux VM. No GPU or LLM key is required to ingest and browse basic traces. The quickstart provides frontend `5667`, HTTP ingestion `8000`, gRPC `8001`, and real-time `8002`; lite also publishes Postgres `5433` and Quickwit `7280/7281`. Those Quickwit ports are **not** Laminar's public trace receiver. The Compose files have no CPU/RAM limits and use `pull_policy: always`; Laminar application images and RabbitMQ are not pinned to immutable digests. Evidence: `/Users/workie/proj/lmnr-src/docker-compose.yml:9-14,27-30,52-89,118-145`; `/Users/workie/proj/lmnr-src/docker-compose-full.yml:8-10,65-81`.

| Component | Baseline necessity | Can be omitted? |
|---|---|---|
| App-server + Postgres + ClickHouse | Basic ingestion, control metadata, trace queries | Not in the standard useful stack |
| Frontend | Onboarding/project API key, trace/eval UI, migrations | A bespoke headless deployment is not the supported quickstart |
| Quickwit | Shipped by default; full-text indexing/search | Backend has `QUICKWIT_ENABLED` gating; omitting it needs coordinated frontend/backend configuration, not deleting a service and assuming parity (`app-server/src/features/mod.rs:55-57,117`) |
| RabbitMQ | Full stack's queued processing | Yes: lite uses in-process queues; not durable pending-work equivalence |
| Valkey / Redis-protocol service | Full stack cache/pubsub | Yes in lite; do not call production fallback behavior equivalent to a resilient distributed cache |
| Dedicated consumer | Production scaling/worker separation in Helm | Not an extra Compose service; producer and consumer can share app-server |
| S3 / cloud storage | Optional exports/artifacts or production storage choices | Not required for base Compose trace persistence |
| PII-redactor + ONNX model | Optional server-side content masking | Not in base Compose; cannot protect content before it has left Hutan |
| LLM profiles/provider, Slack/email, OAuth | Optional AI features/notifications/auth integrations | Basic local trace viewing does not require paid inference or external OAuth |

**RAM/CPU:** upstream Compose and the inspected setup guide give no validated laptop minimum. As scale indicators, the [official Helm values](https://github.com/lmnr-ai/lmnr-helm/blob/main/charts/laminar/values.yaml) request 1 GiB each for frontend and app-server, 0.5 GiB for the consumer, and 1 GiB for a Quickwit indexer, with larger limits (ClickHouse 4 GiB; indexer 4 GiB). These are Kubernetes scheduling defaults, **not measured Compose RSS or minimum hardware requirements**. For an opt-in laptop trial, budget a VM around **4 vCPUs / 8 GiB RAM and at least 10 GiB of free initial disk headroom [INFERENCE]**, with explicit retention and disk monitoring. This is deliberately conservative planning, not a claim that the stack needs or fits exactly those values. It is substantially heavier than adding a bounded SQLite file to `hutand`.

**Startup time:** not measured. Initial image downloads, VM startup, migrations, and model-price loading can dominate; warm restart time is a separate measurement. Plan for **tens of seconds to minutes [INFERENCE]**, not an instant native pane. The frontend attempts an external pricing download with a 30-second timeout and continues without pricing on failure (`/Users/workie/proj/lmnr-src/frontend/instrumentation.ts:50-59,94-98`). Healthchecks in Compose include 10-second Quickwit intervals; they are not evidence of a fixed startup duration. ARM64 image availability and idle/ingest RSS on this workstation remain unverified. No images were pulled to answer this spike.

**Offline:** after obtaining compatible images, local databases/trace viewing can operate without Laminar Cloud **[INFERENCE from the local deployment graph]**. This is not an audited air-gap guarantee: telemetry is enabled by default, model pricing attempts network access, OAuth/Slack/email are network services, and external model judges/AI features require their providers. A preloaded local OpenAI-compatible model is a possible opt-in AI backend, not something this research ran. Disable egress or explicitly audit it for an actual offline requirement.

### 3.6 Telemetry and local privacy

Self-hosted does **not** mean zero outbound telemetry by default:

- Set **`LAMINAR_TELEMETRY_DISABLED=true`** in the repository-root environment and recreate the frontend. README explicitly documents this (`/Users/workie/proj/lmnr-src/README.md:158-162`).
- The self-host heartbeat uses PostHog, an opaque persistent instance ID and six-hour reporting window. Its payload includes version/environment, table counts, feature booleans and an optional operator label, not trace bodies in this code path. Evidence: `/Users/workie/proj/lmnr-src/frontend/lib/telemetry/index.ts:9-10,21-55,69-95`; `frontend/lib/telemetry/stats.ts:61-110`.
- Browser/product analytics are a separate `POSTHOG_TELEMETRY` flag; self-host heartbeat has its own opt-out. Frontend Sentry initialization is cloud/DSN-gated; backend external tracing is DSN plus `ENABLE_TRACING` gated. Evidence: `/Users/workie/proj/lmnr-src/frontend/lib/features/features.ts:135-166`; `frontend/sentry.server.config.ts:20-29`; `app-server/src/features/mod.rs:80-86`.

## 5. A — Export Hutan spans to Laminar

### 5.1 Proposed trace shape and names

**[INFERENCE]** There are no mandatory magic **span names** for generic OTLP ingestion. Names should be stable operation labels; attributes and parent relationships drive recognition. Use one trace per Mawas/harness **turn**, group turns by a stable session ID, and use span links for detached/fan-out work rather than an indefinitely open session root.

| Hutan operation / suggested span name | Laminar type | Important canonical attributes / relationships |
|---|---|---|
| `invoke_agent <backend>` | `DEFAULT` | `gen_ai.operation.name=invoke_agent`; `hutan.session.id`, turn/workspace-at-start, backend, coverage; session/user association on this trace root |
| `chat <model>` — only an actual observed/reported request | `LLM` | `gen_ai.operation.name=chat` (or actual operation), provider/request/response model, request/response ID and usage when available |
| `execute_tool <tool>` / `tools/call <tool>` | `TOOL` | `gen_ai.operation.name=execute_tool`, `gen_ai.tool.name`, call ID, safe outcome; MCP method/server metadata where applicable. Merge one known operation, do not duplicate ACP and MCP observations |
| `hutan.approval.wait` | `DEFAULT` | Approval ID, policy/grant source, allow/deny/expired, deciding client class; child/link of relevant call; separate waiting from execution |
| `hutan.memory.deliver` | `DEFAULT` | Snapshot revision, count/byte budget, backend delivery mechanism and outcome; **no memory text or secret values** |
| `hutan.terminal.command` | `DEFAULT` (or a tool child if actually that tool) | Session/block reference, exit status, duration, safe command category; **no raw command, cwd, argv or terminal output** by default |
| `hutan.agent.session` | `DEFAULT` for bounded lifecycle operations only | Start/resume/stop outcome and harness session correlation; don't export a process-lifetime root to group turns |
| `hutan.delegate` / `hutan.schedule.run` | `DEFAULT` | Dispatch/occurrence IDs, parent/child sessions, links, timing/outcome; only when those services exist |

Hutan always knows its own daemon operations. ACP/app-server-reported tools/usage are `adapter_reported`; native telemetry is `harness_reported`; deliberate journal reconstruction is `reconstructed`. These are observability provenance labels, not authorization facts. An approval span cannot authorize an operation and a telemetry-supplied `approved=true` cannot change an audit receipt.

### 5.2 Exact Laminar wire mapping

Use the [span attribute reference](https://laminar.sh/docs/tracing/structure/span-attribute-reference.md) rather than the older abbreviated table at the bottom of the OTel overview. Source constants corroborate the core keys (`/Users/workie/proj/lmnr-src/app-server/src/traces/span_attributes.rs:8-32,62-118`).

| Purpose | Attributes sent to a Laminar destination |
|---|---|
| Process/resource | Standard resource `service.name=hutand`, `service.version`, deployment environment; instrumentation scope/version. Keep critical Hutan correlation on spans too for the inspected source's resource-loss caveat. |
| Span classification | **`lmnr.span.type` = `DEFAULT`, `LLM`, or `TOOL`**. Evaluation-specific types belong to the evaluation workflow, not ordinary Mawas turns. |
| Session and user | Root **`lmnr.association.properties.session_id`** = exported session pseudonym; optional **`lmnr.association.properties.user_id`** = explicit opaque user pseudonym. Not username/email/vendor account UUID. Laminar also accepts `session.id`/`user.id`, but explicit names avoid ambiguity. |
| Other trace metadata | `lmnr.association.properties.metadata.hutan_turn_id`, `.backend`, `.coverage`; optional `lmnr.association.properties.tags` string array. Use export-safe values; don't put workspace paths in metadata. |
| Provider/model | **`gen_ai.system`**, **`gen_ai.request.model`**, optionally **`gen_ai.response.model`**. Emit Laminar provider alias from Hutan's pinned convention, not by parsing the span's display name. |
| Request usage | **`gen_ai.usage.input_tokens`**, **`gen_ai.usage.output_tokens`**, optional **`llm.usage.total_tokens`**. Omit unknowns. Input is total including cache, not uncached input plus a duplicated cache count. |
| Cache/reasoning | `gen_ai.usage.cache_read_input_tokens`, `gen_ai.usage.cache_creation_input_tokens`, `gen_ai.usage.reasoning_tokens`; Laminar also normalizes current dotted cache spellings. Preserve original source semantics locally. |
| Cost | `gen_ai.usage.input_cost`, `.output_cost`, `.cost` are explicit numeric overrides, **USD according to Laminar's cost guide**. Otherwise Laminar looks up the model/token price. Do not export an invented subscription charge or unknown-as-zero. Keep estimate/billed provenance locally and show the external estimate caveat. |
| Tool detail | Explicit `TOOL` plus tool name/call ID. Optional `lmnr.span.input`/`lmnr.span.output` are JSON-stringified safe arguments/results; omit content by default. |
| LLM conversation content | Only after separate opt-in: JSON-stringified **`gen_ai.input.messages`**, **`gen_ai.output.messages`**, optional `gen_ai.system_instructions` and `gen_ai.tool.definitions`. Current form is message arrays with `role` and `parts`; do not introduce deprecated indexed prompt/completion attributes. |
| Rich hierarchy paths | Optional `lmnr.span.path` and `lmnr.span.ids_path` arrays, aligned root-to-leaf. Set **both or neither**. Start with OTel parent IDs and neither path; add paths only with a verified SDK-compatible mapping. |
| Status/errors | OTel status/timestamps/events, allowlisted error category; sanitize span names and error text too. No raw provider payloads, exception stack paths or URL credentials. |

Laminar lifts session/user/metadata from any span; placing consistent values on the root is simplest. Tags are unioned across spans. Do not place conflicting identities on siblings and depend on arrival-order merging. A debugger's `lmnr.association.properties.metadata.rollout.session_id` is a **different** association: leave it unset unless Hutan intentionally implements the debugger registration/block protocol.

**Accounting:** record each actual request once. Never export both a turn-level aggregate and the same request children as independent LLM costs. Do not sum cumulative conversation usage snapshots. Unknown usage stays absent; subscription usage is not a known marginal dollar bill. Laminar may display a model-price estimate or zero for absent pricing; Hutan must not import that as authoritative billing. Keep its own idempotent usage ledger independent of detailed-trace retention (`docs/spikes/2026-10-18-vault-traces.md:494-521`).

### 5.3 Privacy, credentials and failure behavior

**[INFERENCE]** Endpoint configuration is an explicit daemon-owned destination: protocol, exact URL, enabled scope and content policy. Default **off**; TLS required except explicitly configured loopback development origins. Do not let ambient `OTEL_*` variables silently enable external Hutan export.

- Store the Laminar API key/header secrets **only in Keychain through the daemon**, with a non-secret destination reference in settings. Resolve them at export time, not in the UI, SQLite, environment dumps or logs. Prefer ingest-only credentials. No default Laminar plugin key-file installation.
- Present a destination/content preview: tool names, timings, model/token metadata still disclose activity even without text. Redact before local persistence, then apply a separate export **allowlist**. Drop prompts/reasoning, tool args/results, memory bodies, terminal command/output, repository paths, internal URLs, environment and account identifiers by default.
- Inspect **names, resources, events, links and error fields**, not only attributes. Exact-key/credential-pattern redaction is a defense, not proof against all secrets. Preserve a truncation/redaction marker, not unsafe originals.
- Use installation/destination-scoped pseudonyms for exported session/workspace/user correlations; the mapping remains local. Stable IDs are correlation, not authorization. Changing endpoints requires explicit disclosure/consent and must not forward old credentials across redirects.
- Bound batches, total in-flight bytes, queue length, timeout and retry lifetime. Propose 512 queued spans, 1 MiB encoded batch cap, at most 2 exports in flight and a 5-second request deadline **[INFERENCE; tune against fixtures]**. Do not block model/tool execution on exporter availability and do not create an unlimited offline backlog.
- User sees enabled destination, last successful export, dropped/error counters and **local recording remains available**. Export new completed spans only; historical backfill is a separate selected/sanitized action. Disabling export stops queued disclosure; clearing local traces does not claim to delete copies already delivered remotely.

## 6. D — Can the harness emit real telemetry into hutand?

**Yes, current upstream supports this, but the three contracts differ.** Do not repeat the older blanket assumption that Claude only emits metrics/events, nor confuse Codex's log exporter with its trace exporter. Installed-version support and exact app-server/ACP launch coverage still need fixtures/probes before product claims.

### Claude Code

The [official monitoring documentation](https://code.claude.com/docs/en/monitoring-usage#traces-beta) now documents **beta distributed spans**, off by default:

```text
CLAUDE_CODE_ENABLE_TELEMETRY=1
CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1
OTEL_TRACES_EXPORTER=otlp
OTEL_EXPORTER_OTLP_TRACES_PROTOCOL=http/protobuf
OTEL_EXPORTER_OTLP_TRACES_ENDPOINT=http://127.0.0.1:<hutan-port>/v1/traces
```

A daemon would set these only for an explicitly enabled Hutan-launched process; the example is not a command run by this research. Keep content gates off (`OTEL_LOG_USER_PROMPTS`, `OTEL_LOG_TOOL_DETAILS`, `OTEL_LOG_TOOL_CONTENT`, `OTEL_LOG_RAW_API_BODIES`); disable logs/metrics unless Hutan actually supports and wants them. Standard `CLAUDE_CODE_ENABLE_TELEMETRY` alone plus log/metric exporters does **not** enable traces.

Official span hierarchy is `claude_code.interaction` → `claude_code.llm_request`, `claude_code.tool` → `claude_code.tool.blocked_on_user` / `.execution`, with subagent activity under tool spans. LLM attributes include model, request IDs, durations and usage. A critical normalization detail: Claude's `input_tokens` **excludes** cache reads/writes, while Laminar's input total includes them. Construct the normalized total from known components once; do not copy that count blindly.

For Agent SDK/non-interactive `-p`, Claude reads inbound `TRACEPARENT`/`TRACESTATE`; interactive sessions ignore inbound context. It can propagate context to Bash and HTTP MCP with documented conditions. Therefore an SDK-launched ACP adapter might permit direct parentage, but **its actual launch/turn context propagation is unverified here**. Fall back to explicit session/turn correlation and links, not timestamp guessing presented as certain parentage. Managed enterprise telemetry settings can override developer destinations. Telemetry also does not inherit uniformly into all child processes; consult the same official page rather than assuming the entire process tree exports to Hutan.

### Codex

The [official advanced configuration](https://developers.openai.com/codex/config-advanced/#observability-and-telemetry) primarily describes structured **logs**: API requests, stream completions/usage, tool decisions/results and prompts. The [official configuration reference](https://developers.openai.com/codex/config-reference/) also explicitly defines **`otel.trace_exporter`** separately from `otel.exporter`; the [official `codex-otel` README](https://github.com/openai/codex/blob/main/codex-rs/otel/README.md) wires independent logger/tracing layers, `span_attributes` and tracestate.

Proposed per-launch configuration, not edits to the user's global home:

```toml
[otel]
environment = "hutan-local"
log_user_prompt = false
exporter = { otlp-http = { endpoint = "http://127.0.0.1:<port>/v1/logs", protocol = "binary" } }
trace_exporter = { otlp-http = { endpoint = "http://127.0.0.1:<port>/v1/traces", protocol = "binary" } }
```

Codex accepts `-c` configuration overrides; project-local `.codex/config.toml` cannot override telemetry routing. Have the daemon supply selected process overrides, not patch `~/.codex`. Header credentials should be a short-lived local ingestion capability injected transiently, never Laminar's remote project key. `log_user_prompt=false` is **not a universal content filter**: documented tool-result events may include output snippets, and other metadata can identify users/accounts or directories. A `/v1/logs` sanitizer is necessary before local storage/export.

**What can we promise?** Native structured request/usage/tool events and a native trace pipeline, without scraping terminal text. **Not yet established:** that every provider call/native tool/subagent is emitted as a complete stable GenAI span tree in the Hutan-selected Codex version and app-server mode. Treat logs as logs; use adapters to convert only well-defined events into explicitly `reconstructed` spans if necessary, and deduplicate against app-server/native observations. A successful `/v1/logs` request is not proof that Laminar will show LLM spans.

### OMP / oh-my-pi

The [official active environment reference](https://github.com/can1357/oh-my-pi/blob/main/docs/environment-variables.md#11-opentelemetry-export) documents native OTLP export. Its [bootstrap source](https://github.com/can1357/oh-my-pi/blob/main/packages/coding-agent/src/telemetry-export.ts) states that agent core emits **OpenTelemetry GenAI spans**, and registers providers only when an endpoint exists. The [export implementation](https://github.com/can1357/oh-my-pi/blob/main/packages/coding-agent/src/telemetry-export-otlp.ts) installs a real `OTLPTraceExporter`, batch span processor and Node tracer provider, plus optional logs/metrics and agent usage/run callbacks.

```text
OTEL_EXPORTER_OTLP_TRACES_ENDPOINT=http://127.0.0.1:<hutan-port>/v1/traces
OTEL_EXPORTER_OTLP_TRACES_PROTOCOL=http/protobuf
OTEL_TRACES_EXPORTER=otlp
```

- **Only `http/protobuf` is supported** by the inspected runtime; explicit `grpc` or `http/json` disables that signal rather than translating it.
- `telemetry.otlpExportEnabled=false` and `OTEL_SDK_DISABLED=true` disable initialization. The [setting](https://github.com/can1357/oh-my-pi/blob/main/packages/coding-agent/src/telemetry-settings.ts) is normally enabled, but an endpoint is still required; this does not imply unconditional default egress.
- Per-signal endpoints/headers override common values. Percent-encode header values, e.g. the space in `Bearer%20...`; do not persist the header in agent config. The bootstrap lazily loads the exporter graph and the implementation periodically flushes long-lived ACP processes.
- This is genuine native instrumentation, not the Laminar **Pi** integration or terminal transcript parsing. Exact coverage of each installed OMP backend/tool/subagent and inbound parent propagation remain version-specific acceptance work.

### Local collector boundary

**[INFERENCE]** Start with **OTLP/HTTP protobuf traces and logs**, sufficient for OMP and supported Claude/Codex HTTP configurations. `opentelemetry-otlp` is an **exporter**, not a ready-made server: a hutand receiver needs OTLP protobuf types and bounded HTTP handlers. Add gRPC only for a demonstrated requirement, not because generic OTel examples use port 4317. No separate Collector daemon is required.

- Bind only loopback, to a daemon-selected port; inject endpoint plus a per-launch/session ingestion capability into selected children. Do not silently claim the machine-wide standard port or accept unauthenticated LAN traffic. Content controls are enforced again on the receiving side.
- Limit decompressed body bytes, spans/logs per request, string/attribute/event/link counts, concurrent decodes, sender rate and total ingress memory. Return protocol-appropriate rejection/partial-success/error rather than acknowledge unsupported data as stored. Do not advertise metrics reception until implemented.
- Authenticate and attribute by the launch capability; do not trust a span's `hutan.session.id` to read/write another session. Keep upstream correlation IDs as untrusted metadata. Telemetry cannot mutate approvals, memory or grants.
- Preserve upstream trace/span IDs. Use reliable context propagation where supported; otherwise link to the Hutan turn/session and show confidence/provenance. Don't re-ID every span or infer precise nesting from wall-clock overlap.
- Apply a versioned normalizer and idempotent source keys. One request observed via native OTLP and app-server usage must not become two bills. Retain source/count semantics and unknown fields safely; don't copy arbitrary raw payloads into SQLite.
- Hutan owns redaction/export. The harness gets a local ephemeral capability, **not the Laminar API key**. Disabled local collection means no injected endpoint. Explicitly select inherited exporter variables to avoid accidental remote egress from a user's ambient shell settings.
- Native exporters usually send **completed** spans in batches. Hutan can show its own in-progress turn/tool state, but should not promise live LLM starts before the harness exports them. Adapter events can supply a separate observed start where actually available.

## 7. B — Run Laminar locally, detected or managed by Hutan

**Recommended first version [INFERENCE]:** Settings → Traces → External backend → **Connect existing Laminar**, with user-entered API/frontend URLs, Keychain key storage, an explicit connection check and an **Open dashboard** action. Do not network-scan for instances or auto-start Docker when opening Hutan. Endpoint availability may be detected only for the configured destination.

If managed Compose is later requested:

1. Make it a separate **opt-in installation** with a clear VM/container/RAM/disk disclosure. Require an existing compatible engine; never silently install Docker Desktop, pull images, accept licenses, or sign up for cloud services.
2. Pin a reviewed source revision and image digests, choose a unique per-user Compose project and dedicated data directory/volumes, bind all published ports to `127.0.0.1`, replace sample credentials, disable outbound telemetry, and keep AI features off initially. The upstream `name: lmnr`, global `container_name: clickhouse`, broad host port bindings and `pull_policy: always` are not a safe multi-app managed lifecycle contract.
3. Resolve managed secrets from Keychain only for the authorized subprocess invocation; never write Hutan-owned API keys into `.env` or plugin JSON. Be honest that Docker daemon/container inspection can expose environment credentials, and Laminar's own backend stores its own project keys/provider profiles. Hutan cannot claim this separate stack magically inherits its Keychain-only security model.
4. Separate **Start**, **Stop**, **Restart**, **Upgrade**, and **Delete data**. Stop only the stack Hutan owns, never the user's general Docker VM or unrelated projects. Stop preserves volumes; deleting them is an explicitly approved destructive action. Detection mode never stops a user-owned stack on quit.
5. Start asynchronously outside the interactive critical path, with a bounded deadline and visible readiness/error state; no automatic crash/pull loop. Record warm/cold startup, idle/load RSS/CPU, disk growth and ARM64 compatibility in a later explicit smoke experiment before offering supported management.
6. Default no start-at-login. State follows `hutand`'s documented lifecycle, not the window's visibility; a user can choose to leave an owned stack running. If the destination disappears, local traces continue and export shows bounded drops/errors.

This is materially more operational work than “run docker compose.” Local Laminar gives powerful SQL/eval/browser/debugger functionality, but most of that is not needed for MW-7's first native traces.

## 8. C — A local Laminar-like store, not a Laminar clone

### Model to borrow

**[INFERENCE]** Borrow **traces → typed spans → events/links**, session/user association, request-scoped usage, explicit evaluation datapoints, and the UI separation between conversation and waterfall. Retain stable source provenance and versioned normalization. Do **not** copy the server's distributed database stack, its UUID-padded span IDs, content duplication/dedup dictionaries, SQL engine, LLM Signals infrastructure, or its full catalog of compatibility heuristics.

Keep local canonical fields independent of exporter aliases:

| Table | Core fields / rule |
|---|---|
| `traces` | 16-byte ID, root ID, session/turn, workspace-at-start, start/end/outcome, coverage and convention revision |
| `spans` | `(trace_id, span_id)` unique, 8-byte span ID, parent, name/operation/kind, monotonic duration where locally observed, wall-clock times, status, bounded safe attributes, source/instrumentation identity |
| `span_events`, `span_links` | Bounded records; links support detached agents/fan-in and uncertain cross-harness association |
| `trace_sources` | Unique operation/journal-sequence/upstream source key; references to existing chat journals and terminal blocks, not another prompt/output copy |
| `trace_retention_state` | Accounted bytes, prune/checkpoint progress, dropped/truncated counts, recording/degraded status |
| Separate usage ledger | Idempotent request/aggregate source key, counts with semantics, price revision/currency and known/estimated/billed distinction; detail pruning must not rewrite totals |

This closely follows, rather than supersedes, the schema already proposed in `docs/spikes/2026-10-18-vault-traces.md:458-521`. Persist starts for Hutan-observed spans, finish on real outcomes, and mark unfinished work **interrupted/unknown** on daemon restart. Do not invent post-crash completion times or infer hidden LLM requests from generated text.

### Initial bounds and failure policy

Reuse the existing proposed **30-day**, **256 MiB soft / 320 MiB hard** detailed-trace policy, separate `traces.sqlite`, ≤64 attributes / 16 KiB attributes per span, ≤32 events / 16 links, pages ≤200 rows. These are proposed budgets, **not implemented guarantees**. They include DB/WAL/maintenance headroom, not only attribute lengths. Keep receiver queues/batches/concurrency byte-bounded too. Avoid per-token writes and long readers that prevent checkpointing.

On pressure, prune old completed details before admission; emit completeness/drop markers; if progress is unsafe, stop detailed recording and expose degradation **without stopping a turn**. Never silently drop security audit/grant records with optional traces. No unbounded channels, tasks, pending export spool or arbitrary-JSON indexes. This is the existing policy at `docs/spikes/2026-10-18-vault-traces.md:478-492` plus the receiver boundary above.

### Rust crates

| Crate | Role | License / official evidence |
|---|---|---|
| `opentelemetry` | Canonical context/IDs and trace API | Apache-2.0; [manifest](https://github.com/open-telemetry/opentelemetry-rust/blob/main/opentelemetry/Cargo.toml) |
| `opentelemetry_sdk` | Provider/processors and bounded export integration where needed; not Hutan's persistence layer | Apache-2.0; [manifest](https://github.com/open-telemetry/opentelemetry-rust/blob/main/opentelemetry-sdk/Cargo.toml) |
| `opentelemetry-otlp` | Optional outward HTTP/protobuf exporter; gRPC possible via feature selection | Apache-2.0; [manifest](https://github.com/open-telemetry/opentelemetry-rust/blob/main/opentelemetry-otlp/Cargo.toml). Disable unused signals/default features; avoid adding a second TLS/runtime convention. |
| `opentelemetry-semantic-conventions` | Attribute constants; pin convention revision and experimental GenAI surface deliberately | Apache-2.0; [manifest](https://github.com/open-telemetry/opentelemetry-rust/blob/main/opentelemetry-semantic-conventions/Cargo.toml); experimental conventions are feature-gated. |
| `opentelemetry-proto` and protobuf/HTTP dependencies | Decode receiver requests; generated message types, not a collector service | Official [Rust workspace](https://github.com/open-telemetry/opentelemetry-rust) supplies the protocol crate; review exact selected feature/dependency licenses with the ordinary Hutan dependency gate before adoption. |

The inspected upstream manifests identify the main OTel crates as **0.33.1**, but that is a source snapshot, not a requirement to add mutable `main` dependencies or a claim that Hutan's lockfile already contains them. No crate was installed or dependency gate run. SQLite remains the bounded local store; adopting OTel does not require ClickHouse or a separate collector.

### Native user experience

A registered **Traces** page reachable from Mawas Home, a session and a workspace: list by time/backend/outcome/duration; waterfall and tool/approval waits; memory delivery revision/count; usage with unknown-coverage flags; details with journal/block links. Default content stays in existing journal views and is fetched only when deliberately opened. Show **not observed**, **reported by harness**, **reconstructed**, **interrupted**, and **recording dropped**, rather than a false complete execution.

UI only renders daemon queries/events: virtualized lists, cursor-based pagination, coalesced invalidation, no hidden-page polling. Controls cover recording, retention, clear, and explicit export. This is consistent with ADR 0017 and `docs/spikes/2026-10-18-vault-traces.md:545-563`, not an embedded Laminar web frontend.

## 9. E — Evaluations and datasets for Mawas quality, later

**[INFERENCE]** Start from a small, human-reviewed dataset of real product questions/tasks: correct memory delivery and scope, truthful “saved” receipts, approval refusal/always-ask behavior, harmless read-only tool selection, delegation outcomes, stop/cancel behavior and bounded context. A dataset row contains sanitized `data`, expected `target`/rubric and metadata identifying fixture version, harness/model, memory revision and policy revision. Never export credentials, private repo content, full memory snapshots, or vendor login material as convenient fixtures.

Use Laminar's [manual evaluation API](https://laminar.sh/docs/evaluations/manual-evaluation.md) or a thin separate Python/TS evaluator around an explicit Hutan test executor; a Rust daemon does not need to embed those runtimes. Preserve the documented evaluation structure (`EVALUATION` root, `EXECUTOR`, model/tool children, `EVALUATOR` scores), run groups, comparison and trace associations. See [evaluation concepts](https://laminar.sh/docs/evaluations/concepts.md).

1. Deterministic fixture/code scores first: no unauthorized action after Deny, required confirmation present, correct scoped memory IDs delivered, bounded output, exact receipts/provenance. These belong in normal free tests where suitable.
2. Explicit live-harness evaluation jobs later: isolated temporary `HUTAN_HOME`, sandboxed test repositories, no user's real app/home/Keychain, fixed budgets/concurrency, cancellation and approval policy. Real harness side effects do not become safe just because a test is called an “eval.”
3. Model judges only after separate consent, spend limits and a concrete rubric; report judge/model/version and uncertainty. Never turn them on in the ordinary gate or on every personal conversation by default.
4. Humans can select failures into a **labeling queue**, edit/correct and push approved examples to datasets. Keep training/evaluation examples separate from curated Mawas memory; scores and Signals do not automatically authorize writes or “learn” policy changes.
5. Metadata-only exports are insufficient for many semantic judgments and playground/replay tasks. Request a selected sanitized example explicitly, rather than silently broadening all trace capture. Every export remains a daemon-authorized egress action.

Laminar's debugger may help iterate an instrumented test executor, but it cannot safely replay arbitrary shell mutations or restore the user's running Hutan environment. Its cached-prefix benefit does not make subsequent live provider/tool calls free or reversible.

### Decisions for the user — five at most

1. **Where is the primary trace history?** Recommend **native daemon SQLite + Traces page**, with Laminar an optional destination, not the sole archive.
2. **How much content may traces contain or export?** Recommend **metadata-only by default**, journal/block references locally, separate selected-example consent for content/evals. Do not enable raw prompts/tool output/reasoning capture globally.
3. **Which external backend, if any?** Recommend **none by default**; user-configured Laminar cloud or existing self-host with an ingest-only Keychain key. No account creation or Docker installation during onboarding.
4. **Should native harness telemetry be enabled?** Recommend explicit **per-harness/per-launch opt-in to the local receiver**, source content gates off, version/coverage shown. It is the best route to real inference/tool spans, not a universal completeness guarantee.
5. **Should Hutan manage Laminar or build its advanced analytics?** Recommend **connect/detect only now**, defer managed Compose and Signals/enterprise choices; add curated evals once local traces are trustworthy. Do not reimplement Laminar's full SQL/eval/browser/debugger platform inside MW-7.

## 11. What remains unverified

- No Laminar container was pulled or started; startup time, real memory/CPU/disk footprint, ARM64 image compatibility, offline egress behavior and live UI mappings were not measured.
- No Laminar plugin was installed; its internals, installed harness compatibility, content capture and permissions were not experimentally checked. We did not modify `~/.omp`, `~/.claude`, `~/.codex`, the user's app/data/logs, or Keychain.
- Upstream native telemetry documentation/source establishes capabilities, not that Hutan's currently installed harness versions and ACP/app-server adapters enable all of them. Cross-process traceparent support, request/tool coverage and duplicate usage need explicit versioned acceptance work.
- Public source licensing is established for the named OSS components, not enterprise image contents or every transitive dependency/model. Signals/enterprise packaging discrepancies require release-specific confirmation before any support/distribution claim.
- All slice sizes, storage/receiver defaults and VM planning figures are proposals. No tests/builds/linters were run for this documentation-only investigation.

**Bottom line:** copy Laminar's useful **trace model and reading experience**, speak its OTLP dialect at a narrow export boundary, and use its mature external workbench when wanted. Keep Mawas's memory, safeguards, audit, local history and process authority in `hutand`.
