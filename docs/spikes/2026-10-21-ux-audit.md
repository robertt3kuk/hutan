# UX audit — Hutan desktop at `4f33add` (debug build)

Method: live walk of the real app driven with Cua Driver, in a scratch `HUTAN_HOME` (`~/hutan-scratch/ux-audit/home`), against the design rules of Impeccable (Operate mode), the GPUI Kit design guide, Vercel's web-interface rules (translated to native), and the frontend-design skill. Everything below marked **[FACT]** was observed in this session; **[INFERENCE]** is a guess I did not verify. Screenshot paths are absolute under `~/hutan-scratch/ux-audit/shots/` (written to `/Users/homie/hutan-scratch/ux-audit/shots/`).

Scope walked: first-run wizard, open folder, new terminal (blocks), split and docks, command palette, jump, Agents page and overview, Tasks, Mawas Home (enabled through Settings), Settings (Appearance, themes, icon theme, Problems), New Agent picker (nothing sent), Resources, Changes, Requests, Agents right panel, quit dialog, relaunch, narrow window, comfortable density, and the icon-pack / colour-pack live-edit repaint bug (§4).

Not covered: the History index (kept off on purpose), sending any model turn, the Hutan.app bundle (I ran the debug `hutan-desktop` binary from `~/hutan-scratch/ux-bin/`, so the menu bar title reads "hutan-desktop", "Available when Hutan runs from Hutan.app" greys appear in the wizard, and notifications could not be exercised), real tooltips (the driver does not hover), keyboard Tab-focus rings, VoiceOver, display scale other than 2×.

Environment caveat **[FACT]**: another app (Orca) was maximised over the whole display for the entire session, so Hutan was fully covered unless I brought it forward. That matters for §4 and for harness reliability (§6).

## 1. Heuristic checklist (Operate mode, native macOS developer tool)

Each item is a yes/no test I applied while walking. Source skill in brackets: **IMP** = Impeccable (`SKILL.md`, `reference/operate.md`, `critique.md` cognitive-load and Nielsen sections, `audit.native.md`), **GPUI** = `gpui-kit-design-guides/references/design-guides.md`, **VER** = Vercel web-interface-guidelines (native translation), **FD** = Anthropic `frontend-design`, **HUT** = Hutan `docs/design.md` / `docs/themes.md` / chrome-v3 / settings-v2.

| # | Check | Source |
|---|---|---|
| H1 | The window title, tab and row names let me tell objects apart without opening them (recognition over recall; "name the object and the verb"). | IMP Nielsen #6, GPUI "Interface language", FD "name things by what users understand" |
| H2 | One focal point per surface; accent, bold, badges and primary buttons are scarce; hide the accent and the hierarchy still reads. | GPUI "Hierarchy", "Emotion budget"; IMP operate (accent only for action, selection, state) |
| H3 | At most ~4 decisions visible at a time; 8+ flat choices are an overload. | IMP cognitive-load checklist (Miller/Cowan rule) |
| H4 | Familiar controls: native menus/popovers, standard select and switch, no reinvented affordances; Button for in-app commands, Link only for URLs. | IMP "product slop test", GPUI "Button vs Link", "Components" |
| H5 | Every control has default, hover, focus-visible, pressed, selected, disabled, loading, error; selection is shown on the item's own surface. | GPUI "Interaction states", IMP operate "Components", VER Focus States |
| H6 | Empty, loading, error, disabled and read-only states exist and teach the next action (one CTA, not three); loading states say what is loading. | IMP "Empty states that teach", GPUI "Start from the task", VER "Handle empty states" |

## 3. Findings

IDs are stable for the slice plan in §5. Severity: blocker / major / minor / polish. Area is the probable component.

### F1 · Session titles are indistinguishable — **major** · area: sessions, titles
- Steps: ⌘T, `cd ~/…/proj-demo`, ⌘D, ⌘⇧D; open the jump palette (⌘P) and type `proj`.
- Expected: each terminal has a name I can tell apart (project, last command, or a number).
- Actual **[FACT]**: all three sessions are titled `~/h/u/proj-demo` (a fish-style abbreviated cwd that cannot be read without knowing the path) in the tab strip, the pane tabs, the Projects tree, the jump palette (three identical rows, subtitle `Home · ux-audit/proj-demo · main ·` with a trailing dot), the Resources panel and `hutan ls`. The `~/h/u/…` abbreviation also lost the leading directories (`home/Hutan` first, then `ux-audit/proj-demo`).
- Evidence: [15](/Users/homie/hutan-scratch/ux-audit/shots/15-new-terminal.png), [19](/Users/homie/hutan-scratch/ux-audit/shots/19-split-down.png), [54](/Users/homie/hutan-scratch/ux-audit/shots/54-jump-typed.png).
- Rules: H1, H8, GPUI "name the object", HUT principle 1 (attention first needs identity).

### F2 · Terminal prompts corrupt after a few resizes; block chips drift — **major** · area: terminal reflow / daemon screen model, blocks overlay
- Steps: ⌘T, run a few commands, ⌘D, ⌘⇧D, ⌘B, ⌘L, ⌘J, then ⌘J, ⌘L, ⌘B (nine pane-width changes in ~25 s).
- Expected: the prompt redraws cleanly at each width; block chips stay on their command row.
- Actual **[FACT]**: stacked partial prompts such as `homie@homies-MacBook-Pro ~/h/u/proj-…acBook-Pro ~/h/homie@homies-MacBook-P`; a duplicated `-Phomie@homies-MacBook-Pro ~/h/uhomie` row; the `✓ 39 ms` chip sits on the `README` wrap line instead of its command row after the sidebar went compact. `hutan history <session>` (daemon scrollback) prints the same garbled lines, so the corruption is in the daemon's terminal state, not only in painting.
- Cause **[INFERENCE]**: width changes reflow wrapped lines in the daemon grid while fish (which truncates its own prompt with `…` when narrow) repaints with cursor-up/erase-line sequences that assume no reflow. A comparison with Terminal.app and Ghostty was not done; if they stay clean, this is Hutan's reflow policy. Each dock toggle is a resize, so the user triggers this constantly.
- Evidence: [20](/Users/homie/hutan-scratch/ux-audit/shots/20-cmdB-compact.png), [22](/Users/homie/hutan-scratch/ux-audit/shots/22-cmdJ-bottom.png), [23](/Users/homie/hutan-scratch/ux-audit/shots/23-cmdK.png).
- Rules: HUT principle 2 ("the terminal is sacred"), H5, H17.

The Today rail never collapses. At ~650 pt wide the page works but the Today rail takes half of it. The doc promises a 480 pt centre floor; there is no per-page floor.

### F5 · History index consent is the default right-panel content, with all four sources pre-ticked — **major (trust)** · area: History panel
- Steps: first launch; the right dock opens on History.
- Actual **[FACT]**: "Show your agent sessions … Pick what Hutan may read" with **Hutan, Claude Code (`~/.claude/projects`), Codex (`~/.codex/sessions`), OMP (`~/.omp/agent/sessions`) all ticked**; one click on the orange **Enable** starts reading three third-party transcript stores. ## 4. Repaint bug: icon-pack (and colour-pack) edits "do not repaint until the next input event"

### Verdict
**It is not a file-watcher or theme-reload bug.** The edit is detected and applied in under a second whenever the window is visible. The window stops presenting frames when it is **fully covered by another window**, and it presents the latest state again when it becomes visible (activation, no input needed) or when it receives any input event. The orchestrator's "frontmost" window was almost certainly covered again after each foreground-mode driver action (§6). Colour-pack edits behave the same way as icon-pack edits.

### Mechanism
- GPUI (same revision Hutan pins, `ef376006…`, `Cargo.toml:86`) stops its display link when the window is not `NSWindowOcclusionStateVisible` and starts it again when it becomes visible: `crates/gpui_macos/src/window.rs` `start_display_link` (lines 835–845) and `window_did_change_occlusion_state` (lines 2993–3012) in `~/.cargo/git/checkouts/zed-a70e2ad075855582/ef37600/`. `crates/gpui/src/platform.rs:94-95` documents "macOS: `NSWindow.occlusionState`". **[FACT]** by reading the source.
- Hutan's theme/icon worker applies the change on its own thread; with the display link stopped, **[INFERENCE]** the new state is marked dirty but no frame is drawn. An input event (mouse or key) makes the window draw once, which is why "the next input" looks like the trigger.

### Method
Pack `canopy-lines` from `docs/themes.md § Icon packs` (two icons) installed at `<home>/icon-themes/canopy-lines/`, selected with `appearance.icon_theme = "canopy-lines"` (this itself repainted within 0.59 s, window frontmost). To make edits unmistakable I replaced `icons/search.svg` with seven different shapes (square, disc, triangle, diamond, cross, ring, bars) and compared the 36 × 34 px crop of the nav Search icon between screenshots (MD5 of pixels). Colour pack `canopy-day` (light) / `canopy-night` (dark): one token, `ui.accent`, switched between hues; compared the `+ New task` button crop. Writes were plain (`open(path,'w')`) and atomic (write temp + `rename`), the way editors save. Time = screenshot midpoint minus the moment the `write` returned. Each Cua `get_window_state` takes 0.33–0.5 s, so every "time to change" below is **an upper bound with ±0.4 s resolution**.

Foreground vs background: the *input method* does not matter; the *window state* does. Foreground-mode driver actions (`delivery_mode:"foreground"`) activate Hutan, act, then **restore the previously frontmost app** (Orca), which is how a window that was "frontmost" before the action ends up covered right after it **[FACT]**: with Hutan frontmost the restore is a no-op (4/4 front kept); with Orca frontmost Orca was restored (3/3). So a sequence "save → screenshot (stale) → click (shows the edit) → save → screenshot (stale) → click (shows the previous or the new edit)" reproduces "one event late" exactly, and with a few seconds of idle it reproduces "long delays".

### Colour pack versus icon pack
Same behaviour in every state tested. Two differences: a selected-then-edited colour pack needed a click once while four modifier/escape keys were ignored (trial 10 note) **[FACT, not reproduced in 2 later trials]**; and the Settings Problems list reported the unselected `canopy-day` pack's contrast warning (`diff.hunk.foreground on diff.hunk.background: contrast 4.26:1`), which is correct per `docs/themes.md § Problems and contrast`.

### What this means
- For users: **no defect when the window is visible**, including side by side with an editor. A window that is fully covered shows its last frame until it is uncovered; macOS also does this for other apps. The only user-visible risk is a screenshot or computer-use tool that captures a covered window.
- For automation and tests (this audit's driver, `hutan ui` screenshot flows, any agent that verifies pixels): keep the window frontmost (`bring_to_front`) and do **not** use foreground-mode actions that restore the previous app; wait ≥ 0.7 s after an edit; if the window must stay covered, send one cheap input (key) before the screenshot.
- Optional product hardening (not required): document in `docs/themes.md § Hot reload` that a fully covered window repaints when shown, and expose a debug switch that keeps the display link running (the existing GPUI code has none; **[INFERENCE]** it would need a GPUI patch).

## 6. Test-harness notes (to avoid re-learning)

- **Hutan ignores background-delivered synthetic clicks even when frontmost** [FACT]: `click` with `delivery_mode:"background"` at a visible button did nothing at four separate tries; `delivery_mode:"foreground"` worked every time. Background **keys** reached the app (§4 rows 10, 12). [INFERENCE] GPUI hit-tests from the last hovered position, which a posted click does not update.
- **First minute**: the first three inputs (one background click, one foreground click, one Return) left the wizard visibly unchanged while Hutan was covered by Orca; after the first accessibility-tree read (`Accessibility activated` in the log) the next click advanced exactly one step. Cause not isolated (occlusion vs a11y activation); consistent with §4.
- `get_window_state` always costs 0.33–0.5 s, so latencies below ~0.4 s cannot be resolved. Palette open, split, dock toggle and Settings open were all painted by the time the next screenshot came (≤ 1.0 s); I did not measure typing latency per key.
- The driver's coordinate space is the screenshot (1366 × 854 for a 1280 × 800 pt window); `move_cursor` with `scope:"desktop"` uses 2× pixels.
- I accidentally triggered three system prompts in the user's session while probing: `screencapture` from the shell raised a Screen Recording request, `osascript … Finder` raised an Automation request, and activating Tailscale opened its Settings and a DNS sheet (I clicked Manage… by mistake, saw "Not Using Tailscale DNS", and closed it with Done, changing nothing). I answered both system prompts **Deny / Don't Allow**; Tailscale Settings is no longer on screen. Nothing was granted.
