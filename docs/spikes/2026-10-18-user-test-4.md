# Hutan hands-on user test — round 4: Settings rebuild

## Executive summary

**Settings is substantially more complete, but this build still has two major interaction/lifecycle defects.** Notifications, history indexing, restore policy, security, harness environment, scoped assistant selection and data locations are now discoverable. Changed daemon settings save, their live/restart classification is exposed, restart banners work, comments survive writes, Reset removes keys, and a deliberately broken daemon.toml has a useful recovery panel.

The most important remaining problems are:

1. **Major — cancelling a Settings confirmation can strand keyboard input.** After cancelling Clear key, the search field could be clicked/focused but Command-A and typing did not replace its old query. The same symptom occurred after the integration confirmations. Reopening Settings through its explicit action recovered search.
2. **Major — Stop daemon → start it again from the CLI leaves the desktop latched in “daemon stopped”.** CLI requests and even creating a new terminal work, but the terminal refuses keyboard input; the UI Start action says the daemon is already running without fixing the stopped state. A UI daemon Restart recovered it.
3. **Minor — restart wording is still wrong for “Leave them stopped”.** The confirmation promises shells restart even when the selected policy deliberately leaves them stopped.
4. **Minor — keyboard navigation is improved, not completely fixed.** Tab/category arrows and Down/Return selection work. Escape left the Keyboard dropdown open in the exercised path.
5. **Minor — Assistant idle timeout advertises “at least 0”, but 1 is rejected because the actual rule is 0 or at least 60.**

There was **no paid model turn, agent Start, login/logout, hook mutation, API-key mutation or login-item enablement**. An unsent, idle OMP assistant was opened to inspect Automatic selection. All changed daemon keys were reset, the project override and terminal environment were removed, the disposable layout preset was deleted, and the app/daemon/shells were stopped. No test-bundle processes remain.

## Findings

### R4-1 — Cancelling a confirmation can strand Settings keyboard input

**Severity: major. Probable area: modal focus restoration / Settings input routing.**

**Steps:** Open Models, add the keyless port-9 provider, click Clear key. Click the visible Cancel button at screenshot coordinates (892,276). Click Settings Search, Command-A, type `Data & logs`. The same search-input symptom was encountered after inspecting/dismissing integration confirmations.

**Expected:** Cancel closes only the confirmation and returns ordinary keyboard editing to Settings. Search becomes `Data & logs` and filters navigation.

**Actual facts:** Confirmation disappears. Search has an orange focus outline but remains **Models** after Command-A/type; the intended query is not inserted (`r4-49-after-clear-cancel.png`). Earlier Escape also did not dismiss Settings in the affected state. Mouse actions continued to work; CPU was low. Explicit `workbench::OpenSettings` re-created/focused the search field and subsequent typing worked. This was not an app-wide CPU hang.

**Evidence:** `r4-48-clear-key-confirm.png` → `r4-49-after-clear-cancel.png`; integration sequence `r4-33-integration-confirm.png`–`r4-38-after-escape.png`; raw foreground events in `r4-observations.json`; `r4-modal-input-sample.txt`. At that investigation desktop CPU **0.6%**, RSS **165712 KiB**, daemon CPU 0%.

**[INFERENCE]:** A dismissed modal leaves keyboard focus/dispatch pointing at an obsolete field or modal handler. No source diagnosis is claimed.

### R4-2 — Stop→CLI Start reconnects control requests but leaves terminals unable to type

**Severity: major. Probable area: daemon lifecycle / desktop stopped-state latch / terminal input gating.**

**Steps:** With own shell and idle assistant, Data & logs → Stop daemon → confirm Stop Sessions & Daemon. Start the same home7 daemon using the bundle CLI with inline HUTAN_HOME. Let it run; use UI action daemon::Start as well. Open a new terminal with Command-T. Click its prompt, type `printf 'R4_RECONNECT_OK\\n'` and Return.

**Expected:** Desktop recognizes the running daemon, removes stopped banners and allows terminal input. UI Start either reconnects or accurately reports an actionable issue.

**Actual facts:** Stop works: socket disappears and status exits 3. CLI Start reports protocol 0.28 pid **17833** with two restored sessions. Subsequent `ui layout`, Settings mutations and new terminal creation succeed. Yet after more than six minutes the desktop still displays **hutand stopped**, **Daemon stopped / Start** and “The daemon is stopped”. UI Start says **“The daemon is already running”** without recovery. The newly created shell has its normal prompt but does **not receive typed characters**; CLI `history` contains only the initial fish welcome/prompt, not R4_RECONNECT_OK. A UI **Restart** launches pid **57624**, clears stopped state and the same terminal accepts/prints **R4_RECOVERED**.

**Evidence:** `r4-108-stop-confirm.png`, stop status/CLI Start output in observations; `r4-120-start-action-refresh.png`, `r4-121-new-terminal-after-start.png`, `r4-122-reconnected-terminal-input.png`; corresponding `ls` and `history`; `r4-129-recovery-input.png` / `r4-130-final-running-state.png`; `r4-stopped-input-sample.txt`. During failure desktop **0.5% CPU / 178400 KiB RSS**, daemon **0% / 22592 KiB**.

**[INFERENCE]:** Explicit Stop sets a desktop lifecycle/input gate that normal reconnection and “already running” Start do not clear. Backend availability alone is not the problem.

### R4-5 — Idle timeout’s visible allowed range contradicts validation

**Severity: minor. Probable area: Assistant numeric-setting metadata / validation copy.**
