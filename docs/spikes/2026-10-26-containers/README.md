# Which container runtime for sandboxed agents — research (2026-10-26)

Slice `CONTAINER-SPIKE`. Docs only. Input: `docs/spikes/2026-10-26-sandbox/README.md` § 3 and ADR 0021 decision 7 (a container is a *placement* for terminals and agents; `SANDBOX-3`). User, 2026-10-26: "any container — research what's best".

**Method and limits.** Nothing was installed, started or pulled (the brief's rule). On this machine (macOS 27.0.1, arm64) none of `container`, `docker`, `podman`, `colima`, `limactl`, `orb`, `sbx`, `devcontainer` is on `PATH` (`command -v`), and `/Applications` holds no Docker, OrbStack or Rancher app. Everything below is read from vendor documentation, upstream source and issues (linked), Homebrew's formula API, and GitHub release metadata (sizes come from `HEAD`/API calls, no file was downloaded). The only local measurements are `sw_vers` and `omp --help`/`omp auth-gateway --help` (read-only). **No bind-mount, `git status` or `cargo check` timing was measured by us**; § 1.3 gives the published numbers and § 5 a ready script for when the user allows an install. Claims I could not verify are marked `[INFERENCE]`; vendor claims are marked *(vendor)*. Versions current on 2026-10-25: Apple `container` 1.6.1 (2026-10-23), OrbStack 2.2.5, Docker Sandboxes `sbx` 0.49.2, Colima 0.10.3, Lima 2.2.1, Podman 6.1.4, Rancher Desktop 1.24.0.

## Answer in one screen

1. **First-class runtime #1: Apple `container`** (macOS 26+, which Hutan's macOS 27 target satisfies). It is the only candidate that gives a **VM per container** (a real kernel boundary), costs nothing, is Apache-2.0, needs no account and no third-party daemon, and has the three primitives Hutan needs: `exec -it` for PTYs, `exec -i` for stdio harnesses, and **host unix sockets that can be passed into the guest** (`-v host.sock:/guest.sock`, fixed upstream in March 2026). Its weaknesses are real and measured by others: warm start ≈ 0.9 s vs ≈ 0.3 s, **virtiofs bind mounts are the slow path** (maintainer: ≈ 3× slower than a named volume, which is itself 2–3× slower than native for builds), young (1.x; security advisories in four releases since August), no allowlist networking.
2. **First-class runtime #2: "Docker Engine-compatible" as one adapter** covering **OrbStack, Docker Desktop, Colima, Rancher Desktop and Podman**, reached through the `docker`/`podman` CLI (for PTY/stdio) and the Engine API socket (for detection). They differ in licence, speed and mount performance, not in the dialect Hutan speaks. Tested representative: **OrbStack** (best published bind-mount performance, 75–95 % of native *(vendor)*) with **Colima** as the free-licence check. One shared kernel per VM: a weaker boundary than #1 (OrbStack's docs say their isolated machines are not a full security boundary against kernel attacks).
3. **Do not target** Lima directly (it is a VM reached over SSH: it belongs to the *remote host* placement of ADR 0022, not to containers), Rancher Desktop (Lima underneath, default mount is reverse-sshfs, Electron, 650 MB; works through adapter #2 if the user has it), and Docker Sandboxes `sbx` (proprietary CLI + Docker sign-in, no OMP; detect and mention only).
4. **The daemon socket problem has one answer that works on every runtime:** the daemon starts `<runtime> exec -i <container> hutan relay …` and multiplexes the container's connections over that stdio pipe into a per-session restricted endpoint (SANDBOX-2B). No TCP, no host socket path, no runtime feature needed. On Apple `container` a direct socket pass-through is the zero-code optimisation. Host-socket mounts do **not** work on OrbStack, Docker Desktop, or Colima/virtiofs (§ 1.4).
5. **Credentials (ADR 0015):** one named volume per (harness, account) mounted as the harness home, login run **inside** the container with the harness's own flow; Hutan never reads the volume. Codex: `codex login --device-auth`; Claude Code: URL + pasted code (it stores `~/.claude/.credentials.json` on Linux, not the Keychain); OMP: `omp login` (paste fallback unverified).
6. **Inside the container the container is the boundary** (ADR 0021 decision 4, no stacking): Codex runs with `danger-full-access`/`externalSandbox`, Claude Code runs as a non-root user and may use `--dangerously-skip-permissions`, its Bash sandbox is off. OMP's `yolo` is acceptable only here.
7. **Detection is read-only:** Apple: `container system status --format json` (source-verified: launchd registration check + health ping, exit 1 when down). Docker family: `stat` of known socket paths, then `GET /_ping` and `GET /version` on the socket; Podman: `podman machine inspect`; apps: `stat /Applications/*.app`. Never `open -a`, `container system start`, `docker context use`, a pull, or a run.
8. **Biggest risks:** bind-mount I/O on a git worktree (unmeasured by us), non-root writes to virtiofs mounts on Apple `container` `[INFERENCE]`, a planted `.git/hooks/*` running later on the host unsandboxed, egress control (Apple: host gateway reachable from `--internal` networks, #1320), single-file mounts flaky on Apple (#1251), and the runtime's own security advisories.
9. **Plan:** `SANDBOX-3` becomes seven small slices (§ 4.4); only C-1 (pure crate: trait, argv builders, detection against recorded fixtures) can start now. C-2 onward needs a runtime installed, which needs **the user's permission**.
10. **Ask the user:** (a) may we install Apple `container` (156 MB pkg, admin password once) and, optionally, OrbStack/Colima to measure § 5; (b) is Apple-`container`-first acceptable given macOS 26+ only; (c) is a Hutan-run egress proxy acceptable (needs its own ADR).

Reading: the two Apple benchmarks disagree by 20× on the same operation class (sequential `dd` vs `fio`), so neither says anything about **`git status` on 2 000 files** (pure `lstat`/`readdir` latency) or **`cargo check`** (many small writes into `target/`). The maintainer statement is the best evidence: *metadata-heavy work on a virtiofs bind mount is the weak spot of Apple `container`; named volumes are 3× better.* Docker-family virtiofs has the same inherent cost (OrbStack's own docs say so) but with tuned caches. `[INFERENCE]` for Hutan: keep the **worktree** bind-mounted (same absolute path is the contract), and put `target/`, `node_modules/`, `CARGO_HOME` and the harness homes on **named volumes** (virtioblk on Apple). Measure with § 5 before promising anything.

Cold start (runtime not running): OrbStack "starts in 2 seconds" *(vendor, docs home page)*; no published number for `container system start`, `colima start` (first start downloads a guest image), `podman machine start` or Docker Desktop `[INFERENCE: seconds to tens of seconds]`.

### 1.4 Reaching `hutand` from inside the container (unix sockets)

| Runtime | Host unix socket → guest | Guest socket → host | Evidence |
|---|---|---|---|
| **Apple `container`** | **yes**: `-v /host/path.sock:/guest/path.sock` (how `--ssh` works: `--volume "${SSH_AUTH_SOCK}:/var/host-services/ssh-auth.sock"`, [host integration](https://github.com/apple/container/blob/main/docs/host-integration.md)). Demonstrated by a maintainer ([#357](https://github.com/apple/container/issues/357)); the failing case was a guest path under a symlink (`/var/run` → `/run`), **fixed 2026-03-23** by containerization#568; use real paths | **yes**: `--publish-socket host_path:container_path`; the host path must not already exist as a socket ([`Parser.publishSocket`](https://github.com/apple/container/blob/main/Sources/Services/ContainerAPIService/Client/Parser.swift)). The earlier sandbox spike read this flag as host→guest; it is the **opposite**, container→host. `UnixSocketConfiguration` has both directions `.into`/`.outOf` ([containerization](https://github.com/apple/containerization/blob/main/Sources/Containerization/UnixSocketConfiguration.swift)) | docs, source |
| **OrbStack** | **no in general**: "Unix socket forwarding isn't supported yet" ([discussion #584](https://github.com/orgs/orbstack/discussions/584), 2023; tracking issue [#62](https://github.com/orbstack/orbstack/issues/62) open, last touched 2023-08); only special paths such as `/run/host-services/ssh-auth.sock` ([docs](https://docs.orbstack.dev/docker/#ssh-agent-forwarding)). `-v $SSH_AUTH_SOCK:…` works "in most cases" because of that special casing | sockets created on the shared macOS filesystem are not supported ("Similar to WSL, Unix sockets are not supported on the shared macOS file system", #62) | docs, issues; `[INFERENCE]` still true in 2026 |
| **Docker Desktop** | not generally; `/var/run/docker.sock` and the ssh-agent path are special-cased ([for-mac#6375](https://github.com/docker/for-mac/issues/6375), [OrbStack comparison](https://docs.orbstack.dev/compare/docker-desktop) "SSH agent forwarding — requires special path") | the Docker forum answer says the same ([thread](https://forums.docker.com/t/unix-socket-on-bind-mount/142653)) | `[INFERENCE]` for 2026 |
| **Colima / Lima** | virtiofs: `mkdir …/docker.sock: operation not supported` ([colima#997](https://github.com/abiosoft/colima/issues/997), reproduced 2026-01); Lima has **`portForwards: [{guestSocket, hostSocket, reverse: true}]`** ("`reverse` can only be used for unix sockets", [default.yaml](https://raw.githubusercontent.com/lima-vm/lima/master/templates/default.yaml), implemented by lima#836 for #834), giving a socket *inside the VM* that a container can then bind-mount | Lima default direction (guest → host) | docs, issues |
| **Podman, Rancher Desktop** | not documented; `[INFERENCE]` as Docker Desktop / Colima | — | — |

Consequence: **no host-socket mount is a portable basis.** Design (new, not measured): the daemon starts `exec -i <container> hutan relay --socket /run/hutan/daemon.sock` (a Linux build of the `hutan` CLI in the image). The relay accepts local connections inside the container, tags each with a channel id and multiplexes them over its stdin/stdout to the daemon, which attaches every channel to the session's restricted endpoint (ADR 0021 decision 5; ADR 0022 decision 1: *an acceptor produces an authenticated principal* — the "exec stdio" acceptor's principal is "agent of session X in container C"). The identity is the pipe the daemon itself opened, so no path, port or token has to be protected. Needs: a Linux `hutan` (LX-1 headless crates already `cargo check` on Linux per ADR 0022), a ~100-line mux framing, bounded queues (AGENTS.md invariant).

### 1.5 Candidate verdicts

| Candidate | Verdict | Why |
|---|---|---|
| Apple `container` | **first-class** | boundary strength, licence, no account, socket pass-through, per-container mounts, recent fixes; cost: speed, maturity, mounts |
| OrbStack | **first-class via adapter #2 (tested representative)** | fastest published I/O and start, Docker API; paid for commercial use (Hutan only detects it, never bundles) |
| Colima | **first-class via adapter #2 (free check)** | MIT, scriptable, fastest container start in zot24; no host sockets, user must install `docker` CLI |
| Docker Desktop | supported via adapter #2, not tested by us | commercial terms; ubiquitous |
| Podman | supported via adapter #2 where the CLI flags match | `podman` has Docker-compatible CLI and API; machine mounts `$HOME:$HOME` |
| Rancher Desktop | not targeted | default mount reverse-sshfs ([volumes](https://docs.rancherdesktop.io/ui/preferences/virtual-machine/volumes)); works if it exposes a Docker socket |
| Lima direct | **remote-host placement, not container** | a Linux VM over SSH is ADR 0022's host abstraction; reuse it after LX-1 |
| Docker Sandboxes `sbx` | detect only | proprietary CLI + Docker sign-in; no OMP; but solves credentials (host-side proxy injects tokens, "stays on your host") and network presets (Open/Balanced/Locked Down) — a possible later adapter if users ask |

### 2.1 Claude's reference firewall, what it teaches

`init-firewall.sh` ([source](https://raw.githubusercontent.com/anthropics/claude-code/main/.devcontainer/init-firewall.sh)) flushes iptables, allows DNS (udp 53), SSH, loopback and the **/24 of the default gateway**, builds an `ipset` of GitHub's published CIDRs plus resolved A records for `registry.npmjs.org`, `api.anthropic.com`, `sentry.io`, `statsig.com` and VS Code hosts, sets `INPUT/FORWARD/OUTPUT DROP`, verifies that `example.com` is unreachable and `api.github.com` reachable. Needs `NET_ADMIN` + `NET_RAW` (`runArgs`). Properties for Hutan: it is an **IP allowlist resolved once at start** (CDN IPs rotate, `[INFERENCE]` breakage), it **leaves DNS open** (the DNS-tunnel channel of the sandbox spike § 2, probe "DNS under network off"), it allows the whole host /24 (on Apple `container` that includes the gateway → host services, cf. #1320), and it needs root with capabilities that the agent could use to undo it unless the harness user drops them. Apple's per-container VM is a better home for it than a shared VM, but a root agent in the guest can still `iptables -F`. So: run the harness as a non-root user without `NET_ADMIN` after the init step. Domain-level allowlisting properly needs a proxy (what `sbx`, `srt`, Codex's `network_proxy` do); a Hutan-run proxy is a separate ADR (ADR 0021 "no Hutan-run network proxy in v1").

### 2.2 Credentials: the rule and the shape

ADR 0015/0021 decision 7: Hutan never reads, stores or forwards a token; no API keys from the Keychain into a container environment. Shape that satisfies it:

- **One named volume per (harness, account)**, created by the runtime (`container volume create hutan-cred-claude-work`, `docker volume create …`), mounted at the harness home path inside the container, with the harness's own variable pointing at it (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `PI_CODING_AGENT_DIR` + `OMP_PROFILE=`). This is the ACCOUNTS-MULTI mechanism (ADR 0015 § Amendment: an account is a home folder passed by environment variable) with the folder replaced by a volume; Hutan never lists or opens it. A container account is a **different login** from the host account of the same name (Claude's host login is in the Keychain and cannot be mounted in: the volume's file store is a separate credential); the UI says so.
- **Login = the harness's own login command run through `account.login` with a placement argument**, in a terminal session placed in that container (PTY via `exec -it`); the user finishes it in their browser, pasting the code where the harness asks. Same visible-terminal contract as today.
- **Exfiltration is the residual risk, stated in the UI:** a prompt-injected agent with network access can read the volume it runs in (Claude's own warning: dev containers "do not prevent a malicious project from exfiltrating anything accessible inside the container, including the Claude Code credentials stored in `~/.claude`"; Codex's text is the same). Per-account volumes bound the blast radius to that one login; the network policy is the real control. Never mount the host harness home, `~/.ssh`, or `docker.sock` into the container.
- **Not recommended:** env-var tokens (`CLAUDE_CODE_OAUTH_TOKEN`, `OPENAI_API_KEY`) — visible in `inspect` and process listings; `sbx`'s credential proxy as a dependency; copying `auth.json` by Hutan (the docs' `docker cp` recipe is for the user). **Optional later, OMP only:** `omp auth-gateway`/`OMP_AUTH_BROKER_URL` keep tokens off the container entirely; Hutan would only start OMP's own process, but that is a Hutan-run service and needs its own decision.
- Hutan's own hooks and MCP entry (`hutan agent …`, `hutan mcp`, `hutan integration install`) must run **inside** the container (they edit the harness home in the volume): they need the Linux `hutan` binary and the relay socket of § 1.4.

## 3. Detecting runtimes without side effects

Rules: read-only, bounded (2 s per probe), on demand (opening the Start sheet's *Place in* row or Settings → Sandbox, plus `sandbox.runtimes` for the CLI), results cached ≤ 30 s, **never** at daemon start, never launching an app, starting a service, selecting a context, pulling, building or running. Use the login `PATH` the daemon already computes (`docs/agents.md` § login environment) for binaries.

## 4. Recommendation

### 4.1 Which runtimes, and why

- **Apple `container` first** because the goal is a *boundary for unattended agents* (Superset #3957, Orca #13665 in the sandbox spike § 0): VM-per-container beats a shared kernel for that; it is free for everyone (OrbStack and Docker Desktop have commercial terms that Hutan would otherwise push onto users); it is first-party, so it tracks macOS 27; its socket and mount model is per-container and explicit. Hutan already requires macOS 27 (arm64).
- **Docker-compatible adapter second**, because many users already run OrbStack/Docker Desktop/Colima and will not install a second runtime, and because it is where the best published mount performance is. One adapter, parameterised by binary and endpoint; per-product facts live in `RuntimeCaps`.
- **Detect, never install, never bundle** (answers the sandbox spike's open question 3 in the conservative direction; the user decides).
- Where Apple's weaknesses bite (mount I/O, start time), the user can pick the Docker-family runtime for the same project: the placement setting names *a runtime*, not "container".

### 4.2 `ContainerRuntime` trait shape

The key observation: Hutan's PTY and stdio seams already take a command (`TerminalConfig.argv` → `command()` in `crates/terminal/src/terminal.rs`; `Launch { program, args, cwd, env }` in `crates/agents/src/jsonrpc.rs`). So the trait mostly **builds launches**; only a few calls talk to the runtime. A new service crate `crates/container` (no GPUI; `daemon` links it; `core`/`protocol` untouched except the wire fields below).

```rust
/// One per runtime *adapter*; Apple and Docker-compatible (docker|podman binary) implement it.
pub trait ContainerRuntime: Send + Sync {
    fn id(&self) -> &RuntimeId;                       // "apple-container", "orbstack", "colima", …
    /// Pure and side-effect free (§ 3). Called by `sandbox.runtimes`.
    async fn detect(&self, probe: &dyn HostProbe) -> RuntimeReport;
    fn caps(&self) -> RuntimeCaps;

    /// Idempotent by label `hutan.session=<id>`: create + start, or return the running one.
    async fn ensure(&self, spec: &ContainerSpec) -> Result<ContainerId, RuntimeError>;
    async fn inspect(&self, id: &ContainerId) -> Result<ContainerState, RuntimeError>;  // running|exited(code)|gone
    async fn volume_ensure(&self, name: &VolumeName) -> Result<(), RuntimeError>;
    async fn stop(&self, id: &ContainerId, grace: Duration) -> Result<(), RuntimeError>;
    async fn remove(&self, id: &ContainerId, force: bool) -> Result<(), RuntimeError>;
    async fn list_hutan(&self) -> Result<Vec<ContainerRef>, RuntimeError>;   // by label, for the daemon-start reaper

    /// Launches for Hutan's existing seams; `<cli> exec -it|-i …` argv, env, workdir, user.
    fn exec_pty(&self, id: &ContainerId, cmd: &ExecSpec) -> Launch;   // → terminal crate (PTY owned by the daemon)
    fn exec_stdio(&self, id: &ContainerId, cmd: &ExecSpec) -> Launch; // → Transport::spawn_v2 (ACP, codex app-server, relay)
}

pub struct ContainerSpec {
    pub image: ImageRef,                 // fully qualified, arm64; never pulled implicitly
    pub name: String, pub labels: Labels, // hutan.session, hutan.project, hutan.account
    pub mounts: Vec<Mount>,              // Bind{host, guest, ro} | Volume{name, guest, ro} | Tmpfs{guest, size}
    pub network: NetworkPolicy,          // None | Internal | Open | (later) Proxy{allow: Vec<Host>}
    pub user: User, pub workdir: GuestPath,
    pub env: Vec<(String, EnvValue)>,    // EnvValue::Plain only; no variant can carry a secret
    pub limits: Limits,                  // cpus, memory
    pub root_read_only: bool, pub cap_drop: CapSet, pub init: bool,
}

pub struct RuntimeCaps {
    pub boundary: Boundary,              // VmPerContainer | SharedVm | Unknown
    pub network_none: bool, pub network_internal: bool, pub host_reachable_from_internal: bool,
    pub host_socket_mount: bool,         // true on Apple only
    pub single_file_mount: Reliability,  // Apple: Flaky (#1251)
    pub nested_ro_mounts: bool, pub named_volumes: bool, pub rosetta: bool,
    pub exec_resize: bool, pub needs_admin_to_start: bool,
}
```

Notes: the policy layer (daemon) turns `{preset, harness, project}` into a `ContainerSpec` and **refuses** if `caps` cannot honour it; the adapter never degrades silently. Dispatch by `enum Runtime { Apple(AppleContainer), Docker(DockerCompat) }` (no `dyn` async); `detect`/`caps` pure so they unit-test against recorded CLI/API output. `exec_*` returning a `Launch` keeps PTY ownership, resize (`TIOCSWINSZ` on the daemon's master → the `exec` CLI gets SIGWINCH and forwards it; works from Apple 1.6.1 `[INFERENCE]`, **test**), OSC 133/7 injection and the resource manager unchanged. Caveat to record in `docs/resources.md` when built: `hutan ps` sees the CLI child, not the processes inside the VM — `stats`/`top` per container would be a separate source.

### 4.3 How a contained session is assembled (per ADR 0021 decision 7)

1. **Mounts**: the checkout or worktree at its own absolute path (`-v $WT:$WT`); for a linked worktree also the repo's common `.git` at its own path, because the worktree's `.git` file holds an absolute `gitdir:` (sandbox spike § 2 measured the same need under Seatbelt). Protect `hooks/` and `config`: nested read-only mounts, **but single-file mounts are flaky on Apple** (#1251: hard-link files via virtiofs) so mount `hooks/` read-only and neutralise `config` with `GIT_CONFIG_COUNT/KEY_n/VALUE_n` (git ≥ 2.31) `core.hooksPath=/dev/null` `[INFERENCE]`, **and** have the daemon hash `.git/hooks`/`.git/config` before and after a run and warn on change (a hook planted by a contained agent would run later on the host, unsandboxed). `target/`, `node_modules/`, `CARGO_HOME`, `$HOME/.cache` → named volumes. Shell integration dir read-only at the path `HUTAN_SHELL_INTEGRATION_DIR` names.
2. **Network**: `None` for plain terminals/commands by default; chat harnesses need their API: `Open` initially, allowlist later (§ 4.4 C-6). The daemon endpoint is **never** a network address: the relay of § 1.4.
3. **User**: non-root uid (Claude refuses root); bind-mount write access as non-root on Apple's virtiofs is **unverified** (the docs' example listing shows host files as `root root` inside the guest; `container machine` solves it by mapping the host uid; regular containers: unclear) → C-2 must test `--uid/--gid` against a mount owned by the host user.
4. **Per harness** (§ 2): home volume, env var, flags for "container is the boundary", `hutan` binary + relay for hooks/MCP.
5. **Lifecycle**: container labelled; the daemon's reaper (on start) lists `hutan.*` labels and stops orphans (ADR 0009 process survival); an `exec` child dies with the daemon but the container does not.

No runtime. | nothing — **done** (branch `slice/C-1`; see the note below the table) |

**C-1 as built (2026-10-26).** `crates/container` (`hutan-container`), not linked by the daemon until C-2. Differences from the § 4.2 sketch, all on purpose: `detect` is synchronous over an injected `HostProbe` (the daemon runs it on a blocking thread), the lifecycle methods are `impl Future + Send`; `RuntimeCaps.nested_ro_mounts` is `nested_mounts` (it also covers a volume for `target/` under the worktree mount) and `needs_admin_to_start` is dropped (no document read says any runtime needs admin to *start*); `Mount::Tmpfs` has no size (Apple's `--tmpfs` documents none); `EnvValue` is just `EnvVar` (plain only, credential-looking names refused). **Capabilities the sources did not settle are recorded closed and refuse sessions until C-2/C-5 test them on a real runtime**: Apple `nested_mounts` and `exec_resize` are `false`, so on Apple a linked worktree with protected `hooks/` or a `target/` volume under the worktree is refused; `CONTAINER_FLOOR` (1.6.1, the only release whose docs and source were read) marks older Apple `container` `Unsupported`. Detection fixtures and what each was transcribed from: `crates/container/tests/fixtures/SOURCES.md` — real listings for Docker Desktop, Colima and OrbStack, podman's own source for its headers and `/version`, and **synthetic** values for Rancher Desktop and an unrecognised engine (marked as such). Not done, by design: Docker contexts (probe 7, display only), `sbx`, and licence text in the report.

Dependencies fixed by ADR 0021: not before REMOTE-SPIKE's transport decision (ADR 0022 proposed, not accepted), a user decision on the runtime dependency, and a runtime being installed to test against.

### 4.5 Risks

| Risk | Detail / mitigation |
|---|---|
| **Mount I/O on a worktree** | virtiofs is the slow path on every runtime; on Apple measured ≥ 2× slower on small writes (zot24) and ≈ 3× vs a named volume (maintainer). Unmeasured for `git status`/`cargo check`. Mitigate with volumes for build output; measure first (§ 5); offer a *clone mode* (private clone in a volume, merged with `hutan wt merge`) only if the numbers demand it |
| **Young runtime** | Apple `container` release versions "are product versions, not semantic versions"; helpers' XPC APIs "do not guarantee CLI or API compatibility across different versions"; security advisories in 1.3.1 (path traversal in bundle ids, OCI layout symlinks), 1.4.1, 1.5.0, 1.6.0 (digest pinning not verified, symlink swap during `build`) ([releases](https://github.com/apple/container/releases)). Pin and display the version; refuse below the tested floor; show "update available" is out of scope |
| **Network containment gaps** | `--internal` still reaches the host gateway (#1320); no allowlist anywhere; DNS leaks; Claude's script leaves DNS open and is root-reversible. Label honestly (ADR 0021 decision 6) |
| **Planted `.git/hooks`** | see § 4.3 item 1 |
| **Credentials in the volume** | § 2.2; bounded per account; network policy is the control |
| **Docker socket = root on the Mac** | never mount `docker.sock` into an agent container (Docker's own comparison table: "Container with socket mount — Partial (namespaces) — Shared host daemon"); `sbx` gives agents their own daemon instead |
| **Shared kernel on adapter #2** | OrbStack's docs: not a boundary against kernel exploits; the UI names `Boundary: shared VM` from `RuntimeCaps` |
| **Non-root + bind mounts, uid/gid, case** | unverified on Apple (above); APFS is case-insensitive by default, the guest is not |
| **Path symlinks** | `/var`→`/private/var`, `/tmp`→`/private/tmp`: canonicalise every host path; the Apple socket bug (#357) was a guest symlink |
| **Single-file mounts flaky on Apple** | #1251; avoid |
| **Process visibility** | `hutan ps|top|kill` see the `exec` CLI only; document, add per-container stats later |
| **CLI output stability** | `--format json` shapes change across releases: tolerant parsing, recorded fixtures per tested version, feature-detect via `version` |
| **Images** | arm64 only; never pull or build silently (network, disk); user confirms; fully qualified refs always |
| **Licences are the user's** | OrbStack/Docker Desktop terms apply to the user's company; Hutan states the licence in the detection report and never bundles or installs |
| **macOS 26+ floor** | Hutan targets 27; if the floor ever drops, Apple `container` is simply `Unsupported{reason}` |

## 5. Measurement plan (run **only with the user's permission**)

Install Apple `container` (`brew install container` or the pkg; `container system start`), and optionally OrbStack and/or Colima (`brew install --cask orbstack`; `brew install colima docker && colima start --vm-type vz --mount-type virtiofs`). Uninstall afterwards (`/usr/local/bin/uninstall-container.sh -d`; `colima delete`; remove the cask). Fixed inputs: the Hutan checkout at its own absolute path (2 104 tracked files; native `git status` 31 ms on this machine, sandbox spike § 2 Overhead), a linked worktree of it, an image with git, a Rust toolchain and `cargo` (a user-approved build). For each runtime, 5 runs each, median and p95, cold = right after starting the runtime, warm = second container:

1. `start`: `time <rt> run --rm <img> true` (warm and cold).
2. `git status` in the worktree bind-mounted at the same path: `<rt> run --rm -v $WT:$WT -v $COMMON:$COMMON -w $WT <img> git status --porcelain` vs native (also `git diff --stat` after touching 200 files).
3. `cargo check --locked` on the checkout, `target/` on (a) the bind mount, (b) a named volume (`-v hutan-target:$WT/target`), vs native; second run (incremental) too.
4. 5 000 small file creates (the sandbox spike's workload) on bind vs volume.
5. PTY: `exec -it` + `stty size` after resizing the host PTY; unix socket pass-through (Apple `-v sock:sock`; Lima `reverse: true`); `--network none` + `curl` fails; non-root `touch` into the bind mount; `.git` single-file read-only mount over 50 start/stop cycles (#1251).

Results go into this directory as `measurements.md`; § 1.3 then loses its "published only" caveat.

## Open questions for the user
1. May we install Apple `container` (and optionally OrbStack/Colima) to run § 5? Without it C-2 onward cannot be tested and every claim above about speed stays published-only.
2. Is "Apple `container` first, Docker-compatible second, detect-only" the order you want, or should the Docker family come first because you already use one of them?
3. Is a Hutan-run egress allowlist proxy acceptable (ADR needed), or should chat harnesses in containers run with the network open and labelled so?
4. Clone mode (private clone in a volume) as an alternative to bind-mounting the worktree: only if the measurements show bind mounts are unusable.
