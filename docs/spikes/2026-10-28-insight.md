# Spike: what each harness exposes for an agent insight panel (INSIGHT-SPIKE)

Date: 2026-10-28 · Question (user, 2026-10-28): *"in the sidebar we can see the focused agent's analytics or context — what costs what"* · Feeds: slice `AGENT-INSIGHT` of `docs/spikes/2026-10-28-ui-study/README.md` §5 (plan row 7, `mock-insight.svg`) · Method: documentation, upstream source, recorded fixtures of this repo, and runs of the real binaries in scratch directories (no login, no model call). No product code; evidence is in `docs/spikes/2026-10-28-insight/`.

## Summary

1. **Every harness gives the two numbers a context meter needs** (used, window), in a chat and, with help, in a terminal. Nothing gives a *dollar cost for a subscription login that is not the harness's own estimate*, and Codex gives none per turn at all.
2. **The breakdown by category (system prompt / tools / project files / skills / messages) is the scarce data.** Only Claude Code has a structured API for it (`get_context_usage`, now **verified by a run**: categories with ids, per-tool-call, per-skill, per-memory-file tokens, and a message split by tool type). OMP has it internally and prints it as text for `/context`; its **extension API does not expose it** (verified), but a *fixed part vs messages* split is derivable exactly (below). Codex has no breakdown at all.
3. **The first open question of the study is answered: an OMP extension cannot read the category breakdown.** `ExtensionContext` has `getContextUsage()` (`{tokens, contextWindow, percent}`) and `getSystemPrompt()`; no `getContextBreakdown` (checked at runtime on 18.12.3 and in the source on `main`). What an extension *can* do, verified: `getContextUsage().tokens` at `session_start` equals the sum of the non-message categories of `/context` (10 678 = 4 124 + 6 386 + 168), so *fixed overhead* = that number and *messages* = used − fixed, exact up to OMP's own estimator.
4. **Per-call usage with cost is available to an OMP extension** (`message_end` / `turn_end` carry `usage {input, output, cacheRead, cacheWrite, totalTokens, cost{…total}}`, `agent_end` + `ctx.sessionManager.getUsageStatistics()` the cumulative totals incl. subagent cost), as are tool names and arguments (files). This is everything phase B needs for OMP in a terminal.
5. **Claude Code in a terminal has four usable channels, none of them free:** the status-line JSON (context window, cost, durations, cache hit ratio; one command per user, `--settings` outranks the user's own), hooks (`duration_ms`, tool, path; no tokens), the transcript (assistant `usage`, plus `cost-state` and `system.contextUsage` records that we **observed in a real transcript**), and OpenTelemetry (everything, but needs an OTLP receiver in `hutand`). The transcript is the cheapest; it needs the history-index opt-in.
6. **Codex in a terminal:** hooks give the rollout path (`transcript_path`), the rollout's `token_count` events carry `total` and `last` usage and the window. No breakdown, no cost.
7. **Two defects in what Hutan shows today** (details § 4): the Codex context chip reads the cumulative `total` where Codex's own TUI reads `last` (the recorded fixtures show 41 290 against a true context of 20 672 on a 475 000 window), and cache-write tokens, `_meta.quota` and Codex's `account/usage/read` thread estimate are dropped. Fix the first before the panel shows the same number in a bigger font.
8. **Recommendation:** one daemon-side aggregator (`AgentInsight`) that merges blocks from the best source per block and says which source each block came from (the mock's *Sources* chips). Phase A (chats) already needs the daemon aggregator, because the desktop only holds the newest loaded journal page; protocol 0.58 therefore lands in phase A and carries the reporter input too, so phases B and C add no protocol change (§ 5, § 6).

## 4. What Hutan stores and shows today, and two defects found

| Where | Holds | Limits |
|---|---|---|
| Chat journal (`chat.history`, SQLite, `AgentEventKind`) | every `usage {total?, last?, context_window?}`, `tool_start/end {name, title, input, status, duration_ms}`, `file_diff {changes}`, `turn_completed {duration_ms}`, `message_end` | the desktop reads the newest 200 events and pages back on demand |
| `usage_turns` (schema v19, 35 days) | one row per ended chat turn: harness, provider, model, input / cached / output / reasoning / total tokens, `cost_usd`, time | no tool, file, context or session-level aggregates; no read request by session (`usage.summary` sums by harness/provider and day/week) |
| `agent.tree` node `usage` (`Usage {kind, input, output, cache_read, cache_write, reasoning, context_tokens, context_window, cost_usd}`) | the latest figure a reporter or adapter gave; ACP chats: `acp.context` with `cost_usd` | one record per node; no history; shown as one muted label (`3.2k/200k tok · context`, `usage_label`) in the agents list |
| Chat header chip (UX-CONTEXT-METER) | `context 61 % · 122k / 200k` from the newest `usage` event with a total; tooltip with cumulative counts; cost is not shown | see defect 1 |
| Usage section of the Agents page, status item, `hutan usage` | limit windows, today / week tokens and an estimated cost per harness | not per session |
| Inspector panel (`panels/inspector.rs`) | tabs Info / Requests / Changes | no usage tab |
| Terminal sessions | `SessionInfo.agent {state, message, …}` and the node (`model`, `activity`) when the extension or hooks report; the shipped OMP extension reports neither usage nor activity | — |
| Checkpoints (`checkpoint.diff {stat}`) | per chat turn: files with `added`/`removed` | chats in a git checkout only |

**Defect 1: the Codex context chip overstates.** `Transcript::context_use` (`crates/chat_view/src/model.rs`) takes `used` from the `total` of the latest event. That is right for ACP (`usage_update.used` is the context, mapped to `total`), wrong for Codex, whose `total` is cumulative. In `approval-decline.jsonl` the second request reports `total 41 290`, `last 20 672`, window 475 000: the chip shows 9 % where Codex's own formula gives about 4 %, and the gap grows with every request of a long thread. The panel must not repeat it. Rule for the fix: when an event carries both `total` and `last`, the context is `last.total_tokens`; when it carries only `total`, that is the context.

**Defect 2 (smaller): dropped fields.** `TokenCounts` (`crates/core/src/agent.rs`) has no cache-write counter, so Codex's `cacheWriteInputTokens`, the ACP prompt's `cachedWriteTokens` and Claude's `_meta.quota.token_count.cachedWriteTokens` are discarded (this matters for Claude, where cache writes are priced above plain input); `_meta.quota.model_usage` (per-model spend including subagents) and `PromptResponse` `thoughtTokens` are not read; Codex's `account/usage/read` is never called. Adding the cache-write counter is an additive `core`/protocol change that belongs with the 0.58 bump.

## 5. Design: one aggregator, per-block provenance

**The record** (`crates/core`, `AgentInsight`; all blocks optional, a number nobody reported is absent, never zero):

```text
AgentInsight
  session_id, node_id            the main node, or a subagent when its row is focused
  seq, as_of_ms
  model        {id, provider?, thinking?}
  context      {used, window?, exactness: reported|estimated, as_of_ms,
                breakdown?: [{id, label, tokens, kind: used|buffer|free|deferred}],   ≤ 16 rows
                compact_at?}
  totals       {turns, input?, output?, cache_read?, cache_write?, reasoning?,
                cost_usd?, cost_kind: reported|estimate, cache_hit_ratio? (derived)}
  turns        [{n, turn_id?, started_ms, duration_ms?, outcome, input?, output?, cache_read?,
                 cache_write?, reasoning?, cost_usd?, context_after?, tool_calls?, tool_failed?}]   newest last, ≤ 200
  tools        {calls, failed, by_name: [{name, calls, failed, ms?}]}   ≤ 16 names + "other"
  files        {count, added, removed, items: [{path, kind, added, removed}], truncated}   ≤ 100
  time         {started_ms, wall_ms, active_ms?, api_ms?, tool_ms?}
  sources      [{block: context|breakdown|turns|tools|files|time,
                 source: chat|extension|hooks|statusline|transcript|osc7501, as_of_ms}]
```

`breakdown[].id` is a closed vocabulary the desktop knows (`system_prompt`, `tools`, `project_context`, `skills`, `messages`, `mcp`, `fixed` for OMP's non-message part, `autocompact_buffer`, `free`); an unknown id from a newer harness renders under its label. `exactness` and `cost_kind` drive the wording in the panel (`≈`, "estimate", "as of <time>"); a block whose source is stale shows its age.

**Merge rule** (the Orca precedence, per block): for each block the daemon keeps the newest report of the *best* source: `chat` (it sees the harness's own protocol) > `extension` > `statusline` > `hooks` > `transcript` > `osc7501`; a lower source only fills a block a higher one never reported. The `sources` list is how the mock's "Sources: OSC 7501 · extension · transcript" row is drawn.

**Wire (protocol 0.58, capability `agent.insight`; the number follows the study plan, the real one is the next free at merge):**

- `agent.insight {session_id, node_id?}` → `{insight: AgentInsight}`; `not_found` for an unknown session; a session nothing has reported on returns `sources: []` with no blocks.
- Event `agent.insight_updated {session_id, insight}` (whole snapshot, `seq` increasing): sent **only to connections whose `client.focus` is that session** (the request that exists today), coalesced to one per second per session, replacing a queued one for a slow client. No new watch request.
- Reporter input for terminals: `agent.report` gains an optional `insight` object (`context`, `turn`, `tools_delta`, `files_delta`; ≤ 4 KiB; the existing `seq` rule per `(session, source, node)`), and the CLI `hutan agent report --insight-json -` reads it from stdin. One channel for the extension and for the hooks; phases B and C add no protocol.
- Additive `Usage`/`TokenCounts` field `cache_write` (core + golden fixtures) with the same bump.
- CLI `hutan insight [<session>] [--json] [--watch]`; MCP `agent_insight {session_id}` (read-only, `Observe` class of `[control]`).

**Budgets** (all enforced by tests, as `docs/vision.md` budgets are):

| What | Budget |
|---|---|
| State per session | ≤ 48 KiB (turn ring 200 × ≤ 96 B, files ≤ 100 paths of ≤ 260 B, tools ≤ 17 rows); at most 64 sessions tracked, least recently focused evicted |
| Snapshot on the wire | ≤ 32 KiB; larger is cut at the caps above and says `truncated` |
| Update rate | ≤ 1 `agent.insight_updated` per session per second, to focused connections only; idle: no timers, no polling (one-shot coalescing timer) |
| Per chat event | O(1) amortised in the pump, no allocation for events that carry no insight |
| Cold build from the journal (restart, first focus) | newest ≤ 5 000 events in ≤ 50 ms [target, measure in slice A]; older turns come from `usage_turns` rows |
| Reporter | ≤ 1 `hutan agent report` per 500 ms per node (the extension already serialises spawns with a 1.5 s bound); payload ≤ 4 KiB |
| Transcript tail (phase C) | ≤ 256 KiB per read, byte-offset resume as the history index does, ≤ 1 read per second, only for a session some connection has focused (stops 30 s after it lost focus); never scans directories |

**Privacy.** Insight carries file paths and tool names, no text of messages, prompts, tool output or diffs; paths are relative to the session's cwd when inside it. Paths are fine over the local protocol (as `checkpoint.diff` and `changes.*` already do) but never go into notification or hook payloads. Reading a third-party transcript (phase C) is allowed only for a source the user enabled in `[history]` (same opt-in as the index, `docs/history-index.md`); no harness credential or token is read (ADR 0015). Cost is only what a harness reported or derived from its own price table, always labelled; Hutan keeps no price table and shows `—` where nothing was reported (Codex).

## 7. Risks

| Risk | Mitigation |
|---|---|
| OMP and Claude Code change their extension/hook/transcript shapes (both ship weekly) | per-version fixtures, unknown fields ignored, unknown breakdown ids rendered by label, the block's source and age always shown |
| Per-call spawn of `hutan` from an extension on a long agent loop | one report per 500 ms at most, the existing serialised queue and 1.5 s bound; measure in slice B |
| Claude Code's status line is one command per user | opt-in, chained wrapper that execs the user's command and passes its output through; never installed silently (`docs/integrations.md` already refuses to replace a status line) |
| OTLP would give the richest Claude Code and Codex data | needs an OTLP/HTTP receiver in `hutand` and `OTEL_*` in the PTY environment, which Claude Code removes from child processes and ignores from repository settings; heavy for the gain over the transcript. Not proposed; revisit if C proves too coarse |
| A hidden `/context` to measure context from outside | changes the conversation; kept as the user's explicit button |
| Numbers that disagree between harnesses | `exactness`, `cost_kind`, per-block source and the unit in every label; the chat chip and the panel read the same reducer |
