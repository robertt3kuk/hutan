## 0. Summary

- Competitors' loudest UX failures cluster into **sixteen themes** (§2). Hutan already covers a surprising amount (§3): one attention list with a keyboard jump, decided-by on approvals, plain-terminal mode, a shared text field with readline keys, an explicit send key, close-with-undo, login-free local use.
- The biggest **missing** pieces, by evidence: (1) message queue / stop semantics while an agent runs, (2) checkpoints / rewind of agent edits, (3) find in terminal and chat, (4) approval cards that state their scope and default to the safe choice, (5) a "jump to latest" anchor, (6) a context meter, (7) live Changes (stale diffs) and a staged/unstaged split, (8) per-session notification mute and banner clearing, (9) clickable `path:line`, (10) session names you can tell apart (audit F1).
- **35 slices** are ranked in §5 by *impact × evidence ÷ effort*; cards are in §6. Ten are in **wave 1** (small, mostly `desktop`-only, no protocol change): `UX-PARITY-RULE`, `UX-REPAINT-DOC`, `UX-APPROVAL-CARD`, `UX-JUMP-LATEST`, `UX-CONTEXT-METER`, `UX-SESSION-NAMES`, `UX-HISTORY-CONSENT`, `UX-MAWAS-LAZY`, `UX-DRAFTS`, `UX-TERM-RESIZE` (phase A, a reproduction and golden test).
- Five decisions for the user are in §8.

### Conventions

- **Ids.** `UX-A`, `UX-B`, `UX-C` already exist as merged briefs from the October user-test rounds (`docs/briefs/UX-{A,B,C}.md`). New ids here carry a descriptive suffix; the audit's ids (`UX-SESSION-NAMES`, …) are reused where they match. `UX-PACK-PICKER` and `UX-SETTINGS-IA` are **not new slices**: they are already `TH-3` and `ST-5…ST-7` (§4).
- **Score** = Impact (1–5) × Evidence (1–5) ÷ Effort weight (S = 1, S–M = 1.5, M = 2, M–L = 3, L = 4). Impact is how often a user hits it and how bad it is; Evidence is reaction/comment counts across products plus anything the audit observed live. All three numbers are **[INFERENCE]** judgements; the effort weights only order the list, they are not estimates. Large, high-evidence slices (queue, checkpoints) sit lower than their evidence deserves on purpose; §7 schedules them anyway.
- **Acceptance checks** are either **T** (a test: unit, or GPUI scenario under `crates/desktop/tests/*_gpui.rs` against the real daemon with a temporary `HUTAN_HOME`) or **S** (a Cua Driver screenshot). Cua rules from the audit (`ux-audit.md` §4 and §6): keep the Hutan window frontmost (`bring_to_front`), use foreground-mode clicks, wait ≥ 0.7 s after a state change, hover does not work, GPUI exposes no accessibility tree today so assertions are pixel crops (`developer-tools.md` §3.8), and `hutan ui layout|run` is the state oracle. Never touch the user's real `Hutan.app` or home (`docs/process.md:105`, `docs/status.md:14`).
- **Status words** for "Hutan today": **covered** (does what the competitor lesson asks), **partial**, **missing**, **unknown**.

## 7. Waves, parallelism and the 16 GB laptop

Rules that bound the schedule (`docs/process.md:101-104`, `docs/status.md:13`): builds use 4 jobs and tests 4 threads; **one heavy job at a time** (a cargo build, clippy or nextest run); `just check` takes a machine-wide lock, so implementers may code and run targeted `cargo nextest run -p <crate>` side by side while full gates queue; research, review and UI-check agents are light; remove each worktree after merging; check `df -h ~` and `just sweep` before dispatching. In this plan, "parallel" therefore means **disjoint file sets in separate branches, with at most two coding agents active** and gates serialized by the lock. A protocol-touching slice goes through the contract owner one at a time (`AGENTS.md:51`).

## 8. Decisions for the user (five)

1. **D1 — Queue and steer semantics (`UX-QUEUE-STEER`).** While an agent works, should the chat's send key **queue** the message (visible, editable chips; a separate chord interrupts and sends; Stop clears the queue unless told otherwise), or **steer** the running turn? *Recommended:* queue by default, steer only where an adapter advertises it; this keeps `SK-1`'s single send-key rule. Evidence: Claude Code [#50246](https://github.com/anthropics/claude-code/issues/50246) (R254), OpenCode [#4821](https://github.com/anomalyco/opencode/issues/4821) (R126), [#32157](https://github.com/anomalyco/opencode/issues/32157) (R84).
2. **D2 — How far does the Changes view go as a git client (`UX-CHANGES-INDEX`)?** (a) read-only staged/unstaged markers now, no stage/unstage actions (recommended; consistent with the editor spike's non-goal "git UI beyond the gutter and existing Changes view", `editor.md` §3.2); (b) add stage, unstage and commit-selected. Evidence for (b): Zed [#26560](https://github.com/zed-industries/zed/issues/26560) (R897), Warp [#8542](https://github.com/warpdotdev/warp/issues/8542) (R44).
3. **D3 — Checkpoints (`UX-CHECKPOINT`).** Approve an ADR for per-turn snapshots of the checkout in hidden git refs, with a previewed, undoable restore and "files only" when the harness cannot rewind the conversation? *Recommended:* yes, as a spike plus ADR first. It costs disk (bounded by a retention rule) and only works in git checkouts. Evidence: Codex [#9203](https://github.com/openai/codex/issues/9203) (+538), [#11626](https://github.com/openai/codex/issues/11626) (+229).
4. **D4 — Permission modes of harness chats (`UX-MODE-CHIP`).** Ordinary chats launch the harness bare, so the user's own bypass or yolo config applies unseen. (a) **Show, never change** — a chip with the real mode (recommended; the cost of silent changes is documented in cmux [#3547](https://github.com/manaflow-ai/cmux/issues/3547)); (b) default every Hutan chat to ask-before-acting like Mawas "Ask" with a per-chat override, which risks the "fully manual or no guardrails" cliff (Orca [#13081](https://github.com/stablyai/orca/issues/13081)).
5. **D5 — Multiple windows (`UX-MULTI-WINDOW`).** Hutan is one window per data folder by design (`docs/design.md:514`). Spend an L-sized spike now, or **defer until after the editor lands** (recommended; the editor raises the need, and the model change touches notifications, focus reporting and the single-instance lock)? Evidence: Zed [#6722](https://github.com/zed-industries/zed/issues/6722) (R327), [#53528](https://github.com/zed-industries/zed/issues/53528) (R54), Orca [#6074](https://github.com/stablyai/orca/issues/6074) (R38).

Open decisions elsewhere that interact with this plan and are not repeated: editor decision 5 (a unified ⌘P palette) changes the jump rows in `UX-SESSION-NAMES`; the direction decisions D-1…D-6 (`docs/roadmap.md:186`) include remote `hutand`, which inherits the lessons in § "Deferred".
