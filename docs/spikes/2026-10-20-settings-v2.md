# Settings v2 — inventory, comparison and proposed structure

## Recommendation

Make Settings a coherent **management surface organized by user intent**, not one page per Rust namespace. Preserve the working TOML/protocol ownership boundaries and the controls already delivered; do not restart ST-1/ST-2/ST-3 as though they were still missing. Prioritize accurate Mawas configuration provenance, then navigation/search and keyboard editing, before portability and convenience features.

**Evidence boundary.** Fresh source inventory of the main checkout at `aee7f9e87b707c6430615c30e216caa4d7a44175` (`docs(briefs): SK-1 send key`). Current protocol is 0.32 (`crates/protocol/src/lib.rs:74-78`). This document is source research and a proposal, not a runtime or visual acceptance report. No builds, tests, application launches, model calls, credential access or user-config modifications were performed. Peer evidence is official documentation or official upstream source; documentation is a moving snapshot, not proof of the installed peer version. Proposed behavior below is explicitly future work; `[INFERENCE]` marks conclusions not exercised in a running application.

### Ownership to retain

- Desktop preferences live in `settings.toml`; keyboard overrides live in `keymap.toml`. Their usual directory is `~/Library/Application Support/Hutan`, relocated by `HUTAN_HOME` (`crates/settings/src/store.rs:24-65`). Defaults < user < workspace < project < runtime; tables merge deeply, arrays/scalars replace; invalid namespace values keep the last good value and produce diagnostics (`crates/settings/src/lib.rs:1-9`).
- The daemon owns `daemon.toml`. `daemon.settings.get/set` supplies typed entries, defaults, file presence and apply/restart metadata, validates edits and preserves comments; setting `null` removes a key (`crates/protocol/src/daemon_settings.rs:1-40,71-95`; `crates/daemon/src/daemon_settings.rs:994-1015,1183-1240`). It is not a second desktop settings namespace.
- Provider metadata, Mawas choices, grants and memory are records, not TOML preferences; account tokens and integrations have different external owners. The inventory below distinguishes them. Daemon settings mutation, assistant reset, grant management and memory writes are user-only at the request classifier (`crates/daemon/src/router.rs:689-706`). Preserve that boundary regardless of page placement.
- The existing catalog contains 19 registered preference namespaces and 25 visible pages, including synthetic management pages; `sidebar` shares the Projects Sidebar page (`crates/desktop/src/settings.rs:1165-1187`; `crates/desktop/src/workbench/settings_schema.rs:336-367`). The present surface is an 860 × 600 sheet with a 220-pixel navigation column (`crates/desktop/src/workbench/settings_sheet.rs:991-1055`). Reducing page fragmentation is a recommendation, not evidence that this layout has been visually tested.

### Separate `keymap.toml` inventory

- Repeated `[[binding]]` tables have exactly `keys`, `action`, optional `context`. Keys can be whitespace-separated sequences; `action = "none"` unbinds defaults (`crates/settings/src/keymap.rs:1-20,170-188,303-375`).
- Built-ins precede user entries; overrides match keys/context, with global unbind able to remove matching defaults across contexts. Parsing records diagnostics for invalid bindings and unknown fields (`crates/settings/src/keymap.rs:211-218,245-272,284-318`). This is one user file, not a workspace/project file in `SettingsPaths` (`crates/settings/src/store.rs:24-40`).
- Current Keyboard page lists only user-file bindings, with search, Open file and Reload; it does not render a full built-in/effective binding editor (`crates/desktop/src/workbench/settings_pages.rs:845-953`). V2 should make all actions discoverable and support record/change/unbind/reset without making users author TOML.

## 5. Remaining correctness and discoverability issues

1. **Persisted Mawas provenance needs a daemon read API.** The UI's `chosen` cache describes this window's writes; refresh reads existing assistant sessions. `assistant_selected` can only infer some backend mismatches and does not recover an exact stored model/provider choice (`crates/desktop/src/workbench/settings_assistant.rs:1-13,230-281,634-655`). [INFERENCE] After relaunch, a stored override matching the inherited backend, or a scope with no conversation yet, cannot reliably be represented as an explicit override by this path. Add a read-only resolved-config DTO; do not create a conversation just to discover settings.
2. **Permission name/ID precedence needs an honest resolved value.** The daemon applies ID and then name (`crates/daemon/src/config.rs:431-445`); the UI searches ID first and takes the first explicit match (`crates/desktop/src/workbench/settings_assistant.rs:497-518`). [INFERENCE] When both exist with different values, that UI value can differ from enforcement. Report both sources and the winning name override; edit/reset the winning source or explicitly normalize to a single ID record with user confirmation. Do not silently change enforcement precedence in an IA-only slice.
3. **Scope editing still has an implicit mode.** Default writes follow effective source; selecting a page resets its chosen edit layer (`crates/desktop/src/workbench/settings_layers.rs:83-118`; `crates/desktop/src/workbench/settings_sheet.rs:253-270`). Recommendation: sticky explicit edit scope, with an effective-value preview, instead of source-dependent destinations.
4. **Search is page-oriented.** It filters catalog pages; custom terms are keyword strings and dynamic binding text, not independently addressable results (`crates/desktop/src/workbench/settings_schema.rs:393-425`; `crates/desktop/src/workbench/settings_pages.rs:159-170`). A query can find Models without landing at Set key. Recently changed, semantic filters and result anchors are proposals, not existing features in this renderer (`crates/desktop/src/workbench/settings_sheet.rs:276-320,932-989`).
5. **Privacy actions must name what remains.** Index disable retains data, memory archive retains revisions and snapshots, provider removal can delete a credential before a later DB failure (`crates/desktop/src/workbench/settings_labels.rs:1127-1128`; `crates/storage/migrations/0013_memory.sql:33-55,75-84`; `crates/daemon/src/providers.rs:374-400`). “Reset”, “Revoke”, “Archive”, “Clear” and “Erase” cannot be interchangeable labels.

### File-only policy

**Most previously file-only ordinary settings already have controls.** Do not list notification policy, history disable, daemon permission toggles, env maps, executable paths or MCP as proposed first-time exposure; §§1–3 show the cutover.

- **Gain UI:** full keybinding overrides; structured saved-layout dock/panel/status content; exact Mawas stored/effective config and permission provenance; history source/role choices; portable settings import/export. The first two close current file-only editing gaps (`crates/desktop/src/workbench/settings_pages.rs:845-953`; `crates/desktop/src/settings.rs:217-291`).
- **Remain file-capable, not exclusively file-only:** raw layout maps and advanced keymap context strings. Offer a known-ID UI plus Open file for expressions/values not safely representable by that editor; preserve unknown text, do not silently erase it. Current keymap accepts nonempty context strings (`crates/settings/src/keymap.rs:364-375`).
- **Remain launch/environment-only:** storage root and socket relocation. These are not preference keys and need process coordination/data migration, not a “save and move” control. `HUTAN_HOME` settings resolution is explicit in `crates/settings/src/store.rs:43-65`; daemon path/socket resolution is in `crates/daemon/src/paths.rs:11-106`.
- **Remain user actions, not raw flags:** setup completion, destructive maintenance, harness login, install/uninstall and permission grants. Surface their existing operations with confirmations/receipts; do not publish generic editors for implementation records (§§2–4).
- **Never a file-only secrets fallback:** no API keys in TOML/env editors. Their present boundary is Keychain; environment fields should continue warning about plaintext (`crates/gateway/src/credentials.rs:1-20`; `crates/desktop/src/workbench/settings_labels.rs:1119-1126`).

### Scope, provenance and reset contract

1. **Edit target is explicit and sticky:** User / Workspace ‹name› / Project ‹name› with exact path and owning host. Only offer real available scopes; a standalone project has no fictional parent workspace. “This Mac / daemon-owned” accompanies app-wide controls. Existing per-page layer eligibility is the starting constraint, not a promise all keys can inherit (`crates/desktop/src/workbench/settings_layers.rs:38-81,94-118`).
2. **Show three distinct facts per row:** selected-scope explicit value (or Inherit), effective value + winning source, and apply status. Example: “User: 13 pt · Effective: 15 pt · Modified in Project api”. If editing User under a project override, preview “Saved for other projects; this project still uses 15”. Never silently switch write destination to make the edit appear effective.
3. **Reset means remove selected override.** Label “Reset to inherit”; preview fallback value and source, disable when that scope has no explicit key. Page reset lists exact scope/key removals and excludes credentials, grants, records and lifecycle operations. Current delete semantics and exclusions are already available (`crates/desktop/src/workbench/settings_sheet.rs:427-445`; `crates/desktop/src/workbench/settings_layers.rs:153-225`).
4. **Do not conflate three scope systems.** Desktop layers are file inheritance; Mawas backend selection is daemon `app_meta` scope records; grants/memory are their own scoped ledgers. Present a consistent scope vocabulary, but route writes through the proper owner. Mawas backend chain and permission name/ID chain are not identical today (`crates/daemon/src/assistant.rs:457-494`; `crates/daemon/src/config.rs:431-445`). A resolved-config API must say which chain applies.
5. **Security policy stays user-controlled.** Do not let a repository `.hutan/settings.toml` widen daemon permissions, grants or automatic execution. Retain user-only policy writes (`crates/daemon/src/router.rs:689-706`). Initially retain current desktop override eligibility; broaden per-key eligibility only as an explicit contract decision, not by globally flipping the namespace trait.
6. **Separate defaults from running conversations.** Display “New conversations will use …; existing conversation uses …”. Inherit/reset must not imply model/session migration; the existing daemon reset explicitly leaves sessions untouched (`crates/daemon/src/assistant.rs:542-544`).

### Apply/restart and validation contract

- Preserve daemon-supplied `applies`, `set_in_file`, `pending_restart` and the persistent pending banner. The current restart flow counts live sessions and confirms before stopping/restarting; it consults restore policy (`crates/protocol/src/daemon_settings.rs:25-40,71-78`; `crates/desktop/src/workbench/settings_sheet.rs:943-948,1084`; `crates/desktop/src/workbench/daemon.rs:363-389`). **Never auto-restart as a side effect of editing.**
- UI metadata should distinguish **Now**, **New terminal**, **New conversation**, **Daemon restart**, with precise exceptions rather than treating all `Live` daemon settings as existing-session migration. Desktop shell/env spec construction and assistant reset demonstrate the distinction (`crates/desktop/src/settings.rs:147-163`; `crates/daemon/src/assistant.rs:542-544`). A future richer wire field can be additive; do not reinterpret today's `Applies::Live` silently.
- Use finite choices for theme, preset, row/tab IDs, history sources/roles, notification kinds, backend/provider and discovered models. Keep explicit custom model ID for OpenAI-compatible endpoints and custom shell/program paths; validation must not require a paid call or account login. Current ranges/choices already cover several domains (`crates/desktop/src/workbench/settings_schema.rs:205-249`; `crates/daemon/src/daemon_settings.rs:43-53,253-436`).
- Invalid input remains visible, unsaved, with the server error beside the row; distinguish “saved on disk, apply failed” from total failure. The daemon already reports that history-specific partial success precisely (`crates/daemon/src/daemon_settings.rs:1267-1276`). Do not replace authoritative validation with optimistic success.
- Search, modified indicators and recency must not render plaintext environment values or secrets. A key-level modified badge is based on explicit presence, even if the value equals the default. Multi-variable maps should show per-variable provenance rather than attributing a merged map to one scope (deep-merge semantics: `crates/settings/src/lib.rs:4-9`).

### Search that covers custom pages

Proposed one desktop metadata catalog, extending the existing schema/catalog rather than creating a remote search service:

- Each setting/action/link has stable ID, page/section/anchor, title/help/aliases, owner, scope eligibility, apply metadata, explicit-presence status and an activation target. Custom providers/accounts/MCP/grants/memory entry points register searchable items like generated fields; account names, provider names and server names may be included locally, but never tokens, env values or memory contents.
- Return rows such as **Models & providers › Provider › Set API key** or **Mawas › Memory › Manage memory**, not only matching page names. Query “login”, “endpoint”, “send key”, “return”, “don't ask”, “workspace permission”, “memory off”, “MCP server” and exact dotted IDs must work. Navigate, scroll and focus the target, including custom controls.
- Preserve literal-key search and existing custom-page keywords (`crates/desktop/src/workbench/settings_labels.rs:1034-1089`); add multi-token matching and filters from the pattern table. Do not add model-powered settings search.
- Reuse the same targets for command-palette settings actions. Keyboard tab/arrow navigation currently exists for generated/daemon rows; custom actions need equal participation rather than only mouse affordances (`crates/desktop/src/workbench/settings_keys.rs:1-8,72-115`).

## 9. Decisions for the user — at most five

1. **Where should Settings live?** Recommendation: retain one Settings entry point and the existing sheet for ST-5, with the thirteen-page structure; consider a resizable separate window only after a real-window review shows the sheet is constraining. Do not simultaneously redesign windowing and data ownership.
2. **Should editing an inherited value automatically edit its source?** Recommendation: **no** in v2. Use a sticky explicit User/Workspace/Project target, show the effective winner separately, and Reset only that target. Keep current namespace eligibility initially; do not make security/account/preferences repository-overridable wholesale.
3. **Which page owns permissions?** Recommendation: Mawas owns its mode/grants/context/memory; Agents & harnesses owns general agent-control policy; History & privacy is the readable cross-domain index with links, not a third copy of mutable permission controls. Keep Ask before acting as the default and preserve daemon user-only enforcement.
4. **How should message sending be presented?** Recommendation: adopt SK-1's explicit ⌘Return/Return choice with default ⌘Return, quick switch beside the composer hint and consistent behavior for message inputs; non-message forms keep their own submission semantics. Treat SK-1 as the implementation owner and integrate its resulting key, not another send-key slice.
5. **Portability or full backup/sync first?** Recommendation: local, previewed, secret-free **preferences/keymap export/import first**. No cloud sync, automatic grants/consent restore, raw live-DB backup or blanket erase button in Settings v2; design a separate consistent data-backup/erasure contract if that becomes a user priority.
