## 2. Deep notes (8)

### 2.1 Omnigent (Databricks) — the "meta-harness"
- **Thesis** ([Databricks, 2026-06-13](https://www.databricks.com/blog/introducing-omnigent-meta-harness-combine-control-and-share-your-agents)): each harness "only understands its own sessions"; a layer above composes, governs and shares them. Roadmap line: "an Omnigent Server MCP so agents can work across your sessions" — i.e. the same idea as Mawas reading across agents, planned, not shipped as of that post.
- **Supervising many agents.** Sidebar with pinned/project-grouped sessions and parent→sub-agent hierarchy ([0.17.0, 2026-10-06](https://omnigent.ai/releases)); **Inbox** with *All / Unread / Awaiting response* tabs and cards expandable in place ([0.18.0, 2026-10-13](https://omnigent.ai/releases)).
- **Polly** (example agent): "writes no code herself… plans, delegates to coding sub-agents (Claude Code, Codex, or Pi) in parallel git worktrees, then routes each diff to a reviewer from a different vendor than the one that wrote it. You merge." ([README](https://github.com/omnigent-ai/omnigent)).
- **Security / governance.** Stateful policies ("after an agent downloads a package from npm, require approval to git push"), per-session and per-user period cost budgets ("ask before crossing thresholds, block expensive models at the limit", 0.17.0), OS sandbox with egress proxy that injects secrets so the agent never sees them, MCP registry+gateway applying the same policy wherever the agent runs (0.19.0), sandboxed agents use approved git repos over SSH "without ever holding the key" (0.19.0).
- **Review.** PR tab can merge, edit, label, request reviewers, comment (0.20.0, 2026-10-28); GitLab MR + Azure DevOps (0.18.0).
- **Cross-agent messaging.** Agents are composed in YAML, sub-agents/reviewers declared there; users can also "ask one agent to review another's work".
- **Memory.** Optional `hindsight` store extra; nothing like a user-visible memory notes page found [INFERENCE: I did not read the docs section on it].
- **Complaints/gaps in issues** ([open issues by reactions](https://github.com/omnigent-ai/omnigent/issues)): multi-repo workspaces (#2303, 11 reactions, opened 2026-07-09); native CLI harness as a named agent's brain "intentional or a gap?" (#1596); remote agents via A2A (#9256, 2026-10-06); the repo header shows 2,684 open issues+PRs on 11.2k stars (GitHub API count). Label is **alpha**.
- **Why it matters:** the only entrant with a *policy engine*, shared-session collaboration and a lead-agent example all in one open-source stack, backed by a big-data vendor. It is server-centric (Python server, hosts), where Hutan is local-daemon-centric.

### 2.2 Orchestrator.inc / Agent Orchestrator (AO)
- **Product** ([README](https://github.com/OrchestratorInc/agent-orchestrator), [docs](https://docs.orchestrator.inc/)): per-project **orchestrator agent** "plans the work, starts a worker for each piece in its own worktree, and comes back only when something needs you"; Kanban lanes *Working / Needs you / In review / Ready to merge*; **failed CI, review comments and merge conflicts go back to the worker that owns the branch**; a reviewer agent reads every PR; mobile apps (push on question/approval, reply, approve, start work, review) and Cloud workers.
- **State honesty — closest to Hutan's rule.** "Orchestrator does not persist a display-status label. It derives what you see from durable facts… A failed or unknown runtime probe alone is not proof that a session is dead." States: Active / Idle / Waiting for input / **Blocked ("an approval or permission decision is pending; automation will not inject input")** / Exited ([Dashboard docs](https://docs.orchestrator.inc/dashboard/)).
- **Messaging safety:** "Use Orchestrator's message controls for routine follow-ups so lifecycle reactions can apply the correct delivery policy"; a blocked session "cannot accept an ordinary prompt."
- **Notifications:** bell center for needs-input / ready-to-merge / merged / closed; per-device push mute was *removed* in v0.14.7 (2026-10-28).
- **Cadence:** release 2026-10-30 plus multiple nightlies a day ([releases](https://github.com/OrchestratorInc/agent-orchestrator/releases)); 14.0k★, 832 open issues.
- **User complaints (issues):** every daemon restart on Windows sweeps all sessions to `exited` and nothing revives them; worker reports to a dead orchestrator "retry **13,000+ times with no backoff**"; done-reports only arrive bundled into the next user turn, idle orchestrators never woken ([#6639, 2026-10-13](https://github.com/OrchestratorInc/agent-orchestrator/issues/6639)); an agy session stays "working" forever after Escape because the Stop hook never fires ([#5050, 2026-09-07](https://github.com/OrchestratorInc/agent-orchestrator/issues/5050)); stale claude session-id lock after OOM ([#4280](https://github.com/OrchestratorInc/agent-orchestrator/issues/4280)); reviewer harness read-only enforcement ([#3745](https://github.com/OrchestratorInc/agent-orchestrator/issues/3745)).
- **Why it matters:** the best-resourced direct competitor on the *workflow* axis (task→PR→CI→merge loop, mobile, cloud). Its orchestrator is per-project and spawn-oriented. Whether it has any cross-project observer is **not stated** in what I read.

### 2.3 Paseo
- **Product** ([README](https://github.com/getpaseo/paseo), [orchestration docs](https://paseo.sh/docs/orchestration.md)): self-hosted daemon; desktop, iOS, Android, web, CLI, Docker; agents create worktrees, launch other agents and "send prompts to other agents by ID"; schedules; **heartbeats** ("prompt the same agent periodically to continue its task"); agent profiles with "When to use" notes so an orchestrating agent picks by specialty; plugins run on the daemon and show in every client; TypeScript SDK.
- **Security default:** Paseo MCP tools injection is **off by default** (Settings → host → Agents → "Enable Paseo tools"); E2E-encrypted relay optional; "Plugins run with access to your daemon machine… install only code you trust."
- **Needs-you UX:** worker shows in a "Subagents track" near the composer; "your main agent receives a notification when the worker finishes."
- **Traction:** 22.8k★ (created 2025-10-13 so a 2025 product, newly dominant); an HN user (2026-10-03): "I get to connect to my LLM agents even on other machines, remotely via Tailscale and the mobile app UX is quite good." Another: "I found Paseo to be very pleasant, except sometimes I had sub-agents kinda hang" ([HN](https://news.ycombinator.com/item?id=49942434)).
- **Complaints (issues):** iOS app backgrounded → commands queued "until I reopen" ([#3464, 2026-08-16](https://github.com/getpaseo/paseo/issues/3464)); Paseo MCP tools never reach Codex's tool surface ([#3009, 27 comments, 2026-08-08](https://github.com/getpaseo/paseo/issues/3009)).
- **Why it matters:** sets the bar for "agents can orchestrate agents" through an opt-in tool surface plus a mobile app people actually praise.

### 2.4 Harness by Autonomous (openharness) — best written rules for agents-that-start-agents
Source: [llms.txt](https://harness.autonomous.ai/llms.txt) and [repo](https://github.com/autonomous-ai/openharness) (MIT; 1.4k★; Product Hunt 506 followers).
- Agents run `harness new/ps/wait/show/send/close` (CLI) or `harness mcp`; a human sees every harness in desktop/web/phone apps and can "watch it, answer it or stop it".
- **Needs-you is an exit code:** `harness wait` exits 0 idle, **3 "needs the person"**, 4 stopped, 124 timeout; "never answer a harness's question or permission prompt"; "never ask one to publish, deploy, delete or push".
- **Consent is human-only:** "Agents can start other agents" is off by default; run by an agent, `harness settings … on` is **refused (exit 5)**.
- **Bounds:** at most **4 live harnesses** per agent; a harness an agent started may not start harnesses; idle ones the agent started are closed after 30 minutes unless the human typed into them; "starting one does not let you message it, so put everything in the task."
- **Agent Messages** (teammates in the same tab) are experimental and off by default.
- **Why it matters:** this is a ready-made spec for Mawas's `chat_create` / board semantics; most of it matches Hutan's 0.3.5 rules (target-bound grants, never answers for you).

### 2.5 Pane (RunPane) — Sessions
Source: [Sessions docs](https://runpane.com/docs/sessions), [orchestration guide](https://runpane.com/agent-orchestration).
- "A Session is a chat with one agent whose job is to run your other agents… **1 feature = 1 worktree = 1 branch = 1 Pane**; reviews, audits, fixes and QA for it are tabs in that Pane."
- **A watcher:** the Session hears when a pane finishes, gets stuck, needs input or its PR changes; PRs polled "about every 3 minutes" via `gh`.
- Workers return `runpane report --state <ready|blocked|failed|done>` + PR + summary; `sessions overview` shows each pane's live state, branch, PR and latest report.
- **Named locks** so only one worker uses a shared resource (e.g. a test account); released on finish/close/timeout.
- Several Sessions can sit side by side; each has Overview / Files / Changes tabs; **Loops** schedule agents (cron) and a runpane CLI+MCP lets any agent drive the app.
- Their own guide's caveat: "More agents means more diffs to review… orchestration moves [review] rather than removing it" ([guide](https://runpane.com/agent-orchestration)).
- **Why it matters:** workspace-scoped "chat that supervises panes" — structurally the same as a workspace-scoped Mawas; no global cross-workspace view described.

### 2.6 Traycer — agent-to-agent and the "Agent office"
Source: [Agent-to-Agent docs](https://docs.traycer.ai/concepts/agent-to-agent).
- Agents can create child agents (same Task, another Task, or another host), send instructions (reply requested or fire-and-forget), list agents, **read another agent's transcript**, rename/stop/archive/fork agents, claim roles.
- **Capability matrix:** *reference*, *read transcript* and *receive message* are three separate capabilities; only Claude Code on Terminal has an inbox; Codex/OpenCode terminal agents "can send but can't receive" → "another agent can't create a Codex or OpenCode Terminal agent, because the new agent could never receive its brief" (honest limits, similar to Hutan's *exact* vs *state only*).
- **Delivery honesty:** cross-host messages show *queued*, expire after 24 h as **Not delivered**; messages to another user's agents are rejected; max 16 MB.
- **Agent office view** draws agents as people at desks (typing = working, "…" waiting for a reply, "!" needs you, cracked screen = failed turn, envelope pile = unanswered requests) with a timeline replay; **Graph** view as an alternative.
- **Why it matters:** the most developed UI for "who is talking to whom, and what is stuck"; a visual-demo candidate that Hutan has no counterpart to (Hutan has the board, not the message graph).

### 2.7 Offrun — the "human-in-the-loop" meta-harness
Sources: [site](https://offrun.dev/), [Show HN 2026-10-03](https://news.ycombinator.com/item?id=49942434) (78 points, 68 comments).
- Free, macOS, "Free. All of it." Runs Claude Code, Codex, AGY, Grok Build, Muse Code on **your own accounts**, no server in the path.
- **Multi-account failover:** each agent can have several logins; "when one hits its usage limit, the chat moves to the next and says so"; out of logins → offers another agent that "gets the whole conversation".
- **Peer review:** pick a reviewer from your own agent accounts; findings wait until you press *Ask agent to fix*; "Nothing merges on its own."
- **Project memory** as plain files in `.offrun/` (conventions, plan, dead-ends), git-excluded, read at session start and written back.
- Founder answer to "why not Paseo/Orca?": "other meta harnesses focus on agent-in-the-loop, and we focus on… human-in-the-loop"; cloud + mobile promised "in the next 2 months".
- **Thread signals worth keeping** (2026-10-03): *alasano* — "I have an orchestrator agent who is the one I talk to 90% of the time and who is responsible for summarizing information from various project manager agents and only update tiles in the dashboard when I actually need to do something… Over time… the orchestrator sends fewer and fewer requests to me" (essentially Mawas as a user-built tool); *phildenhoff* — tools show agent work "as a transcript of a conversation… The conversation is hidden: your focus is on 'what's next'"; *hn3ufz62f7* — wants "per account rate limit headroom before I dispatch"; *mbil* — projects/directories/machines should not be coupled; *kriomant* — "each of them thinks Git is the only VCS"; *ithkuil* — fear of "a tool that could crash and lose all my sessions".

### 2.8 The attention/safety layer: Perch, Cyclops, Vigil (small, sharp)
- **[Perch](https://github.com/asafofer/perch)** (MIT, 27★): notch card "what was I doing, and what is waiting for me?"; Allow/Deny with **A/D**, answer a question with **1–4**, "Not now (30 min, 2 h, tomorrow)"; jumps to the exact terminal tab / cmux split / herdr pane / tmux pane; honest limit: **without hooks "Perch reads the transcripts, which can only guess when an agent is waiting for you."** Also "never takes the keyboard unless you ask… stays quiet about the session you are already in."
- **[Cyclops](https://github.com/cyclops-team/cyclops)** (v1.1.0): durable fsync'd mailbox between agents; sender identity comes from the socket ("Nothing in a request can name a sender"); doorbell does not type over a human draft ("positively visible human draft holds… never on a clock"); modal/permission-prompt/quota-screen holds; every outcome recorded, uncertain ones as `submitted_unverified`, never retried on a timer; **Accepted / Notified / Claimed / Completed** are different facts and "Cyclops does not infer task completion from idle state." Only 5 of 52 agent manifests are measured against a live CLI.
- **[Vigil](https://github.com/butterlatte-zhang/vigil)** (GPL-3.0): manager→sub-manager→worker tree; "**Zero input takeover.** … Vigil observes and navigates; it never answers a single keystroke on your behalf"; MCP tools scoped by identity (root: spawn/send/kill; sub-manager: +report; worker: report only); cross-subtree traffic goes through the lowest common ancestor so the graph can't cycle; "Honesty as a hard rule — an undeliverable message errors instead of pretending it was sent."
- **Evidence that the problems are real:** OpenRig `rig send` printed `Sent`/`Verified: yes` while the text sat as an unsent draft in the pane ([issue #14, 2026-06-28](https://github.com/mvschwarz/openrig/issues/14), 12 comments) — the same class as the Orca issues Hutan already turned into rules.

## 4. Patterns across the field (what is new since August)

1. **"Lead agent" is now the default pitch.** Polly (Omnigent), per-project orchestrator (AO), Sessions (Pane), operator/lead (OpenRig), manager tree (Vigil), Paseo MCP, Traycer child agents, Harness CLI. Mostly **per-project** and **spawn-oriented** (decompose → workers → PR). I did not find one whose headline is a *global, read-first supervisor over agents of several vendors across all workspaces that labels how complete each fact is* — [INFERENCE: based on READMEs/docs read; I could not test the products].
2. **Needs-you as a first-class state** everywhere: AO lane, Paradev board column, Omnigent *Awaiting response* tab, Harness exit code 3, Perch notch, tuios Inbox, Calyx/octomux approval inboxes, Air "what requires your attention", BAND "blockers, questions".
3. **Status honesty is a known weak spot:** AO #5050 (stuck "working"), Perch "can only guess", Cyclops `submitted_unverified`, OpenRig #14 (`ok:true` but draft unsent), Traycer "Agent status may be stale". The projects that say so explicitly (AO docs, Cyclops, Perch, Traycer) are respected.
4. **Rules for agent-started agents converge:** human consent off by default (Harness, Paseo), caps (Harness: 4), idle cleanup, never answer a child's prompt (Harness, Vigil), messages carry unforgeable sender identity (Cyclops, Parley "peer" marking), delivery state separate from completion (Cyclops, Traycer).
5. **Review is the bottleneck** and everyone adds a second-agent review: Polly (different vendor), Offrun (reviewer on your own accounts, "Nothing merges on its own"), AO (reviewer agent + route findings back), agent-manager (line comments back to agent). Delegator's HN thread: "I'm bottlenecked on the review. I think everyone has this problem now" (2026-10-06).
6. **Mobile is table stakes** for most high-star entrants (T3, Happy, Paseo, AO, Omnigent, Harness; Kepler and Air "coming"). Known failure: iOS background relay (Paseo #3464).
7. **Limits and spend are product features:** Offrun account failover, Omnigent period budgets and "ask every $X", Air per-session cost, Paradev "continue with another agent".
8. **Cloud with a local surface:** AO Cloud, Air Teams, Omnigent sandboxes, Kandev cloud executors — funded by infrastructure rounds (Daytona $1B, Replicas $4M).
9. **Funding is flowing to the category:** Paradev $11.5M (2026-10-26), BAND $17M, Herdr reportedly $6M, plus big-company entries (JetBrains, Spotify, GitKraken, Databricks).
