# Product review — who Hutan is for, the core loop, one simpler model

Date: 2026-10-21 · Author: `ProductReview` · Status: **proposal** (research only; the only file written is this one; nothing was built, launched or run) · Repo state: `master` at `7be0bf0`.

Goal from the user: Hutan should be **clean, easy and intuitive**, and the product side (not only pixels) should be reviewed. This document reviews the *product*: who it is for, the path from first launch to first value, the information architecture, defaults, and ten ranked product bets. Pixel and interaction defects are already covered by `docs/spikes/2026-10-21-ux-audit.md` and `…-ux-plan.md`; I refer to them and do not repeat them.

Labels: **[FACT]** = read in the repo, a doc, or an official page on 2026-10-21 (path or link given). **[INFERENCE]** = my reading, not verified. Click counts in §2 are derived from reading code and docs, **not timed in a window**. Competitor pages are landing pages and change; Superset's own page says it "is getting a new name soon" ([superset.sh](https://superset.sh/)).

Design lens (what the skills ask for, used as the yardstick below): Operate-mode surfaces are judged by task completion, scanability and native expectations (`~/proj/research/pbakaus_impeccable/.omp/skills/impeccable/SKILL.md:38`); onboarding's only job is to reach the moment that proves the product is worth the time, teaching "the 20% that delivers 80%" and moving the rest to the point of use (`…/reference/onboard.md:3,42-52`); simplification means one primary action, smart defaults, progressive disclosure, and documenting what was removed (`…/reference/distill.md:26-37,104-109`); one noun and one verb per concept, with a glossary when inconsistency spans the product (`…/reference/clarify.md:35,78`); name things by what users understand, not by how the system is built (`~/proj/research/anthropics_skills/skills/frontend-design/SKILL.md:65`).

## 0. Summary

- **Positioning:** Hutan is the native Mac control room for the coding agents you already use — real terminals or structured chats, one list of who needs you, review and merge of what they changed — local, account-free, with a daemon that keeps agents alive when the UI restarts (§1.3).
- **The core loop is not closed in the default path.** An agent started with the sheet's default placement (*Main checkout*, `crates/desktop/src/workbench/launcher.rs:899`) can be reviewed but cannot be committed or merged in Hutan: *Merge into …* needs a worktree (`crates/desktop/src/workbench/changes.rs:350-355`) and the daemon refuses `worktree.commit` for the main checkout (`docs/orchestration.md:146`). Competitors close the loop with a PR (Conductor, Claude Code desktop; §1.1, §2).
- **First value takes ≈ 10 actions to a running agent and ≈ 13 to a visible diff** after a skipped wizard, and the wizard itself is 7 steps (`crates/desktop/src/workbench/setup.rs:48-56`), most of them about things a new user has no opinion on yet (§2, §4).
- **Concept overload is the main IA problem:** one unit of work (a started agent) is drawn in ≥ 6 places, "what needs me" has 8 in-window renderings, "Changes" is two different lists plus a view, and 25 settings pages describe the same few concepts with different words (§3).
- **Three biggest simplifications (§3.4):** (1) *one list for "needs you"* — the Agents page — with Mawas Today, the Requests panel and the Tasks page folded into it or hidden; (2) *Session as the one noun* for terminal / agent / chat, with Task and Workspace hidden until used; (3) *a clean default layout*: Projects + Agents on the left, three rail icons on the right (Changes, Agents, History), everything else behind ⋯ and the palette.
- **Ten ranked bets (§5):** `PR-FIRST-RUN`, `PR-FINISH`, `PR-START-1`, `PR-ONE-QUEUE`, `PR-CLEAN-DEFAULT`, `PR-VOCAB`, `PR-SAFE-RUNS`, `PR-LEAN-SETTINGS`, `PR-SHIP`, `PR-MAWAS-SCOPE`. Four conflict with existing plans or ADRs (§5.3).
- **Five decisions for the user (§6):** delivery contract (commit from main / PR help), default placement, first-run depth, Mawas's place, and the word "workspace" versus direction D-1.

### 1.2 Primary personas and their top jobs

No Hutan user research exists beyond four rounds of agent-driven hands-on tests (`docs/spikes/2026-10-17-user-test*.md`, `…-18-user-test-3/4.md`), so these personas are **[INFERENCE]** from `docs/vision.md`, `docs/spikes/2026-10-18-direction.md` §0 (the user's own asks) and competitor issues/pages. Local-first (no account, no telemetry, keys in Keychain) is a constraint on all three, not a persona: Warp #900 (R506), Vibe Kanban #2952/#2812/#2724, Superset #2685 (`ux-plan.md` T12); Hutan today has none of the three problems (`ux-plan.md` T12 "covered"; `docs/vision.md:19`).

**P1 — The fleet operator.** Senior developer who already pays for Claude Code / Codex / Cursor and runs three or more agents at once across worktrees and repos on a Mac ("You already pay for Claude Code, Codex, or Cursor CLI and want one place to orchestrate them", [Orca docs](https://www.onorca.dev/docs)).
1. *When several agents run, show me which one needs me and why, so I can keep them all moving.* Evidence: wrong or stale state is the top complaint (cmux [#1027](https://github.com/manaflow-ai/cmux/issues/1027) R44; herdr discussion [#864](https://github.com/herdrdev/herdr/discussions/864) ▲41; Orca [#12577](https://github.com/stablyai/orca/issues/12577) R10); users praise notification rings (cmux.com testimonials).
2. *Let me approve safely without fatigue.* Evidence: Claude Code [#28240](https://github.com/anthropics/claude-code/issues/28240) R209, Codex [#3085](https://github.com/openai/codex/issues/3085) +125, Orca [#13081](https://github.com/stablyai/orca/issues/13081) R22 (users switch guardrails off) (`ux-plan.md` T2).
3. *Let me review what they changed and ship it.* Evidence: Zed staged/unstaged [#26560](https://github.com/zed-industries/zed/issues/26560) R897, Claude Code [#33932](https://github.com/anthropics/claude-code/issues/33932) R289, Orca "review AI-generated diffs seriously" (docs).
4. *Never lose work when I quit or the app dies.* Evidence: cmux [#480](https://github.com/manaflow-ai/cmux/issues/480) R50, Superset [#3496](https://github.com/superset-sh/superset/issues/3496) R10 (`ux-plan.md` T15).

**P2 — The terminal-native agent user.** Lives in Ghostty/iTerm/tmux, runs one or two TUI agents (Claude Code, Codex, OMP) and distrusts anything that wraps or breaks the TUI (`docs/vision.md:17`; cmux testimonials: "moved from Warp… like a rocket", [cmux.com](https://cmux.com/)).
1. *Keep my terminal exact and fast, and keep my viewport.* Evidence: Claude Code [#3648](https://github.com/anthropics/claude-code/issues/3648) R836 (viewport jumps), Ghostty find [#189](https://github.com/ghostty-org/ghostty/issues/189) +1221, links [#1972](https://github.com/ghostty-org/ghostty/issues/1972) +230.
2. *Tell me when the agent in this tab is blocked, without changing how I work.* Evidence: cmux's notification rings; herdr "agent not recognised" ([#803](https://github.com/herdrdev/herdr/issues/803), [#1170](https://github.com/herdrdev/herdr/issues/1170)).
3. *Let me find and resume yesterday's session, whichever tool it was.* Evidence: Zed [#37074](https://github.com/zed-industries/zed/issues/37074) R260; Codex [#25319](https://github.com/openai/codex/issues/25319) +165; Hutan's History (`docs/design.md:408-423`).

**P3 — The delegator-reviewer.** Tech lead or solo builder who splits a goal into scoped tasks, runs them in isolated branches, compares, reviews with line comments, merges and cleans up (Orca: "Fan one prompt across five agents… compare the results and merge the winner", README; Conductor's loop above). May overlap with P1 — [INFERENCE] keep as a separate persona only while Tasks with dependencies stays a product feature.
1. *Hand off a well-scoped job and come back to a reviewable result.* Hutan has tasks with dependencies, delivery states and policies (`docs/orchestration.md:93-132`).
2. *Send my review back to the agent and get a revised diff.* Hutan has line comments and *Request changes* (`docs/orchestration.md:161,166-174`).
3. *Merge, then clean up disk.* Vibe Kanban [#765](https://github.com/BloopAI/vibe-kanban/issues/765) R19 ("26 GB after two days"); Hutan offers cleanup after a merge only (`docs/orchestration.md:163`).

Not primary: the "personal assistant" user of Mawas (`docs/spikes/2026-10-18-direction.md` §0 items 12–14). Mawas serves P1/P3 later (delegation, MW-5) but is not why anyone installs Hutan today — see §3.4 and decision D-P4.

### 1.3 Positioning

> **Hutan is the native Mac control room for the coding agents you already use: run them in real terminals or structured chats, see in one list which one needs you, review and merge what they changed — local, account-free, with a daemon that keeps them alive when the UI restarts.**

Why this and not another sentence:
- It names the *job* (control the agents you already have), not the architecture. Conductor/Superset/Orca sell "parallel agents"; cmux sells "a better terminal"; Hutan's open ground is **terminal-faithful *and* a reviewable work loop, local, native** — the combination none of the eight does (table above).
- "When the UI restarts", not "when the window closes": the daemon survives a UI crash or restart and restores sessions (`docs/vision.md:28`), but the default for the last window is **quit** and ⌘Q asks whether to stop live sessions (`docs/design.md:552-589`; `crates/desktop/src/settings.rs:1093`). A claim of "runs with the window closed" would be false by default.
- Differentiators the evidence supports: one honest queue (cmux #1027, herdr #3871/#846 show competitors getting state wrong; Hutan reasons from real approval objects, `docs/design.md:93-99`); no account wall and no telemetry code (`ux-plan.md` T12); light and idle at 0 % CPU, 85–161 MB RSS, 0.37 s to a window (`ux-audit.md:44-45`) against Superset #2861/#4412 and Orca #6795 lag reports.
- What Hutan is *not* (say it in the README and the first screen): not a model, not a hosted service, not an editor-first IDE (`docs/vision.md:73-78`).

## 2. Core loop and first value

**The loop:** Start → Watch and unblock → Review → Deliver → (resume later). **First value moment** (my proposal): *the user reads, in Hutan, a diff an agent wrote.* Merge is the second moment. Everything before the first moment is cost.

### 2.2 Friction and dead ends, ranked by damage to the loop

1. **The default placement cannot be finished** (row 6′). Evidence above; a competitor that always isolates (Conductor) always has a delivery path, and the one that forced worktrees (Orca "+" #2654 R16) was criticised for it — Hutan's "never force a worktree" (`docs/vision.md:37`) is right, but then *Finish* must work in both placements.
2. **No PR step.** Conductor, Claude Code desktop (`gh`-based *Create PR*, PR status, *Auto-fix*, *Merge when ready*) and Orca all end in a PR; Hutan ends at a local merge and "never pushes" (`docs/orchestration.md:143,176-178`). [INFERENCE] For P1/P3 the last mile is a context switch to a terminal.
3. **The first screen does not ask for a repo.** The Welcome pane's one button is *Start…* (row 2); the loop's first object (a project) is hidden in the sidebar.
4. **Seven-step wizard**, with consents that have no context yet (history sources, login item, notifications, global shortcut), then silence (row 1). Opposite failure: skipping leaves the "needs you" queue incomplete for terminal agents (row 3b).
5. **Start sheet width.** Nine rows; *Where*, *Title*, *After*, *Queue as task* matter only to P3. Every start is also a task (`docs/design.md:525`), so the Tasks page [INFERENCE] fills with plain terminals and one-off agents that nobody planned.
6. **A session that `cd`s into a repo stays under Home and Changes says "This workspace has no git checkout"** (audit F6, `ux-audit.md:96-101`); `UX-PLACEMENT-CLARITY` (`ux-plan.md:671-677`) is not scheduled in `docs/roadmap.md:178-183`.
7. **Install dead end:** a harness missing and no `npm` (user-test-2 N8).
8. **Three meanings of "done"**: agent finished, task `done`, delivery `merged` surface in three places with three vocabularies (`docs/orchestration.md:97,124`; `docs/design.md:93-95`).

Already fixed on `master` since the audit (not re-verified in a window): distinguishable session names, history consent unticked, lazy Mawas start, jump-to-latest, safe approval cards, attention controls, Changes freshness, links/drop/paste (`docs/status.md:12-15`).

### 3.3 The root cause

Hutan was built daemon-up: each daemon service got a panel, a settings page and a CLI group (ADR 0010: "every UI feature is a registered panel", `AGENTS.md:34`). That gives a flexible workbench, but the **default arrangement shows the registry instead of the user's job**. The principle "nothing is fixed" is compatible with an opinionated default; it just has not been exercised.

### 3.4 Proposed model: three nouns, two places, one list

- **Nouns the user must learn:** **Project** (a folder or repo, made automatically), **Session** (anything running: a terminal, an agent in chat view, an agent in terminal view), **Changes** (what a session produced; one screen). Everything else is an attribute or appears when used: *worktree* (a property chosen in the Start sheet, shown as a badge), *task* (only if you Queue), *workspace* (only if you create one), *Mawas* (only if you turn it on).
- **Two places:** the **sidebar** (Projects, plus the Agents queue row) and the **panel** on the right (Changes, Agents, History). The centre is the one thing you are doing.
- **One list:** the **Agents page** is *the* queue: Needs you → Working → Review → Idle → Finished. The sidebar's *Needs you* group stays as a compact projection at the top of Projects; the Agents panel is the same list scoped to the focused session; nothing else renders "needs you".

What to merge, rename, hide or remove (each row is a parity record in the format of `docs/process.md:149` and `docs/design.md:146-152`):

**1. `PR-FIRST-RUN` — a first run that ends at the first value.**
- *Problem.* Seven steps, only one of which is needed to start; then a Welcome screen whose only button starts a plain terminal. Skipping hides the "needs you" queue's inputs (hooks, notification permission).

Keep *Run setup again* with all seven steps.

**2. `PR-FINISH` — Finish works wherever the agent worked.**
- *Problem.* The default placement is Main; Changes has no commit there; the task *Accept* records a decision but delivers nothing (row 6′).
- *Evidence.* `workbench/changes.rs:350-355`, `changes/delivery.rs:136-145,262-266`, `docs/orchestration.md:146`, `launcher.rs:899`; the same loop is closed in Conductor ("review the diff, open a pull request, merge, and archive") and Claude Code desktop (PR flow); Zed's staged/unstaged demand (#26560 R897) shows commit-from-review is wanted.

- *Acceptance.* GPUI scenario over a real daemon: Main-checkout agent edits → review → *Finish* → a local commit on the current branch, the task `merged`/`accepted`, nothing pushed. Daemon test for the refusal paths.

## 6. Decisions for the user

1. **D-P1 — How far does Hutan go to finish the loop?** (a) *Recommended:* commit-all from the main checkout (never push) **and** a prepared, unexecuted PR command in a visible terminal; (b) (a) plus Hutan runs `gh`/`git push` itself (needs an ADR; breaks "never pushes"); (c) keep today's behaviour (review-only in main, local merge for worktrees). Affects `PR-FINISH`, `PR-SHIP`.
2. **D-P2 — Default placement of an agent start.** (a) *Recommended:* Main checkout, with a worktree suggested (not forced) when the checkout already has a live agent or is dirty; (b) always a worktree (Conductor; Orca's forced "+" drew #2654 R16); (c) as today. Affects `PR-START-1`.
3. **D-P3 — First-run depth.** (a) *Recommended:* two steps (agents, open a folder) with just-in-time asks; (b) keep seven steps and polish them (audit F15). Affects `PR-FIRST-RUN`, `docs/design.md` § First-run.
4. **D-P4 — Mawas's place.** (a) *Recommended:* a quiet utility (off in setup, no nav row until enabled, no Today rail) until delegation exists; (b) a headline feature with its own page and rail as in ADR 0017. Amends ADR 0017 d1 under (a).
5. **D-P5 — The word "workspace".** The user's group of projects (ADR 0014) collides with Conductor/Superset's per-task workspace, which is also what direction D-1 proposes (`docs/spikes/2026-10-18-direction.md:45,50`). (a) *Recommended:* hide the group until created and make no change to the wire now; (b) rename the group *Group* in the UI; (c) adopt D-1 (task workspaces, protocol major) first. Affects `PR-VOCAB`, §3.4 row 7.
