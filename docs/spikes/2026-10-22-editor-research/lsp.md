# LSP in editors and coding agents: user evidence for Hutan E-11

Research date: 2026-10-21. Scope: Zed, Helix, Neovim (lspconfig/mason), VS Code, Lapce, and agent integrations (Claude Code, Codex, OpenCode).

## Method (reproducible)
- GitHub issues: `gh issue list -R <repo> -S "<terms> sort:reactions-+1-desc" --state all --limit N --json number,title,state,createdAt,comments,reactionGroups,url`. Reactions r = sum of `reactionGroups[].users.totalCount`. Comments c = comment count. `gh search issues --repo` returned noisy, unrelated results, so it was not used.
- Repos and queries: zed-industries/zed (memory, restart, offline, "language server restart"); rust-lang/rust-analyzer (memory, build scripts, trust, proc macros); helix-editor/helix ("lsp", "language server crash OR restart OR memory"); lapce/lapce ("lsp"); microsoft/vscode ("tsserver memory", "typescript server memory"); neovim/nvim-lspconfig and mason-org/mason.nvim (monorepo root, auto-install); anthropics/claude-code and openai/codex and anomalyco/opencode (LSP).
- Docs read: Zed worktree trust and Rust pages; VS Code Workspace Trust; Helix `book/src/languages.md` (via gh api); Neovim `runtime/doc/lsp.txt` (via gh api, v0.12 line); rust-analyzer security manual; Claude Code code-intelligence and plugin troubleshooting; OpenCode LSP docs.
- HN: Algolia `hn.algolia.com/api/v1/search?tags=story`. Reddit was not searched (no direct access); web search snippets only.
- Caveat: LSP-specific complaints in Helix and Lapce are thin at high reaction counts. Treat those sections as weak evidence.

## 1. RAM and CPU (servers, multiple instances)
- **Multi-instance under agents.** rust-analyzer #22765 (OPEN, 2026-07-11, c=2, r=12), "Daemonize rust-analyzer / Share it between clients": "it becomes pretty common for folks to have a bunch of rust-analyzer instances running, which in turn will have a bunch of proc-macro servers running." https://github.com/rust-lang/rust-analyzer/issues/22765
  Hutan should: run one server per (server binary, workspace root) in the daemon and share it between the user's editor and agent calls. Count proc-macro child processes in the supervision.
- **Users cannot turn it off.** Zed #58998 (CLOSED not_planned, 2026-06-10, c=2): "rust-analyzer uses too much RAM, and can't be disabled." https://github.com/zed-industries/zed/issues/58998
  Hutan should: let users disable a server per project and per language, and show its RSS in the UI.
- **General memory complaints.** Zed #18673 (OPEN, 2024-10-03, c=63, r=89), "Zed uses lot of RAM": https://github.com/zed-industries/zed/issues/18673. rust-analyzer #11325 (CLOSED, 2022-01-20, c=23, r=69), "Why does Rust Analyzer use so much RAM and CPU?": https://github.com/rust-lang/rust-analyzer/issues/11325. rust-analyzer #1252 (CLOSED, 2019, c=40, r=57), "RA uses quite a lot of RAM": https://github.com/rust-lang/rust-analyzer/issues/1252.
  Hutan should: set a memory budget per server and surface it. Do not rely on the server being "light".
- **Workspace-wide checks on save.** Zed Rust docs (https://zed.dev/docs/languages/rust): rust-analyzer `checkOnSave: true` runs `cargo check --workspace --all-targets` on every save, which "does not scale well" on large projects. Zed's own recommended fix is to disable it or narrow it, and use `linkedProjects` for multi-project folders.
  Hutan should: do not default to a workspace-wide check on save. Scope it to the changed crate or package.
- **Claude's own docs admit it.** Claude Code plugin troubleshooting (https://code.claude.com/docs/en/plugins/troubleshooting): "Language servers such as rust-analyzer and pyright index the whole project." The fix offered is to disable the plugin.
  Hutan should: give a per-server off switch that agents can see, so they fall back to search instead of waiting on the server.
- **TypeScript: process count and memory.** Scott Spence, "Revisiting LSP in Claude Code" (2026-10-10, https://scottspence.com/posts/revisiting-lsp-in-claude-code): default setup used about 935 MB across 4 processes. With `initializationOptions.tsserver.useSyntaxServer: "never"` it used about 725 MB across 3.
  Hutan should: count each TS server child process and set the syntax-server option explicitly.
- **TS slow vs VS Code and Neovim.** Zed #18698 (OPEN, 2024-10-03, c=76, r=180), "Typescript server is slow on Zed compared to VSCode": "I still don't get the same speed as VSCode or even NeoVim." https://github.com/zed-industries/zed/issues/18698
  Hutan should: benchmark the TS path against a direct tsserver run before shipping. Users compare against VS Code and Neovim.
- **Closed as duplicate.** rust-analyzer #20818 (CLOSED, DUPLICATE, 2025-10-09, c=1, r=1): memory in large monorepos. Low signal, but the topic recurs. https://github.com/rust-lang/rust-analyzer/issues/20818

## 2. Restarts, startup, offline, readiness
- **Startup blocked by update checks.** Zed #9789 (OPEN, 2024-03-25, c=38, r=107): LSP start is delayed until Zed checks for new versions. Quote: "All the while the LSP DOES NOT WORK." https://github.com/zed-industries/zed/issues/9789
  Related: Zed #4628 (CLOSED, 2023-07-13, c=57, r=52), stuck at "Checking for updates for <lang> language server": https://github.com/zed-industries/zed/issues/4628. Zed #24878 (Offline Support meta, OPEN, c=12, r=174): https://github.com/zed-industries/zed/issues/24878
  Hutan should: never block server start on the network. Start from the installed binary and report the state.
- **Partial answers while indexing.** Claude Code #76870 (OPEN, 2026-07-12, c=12, r=1): the built-in LSP tool "can return silently incomplete symbol results." Cause 1: the first query arrives before the initial index. Cause 2: only Write and Edit sync document state, so Bash, `git checkout`, `sed -i`, and formatters do not. https://github.com/anthropics/claude-code/issues/76870
  Hutan should: include an explicit "indexing / stale" status in every agent-facing LSP result. Sync the buffer or file on every write path, not just the agent's own edit tool.
- **Race at startup.** Claude Code #13952 (CLOSED, 2025-12-14, c=55, r=102): the LSP manager starts with 0 servers before plugins load (async race). https://github.com/anthropics/claude-code/issues/13952 Also #14803 (CLOSED, 2025-12-20, c=73, r=56), "LSP plugins not recognized - 'No LSP server available'": https://github.com/anthropics/claude-code/issues/14803
  Hutan should: model server state explicitly (starting, ready, indexing, failed, stopped) and never report "no server" while one is starting.
- **Crash and zombie handling.** Claude Code #79744 (CLOSED not_planned, auto-closed as inactive, 2026-07-21, c=1): after a server was killed, the client reported "Cannot send request … server is running", and restartOnCrash did not respawn it. https://github.com/anthropics/claude-code/issues/79744
  Hutan should: supervise with a visible restart and backoff. A killed server must be re-spawned or marked failed, never left as a zombie.
- **Hung on cargo.** rust-analyzer #10910 (CLOSED, 2021-12-03, c=39, r=11), stuck at "waiting for cargo metadata or cargo check": https://github.com/rust-lang/rust-analyzer/issues/10910. Also #9720 (CLOSED, 2021-07-29, c=29, r=14), "OUT_DIR not set, enable 'run build scripts' to fix": https://github.com/rust-lang/rust-analyzer/issues/9720
  Hutan should: show progress with a timeout and a cancel path for the build-script and metadata steps.
- **Agent process leaks (daemon hygiene).** Codex #30408 (OPEN, 2026-06-28, c=62, r=19): MCP server processes leak, 9+ GB RSS. https://github.com/openai/codex/issues/30408 Claude Code #43408 (CLOSED, 2026-04-04): spawned worker processes not cleaned up: https://github.com/anthropics/claude-code/issues/43408 Claude Code #65438 (CLOSED, 2026-06-04): plugin cache `.in_use` PID locks never reaped, about 285k accumulated: https://github.com/anthropics/claude-code/issues/65438
  Hutan should: the daemon owns child processes, reaps them on exit and on session end, and logs leaks.

## 3. Trust and security (servers that run build scripts)
- **rust-analyzer assumes trust.** Security manual (https://rust-analyzer.github.io/book/security.html): "At the moment, rust-analyzer assumes that all code is trusted." Proc macros and build scripts run by default. `.cargo/config`, `rust-toolchain.toml`, and VS Code workspace config can override executables.
  Hutan should: treat "open a folder" as "run build scripts and proc macros". Gate that behind the trust prompt, not only the server spawn.
- **Untrusted mode is not really possible.** rust-analyzer #9224 (OPEN, 2021-06-11, c=5), "Support untrusted workspaces in VSCode": jonas-schievink says disabling trust properly means avoiding any toolchain invocation, because `.cargo/config`, `rust-toolchain`, and build scripts can run code. https://github.com/rust-lang/rust-analyzer/issues/9224 Related: #14375 (CLOSED, 2023-03-18, c=9), "Arbitrary code execution during compile from rust-analyzer"; maintainer: "That's by design and documented." https://github.com/rust-lang/rust-analyzer/issues/14375
  Hutan should: state in the trust prompt exactly what runs (build scripts, proc macros, the server binary, toolchain overrides). Do not promise sandboxing.
- **Zed's per-worktree trust.** Zed worktree trust docs (https://zed.dev/docs/worktree-trust): every worktree starts in Restricted Mode, which blocks installing and spawning language servers and MCP servers and parsing `.zed/settings.json`. Global language servers still run. Trust persists per worktree and per host. `trust_all_worktrees` exists but is "not recommended". Single-file worktrees each need trust unless the parent is trusted.
  Hutan should: copy the per-folder model, but also decide whether daemon-global servers respect trust. Zed says they do not block, and that is a gap.
- **VS Code shares trust with agents.** VS Code Workspace Trust docs (https://code.visualstudio.com/docs/editing/workspaces/workspace-trust): "Workspace trust is shared between your VS Code window and the Agents window... agents will not run in either place." Also: "Some settings contain paths to executables (for example, linter binaries), which if set to point to malicious code, could cause damage." Terminals, tasks, and debugging are blocked until trust is granted.
  Hutan should: make agents and the LSP share one trust state, and disable workspace settings that name executables until the folder is trusted.
- **Sandboxing requests.** Zed #12358 (OPEN, 2024-05-27, c=13, r=57): isolate (sandbox) language servers. https://github.com/zed-industries/zed/issues/12358 Zed #13918 (OPEN, 2024-07-07, c=0, r=45): pin and check the hash of downloaded binaries. https://github.com/zed-industries/zed/issues/13918
  Hutan should: pin server versions and hashes, and record them in the trust record.

## 4. Auto-download
- **The main complaint.** Zed #12589 (OPEN, 2024-06-02, c=94, r=361), "Zed downloads NodeJS binary and npm packages from Internet without user's consent." Zed fetches Node from nodejs.org with no prompt and no disable option. The Supermaven binary was fetched with only TLS verification. https://github.com/zed-industries/zed/issues/12589
  Hutan should: never auto-download. A missing server shows "not installed" plus the exact command or the path to set. This is the E-11 rule.
- **Zed auto-installs Rust.** Zed Rust docs: if rust-analyzer is not on PATH, Zed installs its own, unless `ignore_system_version` is set.
  Hutan should: do not do this. Use the binary on PATH or the user's configured path only.
- **OpenCode defaults to download.** OpenCode LSP docs (https://opencode.ai/docs/lsp): LSP is disabled by default, but built-ins auto-install for several languages. `OPENCODE_DISABLE_LSP_DOWNLOAD=true` turns that off. The docs say "vary by version or project."
  Hutan should: if an env flag is needed to stop downloads, the default is wrong.
- **Claude's install prompt.** Claude Code code-intelligence docs (https://code.claude.com/docs/en/plugins/code-intelligence): after an edit, a "LSP plugin recommendation" dialog offers to install a plugin. It shows once per session, auto-dismisses after 30s, and stops after 5 ignores.
  Hutan should: avoid install prompts triggered by an agent edit. Put the install action in settings, not in the agent flow.
- **Mason users still ask for auto-install.** mason.nvim #1286 (OPEN, 2023-05-04, c=30, r=28), "Automatically install npm". https://github.com/mason-org/mason.nvim/issues/1286 #103 (CLOSED, 2022-07-20, c=9, r=42), configuration to auto-install missing tools: https://github.com/mason-org/mason.nvim/issues/103. Failures: #428 (OPEN, c=48), does not run on NixOS: https://github.com/mason-org/mason.nvim/issues/428. #1486, support for an environment behind a firewall: https://github.com/mason-org/mason.nvim/issues/1486
  Hutan should: auto-install is a demand and a failure source. Offer the command and let the user run it.
- **Codex proposal.** Codex #8745 (OPEN, 2026-01-05, c=71, r=608) proposed auto-detect and auto-install, "opt-in or prompt". https://github.com/openai/codex/issues/8745
  Hutan should: if an install path is ever offered, it must be explicit and per-folder, not a default.

## 5. Diagnostics noise, scope, and monorepo roots
- **Users want project-wide diagnostics.** VS Code #13953 (OPEN, 2016-10-18, c=100, r=2003), "Show all errors and warnings in project for all JavaScript and TypeScript files, not just opened ones." Quote: "I still need to go to my terminal and run our own make commands." https://github.com/microsoft/vscode/issues/13953
  Hutan should: keep the default scope for agents as "changed files plus their importers", and offer a full project check on demand.
- **Diagnostics draw over code.** Helix #1462 (CLOSED, 2022-01-08, c=21, r=73), "Intrusive Diagnostics": "Diagnostics appear on top of the code." https://github.com/helix-editor/helix/issues/1462 Zed #4901 (CLOSED, 2023-03-19, c=67, r=396), inline errors wanted: https://github.com/zed-industries/zed/issues/4901
  Hutan should: show diagnostics in a gutter or list by default. Inline only on the cursor line.
- **Agent context pollution.** OpenCode #16353 (CLOSED, 2026-03-06, c=2): "LSP.diagnostics() aggregates diagnostics from ALL active LSP clients ... with no workspace/project path filtering." Diagnostics from external projects appeared in tool results. https://github.com/anomalyco/opencode/issues/16353 Also opencode-ai/opencode #77 (OPEN, 2025-04-26, c=1): diagnostics for deleted files: https://github.com/opencode-ai/opencode/issues/77
  Hutan should: filter agent-facing diagnostics by the agent's workspace root and by file existence.
- **False positives in monorepos.** Claude docs: "A language server that isn't configured for the workspace can report unresolved imports for internal packages." https://code.claude.com/docs/en/plugins/code-intelligence (troubleshooting, https://code.claude.com/docs/en/plugins/troubleshooting, section "False positive diagnostics in a monorepo").
  Hutan should: show the resolved root and config for each server, so a user can see why a package is missing.
- **Root detection bugs (Neovim).** nvim-lspconfig #4015 (CLOSED 2025-08-19, c=21): JS/TS servers attach to files that are only in the workspace directory (a lock file). https://github.com/neovim/nvim-lspconfig/issues/4015 #3818 (OPEN 2025-05-03, c=13): `.oxlintrc.json` not found because `insert_package_json()` searches breadth-first. https://github.com/neovim/nvim-lspconfig/issues/3818 #4457 (OPEN 2026-06-23, c=1): tsgo root_dir aborts when `deno.json` sits beside a lockfile. https://github.com/neovim/nvim-lspconfig/issues/4457 #4391 (OPEN 2026-04-15, c=4): denols root_dir logic incorrect. https://github.com/neovim/nvim-lspconfig/issues/4391 #4227 (OPEN 2025-12-05, c=4): eslint `workingDirectory.mode=auto` breaks path resolution in monorepos. https://github.com/neovim/nvim-lspconfig/issues/4227
  Hutan should: write root-detection tests with monorepo fixtures (lockfile beside deno.json, nested package.json, breadth-first vs. topmost). Each one of these bugs is a fixture.
- **Helix root rule.** Helix languages docs (source `book/src/languages.md` in helix-editor/helix, read via gh api; the hosted docs page was not fetched): roots are found starting at the file, and Helix "remembers the *topmost* i.e. *last* directory that contains a marker file." `workspace-lsp-roots` in `.helix/config.toml` stops the search early. `required-root-patterns` gates start after the root is chosen.
  Hutan should: use the topmost marker by default, with a per-project override in its own project config. Add a required-pattern gate.
- **Neovim reuse rule.** Neovim `runtime/doc/lsp.txt` (master branch, read via gh api; sections `lsp-activate`, `vim.lsp.enable()`, and the `reuse_client` option of `vim.lsp.start`): `reuse_client` default "re-uses a client if it has the same name and if the given workspace folders (or root_dir) are all included in the client's workspace folders." Configs activate "if `root_markers` or `root_dir()` resolved a workspace root, or the config has `workspace_required=false`". https://github.com/neovim/neovim/blob/master/runtime/doc/lsp.txt
  Hutan should: share a server only when the requested root is included in its workspace folders. Otherwise start a new one.
- **Shared server request (old).** nvim-lspconfig #842 (CLOSED, r=8): share one server across workspace folders. https://github.com/neovim/nvim-lspconfig/issues/842 nvim-lspconfig #3003 (OPEN, 2024-02-09, c=16): workspaces not re-added after removal. https://github.com/neovim/nvim-lspconfig/issues/3003

## 6. Do coding agents benefit from LSP?
- **Codex maintainer, the strongest primary statement.** openai/codex #8745, comment by etraut-openai (2026-01-06): "the language server protocol was not designed for coding agents, and it's not clear LSPs are a good match here. We've experimented with the idea, and it hasn't provide the benefits that I initially thought it might." The maintainer suggested AGENTS.md lint and typecheck commands instead. https://github.com/openai/codex/issues/8745 (c=71, r=608 at time of research). Benefits asked for in the thread: lower-latency structured diagnostics, semantic signals, rename.
  Hutan should: lead with diagnostics after edits. Do not sell LSP as a grep or navigation replacement without measured evidence.
- **Spence measured it (2026-10-10).** https://scottspence.com/posts/revisiting-lsp-in-claude-code. Findings:
  - Diagnostics are the real value. Type errors arrive without a tool call, but about 30s late. Two short sessions missed the error completely.
  - Grep beat LSP for references: 9/9 correct, faster, cheaper. LSP missed a `vi.mock` string reference and could not answer "can I delete it".
  - LSP was about even for types (hover).
  - Svelte: the TypeScript server cannot see `.svelte` callers. References from `.ts` found 23, from `.svelte` 89, and grep 90.
  - First LSP call wrong in 18 of 19 sessions, because the syntax server answered during project load. With `useSyntaxServer: "never"`, the first call was right in 12 of 12 sessions.
  - Changes from the shell are missed (`git checkout`, appended lines, formatters).
  Hutan should: run diagnostics after each agent write, wait for "ready" before any LSP answer, and fall back to search for references.
- **OpenCode docs agree.** https://opencode.ai/docs/lsp, best practices: "Language servers can get out of sync, use significant memory, vary by version or project, and slow down agent workflows... In many projects it is better to have the agent run lint, typecheck..." OpenCode v2 docs (search snippet only, https://opencode.ai/v2/docs/lsp): "does not currently use LSP when reading, writing, editing, or patching files". The v2 page could not be fetched, so cite it as a snippet only.
  Hutan should: the agent's default verify step is the project's lint or typecheck command. LSP adds on top of that.
- **Claude's built-in LSP shipped and drew interest.** HN "Claude Code gets native LSP support" (https://news.ycombinator.com/item?id=46355165, 2025-12-22): 511 points, 339 comments. HN "Claude Code LSP" (https://news.ycombinator.com/item?id=47216765, 2026-03-02): 77 points, 39 comments. Comments are not clearly on-point, so use only the counts.
- **Breakage in agent LSP integrations.** OpenCode #56276 (CLOSED 2026-10-17, c=2): "LSP servers never start on file operations in v2.0.32", and no `lsp` tool was exposed. https://github.com/anomalyco/opencode/issues/56276 Claude #14803, #16084 (Windows: "No LSP server available for file type: .rs"). https://github.com/anthropics/claude-code/issues/16084 Claude #45132 (OPEN, 2026-04-08, c=15, r=98): add Scala (Metals) plugin. https://github.com/anthropics/claude-code/issues/45132 Claude #16849 (CLOSED, c=15, r=137): Dart/Flutter support: https://github.com/anthropics/claude-code/issues/16849
  Hutan should: test the "server never started" path on each platform, since most failures are "no server available".
- **Agent-facing LSP tool requests.** Codex #30561 (OPEN, 2026-06-29, c=1, r=5): IDE-like semantic navigation. https://github.com/openai/codex/issues/30561 Community tools: cclsp (ktnyt) and llmcc (allenanswerzq), both named in the #8745 thread.
  Hutan should: expose navigation as an optional tool, not the default path.

## 7. Thin or weak areas
- **Lapce:** only generic LSP-adjacent issues. lapce/lapce #700 (OPEN, 2022-06-28, c=71, r=46), "Vim Support." #374 (CLOSED, r=20), "Typescript Support." #558 (CLOSED, c=37, r=19), "Plugin Support." No LSP-specific complaint about RAM, restarts, or trust was found. Say so in the brief.
- **Helix:** the highest-reaction editor item for E-10 is #1125 (OPEN, 2021-11-18, c=82, r=356), "automatic reload when file changes externally": the request is to reload when unmodified and treat the reload as one undoable change. https://github.com/helix-editor/helix/issues/1125 Helix LSP-specific issues have low reactions. Restart and crash searches returned nothing relevant.
- **Neovim:** no single high-reaction complaint about core LSP. Problems are many but spread across low-reaction nvim-lspconfig issues (see section 5).
- **Zed #38109 (directly relevant to E-10):** "Zed out of sync with changes made outside of editor" (CLOSED, 2025-09-13, c=100, r=178). File add, remove, or rename outside Zed does not update the project panel or open buffers. An AI-created file replaced on disk was not reflected in the buffer. https://github.com/zed-industries/zed/issues/38109
  Hutan should: the reload and conflict path is the most-reported E-10 failure. Test external writes by agents, not just user edits.

## Recommendations for the slices
1. E-11: never auto-download or auto-install. A missing server shows "not installed", the command to install it, and the path to set. Zed #12589 (r=361) is the reason.
2. E-11: one trust state per folder, covering server spawn, build scripts and proc macros, and executable paths in workspace settings. Agents and the LSP share it. Follow Zed worktree trust and VS Code's shared Agents trust, and say plainly that rust-analyzer does not sandbox.
3. E-11: the daemon owns one server per (binary, root), shared by user and agent. It reports starting, indexing, ready, failed, and stopped; restarts with backoff; reaps children; shows RSS; and can be disabled per project. Avoid Claude #76870 and #79744 and rust-analyzer #22765 (r=12).
4. E-11: root detection uses the topmost marker with a per-project override, and shares a server only when the root is inside its workspace folders. Build monorepo fixtures from nvim-lspconfig #3818, #4457, and #4227, and Helix's `workspace-lsp-roots`.
5. E-10: after an agent write, run diagnostics for the changed files and their direct importers, mark results as stale until the server is ready, and filter by workspace root (OpenCode #16353). Do not make LSP the default for references: Spence found grep beat it 9/9. Reload clean buffers and show a conflict bar for dirty ones, since Zed #38109 (r=178) and Helix #1125 (r=356) show the failure is reported often.
