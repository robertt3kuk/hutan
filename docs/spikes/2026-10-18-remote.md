# Remote hosts and transports — D-3 research and design

**Status:** proposal, not an implementation or accepted decision.

**Recommendation:** accept **D-3: SSH first → direct TLS second → E2EE relay later**. Introduce a transport boundary without changing Hutan’s frame encoding, event sequencing, replay, snapshot rules, or terminal credit-1 pacing. Use **the system OpenSSH executable**, not a Rust SSH implementation, for the first remote transport.

The local daemon remains the default host. A remote host is an explicitly selected execution and storage location—not an extension of the laptop filesystem, and not an implicit synchronization destination.

## 2. Hutan’s existing seam: framing is ready; connection ownership is not

| Area | Current behavior | Required change |
|---|---|---|
| Client stream | Concrete `UnixStream`; handshake and read/write loops use Unix owned halves. | Generic async read/write plumbing. |
| Server authentication | `conn::serve` checks peer UID before handshake. | Keep this check in the local acceptor; pass an authenticated principal into generic serving. |
| Endpoint resolution | Local socket path and local autostart are coupled to dialing. | Typed endpoint configuration; local autostart only on local endpoints. |
| Reconnection | One reconnecting `Connection` owns its thread, state, supervisor, generations, and channels. | Reuse one `Connection` per host. |
| Shutdown UI | Treats disconnect as potentially successful shutdown, then waits for socket-path disappearance. | Separate “request accepted,” “connection lost,” and “termination confirmed.” |
| Daemon watchdog | Disappearing/replaced local socket stops the daemon because the comment assumes nobody can reach it. | Define multi-listener lifecycle explicitly before enabling TLS. |
| Paths and attachments | Paths are read by the daemon. Desktop-selected local paths can currently be transmitted as path strings. | Make the owning host explicit in the client model; upload laptop files rather than reinterpret their paths remotely. |

### Invariants to retain

The actual frame is:

```text
u32 big-endian payload length | u8 kind | payload
```

**The length excludes the kind byte.** The maximum payload is 4 MiB. Kinds remain control JSON, terminal render, and terminal input. Source: `crates/protocol/src/frame.rs:1-24,100-135`.

ADR 0002 additionally requires:

- Major/minor negotiation and capability-gated additive features.
- Epoch-scoped replay and sequence watermarks.
- Subscribe-before-snapshot.
- Credit-1 terminal rendering with latest-state coalescing.
- Bounded outbound queues and disconnect/replay recovery for slow consumers.

Source: `docs/adr/0002-ipc-transport-and-framing.md:18-44`.

A transport adapter must not decode and re-encode these frames.

## 3. Connection methods and tradeoffs

| Method | Advantages | Costs and limits | Recommendation |
|---|---|---|---|
| Local IPC | Lowest complexity and latency; OS peer authentication. | OS-specific endpoint and peer identity handling. | Default; preserve Unix behavior and add Windows named-pipe support through the platform layer. |
| SSH command stdio | No new listening port; inherits known hosts, agents, bastions, enterprise configuration; simple byte stream. | Requires remote proxy binary and suitable SSH command execution; shell stdout pollution must be diagnosed. | **First remote method.** |
| SSH socket/port forwarding | Can reuse local-looking socket plumbing; useful for third-party clients. | Extra listeners, cleanup and forwarding policy; Unix socket forwarding is not the cross-platform seam. | Not the primary desktop path. |
| Direct TLS | Fewer subprocesses; good LAN/VPN/Tailscale experience; usable by future non-SSH clients. | Exposed listener, device credentials, enrollment, revocation and key recovery. | Second, explicitly enabled. |
| E2EE relay | Outbound-only reachability through NAT; future mobile access. | Broker operation, metadata exposure, account/device authorization, cryptographic transport and reconnect complexity. | Later, with a separate security ADR. |

herdr demonstrates SSH command stdio and a local bridge socket; its saved-host checks distinguish an already-running compatible server from bootstrap. Sources: `src/remote/attach.rs:1,53-105,108-138`.

Orca demonstrates a more elaborate alternative: managed remote runtime installation, SSH tunnels, identity verification beyond “port opened,” and stdio fallback. Sources: `docs/spikes/2026-10-18-orca-process-remote.md:38-45`.

Hutan does not need Orca’s entire remote runtime stack to deliver SSH control of `hutand`.

### Recommendation

Use one supervised system `ssh` process per active host connection. Do not initially introduce an OpenSSH ControlMaster owned by Hutan: one persistent framed connection already multiplexes Hutan operations.

This also avoids a Unix-only `openssh` crate blocking Windows. A Windows implementation can invoke installed OpenSSH; executable availability must be reported honestly.

## 5. Concrete transport boundary

### Client model

Proposed types, not existing APIs:

```rust
enum Endpoint {
    Local(LocalEndpoint),
    Ssh(SshEndpoint),
    Tls(TlsEndpoint),
    // Relay is added only when implemented.
}

struct ConnectOptions {
    endpoint: Endpoint,
    expected_host_id: Option<HostId>,
    local_autostart: Option<LocalAutostart>,
    // Existing protocol/capability/reconnect options.
}
```

Make it structurally impossible to apply local daemon autostart to an SSH/TLS endpoint.

Prefer generic stream handling:

```rust
async fn handshake<R, W>(
    reader: &mut FramedRead<R, FrameCodec>,
    writer: &mut FramedWrite<W, FrameCodec>,
    hello: Hello,
) -> Result<Welcome, ClientError>
where
    R: AsyncRead + Unpin,
    W: AsyncWrite + Unpin;
```

For the reconnecting supervisor:

1. Match the endpoint at the dial boundary.
2. Instantiate the same generic connected-session implementation with the returned reader/writer.
3. Keep transport ownership alongside it:
   - Local: socket/pipe handle.
   - SSH: child handle, stdin/stdout, bounded stderr drainer.
   - TLS: authenticated TLS stream.
4. On cancellation, close transport I/O, terminate/reap an owned SSH child, and cancel the existing read/write tasks.

This avoids allocating or copying per frame. A one-time boxed stream is an alternative if generic branching makes the supervisor substantially harder to maintain; it is not necessary to establish the seam.

### Daemon model

Separate authentication from generic framed serving:

```text
Unix acceptor
  -> verify peer UID
  -> AuthenticatedPeer::LocalUser
  -> serve_io(reader, writer, peer, context)

Named-pipe acceptor
  -> verify OS identity / ACL policy
  -> AuthenticatedPeer::LocalUser
  -> serve_io(...)

TLS acceptor
  -> validate certificate + active device record
  -> AuthenticatedPeer::Device
  -> serve_io(...)
```

Only acceptor/authentication modules may construct `AuthenticatedPeer`. A claimed `device_id` or `client.kind` in JSON is not authentication.

The current UID rejection must remain **before** processing a local connection’s hello. Never replace it with an “optional auth callback” whose default permits unauthenticated TCP.

`ConnHandle` gains the authenticated principal. Existing control policy remains enforced; transport authorization is an additional boundary, not a replacement.

## 6. `hutan proxy`: exact contract

Proposed invocation:

```text
ssh -T [SSH options] target hutan proxy
```

For a managed installation, use its recorded executable path rather than depending on the remote login shell’s `PATH`.

`hutan proxy`:

1. Resolves the **remote** local IPC endpoint using the same platform resolver as the daemon/client.
2. Connects to an already-running daemon.
3. Copies stdin → socket and socket → stdout with bounded buffers.
4. Writes diagnostics only to stderr.
5. Does not parse Hutan frames, inject a hello, add a ready marker, use line encoding, base64 the stream, or allocate a PTY.
6. Never installs, upgrades, starts, or restarts a daemon implicitly.
7. On stdin EOF, shuts down the socket’s write half and drains pending output with a bounded shutdown deadline.
8. On socket EOF/error, stops the bridge rather than waiting forever for input.
9. Exits unsuccessfully when it cannot connect or bridge.

The remote daemon sees the proxy’s local UID, preserving the existing local authentication model. The SSH server authenticates the remote login user; OpenSSH validates the SSH server.

This means SSH is **account-level access**, not a revocable Hutan device credential. Someone retaining SSH access as that remote user can run another proxy after a TLS device is revoked.

### SSH process policy

Defaults:

```text
-T
-o BatchMode=yes
-o StrictHostKeyChecking=yes
-o ForwardAgent=no
-o ForwardX11=no
-o ClearAllForwardings=yes
-o ServerAliveInterval=15
-o ServerAliveCountMax=3
```

Use a bounded connection deadline. Honor the chosen SSH alias and its `ProxyJump`/`ProxyCommand`; do not attempt to reimplement the configuration parser.

Host creation should distinguish:

- SSH configuration/authentication preparation.
- Explicit trust confirmation of a new SSH host key.
- Noninteractive operational connection.

Never silently use `StrictHostKeyChecking=no`. Never share framed stdin with a password prompt. If interactive setup is required, direct the user through an explicit terminal/setup operation before reconnecting.

Use argv, not a local shell command string. SSH still passes the remote command through a remote shell: quote remote paths with the selected remote-shell rules, and reject unsupported combinations rather than assuming POSIX quoting works in PowerShell. See [`openssh`’s remote-shell documentation](https://github.com/openssh-rust/openssh/blob/master/src/lib.rs).

Drain stderr continuously into a bounded diagnostic buffer, for example 16 KiB retained. Treat it as untrusted terminal/log content. Do not parse localized stderr into authoritative lifecycle facts.

A remote shell printing to stdout will corrupt the frame stream. Report a specific “unexpected bytes before Hutan welcome; check remote shell startup output” diagnostic; do not strip arbitrary bytes until a frame happens to parse.

## 7. Host identity and handshake

### Identity distinctions

Keep four concepts separate:

1. **Host profile ID:** local catalog identity; exists before first contact.
2. **Host installation ID:** random stable UUID generated once per daemon data directory.
3. **Transport authority:** SSH known-host identity, or pinned TLS host authority.
4. **Epoch:** changes every daemon boot; already scopes replay.

A hostname, PID, SSH alias, or boot epoch is not the stable host identity. A UUID is not cryptographic authentication.

Orca makes the same distinction: its installation UUID persists per profile; machine-binding information is a hint, not an identity proof. Source: `src/shared/runtime-host-descriptor.ts:3-18`.

### Additive wire fields

Capability: `host.identity`.

Proposed hello additions:

```json
{
  "id": 0,
  "method": "hello",
  "params": {
    "protocol": {"major": 0, "minor": "<allocated minor>"},
    "client": {"kind": "desktop", "version": "..."},
    "capabilities": ["host.identity"],
    "expected_host_id": "stable-installation-uuid",
    "resume": {"epoch": "boot-uuid", "seq": 123}
  }
}
```

Proposed welcome addition:

```json
{
  "host": {
    "id": "stable-installation-uuid",
    "name": "gpu-server",
    "platform": "linux",
    "arch": "aarch64",
    "path_style": "posix",
    "authority_spki_sha256": "optional-until-TLS-is-configured"
  }
}
```

Rules:

- `expected_host_id` is optional and defaulted.
- `host` is optional/defaulted in the client’s welcome DTO.
- A new daemon rejects a mismatching expected identity **before replay or snapshot delivery**.
- A new client validates identity before installing the connection’s state or issuing mutations.
- A known SSH profile may pin the initial installation UUID after SSH host authentication and user-approved first contact.
- Adding a TLS endpoint to an existing SSH profile requires an authenticated binding to the same installation; do not merge profiles merely because their UUID strings match.
- If an old daemon lacks identity support, local operation remains compatible. A saved remote profile requiring identity must show “upgrade required,” not silently downgrade its identity guarantee.
- A changed identity is an explicit replacement/re-pair operation. Do not transfer the old resume point or saved session selections automatically.

Existing handshake DTOs have no host identity: `crates/protocol/src/messages.rs:389-409,756-763`.

## 8. Host installation and upgrades

Installation and daemon lifecycle are explicit management actions, separate from connecting.

Proposed commands:

```text
hutan host add <name> --ssh <alias>
hutan host inspect <name>
hutan host install <name> --version <version>
hutan host start <name>
hutan host upgrade <name> --version <version>
hutan host disconnect <name>
hutan host remove <name>
```

“Remove host” disconnects and removes the laptop profile; it does not stop remote jobs or delete remote data.

### Managed installation procedure

1. Authenticate SSH and identify remote OS, architecture, executable format and libc requirements.
2. Inspect existing Hutan installation/version/protocol **without starting it**.
3. Show the selected artifact, target directory, service behavior and whether sessions must stop.
4. Download a release artifact locally from Hutan’s official release origin.
5. Verify a signed release manifest against a pinned release-signing key. A checksum downloaded from the same compromised source is not sufficient.
6. Transfer to a unique staging directory over SSH/SFTP.
7. Acquire a remote per-user install lock; verify artifact hashes and permissions.
8. Install immutable version directories, for example:

   ```text
   ~/.local/share/hutan/runtime/<version>-<target>/
     hutan
     hutand
     manifest.json
   ```

9. Atomically update a small “current installation” pointer only after verification.
10. Start only after an explicit management action; verify the framed welcome and stable installation identity.
11. Record success only after that verification. Preserve the previous version for rollback.

Do not use `curl | sh`, require sudo, overwrite an executing binary in place, or put user secrets into SSH command arguments.

Orca supplies useful precedent for versioned remote installs, staging, locks, executable modes and finalization: `docs/spikes/2026-10-18-orca-process-remote.md:38-42`, citing its `orcad-remote-install.ts`.

### Upgrade behavior

- If the running daemon is protocol-compatible, continue connecting and offer an upgrade.
- Merely installing newer binaries does not replace the running process.
- If a restart is required, show live-session consequences and use the lifecycle/restore design.
- Do not claim uninterrupted PTY preservation across a `hutand` replacement: Hutan has no evidenced process-handoff mechanism.
- A major protocol incompatibility becomes “upgrade/restart required”; do not kill an incompatible daemon automatically.

- Binary rollback is permitted only when the storage schema remains backward-readable. Otherwise restore a consistent pre-upgrade backup, with user confirmation.

The initial supported remote release matrix should follow Linux headless support, then additional published targets. Unsupported targets receive a clear manual-install path, not an attempted local compilation or guessed download.

## 9. Direct TLS and device pairing

Use `tokio-rustls` with a reviewed, pinned rustls release and explicit crypto-provider selection appropriate to that release. rustls supports TLS 1.2/1.3, production deployment, and Tokio integration; its licenses are Apache-2.0, MIT or ISC at the user’s option. Source: [official rustls README](https://github.com/rustls/rustls/blob/main/README.md).

### Listener policy

- TLS is disabled by default.
- Require explicit bind address configuration; show a warning for wildcard/public binding.
- Use TLS 1.3 and ALPN `hutan/1`.
- Require client certificates for the normal control listener.
- Verify the client certificate chain **and** an active device record before Hutan hello.
- Bind device ID to its verified key/certificate; ignore conflicting claimed identity.
- Disable 0-RTT for mutation-bearing connections.
- Firewall/VPN controls are defense in depth, not authentication.

### Secure enrollment

Do not present a short numeric code as sufficient cryptographic authentication.

Recommended first pairing flow:

1. An already-trusted local IPC or SSH administrator invokes `device.pairing_create`.
2. The daemon opens a **temporary, restricted pairing listener**, separate from its normal mTLS control listener.
3. It returns an invitation containing:
   - installation ID;
   - pairing endpoint;
   - pinned host authority certificate/SPKI fingerprint;
   - 256-bit random single-use enrollment secret;
   - invitation ID and expiry, default five minutes.
4. The user transfers the invitation by QR or an authenticated copy/paste channel.
5. The new device creates its private key locally and connects with pinned server authentication.
6. Over that TLS connection it presents the invitation secret and a CSR/proof of possession.
7. The daemon shows the requesting device and key fingerprint to the local administrator for confirmation.
8. On approval, issue a device certificate, consume the invitation atomically, close its pairing listener, and reconnect through normal mTLS.

The temporary listener may dispatch **only** pairing methods. It must not expose daemon control to an unauthenticated enrollee.

A short displayed code can identify the pending request for human confirmation. If entering only a low-entropy code is later required, select a reviewed PAKE protocol and implementation under a separate security design.

### Proposed device wire operations

Capability: `device.pairing`.

Trusted local/SSH administration:

```text
device.pairing_create { label?, ttl_seconds? }
  -> { invitation_id, invitation_uri, expires_at }

device.pairing_list {}
  -> pending requests with device key fingerprints

device.pairing_approve { invitation_id, request_id }
device.pairing_cancel { invitation_id }

device.list {}
device.revoke { device_id }
```

Restricted pairing listener:

```text
pairing.enroll { invitation_id, secret, device_label, csr_der_base64 }
  -> { request_id, state: "pending" }

pairing.status { request_id, proof_of_possession }
  -> pending | approved certificate bundle | rejected
```

These use ordinary control frames. Enrollment authorization is narrowly scoped and bounded; it is not derived from `ClientKind::Desktop`.

Default paired devices are full controllers of that host; explain this prominently. Do not advertise a read-only device role until every relevant method and binary terminal-input path enforces it.

Revocation updates persistent device state and terminates existing connections for that device. TLS resumption must not bypass the active-device lookup.

### Key storage

- Keep host authority keys, TLS server keys and device private keys encrypted through the platform secret-store/vault boundary.
- SQLite stores public certificates, fingerprints and opaque secret references—not plaintext private keys.
- On a headless host without an available OS secret store, require an explicitly unlocked encrypted file vault/passphrase arrangement.
- Do not silently degrade to plaintext key files.
- An unattended server needs an explicit unlock policy. Automatically storing a decryption password beside the encrypted key does not provide the claimed protection.
- Certificates and public pins are not secrets; enrollment secrets are.
- Never journal or trace invitation secrets or private key material.
- Host-authority rotation requires proof through existing trust or re-pairing; never accept a changed pin automatically.

The existing non-macOS credential backend refuses persistence rather than pretending it succeeded; retain that honesty when introducing headless key storage. Evidence: `docs/spikes/2026-10-18-hutan-model-lifecycle-transport.md:67,81`.

## 10. Storage and settings

### Host catalog

The host catalog is **client-owned local state**, available even when the local daemon is stopped. Remote profiles must not be stored solely behind the local daemon’s availability.

Use one client-state SQLite catalog shared by desktop and CLI, with transactional updates:

| Table | Essential columns |
|---|---|
| `host_profiles` | `profile_id` PK, `label`, `kind`, typed endpoint/config JSON, `expected_host_id` nullable, `created_at`, `updated_at`, `retired_at` nullable |
| `host_trust` | `profile_id`, `transport_kind`, public authority/pin, `device_id` nullable, `credential_ref` nullable, `approved_at`, `revision` |
| `host_last_answers` | `profile_id` PK, last verified host descriptor, daemon version, capabilities, epoch, observation timestamp |

Endpoint configuration contains no passwords/private keys. SSH private-key *paths*, if explicitly selected, are configuration; authentication stays with OpenSSH.

Do not persist session transcripts or remote snapshots in this catalog by default. A last-answer descriptor is not a live-state claim.

### Daemon-owned tables

| Table | Essential columns |
|---|---|
| `host_identity` | singleton ID, stable `host_id`, display name, creation time, optional authority public certificate and `authority_key_ref` |
| `devices` | `device_id` PK, label, public-key fingerprint, certificate serial, creation time, last seen, revoked time |
| `pairing_invites` | invitation ID, hash of random secret, expiry, consumed/cancelled time |
| `pairing_requests` | request ID, invitation ID, CSR/public key, state, request expiry |
| `attachment_uploads` | upload ID, owning authenticated principal, declared length/type/hash, received offset, staging path, expiry |
| `attachment_objects` | object ID, owner, size, MIME/type, hash, creation and retention metadata |

Private keys remain behind secret references. Pairing approval and single-use consumption are one transaction. Expired staged attachment files have bounded cleanup.

Daemon-local IDs remain unchanged on the wire.

Qualify layout persistence, search results, notifications, terminal handles, pending commands and drag payloads. A session dragged across hosts must not appear to “move” a live process. Reject it with an explanation; any future export/recreate operation is a different action.

Host-switching must not redirect an already-composed destructive command to the newly selected host. Capture the target host and connection generation when the action is created.

### Contact states

Adopt Orca’s evidence model:

```text
live(status, observed_at)

unverifiable(
  reason: never_asked | connecting | transport_down | probe_failed
          | identity_mismatch,
  last_answer?
)

refused(reason, last_answer?)

retired(last_answer?)
```

Sources: `src/shared/runtime-host-contact.ts:4-36,62-88`.

- `live`: authenticated, identity-checked and synchronized.
- `unverifiable`: current state cannot be established. Preserve last-known sessions, visibly stale.
- `refused`: an authenticated endpoint explicitly rejected authorization.
- `retired`: local removal/retirement or authoritative end of the pairing.

A generic SSH exit code 255, TCP refusal, timeout, or dropped connection is **not evidence that sessions exited**. A host-key mismatch is a security error, not an opportunity to replace trust.

Keep transport state (`connecting`, `ready`, `down`) separate from contact evidence and bootstrap phase (`installing`, `starting`, `upgrading`).

### Lifecycle boundary

Closing the laptop UI must disconnect remote hosts, not invoke `daemon.shutdown` on them. Apply local close behavior only to the local host; stopping a remote host is an explicit, host-labelled operation.

A TLS-only headless host must not be killed merely because its local UDS file vanished. Replace the current single-endpoint assumption with listener supervision:

- Detect and report local endpoint failure.
- Never unlink/rebind over a replacement endpoint blindly.
- Keep valid configured remote listeners serving unless a stronger integrity failure requires termination.
- Treat loss of the daemon lock/data-directory integrity separately from loss of one listener.

### Shutdown reporting

Current `daemon.shutdown` queues an empty result after cancellation is requested; it is not a post-exit receipt. Source: `crates/daemon/src/router.rs:143-164`.

Proposed capability: `daemon.shutdown_receipt`, adding optional response fields:

```json
{
  "accepted": true,
  "shutdown_id": "...",
  "epoch": "boot-being-stopped"
}
```

The UI may say **“Stop requested”** after acceptance. EOF alone becomes “disconnected,” not “confirmed stopped.”

- Locally, OS process/lock observation can confirm termination.
- Over SSH, an explicit management check can verify the original daemon instance is gone using its local lock/process identity.
- Over TLS alone, do not promise proof of process exit after the sole authority has disappeared. Show confirmation as unavailable unless a separate trusted supervisor supplies it.

Do not carry socket-path polling into remote shutdown logic.

## 12. Files, attachments and credentials

### Ownership rules

- Session cwd, project/worktree paths, file attachments, credentials, index and memory belong to the **selected daemon host**.
- A laptop file picker returns a laptop file, not a remote path.
- A remote path picker queries the remote host.
- Opening `/home/user/repo/file` from a remote session must not invoke the laptop’s local opener on that string.
- OSC 7 paths remain associated with their terminal’s host; terminal output cannot redirect the host manager.
- Provider keys used on a remote host are provisioned there explicitly. No automatic copying of laptop credentials or SSH agent forwarding.
- Keep the personal assistant local by default. “Stored locally on the executing server” is not equivalent to “stored only on this laptop”; the UI must make that distinction explicit.

Existing `File { path, picked }` can read outside workspace roots for a user-picked path; existing `Image` may read a daemon path or inline base64. Sources: `crates/protocol/src/assistant.rs:255-283`.

### Remote attachment behavior

For an existing compatible remote daemon:

- Small images can use the existing inline representation.
- Pasted text can use the existing bounded text representation.
- Remote path attachments continue to use daemon paths.
- Local-file upload requiring unsupported capability is visibly unavailable—never fall back to transmitting the local path.

Existing image limits: 5 MiB by daemon path, 3,000,000 decoded bytes inline; pasted text limit 256 KiB. Source: `crates/protocol/src/assistant.rs:26-34`.

### Capability-gated uploads

Capability: `attachment.upload`.

```text
attachment.upload_begin {
  filename, media_type, length, sha256
}
  -> { upload_id, chunk_bytes: 65536 }

attachment.upload_chunk {
  upload_id, offset, data_base64
}
  -> { received_offset }

attachment.upload_commit { upload_id }
  -> { attachment_id, size, sha256, media_type }

attachment.upload_abort { upload_id }
```

Add a capability-gated attachment variant:

```json
{"kind":"uploaded","attachment_id":"opaque-host-owned-id"}
```

This stays within ordinary control frames: **no new frame kind or change to the proxy**. Base64 is acceptable for bounded, low-volume attachment transfer; measure before designing another binary data protocol.

For the initial implementation, use one outstanding upload chunk per upload. At high RTT this limits throughput, but remains simple and bounded; it must not block interactive frames. A later pipelined upload window can be introduced without changing terminal ACK semantics.

Security:

- Owner-check every upload/object lookup.
- Treat filenames as display metadata, never destination paths.
- Enforce quotas before writing; verify declared length, hash and actual content.
- Store staged files privately.
- Do not decompress archives automatically.
- Apply current attachment authorization/redaction rules after upload.
- Keep raw file contents out of diagnostic logs.
- No automatic cross-host transfer or background filesystem synchronization.

Remote browsing/download should use bounded `file.list`, `file.stat`, and range-read operations with the same host/principal policy. Do not turn the first SSH release into a remote-mounted filesystem or bidirectional editor synchronization project.

## 13. RTT, latency budgets and flow control

### Orca reference constants

Orca’s remote terminal multiplex defines:

| Limit | Value |
|---|---:|
| Stream chunk | 48 KiB |
| Output batch maximum | 64 KiB |
| Initial/max per-stream ACK window | 512 KiB / 2 MiB |
| Initial/max aggregate ACK window | 2 MiB / 8 MiB |
| Pending bytes | 256 KiB |
| ACK flush | 192 KiB or 4 ms |
| Recovery scrollback | 1,000 rows |
| Active streams | 128 |
| Concurrent/queued PTY waits | 32 / 128 |

Source: `src/shared/terminal-multiplex-flow-control.ts:1-18`.

These are **not Hutan-compatible terminal ACK settings**. Orca’s byte-window stream and Hutan’s latest-state render credit have different semantics.

### Keep credit-1, acknowledge its limit

With one outstanding render, a terminal can produce approximately one newly acknowledged render per RTT under sustained load:

| RTT | Approximate ACK-paced ceiling |
|---:|---:|
| 50 ms | 20 renders/s |
| 100 ms | 10 renders/s |
| 200 ms | 5 renders/s |

This is a protocol-derived estimate, not a measured WAN result. Rendering cost and batching can lower it.

An input arriving while an old render awaits acknowledgement can incur another credit cycle. Therefore do **not** promise “RTT plus a few milliseconds” for every keystroke under sustained rendering.

Proposed targets:

- Uncongested `daemon.status`: p95 ≤ RTT + 10 ms, excluding reconnect.
- Input-to-visible-echo with no prior render outstanding: p95 ≤ RTT + 20 ms.
- Credit-blocked echo under load: p95 ≤ 2 × RTT + 20 ms.
- UI input/focus handling remains local and responsive regardless of network RTT.
- Cancellation and host switching do not wait for a remote request timeout.
- Control/input enqueue delay introduced by upload traffic: p95 ≤ 10 ms before transport writing, under the test fixture.

These are acceptance budgets, not established performance claims.

### Local scheduling improvements, no wire change

1. Preserve credit-1 and latest-state coalescing.
2. ACK promptly after a render is safely applied to the client model; do not wait for an unrelated animation/timer.
3. Prioritize input/ACK/control over **unsent** bulk upload chunks.
4. Bound bytes as well as message count. A 1,024-message queue containing near-4-MiB frames is not a useful remote memory budget.
5. Proposed outbound byte cap: 8 MiB per remote connection, with accounting for queued and currently written frames.
6. Keep attachment chunks small enough to limit head-of-line blocking.
7. Avoid attaching all hidden terminals unnecessarily; preserve their host state and fetch/reattach on focus.
8. Keep PTY ingestion independent of a slow remote renderer.
9. Do not replay user mutations automatically after an ambiguous transport failure.

A partially written frame cannot be preempted without corrupting the stream. A large snapshot/history response can therefore delay subsequent traffic even with fair scheduling. Bound/paginate bulk responses; proxy copy chunk size alone cannot solve frame-level head-of-line blocking.

## 14. Prototype and measured round trips

### SSH availability

Executed a noninteractive probe:

```text
ssh -T \
  -o BatchMode=yes \
  -o StrictHostKeyChecking=yes \
  -o ConnectTimeout=3 \
  -o ConnectionAttempts=1 \
  -o ControlMaster=no \
  -o ControlPath=none \
  localhost true
```

Observed:

```text
ssh: connect to host localhost port 22: Connection refused
exit status 255
```

No prompting or SSH-server configuration was attempted. **The experiment therefore simulated the SSH stdio leg with ordinary process pipes. It did not measure SSH encryption, network RTT, bastions or remote bootstrap.**

### Setup

- Existing `target/debug/hutand`, reporting daemon version `0.1.0`, protocol `0.29`.
- `HUTAN_HOME=$(mktemp -d ...)` assigned inline when starting it.
- `HOME`, XDG config and XDG data redirected into the isolated temporary experiment directory.
- A tiny Rust bridge compiled with `rustc -O`.
- Two paths:
  1. Python harness → Unix socket → isolated daemon.
  2. Python harness → process stdin/stdout pipes → Rust byte bridge → same isolated daemon.
- Real framed `hello` and sequential `daemon.status` requests.
- 20 warm-up requests, then 1,000 measured requests per path.
- Timing used a monotonic high-resolution clock; each interval included writing the request and reading/decoding the complete response.
- Response IDs, absence of protocol errors, control-frame kind and payload bounds were checked.

The bridge’s essential implementation was:

```rust
use std::io::{self, Read, Write};
use std::net::Shutdown;
use std::os::unix::net::UnixStream;
use std::thread;

fn main() -> io::Result<()> {
    let path = std::env::args().nth(1).expect("socket");
    let mut tx = UnixStream::connect(path)?;
    let mut rx = tx.try_clone()?;

    let input = thread::spawn(move || -> io::Result<()> {
        io::copy(&mut io::stdin().lock(), &mut tx)?;
        tx.shutdown(Shutdown::Write)
    });

    let mut out = io::stdout().lock();
    let mut buf = [0u8; 32768];
    loop {
        let n = rx.read(&mut buf)?;
        if n == 0 { break; }
        out.write_all(&buf[..n])?;
        out.flush()?;
    }
    if input.is_finished() {
        input.join().expect("copy thread")?;
    }
    Ok(())
}
```

This is an experiment, not the proposed production implementation: production should use cancellable Tokio copies, bounded draining, defined exit behavior and structured error handling.

### Results

Successful corrected run, milliseconds:

| Path | Samples | p50 | p95 | p99 | Min | Max |
|---|---:|---:|---:|---:|---:|---:|
| Direct Unix socket | 1,000 | 0.157167 | 0.495584 | 1.133458 | 0.087916 | 2.037125 |
| Rust stdio pipes → socket | 1,000 | 0.157417 | 0.423375 | 0.942583 | 0.100000 | 2.057125 |

Hello round trip:

- Direct: **1.949667 ms**.
- Stdio bridge: **483.375375 ms**, including first bridge process startup/readiness in the measured handshake interval.

Do not subtract these percentile values to claim an accurately measured bridge overhead. This is one sequential local experiment on a shared workstation; the lower pipe-tail values reflect run variability, not evidence that a proxy is faster.

### Discovered buffering pitfall

An initial implementation used `io::copy(..., stdout.lock())` without explicit per-read flushing. It completed the direct-socket measurements but stalled on the bridge handshake and timed out after 30 seconds.

The corrected bridge explicitly flushed each output chunk and completed both paths. This is directly relevant to a binary stdio proxy: line-buffered stdout can hold a valid frame indefinitely when it contains no newline.

The timed-out attempt’s processes were inspected before retry; no matching experiment bridge/daemon remained. The successful run terminated its isolated daemon and bridge, and the entire temporary experiment directory was removed.

### What the prototype establishes

- Hutan’s existing frame bytes can traverse stdin/stdout pipes and a local byte bridge unchanged.
- No protocol-specific proxy framing is needed.
- Correct buffering/flush behavior matters.
- Steady-state local request/response latency through this bridge was sub-millisecond at p95 in this run.

It does **not** establish remote security, system-SSH performance, high-RTT usability, cross-platform behavior or release-install reliability.

## 15. E2EE relay: later, not “TLS to the broker”

Orca’s relay is a useful separation-of-authority reference:

- Cloud control uses authenticated WebSocket connectivity.
- Its control connection disables compression, limits payloads to 64 KiB and has a 15-second connect deadline.
- End-to-end session cryptography binds protocol/context/transport and relay host identity into a transcript.
- HKDF derives directional keys and a session identity.
- Encrypted records validate direction, payload kind and strict expected counters.

Sources:

- `src/main/runtime/mobile-cloud-relay/relay-control-client.ts:28,61-67`.
- `src/shared/mobile-e2ee-v2-contract.ts:7-40,110-145`.
- `src/shared/mobile-e2ee-v2-node-key-schedule.ts:13-32`.
- `src/shared/mobile-e2ee-v2-framing.ts:12-59,76-91`.

### Recommended Hutan design

First evaluate **end-to-end TLS 1.3 over an opaque relay byte stream**, reusing paired-device mTLS and host pins:

```text
device
  -> outer WSS to broker
  -> opaque bounded byte tunnel
  -> inner mTLS terminated only by hutand
  -> unchanged Hutan frames
```

The broker must not terminate inner TLS. Outer TLS authenticates the broker; inner mTLS authenticates the Hutan host/device.

Advantages:

- Reuses direct-TLS enrollment and revocation.
- Avoids inventing a separate application cryptographic protocol.
- Preserves stream framing and established replay boundaries.

Costs:

- TLS-over-WebSocket adapters need correct backpressure and close semantics.
- Additional handshake latency.
- Routing, rendezvous tickets and mobile clients remain substantial work.

Proposed broker envelope, separate from Hutan protocol:

```text
host.register { relay_host_id, generation, account_authorization }
device.open   { relay_host_id, one_time_ticket }
tunnel.ready  { tunnel_id, generation }

binary tunnel records -> opaque inner TLS bytes
```

Use short-lived tickets, bounded tunnel queues, connection quotas, generation checks, reconnect jitter and no payload compression by default. The broker can deny service and observe endpoint/timing/size/account metadata; E2EE does not hide those facts.

If future mobile/browser constraints require an application E2EE record protocol instead, select a reviewed construction under a separate ADR. Orca is a reference for transcript binding, directional keys, anti-replay counters and fresh session state—not justification for copying custom cryptography unreviewed.

Relay authorization never grants execution authority by itself; inner paired-device authentication does.

## 17. Risks and decisions

| Risk | Mitigation |
|---|---|
| Network failure interpreted as process exit | Evidence-based contact states; preserve stale session state. |
| Remote host accidentally stopped by local close behavior | Host-qualified lifecycle policy; remote stop always explicit. |
| Wrong-host commands after switching/reconnect | Host-qualified references, expected host identity and generation fencing. |
| SSH shell injection or stdout contamination | Argv locally; correct remote quoting; fixed bridge command; no PTY; strict first-frame validation. |
| SSH/TLS revocation confusion | Explain SSH account authority separately from paired-device access. |
| Same-user malware | State the limit: daemon control is user-level authority; vaults do not neutralize malware in an unlocked account. |
| Exposed TLS enrollment surface | Disabled by default; temporary restricted listener; high-entropy secret, pinning, confirmation and quotas. |
| High-RTT terminal choppiness | Measure credit-1 explicitly; do not promise impossible frame rates. |
| Bulk traffic starving input | Byte budgets, bounded chunks and priority before frames begin writing. |
| Upgrade kills long jobs | Explicit restart consent and restore semantics; no fictional seamless handoff. |
| Remote storage mistaken for laptop-local data | Persistent host context and local default assistant; explicit transfers only. |
| UDS watchdog kills otherwise reachable TLS host | Multi-listener supervision before TLS release. |

## 18. Slice breakdown and acceptance tests

These slices are implementation proposals. Only the prototype in §14 was exercised during this research.

### RM-1 — Transport-neutral local connection

- Generalize client and daemon framed I/O.
- Move OS peer authentication into the local acceptor.
- Introduce typed endpoints and local-only autostart.
- Preserve protocol and local defaults.

Acceptance:

- Existing framing/handshake/replay/snapshot fixtures remain unchanged.
- Different-UID/unavailable-peer-credential local connections are rejected before hello.
- Partial reads/writes and frame boundaries split arbitrarily are handled.
- Cancellation closes both loops and does not leak transport tasks.
- Nonlocal endpoint types cannot invoke local autostart.
- Existing local IPC performance budget is retained.

### RM-2 — Byte proxy and system SSH

- Implement `hutan proxy`.
- Add supervised SSH transport and bounded diagnostics.
- Add explicit CLI host profiles and connection errors.

Acceptance:

- End-to-end real SSH fixture carries all existing frame kinds byte-for-byte.
- Proxy stdout contains no diagnostic/banner bytes.
- No PTY requested.
- Missing daemon fails without starting it.
- EOF, half-close, daemon death, SSH death and cancellation terminate/reap correctly.
- ProxyJump and agent-authenticated fixtures work without agent forwarding.
- Unknown/changed SSH keys fail closed.
- Shell stdout pollution produces an actionable error.
- Slow reader memory remains bounded.

### RM-3 — Identity and multi-host desktop

- Add `host.identity`.
- Host catalog and Hosts switcher.
- Host-qualified state, layouts, actions and notifications.
- Evidence-based status states.

Acceptance:

- Two hosts can expose identical session/terminal IDs without cross-routing.
- Switching hosts during a pending action cannot redirect it.
- Wrong installation ID prevents replay, mutations and store installation.
- Network failure leaves sessions stale, not exited.
- Removing a profile does not stop remote sessions.
- Local window close sends no remote shutdown.
- Older local daemons remain compatible.

### RM-4 — Explicit remote installation and upgrade

- Publish supported headless artifacts and signed manifests.
- Stage/lock/verify/activate installations.
- Explicit start/restart/upgrade operations.

Acceptance:

- Interrupted upload cannot replace the current installation.
- Corrupt/unsigned/wrong-target artifacts are rejected.
- Concurrent installs serialize.
- Existing data and installation identity survive binary replacement.
- Live sessions trigger explicit restart consequences.
- No restart on normal connect.
- Storage-incompatible rollback is refused rather than attempted blindly.

### RM-5 — Host-correct files and uploads

- Separate laptop files from daemon paths.
- Add bounded upload methods and uploaded attachment references.
- Remote file chooser and explicit download behavior.

Acceptance:

- A laptop path cannot accidentally read a same-named remote file.
- Uploaded attachment produces the same validated content as a local attachment.
- Cross-device upload IDs are rejected.
- Traversal filenames cannot choose a destination.
- Oversize/hash/MIME failures delete staging data.
- Quotas and expiry bound disk use.
- Unsupported old daemon gets an explicit unavailable feature, not path fallback.

### RM-6 — TLS pairing and device security

- rustls listener, encrypted key storage, pairing, revocation.
- Multi-listener supervision and restricted enrollment dispatch.

Acceptance:

- Unpaired clients cannot reach ordinary RPCs or terminal input.
- Wrong host pin, expired invitation, replayed invitation and mismatched CSR proof fail.
- Enrollment cannot invoke `daemon.shutdown` or other normal methods.
- Revoking a device closes active connections and rejects resumed/new ones.
- Private keys and invitation secrets are absent from DB plaintext, logs and traces.
- Unavailable secret storage fails closed.
- Local IPC removal does not incorrectly declare a live TLS host stopped.

### RM-7 — WAN behavior and bounded scheduling

- Byte-accounted queues and interactive scheduling.
- RTT/loss fixtures at 0, 50, 100 and 200 ms.
- Multiple visible/hidden terminals plus attachment upload.

Acceptance:

- Meet or explicitly revise the §13 latency targets using measured results.
- Credit-1 is preserved; PTY ingestion is not stalled by remote rendering.
- Memory remains within configured queue budgets.
- Control overflow disconnects only the affected client and recovers through replay/snapshot.
- Upload traffic cannot monopolize the next unsent frame.
- Ambiguous mutation failures are not automatically retried.

### RM-8 — Relay, after its security ADR

- Opaque WSS tunnel with inner mTLS.
- Account/rendezvous separation, quotas and reconnect generations.
- No broker-side execution or plaintext access.

Acceptance:

- Broker capture cannot decode Hutan payloads.
- Wrong host/device keys fail despite valid relay account credentials.
- Ticket replay, stale generation and revoked device fail.
- Tunnel buffering is bounded under a stalled peer.
- Reconnect establishes fresh inner TLS state and uses normal Hutan replay/snapshot recovery.
- Metadata and availability limitations are documented honestly.

## Conclusion

Hutan already has the difficult application-level ingredients: a versioned framed stream, replay/snapshot recovery, bounded connection queues and a reconnecting client abstraction.

The clean first step is therefore small in architectural scope: **authenticate and obtain a byte stream, then run the existing protocol over it**. System SSH plus a byte-only `hutan proxy` delivers remote execution without opening a daemon port or importing an SSH stack.

The larger correctness work is around that stream: host-qualified UI state, stable identity, truthful disconnect/shutdown semantics, explicit upgrades, remote-file ownership and high-RTT expectations. TLS should reuse those foundations and add real device pairing and encrypted key custody. A later relay should broker opaque, end-to-end-authenticated bytes—not become another source of truth.
