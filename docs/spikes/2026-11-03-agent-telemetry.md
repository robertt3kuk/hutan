# Spike: how any agent hands Hutan its stats — OpenTelemetry and a public report contract (SPIKE-AGENT-TELEMETRY)

Date: 2026-11-03 · Question (user, 2026-11-03): *"how will the others give their stats — let's do it for the popular ones, Claude Code and Codex first, then a generic channel for the rest"* · Feeds: ADR 0026 (proposed, `docs/adr/0026-agent-telemetry-receiver.md`), slices TEL-0…TEL-4 (§ 6) · Siblings: INSIGHT-C (transcript tails for Claude Code and Codex), `docs/spikes/2026-10-28-insight.md` (what each harness exposes), `docs/spikes/2026-10-20-laminar.md` § 6 (a bounded OTLP receiver was proposed there as TR-1 for a Traces page)

Method: official documentation and upstream source (dated links in § 8), and **runs of the real binaries** in scratch `HOME`s with no login, a dead `HTTPS_PROXY` (`127.0.0.1:9`, so nothing left the machine) and a **local mock model API** on loopback (no model, no account, no cost). Every agent that could be installed without an account was driven through one turn with a tool call while a prototype OTLP/HTTP receiver recorded what it sent. Prototype and sanitised recordings: `docs/spikes/2026-11-03-agent-telemetry/` (`prototype/`, `fixtures/`); the working copy was `~/hutan-scratch/agent-telemetry/` (installs removed afterwards).

Evidence tags: **R** observed in this spike (real binary, version named) · **D** official documentation · **S** upstream source read · **I** inference · **U** unverified. Payload numbers are those of the mock (e.g. 11 000 input tokens) — they prove shape and arithmetic, not any agent's real accounting.

## Summary

1. **Eight agents export OpenTelemetry on their own and all eight were observed sending payloads** (**R**): Claude Code 2.1.316, Codex 0.166.0, OMP 18.14.1, Gemini CLI 0.66.0, Qwen Code 0.26.6, Copilot CLI 1.0.105, Goose 1.57.0, OpenCode 1.19.5. Cursor CLI, Amp and Aider have **no OTel** (**D**, absence not proven for Cursor/Amp); they offer hooks (Cursor), `--stream-json` (Amp, Cursor) and a local analytics log (Aider).
2. **Wire formats differ more than the standard suggests:** protobuf from Claude Code, Codex, OMP, Goose and Copilot (with an env var); **JSON only** from Gemini, Qwen and OpenCode; **chunked bodies without `Content-Length`** from OMP, Gemini, Qwen and OpenCode's traces; no agent compressed. A receiver needs protobuf **and** OTLP-JSON and chunked decoding (gzip: bounded, for agents not seen here); it does not need gRPC.
3. **Is an env var set by the terminal enough?** Yes for Claude Code, OMP, Gemini, Qwen, Copilot, Goose, OpenCode (the last needs one config flag, which `OPENCODE_CONFIG_CONTENT` can carry). **No for Codex:** only `config.toml`/`-c` enables it and the endpoint is read from the config alone (**R**); per-session secrets can still arrive by env (`OTEL_EXPORTER_OTLP_LOGS_HEADERS`, `OTEL_RESOURCE_ATTRIBUTES` are honoured, **R**). **Claude Code's own `~/.claude/settings.json` `env` beats the terminal's environment** (**R**), and managed settings beat both (**D**).
4. **What arrives:** tokens (in, out, cache read/write, reasoning), model, tool name + duration + success and turn boundaries from every agent; **cost** only from Claude Code (per request, an estimate) and OMP (estimate); **context used and window** only from Copilot CLI (a span event) — Claude Code and Codex give none (Codex's rollout does); **files changed** from none in a usable form (counts only). Claude Code and Codex are therefore *not* better served by OTLP than by their transcripts; what OTLP adds there is a **push** (≈ 1 s, no polling, no coupling to the file format).
5. **Hazards measured:** Codex's trace exporter sends **every internal Rust tracing span** (198 KB + 38 KB for one two-call turn) and its log events carry tool **arguments and output** with prompts redacted (**R**); Gemini exports system instructions and the `-p` prompt (in the resource's `process.command_args`); OpenCode exports `ai.prompt` with no gate; Qwen exports `function_args`. And a receiver that *accepts but never answers* delays agents' exits (**Codex +33 s, Claude Code +2 s**), while a closed port costs +1.3 s (Codex) and nothing (Claude Code).
6. **Recommendation:** build the receiver as Hutan's **generic channel** (off by default, per agent, loopback, per-session token, allowlisted attributes, bounded, always answering at once; ADR 0026 *proposed*), **keep transcripts (INSIGHT-C) as the primary source for Claude Code and Codex** and let OTLP push the same numbers when the user opts in, and publish the contract of § 5 (L0 recognised · **L1 OSC 7501** state · **L2 `hutan agent report --insight-json`** insight · **L3 OTLP** with the GenAI semantic conventions) so any other agent can join without a Hutan-side parser.

## 4. Question 3 — design

### 4.1 Alternatives

| Option | What it gives | What it costs / cannot do |
|---|---|---|
| **Transcripts only** (INSIGHT-C; Claude Code, Codex, later Qwen/Copilot/Gemini files) | exact tokens, context window (Codex rollout), Claude `cost-state`, tools, files from edit tools; no listener; works for agents started anywhere | needs `[history]` consent per agent; one parser per format and the record types move between versions (Claude Code 2.1.316 writes `api-request`, `api-request-blob`, `atis-latch`, `cost-state`; Codex 0.166 writes `token_usage_record`); files appear after the fact (seconds); SQLite stores (OpenCode, Goose, Cursor) need schema knowledge |
| **`hutan agent report --insight-json`** as *the* public contract | works for every agent that can run a command from a hook, wrapper or `--stream-json` loop; no new surface; already shipped | someone must write the glue per agent; unavailable inside Contain (socket refused) and across `ssh`/containers (no socket); 4 KiB per report |
| **OSC 7501** (state) | state, kind, app, message, with no setup, through `ssh`, containers, tmux; shipped | OMP's protocol: no usage fields (**S** in the INSIGHT-SPIKE; the `7501;` string is in the OMP binary); any program writing to the terminal can lie within its own session (same for hooks) |
| **OTLP receiver in `hutand`** | eight agents' tokens/tools/model/time live with a few env lines and no per-agent file parser; standards-based, so *future* agents arrive free; works in Contain with network on; per-session by token | the **first TCP listener in the daemon** (new attack surface: § 4.3); enablement differs per agent (§ 4.4); attribute names are agent-private and drift; content leaks to be filtered (F8); the user's own OTel destination cannot be served at the same time |
| **Hybrid (recommended)** | OSC 7501 for state, `hutan agent report` for insight from glue code, transcripts for Claude Code/Codex, OTLP as the generic channel and the live upgrade | four routes → the existing per-block *best source wins* rule (INSIGHT-B) must rank them and never **add** counters from two sources (§ 4.2 rule 8) |

### 4.2 The receiver (what ADR 0026 decides)

1. **Where.** Decode and mappers in a pure service crate (`crates/telemetry`: `prost` subset + `serde_json`, no sockets, no daemon types); the **listener, token registry and settings** in `hutand` (`crates/daemon/src/telemetry/`). `hyper` (http1 server, already locked via `reqwest`) rather than a hand-rolled HTTP parser: chunked decoding (F6), header limits and read timeouts come with it. No gRPC (F7 shows no agent needs it), no TLS (loopback).
2. **Off unless asked.** No socket exists until the user enables an agent (`[telemetry.agents] claude = true` in `daemon.toml`, Settings → Integrations, `hutan telemetry enable claude`). User-only setting, like every `daemon.settings.set`: an agent (MCP, `hutan ui`) cannot turn it on. The listener is bound lazily when the first agent is enabled and closed with the last. `[telemetry] port` is `0` (pick once, persist) or a number; **Codex needs a stable port** because its endpoint lives in a config file (F4, § 4.4); if the persisted port is busy at start the receiver stays down and says so (`hutan telemetry status`, `hutan integration status`) — it never silently re-binds elsewhere.
3. **Bind** `127.0.0.1` only (not `localhost`: no `::1`/DNS ambiguity, no `0.0.0.0`); a restart-friendly bind on the persisted port is a slice detail.
4. **Who can post, and as whom.** Each session gets a **128-bit random capability** when it is spawned: in memory only, never in SQLite, events, logs, `hutan ps` output, argv or notifications; a new spawn (including a restored terminal after a restart) gets a new one. It is accepted in the URL path (`/s/<token>/v1/{traces,logs,metrics}`; all agents append `/v1/<signal>` to a base endpoint, F1) **or** in a header (`x-hutan-token`/`Authorization: Bearer`, constant-time compare) for agents whose endpoint is fixed (Codex, F3/F4). The token selects the session; **nothing in the payload selects one**: `session.id`, `conversation.id`, `hutan.session` are untrusted labels (the agent's own id is kept only to tell two agents in one terminal apart and to cross-check what the hooks reported).
5. **Reject at once, cheaply.** In this order, before reading a body: method `POST`; `Host` in {`127.0.0.1`, `localhost`} (421); `Content-Type` in {`application/x-protobuf`, `application/json`} (415) — a web page can POST to loopback only with "simple" types, so it fails here, and without the token it fails anyway; path/token (401, identical response for every failure); size. Answer **immediately** with `200` + the signal's empty `Export*ServiceResponse` (or the `partial_success` with the rejected count), never hold a connection while mapping (F5).
6. **Bounds.** Header block ≤ 8 KiB; body ≤ 1 MiB on the wire and ≤ 4 MiB inflated (gzip decoded with a limit, F9); ≤ 2 000 records per request and ≤ 64 attributes per record considered, strings cut at 256 characters; ≤ 16 connections, ≤ 4 per session; a token bucket per session (≈ 20 requests/s, 1 MiB/s); read timeout 2 s, keep-alive idle 30 s; a **bounded** channel (64 requests) from the HTTP tasks to one mapper task — when full the request is answered `429` with `Retry-After: 1` and counted, never queued without bound. State per session: one reducer record (the existing `AgentInsight` reducer, ≈ 85 KiB at the caps).
7. **Allowlist, not denylist (F8).** The mappers name every attribute they read; the decoder skips everything else without materialising the string. Content-bearing names (`prompt`, `arguments`, `output`, `ai.prompt*`, `gen_ai.input.messages`, `gen_ai.system_instructions`, `process.command_args`, `function_args`, `tool_input`, `user.email`) are not on any list. Hutan **also** switches each agent's content gates off in the environment it injects (§ 4.4), as defence in depth, never as the control. Nothing is persisted beyond the in-memory insight record; raw payloads are dropped after mapping; nothing is forwarded (**nothing leaves the machine**: the daemon only receives; Hutan never injects a non-loopback endpoint).
8. **Output = `InsightReport` with a new `source: otlp`** (additive minor, capability `agent.telemetry`), through the same reducer as hooks/extension/status line. **Telemetry carries no authority:** it cannot set an agent's state, approvals, tasks, notifications or grants (state stays with OSC 7501 and hooks); it only fills insight blocks. Ranking per block: the best-source rule decides; **counters from two sources are never summed** — a block (e.g. `totals`) is written by one source, chosen by `as_of` and exactness, and OTLP deltas are keyed by the agent's request id to survive retries.
9. **Identification.** `service.name` picks the mapper (`claude-code`, `codex_exec`/Codex's interactive name **U**, `oh-my-pi`, `gemini-cli`, `github-copilot`, `goose`, `opencode`, Qwen's **U**); an unknown `service.name` goes to the generic GenAI mapper (§ 5), and an unknown span/log/metric inside a known service is ignored. Mappers are versioned per agent and tested against recorded fixtures (`fixtures/` here are the first set); a payload shape that stops matching degrades to "not reported", never to zeros.
10. **Failure never reaches the user's agent.** No receiver, a full queue, a disabled agent: every case is a fast HTTP status; the agents ignore them (F5, F9).

### 4.3 Threat model

| Threat | Who | Control | Residual |
|---|---|---|---|
| Another user on the Mac posts or probes | other UID | loopback only, unguessable path/header token, no information in rejections, no read API on the port | a local user can see that *something* listens (`lsof`) |
| A web page posts through the user's browser | browser | `Host` check (rebinding), content types a page cannot send without preflight, token | none known |
| A process in session A reports as session B | same UID, other session | per-session tokens; payload ids ignored | a same-UID process can probably read B's token from B's environment (`ps eww`, **I**); same trust boundary as the daemon's own unix socket (`HUTAN_SESSION_ID` is not secret there either) — no new boundary crossed |
| A contained agent (Seatbelt, network on) | a process Hutan restricts | loopback TCP is reachable (docs/agents.md § Contain), so the parser *is* exposed to it: limits, allowlist, no authority, a fuzz target for the decoder (TEL-1) | it can only misreport its own session's stats |
| Resource exhaustion | any holder of a token | § 4.2 rule 6; one reducer per session; nothing persisted | a noisy agent loses data (counted, shown in `telemetry status`), never stalls the daemon |
| Content/secret leaks into Hutan | the agents | allowlist, gates off, no persistence, no forwarding | the reducer holds tool names and counts only |
| Hutan hijacks the user's own OTel apps | Hutan | **never export `OTEL_*` into every PTY** (a dev server run in that shell would send its spans to Hutan and lose its own collector); enable per agent and per launch (§ 4.4) | a user who already sets `OTEL_*` for an agent keeps it: Hutan detects and does not override, `hutan integration status` says "telemetry goes to your own endpoint" |
| A corrupted hook script prints a fake `HUTAN_OTLP_TOKEN` | same UID | token validated against the registry only | — |

### 4.4 Enabling it per agent (launch-scoped, never global)

`HUTAN_OTLP_ENDPOINT` (`http://127.0.0.1:<port>/s/<token>`) and `HUTAN_OTLP_TOKEN` are exported into a session's PTY **only while telemetry is on** (non-standard names: nothing reads them by accident, so no hijack). What *starts* an agent's export differs:

| Agent | Mechanism | Evidence |
|---|---|---|
| Claude Code | a shell function for `claude` (installed by the existing shell integration, bash/zsh/fish) that sets `CLAUDE_CODE_ENABLE_TELEMETRY=1 OTEL_LOGS_EXPORTER=otlp OTEL_METRICS_EXPORTER=otlp OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf OTEL_EXPORTER_OTLP_ENDPOINT=$HUTAN_OTLP_ENDPOINT` **for that command only** and leaves every `OTEL_*` the user set alone; **or** `hutan integration install claude --telemetry`: user settings `env` + `otelHeadersHelper` (F2, F3) for Claude started outside a Hutan shell. If the user's settings already name an OTLP endpoint (F2) or managed settings exist, Hutan skips and says so | R |
| Codex | a shell function adding `-c 'otel.exporter={otlp-http={endpoint="http://127.0.0.1:<port>/v1/logs",protocol="binary"}}' -c 'otel.trace_exporter="none"' -c 'otel.metrics_exporter="none"' -c otel.log_user_prompt=false` and `OTEL_EXPORTER_OTLP_LOGS_HEADERS=x-hutan-token=$HUTAN_OTLP_TOKEN`; or a `[otel]` block in `~/.codex/config.toml` (fixed port) with the header from env. `${VAR}` is not expanded, so the token **cannot** live in the file | R |
| Gemini CLI | `GEMINI_TELEMETRY_ENABLED=true GEMINI_TELEMETRY_TARGET=local GEMINI_TELEMETRY_OTLP_PROTOCOL=http GEMINI_TELEMETRY_OTLP_ENDPOINT=$HUTAN_OTLP_ENDPOINT GEMINI_TELEMETRY_LOG_PROMPTS=false` (all agent-specific names: safe to set in the PTY env) | R |
| Qwen Code | `QWEN_TELEMETRY_ENABLED=true QWEN_TELEMETRY_OTLP_PROTOCOL=http QWEN_TELEMETRY_OTLP_ENDPOINT=$HUTAN_OTLP_ENDPOINT QWEN_TELEMETRY_LOG_PROMPTS=false` | R |
| Copilot CLI | `OTEL_EXPORTER_OTLP_ENDPOINT=… OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf` (standard names → function wrapper) | R |
| Goose, OMP | standard `OTEL_*` (function wrapper) | R |
| OpenCode | `OTEL_EXPORTER_OTLP_ENDPOINT` + `OPENCODE_CONFIG_CONTENT='{"experimental":{"openTelemetry":true}}'` (**U** whether it merges with the user's own inline config) | R |
| Cursor CLI, Amp, Aider | no OTLP: `hutan agent report` from a hook (Cursor), a `--stream-json` loop (Amp, Cursor), `--analytics-log` tailer (Aider) | D |

Shell functions only see launches from an interactive Hutan shell (not `npx claude` from a script, nor an editor's task runner); the `--telemetry` config install covers those for the two agents where it works, the rest are left out with a visible "not reporting" in `hutan integration status`. A PATH shim directory is the alternative with wider reach and more moving parts; left to the slice.

Remote and containers: `127.0.0.1` inside a container or an `ssh` session is not the daemon's. Those need **OSC 7501** (state) and, if worth it, an `insight=` extension of it (§ 5), or a forwarded port (`hutan host forward`, ADR 0022) — not solved here.

## 5. Question 4 — "Report your agent's stats to Hutan": the public contract

For third parties (agent authors, wrapper scripts, plugin writers). Goes into `docs/integrations.md` as its own section (slice TEL-0); each level works alone and adds to the one below.

| Level | Transport | Carries | You do |
|---|---|---|---|
| **L0 — recognised** | nothing | the program is known by name (`omp claude codex gemini opencode aider`), its title and a spinner become *working/idle* | nothing |
| **L1 — state** | **OSC 7501** on the terminal: `ESC ] 7501 ; state=<working\|blocked\|done\|error\|idle> :kind=… :app=<name> :msg=<base64> ESC \` and `state=clear` at exit (shipped, `docs/integrations.md` § Agents that report in the terminal) | state, what a *blocked* agent waits for and the question, the error, the app name; ≤ 8 KiB; works over `ssh`, containers, tmux | print the sequence |
| **L2 — insight** | **`hutan agent report --source S --agent A [--state …] --insight-json JSON\|-`** (exit 0 always, 200 ms, only inside a Hutan session; hooks call it) | `InsightReport` (≤ 4 KiB; `docs/schemas/agent-insight-report-v1.json`): `turn{phase,outcome?,duration_ms?}`, `tokens{input_tokens,cached_input_tokens,cache_write_tokens,output_tokens,reasoning_output_tokens,total_tokens}` (a **delta** per model call; a counter you do not know stays out, never 0), `context{used,window?,fixed?,estimated?}`, `cost_usd` (cumulative), `api_ms`, `tools[{name,calls,failed,ms}]`, `files[{path,kind}]` | call it from a hook or wrapper; validate against the schema (TEL-0) |
| **L3 — OpenTelemetry** | **OTLP/HTTP** (protobuf or JSON) to `$HUTAN_OTLP_ENDPOINT`, token already in it | what the agent already emits following the **GenAI semantic conventions**, below | read the env var and set your exporter's endpoint (`OTEL_EXPORTER_OTLP_ENDPOINT=$HUTAN_OTLP_ENDPOINT`); no Hutan-specific code |

What L3 reads (everything else is discarded unread; omitting a field is always allowed):

| Hutan reads | From | Notes |
|---|---|---|
| model | `gen_ai.response.model`, else `gen_ai.request.model`; `gen_ai.provider.name` | |
| tokens | `gen_ai.usage.input_tokens`, `…output_tokens`, `…cache_read.input_tokens`, `…cache_creation.input_tokens`, `…reasoning.output_tokens` on `chat` spans (or the `gen_ai.client.token.usage` histogram) | say whether your `input_tokens` **includes** cached tokens with the resource attribute `hutan.usage.input_includes_cache = true\|false` (Claude Code excludes them, Codex/Gemini/OMP/OpenCode include them; the mappers carry a built-in answer per known agent) |
| tool | span with `gen_ai.operation.name = execute_tool`: `gen_ai.tool.name`, status or `error.type`, span duration | the tool's arguments/results are never read |
| turn | span `gen_ai.operation.name = invoke_agent` (start, end, status) | |
| conversation | `gen_ai.conversation.id` | label only |
| extensions (optional, `hutan.` namespace on the `invoke_agent` span or a `chat` span) | `hutan.cost.usd` (cumulative), `hutan.context.used_tokens`, `hutan.context.window_tokens`, `hutan.files.changed` (array of `"<kind>:<relative path>"`, ≤ 32) | the only way to give cost/context/files through L3 |

L2 and L3 are **untrusted input** like every agent report: bounded, redacted where a path or text is shown, never put into notifications or user hooks (`docs/integrations.md` § Insight). Wait for a third party that needs it.

## 6. Question 5 — recommendation and slice plan

**Build it, as the generic channel, behind per-agent opt-in** — and say plainly what it is *not*: not the primary source for Claude Code and Codex.

- **Why a receiver at all.** Six agents (Gemini, Qwen, Copilot, Goose, OMP, OpenCode) have neither hooks nor a transcript parser in Hutan, and each has a different file format (JSONL, three SQLite schemas); their OTLP is already compact and observed (F1–F11). One mapper per agent over one listener is cheaper than one reader per file format, and it covers agents that do not exist yet.
- **Why not instead of transcripts for Claude Code and Codex.** The transcripts carry the rest of the story (Codex's context window, Claude's `cost-state` and file edits) and need no listener, no env and no per-launch enablement; INSIGHT-C is already building them. OTLP's gain there is **latency** (≈ 1 s vs the tail's polling) and independence from the file format.
- **Why not the receiver alone.** Cursor, Amp and Aider have no OTLP; `hutan agent report` (L2) is the universal fallback and costs no new surface.
- **What it costs:** the daemon's first TCP listener (ADR 0026 records the rules a review must hold), a dependency (`prost`), mapper maintenance per agent release (the same weekly drift the transcript readers have), and one more route in the best-source ranking.

| Slice | Content | Done when |
|---|---|---|
| **TEL-0** *(docs + tests, no listener; do first)* | `docs/integrations.md` § "Report your agent's stats to Hutan" (§ 5 above), JSON Schema of `InsightReport`, conformance tests that feed `hutan agent report --insight-json` examples through the real CLI + daemon | a third-party example script passes; schema checked in CI |
| **TEL-1** *(ADR 0026 accepted)* | `crates/telemetry` (prost subset, OTLP-JSON, allowlist mappers: generic GenAI, Claude Code, Codex logs), daemon listener/token registry/limits, `[telemetry]` settings, `telemetry.status` request + capability `agent.telemetry` (protocol minor), `source: otlp`, `hutan telemetry status|enable|disable`; fixtures from `fixtures/` | real-socket tests: the F9 table, the F5 timing bound (a request is answered < 50 ms with the mapper stalled), fixture round-trips for Claude Code, Codex, generic; a fuzz target for the decoder |
| **TEL-2** | enablement for Claude Code and Codex: shell functions in the shell integration, `hutan integration install claude\|codex --telemetry`, conflict detection (user settings/managed settings/own `OTEL_*`), `hutan integration status` words | a real `claude -p` and `codex exec` under a test daemon with a mock API report tokens/tools/model; a conflicting config is reported, not overridden |
| **TEL-3** | mappers + recipes for Gemini, Qwen, Copilot (incl. context), Goose, OMP, OpenCode | each agent's fixture maps to the numbers in F11; unknown attributes ignored |
| **TEL-4** | Settings → Integrations → Telemetry (one toggle per agent, state, last report), Context panel source chip *OpenTelemetry*; CHECKS coverage words | UI check with a recorded session |
| **later** | Aider `--analytics-log` tail, Amp/Cursor `--stream-json` adapter (L2), OSC insight, optional forward to the user's own collector (the Laminar spike's TR-3) | on demand |

Coordination: the Laminar spike (`2026-10-20-laminar.md` § 6, MW-7 TR-1) already proposed "a bounded OTLP receiver". **One listener, two sinks**: whichever lands first owns `crates/daemon/src/telemetry/` and the limits; the other adds its sink (insight reducer vs trace store). INSIGHT-C is unaffected.

**Decisions for the user** (five):

1. **Receiver, yes or no?** Recommended: yes, off by default, per agent. The alternative is transcripts + L2 only and no TCP listener at all.
2. **For Claude Code and Codex: transcripts first, OTLP as the opt-in live upgrade?** Recommended yes (§ 6).
3. **How is it switched on in a terminal?** Recommended: shell functions for Hutan shells by default, plus the explicit `--telemetry` install for agents started elsewhere; never `OTEL_*` in every terminal.
4. **A stable port stored in `daemon.toml`** (needed for Codex's config file) — acceptable? Recommended yes, picked once at random in the ephemeral range.
5. **OSC 7501 `insight=` extension for remote agents:** defer until a third party needs it.
