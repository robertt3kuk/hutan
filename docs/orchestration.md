# Orchestration: projects, worktrees, session placement and tasks

Roadmap M7 and M18: automatic projects and user workspaces (slice M18-A, protocol 0.19, capability `projects.auto`; § Projects and workspaces below), worktrees and placement (slice M7-A, protocol 0.14, capability `worktree`) tasks with dependencies (slice M7-B, protocol 0.16, capability `task`; § Tasks below), and review, merge and the Tasks panel (slice M7-C, protocol 0.22, capability `worktree.review`; § Review and merge, § Tasks panel). Vision: placement is the user's choice — the repository's main checkout (one agent, quick fixes) or a git worktree (isolated parallel work); Hutan never forces a worktree, and it warns when two live agents write to the same checkout.

Wire details: `docs/protocol.md` § Worktrees and placement. Code: `crates/daemon/src/{worktrees,placement}.rs` (daemon), `crates/protocol/src/worktree.rs` (DTOs), `crates/cli/src/commands/worktrees.rs` (CLI), `crates/desktop/src/workbench/worktrees.rs` and `crates/desktop/src/sessions/placement.rs` (desktop).

## Principles

- **git is the source of truth.** Hutan runs `git worktree list --porcelain -z` for the repositories of a workspace and never keeps its own copy of what exists. It remembers one thing: which worktrees *it* created (SQLite table `worktrees`, migration 6), so that a UI can offer cleanup of those and leave the user's own worktrees alone.
- **The daemon owns it** (ADR 0001): creating, listing and removing worktrees, and deriving where sessions work. Clients only ask and render.
- **No network, no prompts.** Every git invocation has `GIT_TERMINAL_PROMPT=0`, `GIT_OPTIONAL_LOCKS=0` (listing never rewrites an index under a running agent), a timeout, and a closed stdin.
- **Never destructive by surprise.** Removing refuses the main worktree, live sessions, a locked worktree and uncommitted changes unless forced; `delete_branch` is `git branch -d`, never `-D`.

## Worktrees

A workspace's repositories are the git repositories its roots belong to; a root that is itself a linked worktree leads to its repository, and one repository reached twice is listed once.

| Operation | Behaviour |
|---|---|
| `worktree.create {workspace_id, repo?, branch, base?, path?}` | Creates a worktree at `path` (default `<parent of the main checkout>/<repo name>-wt/<branch with / replaced by ->`, e.g. `~/proj/hutan` + `slice/M7-A` → `~/proj/hutan-wt/slice-M7-A`). The branch is created from `base` (default `HEAD`) when it does not exist and checked out when it does; `base` is ignored for an existing branch. Refused: invalid branch names (`git check-ref-format --branch`), a `base` that is no commit, an existing path (`conflict`), a branch already checked out in another worktree (`conflict`, naming it). |
| `worktree.list {workspace_id?}` | Per repository the main worktree first, then the others in git's order, each with `branch?`, `head`, `main`, `created_by_hutan`, `dirty`, `live_sessions`, `locked`, `prunable`. |
| `worktree.remove {path, force?, delete_branch?}` | `git worktree remove`. Refused with `invalid_state` and the reason: the main worktree; live sessions in it (always, `force` does not override this); a locked worktree; uncommitted changes without `force`. With `delete_branch` the branch is deleted with `-d` afterwards; an unmerged branch stays, the answer says why (`branch_kept`), and the worktree is removed anyway. |
| `worktree.changed {workspace_id}` | Event after a create or remove, for every workspace with a root in the repository: list again. |

Creating and removing are serialised in the daemon. A repository that cannot be listed any more (its folder is gone) is skipped, not an error for the rest.

## Placement

`SessionInfo.placement` says where a session works: `{kind: main | worktree, root, branch?, shared_with}`.

- **Derivation.** From the session's live directory (OSC 7, so it follows `cd`), else its spec directory: the nearest ancestor containing `.git` is the checkout root. A `.git` directory means `main`; a `.git` file means a linked `worktree` when the private git directory it points to has a `commondir` (a submodule is `main`). The branch is read from that checkout's `HEAD`. No git process is spawned; the directory → checkout answer is cached (60 s, bounded) and cleared whenever `worktree.create` or `.remove` changes something. Sessions outside git have no placement.
- **`shared_with`.** The other live sessions that have an agent (`SessionInfo.agent`, any state; absent once the agent is gone) in the same checkout root — and only for a session that has an agent itself. Two agents in one checkout can overwrite each other's edits; a shell next to an agent is the usual and harmless case and is not flagged. The list is recomputed when an agent is reported or released, when a session changes directory or ends, and announced with the existing `session.updated` event for every session whose list changed.
- Nothing is forced: a session started in the main checkout while an agent works there is allowed, and merely marked.

## CLI

```text
hutan wt new <branch> [--ws ID|NAME] [--base REF] [--model MODEL] [--path PATH] [--repo PATH]
hutan wt ls [--ws ID|NAME] [--json]
hutan wt rm <path|branch> [--ws ID|NAME] [--force] [--delete-branch]
hutan new --worktree <branch> [--ws ...] [--title T] [--attach] [-- argv]
hutan ls
```

- The workspace is `--ws` (a workspace or a project), else `$HUTAN_WORKSPACE`, else the project of the current directory — the daemon finds it through the repository (`workspace.open`), so a linked worktree belongs to the project of its main checkout, and makes it when the directory has none yet (`wt ls` falls back to all workspaces in Home or the home directory; the others stop with a hint). When the current directory chose the project it also picks the repository (`--repo` overrides); otherwise the workspace's first git root is used.
- `wt new` prints the path of the worktree on stdout (`cd "$(hutan wt new feature/x)"`); `--json` prints `{"worktree": {...}}`.
- `wt ls` prints `BRANCH PATH STATE` (`main`, `hutan` = created by Hutan, `dirty`, `locked`, `prunable`, live session count); `--json` prints `{"worktrees": [...]}` with every field.
- `wt rm` takes a path (as written, or relative to the current directory) or a branch; a branch that exists in several repositories is a usage error listing the paths. `--delete-branch` reports a branch that stayed.
- `new --worktree <branch>` reuses the branch's worktree when there is one and makes it otherwise, then starts the session in it, in the workspace that contains the repository (it conflicts with `--cwd`). A branch checked out in the main checkout is refused.
- `hutan ls` has a `PLACE` column: `main`, `wt <branch>` (`wt (detached)`), `-` outside git, and `⚠ shared` appended while `shared_with` is not empty.

## Desktop

Deliberately small (the layout and panels are ADR 0010's business):

- Session rows (the `placement` row field, on by default) show the badge only when it is news (CL-SIDEBAR): `wt <branch>` for a linked worktree, or `main` while another live agent shares the main checkout; a session in the main checkout alone shows none (a one-line row). Tab tooltips keep `main` / `wt <branch>` (`docs/design.md` § session row); a warning border and `⚠` while the checkout is shared; the badge's tooltip names the checkout, branch and the sharing. A session outside git keeps the old folder-name label.
- Palette commands: **Worktree: New Terminal in Worktree…** (asks for a branch, reuses or creates its worktree in the active workspace's repository, opens a terminal there) and **Worktree: Remove…** (a picker of the removable worktrees of the active workspace, then a confirmation with a checkbox for deleting the branch; a worktree with uncommitted changes says so and the confirmation removes it with `force`).

## Projects and workspaces

ADR 0014, slice M18-A (protocol 0.19, capability `projects.auto`). Wire details: `docs/protocol.md` § Projects and workspaces (0.19). Code: `crates/daemon/src/{projects,placement,registry,project_migration}.rs`, `crates/cli/src/commands/{workspaces,projects}.rs`.

Sessions belong to a **project** without anyone opening one; the user's own **workspaces** collect projects deliberately. Both are `WorkspaceInfo` on the wire; the UI says *project* and *workspace*.

- **A project is a repository or a folder.** Identity = the git common directory of the deepest repository around the folder (`.git`, or a `.git` file's `gitdir:` → `commondir`, read from disk like placement; `placement::repository_of`), canonical. So the main checkout and every `git worktree` of it are one project, rooted at the main checkout; a submodule and a repository nested in another one's tree are their own projects; a folder outside git is its own project. `$HOME`, `/` and the Home folder are never projects — they are Home — and a repository *rooted in* `$HOME` (dotfiles) is ignored so it does not swallow every folder below it.
- **Projects are made automatically** (`[projects] auto = true`, default) by the daemon when a session, chat or task needs one: `session.create` / `chat.create` without `workspace_id` go to the project of their folder; so does a task of a workspace (the session's folder is in a member project). Restore keeps the stored assignment and re-derives it only when the stored project's folder is gone while the session's start folder still exists. `auto = false` brings back the old rule: Home, unless the client names a workspace (the desktop names the active one). An explicit `workspace_id` always wins. A session keeps the project it started in; where it is *now* is `SessionInfo.folder` (OSC 7), and `placement` (`main` / `wt <branch>`) tells which checkout.
- **A workspace is the user's container**: a name, a pin, an order, its own `.hutan/settings.toml` layer and layout, and member projects (`parent_id`; a project is in at most one workspace). One step to make one (`workspace.create {name, paths?, project_ids?}`), move a project in or out (`workspace.assign`), delete one without losing its projects (`workspace.delete`). A workspace's `roots`, session counts and activity are those of its projects.
- **Settings layering** (client side): user < workspace < project, where the project layer is `<project root>/.hutan/settings.toml` of the main checkout; a project in no workspace layers only its own.
- **Migration**: every earlier workspace stays a workspace and each of its folders becomes a member project (`project_migration.rs`, once, recorded in `app_meta.projects_auto`); nothing keyed by the workspace id changes and no session moves.

### CLI

- `hutan ws ls [--sort manual|recent|attention|name] [--all]` — the tree: workspaces, each with its projects (indented), then projects in no workspace, then Home. Empty loose projects are hidden unless pinned or `--all`; members and workspaces always show.
- `hutan ws new NAME [PATH…]` makes a workspace with the projects of those folders; `ws add WS PATH|PROJECT` adds a folder (its project is made if needed) or an existing project (a project of another workspace moves); `ws remove WS PROJECT` takes it out again; `ws rename|pin|unpin|rm|move|use` as before (`rm` deletes the workspace only, never its projects; `use` prints `export HUTAN_WORKSPACE=<id>`).
- `hutan project ls|open PATH|rename|pin|unpin|close|recent` — projects flat, with their workspace; `open` makes sure a folder has its project; `close` is refused while its sessions are live and keeps it in `recent`.
- `hutan ls` shows the PROJECT and FOLDER of every session next to its placement badge.
- A target (`WS`, `PROJECT`, `--ws`) is a full id, an exact name (then ignoring case) or an id prefix of at least 4 characters; a target of the wrong kind says what it is.

## Tasks

Slice M7-B (protocol 0.16, capability `task`). A task is a unit of work in a workspace: a title, an optional prompt, the tasks it depends on, where it runs (the main checkout or a worktree) and what it runs (a terminal command, or a chat with Codex, or with OMP or Claude Code over ACP). Tasks are daemon state in SQLite (migration 7: `tasks`, `task_deps`, `task_sessions`); the desktop panel is § Tasks panel. Wire details: `docs/protocol.md` § Tasks. Code: `crates/core/src/task.rs` (no I/O: states, readiness, cycles, ordering, the start queue), `crates/daemon/src/tasks.rs`, `crates/cli/src/commands/tasks.rs`.

### Life of a task

`todo → ready → running → (blocked) → done | failed | cancelled`. Only `todo`, `running`, `done`, `failed`, `cancelled` are stored; `ready` (every dependency `done`) and `blocked` (the running task's agent waits for the user) are derived when a task is shown. A cycle in the dependencies is refused and named; deleting a task others depend on needs `--cascade`.

- **Starting** (`hutan task start`, or by itself with `--auto`): the task becomes `running`, the placement is made (`main`: the workspace's git folder, with a warning when another live agent already works in that checkout; `worktree`: the existing worktree of the branch, else a new one through M7-A, branch default `task/<slug of the title>`), and a session starts there: a terminal running `argv` with `HUTAN_TASK_ID` set, a login shell when the task has no command, or a chat (Codex, `omp` or `claude`: `run: chat {agent}`) that gets the prompt as its first message. If the setup fails the task is back to `todo` and the error says why.
- **Finishing**: exit 0 → `done`, a non-zero exit or a failed session → `failed`, a stopped session → `cancelled`; an agent reporting through the integration hooks (`docs/integrations.md`) that goes idle after a working stretch → `done`, one that ends failed → `failed`; a chat turn that completes → `done`, fails or is cancelled → `failed`. `hutan task done` overrides. Dependants become `ready`.
- **Auto start**: a ready task with `auto_start` starts when fewer than `[tasks] max_parallel` (daemon.toml, default 3) tasks run; the rest wait in the order they became ready. Starting by hand ignores the limit.
- **Restart**: a running task whose session was restored stays running; any other becomes `failed` with outcome `interrupted`. The session that carried a task that failed this way lists it in `recovery.lost` (`task`).
- **Intents**: `task_done` / `task_failed` join the notification intents (`docs/protocol.md` § Notification intents) for the session that ran the task. They replace that session's own pending `session_exited_with_error` / `agent_finished` intent, so one task ending is one notification. Resetting an `auto` task whose dependencies are done starts it again right away.
- To run a finished task again, reset it (`hutan task reset`, or `task.update {state: todo}`): the outcome and times are cleared, earlier sessions stay listed, readiness is recomputed; a running task is refused (cancel it first).

### CLI

```text
hutan task add "<title>" [--ws ID|NAME] [--after TASK]… [--worktree[=BRANCH]] [--base REF]
                         [--prompt TEXT] [--agent codex|omp|claude | --codex | -- ARGV…] [--auto]
                         [--after-policy done|accepted|merged]
hutan task ls [--ws ID|NAME] [--json]
hutan task start|done|cancel|reset|show TASK
hutan task review TASK accept|changes [-m NOTE]
hutan task rm TASK [--cascade]
```

- `TASK` is an id, a unique id prefix of at least 4 characters, or an exact title (equal titles are told apart by the workspace). The workspace is `--ws`, else `$HUTAN_WORKSPACE`, else the project of the current directory.
- `add` prints the new id. `--worktree` alone means `task/<slug of the title>`, `--worktree=BRANCH` a branch; `--agent` (and its shorthand `--codex`) needs `--prompt`.
- `ls` prints each task once, dependencies first, under the task it waits for last (a task with several dependencies lists the others as `also after …`), with state glyphs `○ todo`, `◎ ready`, `▶ running`, `◆ blocked`, `✓ done`, `✗ failed`, `⊘ cancelled`, the shortest unique id and notes (worktree, command, `auto`, outcome). `--json` prints `{"tasks": [...]}`; `show` prints fields, dependencies, dependants and sessions (`--json`: `{task, depends_on, dependants, sessions}`).

### Delivery

Slice DL-1 (protocol 0.25, capability `task.review`). A finished run is not a reviewed result, and a reviewed result is not a merged one. Besides its run state a task has a **delivery**: `none → awaiting_review → accepted | changes_requested → merged | discarded`. Wire details: `docs/protocol.md` § Task delivery and review. Code: `crates/core/src/task.rs` (`DeliveryState`, `AfterPolicy`, readiness), `crates/daemon/src/tasks.rs`, `crates/storage` migration 9.

- **Awaiting review** is set by the daemon when work was left to look at. A terminal run that finishes `done` leaves it when the task has a worktree, or an agent reporting in the terminal worked in the main checkout; a plain command that exits 0 in the main checkout has nothing to review; marking a task done by hand records nothing either. A **chat** is judged turn by turn (FX-REVIEW): only a turn that **changed files** leaves its task `awaiting_review` — what its checkpoint (ADR 0019) says it changed, or, without a checkpoint (not in git, checkpoints off, a failed snapshot), whether it sent a `file_diff`. A turn that changed nothing leaves the delivery as it was (`none` for a fresh task). The task's chat can go on after the task is `done`: each later turn that changes files has the work await review again, and a new message of the user **re-opens** the work (`awaiting_review → none`, recorded in the name of the client that sent it — the desktop, the CLI, an agent) until a turn changes files again.
- **Accept / request changes** (`hutan task review TASK accept|changes [-m NOTE]`, the Changes view header, `task.review`): only a `done` task whose work is not merged or discarded. A change request with a note is sent to the task's chat as a user message when its session is still live, and the task is `running` again until the turn ends (then `done` and `awaiting_review` once more); a terminal task cannot be written to, so the note stays on the task (`hutan task show`, the panel row). Every move records who (`desktop`, `cli`, `agent`, `daemon`) and when; the last 20 are kept (`hutan task show`, `--json`).
- **Merged / discarded** follow the worktree: a merge of the task's branch (`worktree.merge`, from any client) marks every done task on that branch `merged` with the merge commit and strategy; removing the worktree without a merge marks the open work `discarded`. A **Finish** that landed (`worktree.finish` with no failed step: the commit, the merge of a worktree, the push when asked for) also marks the open work (`awaiting_review`, `accepted`, `changes_requested`) of every task whose sessions ran in that checkout `merged`, with the commit and the client that finished; a Finish whose push failed delivers nothing.
- **Dependency policy**: `hutan task add --after A --after-policy done|accepted|merged` (and `after_policy` on `task.create`/`task.update`): the new task is `ready` when each dependency satisfies the policy — `done`: its run finished (today's behaviour, the default); `accepted`: it is done and accepted (or merged); `merged`: it is done and merged. A dependency that works again no longer satisfies `accepted` or `merged`.
- **Agents** (ADR 0016): `task_review` and `worktree_commit` are MCP tools (`hutan mcp`); an agent-originated `task.review` or `worktree.commit` is a mutation and asks the user first, like every other (`docs/control.md`).
- **CLI**: `hutan task review <task> accept|changes [-m NOTE]`, `hutan task ls` has a delivery column and `--json` carries `delivery`, `after_policy` and `delivery_history`, `hutan task add --after-policy`, `hutan wt commit <branch|path> -m MSG`.
- **Tests**: `crates/core/src/task.rs` (delivery moves, policies, history bound), `crates/storage` (migration 9, round trip, restart), `crates/daemon/tests/it/tasks.rs` (auto `awaiting_review`, accept and request changes with and without a live chat, merge and removal, `after_policy` gates, restart, approval of agent-origin reviews), `crates/daemon/tests/it/worktree_review.rs` (`commits`, `committed`/`uncommitted`, `worktree.commit` and its refusals), `crates/cli/tests/it/{tasks,worktree_review}.rs`, golden fixtures `*task_review*`, `*task_reviewed*`, `*worktree_commit*`, `*worktree_committed*`, `event_task_updated_merged`.
- **Staged and unstaged** (`UX-CHANGES-INDEX`, protocol 0.34, capability `worktree.index`, read-only by user decision D2): with uncommitted changes included, every file of `worktree.diff` says `staged` (in git's index, `git diff --cached HEAD`), `unstaged` (the working tree differs from the index, or the file is untracked) or both (staged, then edited again). The Changes view marks each row `staged`, `unstaged` or `both` and its header has *Staged · Unstaged · All*, which only filters the list. Hutan never stages, unstages or commits selected files; merge semantics are unchanged. Tests: `worktree_review.rs::staged_and_unstaged_changes_are_told_apart_and_the_index_is_left_alone`, `changes_fresh_gpui.rs::the_changes_list_marks_staged_and_unstaged_files_and_filters_them`, golden `response_worktree_diff_index`.

## Review and merge

Slice M7-C (protocol 0.22, capability `worktree.review`). Wire details: `docs/protocol.md` § Worktree review and merge. Code: `crates/daemon/src/worktrees/review.rs`, `crates/cli/src/commands/worktrees.rs`, `crates/desktop/src/workbench/{changes,review}.rs`.

- **`worktree.diff` / `worktree.file_diff`** (read-only): what a checkout changed against the merge base of its base branch (default: the repository's default branch) and `HEAD` — its commits, plus staged, unstaged and untracked changes (togglable). Files are listed `added | modified | deleted | renamed` with `+/−` counts; one file's unified diff is fetched on demand. Output is bounded (2 MiB per file, 20 MiB and 5000 files per diff) and flagged when cut; binary files are flagged. git runs with `--no-ext-diff --no-textconv --no-color`, no pager, no prompts, under a timeout; nothing is written to the repository.
- **`worktree.merge {path, into?, strategy, message?}`** runs in the repository's **main checkout** and never pushes. `merge` makes a merge commit (`--no-ff`), `squash` one commit with the branch's changes, `rebase` replays the branch onto the target in its own worktree and fast-forwards the target. It is refused — with nothing changed — when the main checkout is dirty (untracked files count), when `into` is not the branch the main checkout has checked out (the message names what it has, and where `into` is if another worktree holds it), when a merge or rebase is already in progress there, when there is nothing to merge, for a detached HEAD, and, for `rebase`, when the worktree has uncommitted changes or live sessions. A conflict aborts cleanly (`merge --abort`, `reset --merge`, `rebase --abort`) and the error names the files (`data.conflicts`). The answer carries the new commit and `source_dirty`. Removing the worktree afterwards is the client's offer: `worktree.remove {delete_branch: true}`.
- **CLI**: `hutan wt diff <path|branch> [--base REF] [--committed] [--stat]` prints the patch (or `A/M/D/R path +n -m` lines); `hutan wt merge <path|branch> [--into BRANCH] [--squash | --rebase] [-m MSG]` prints what happened and the command that removes the worktree. A conflict prints the reason and one `conflict: <file>` line per file, exit 1. `--json` prints the daemon's answer (`wt diff` adds `patch`).
- **Tests**: `crates/daemon/tests/it/worktree_review.rs` (temporary repositories: commits plus uncommitted edits, rename, binary, untracked, ignored, truncation per file and in total, a hostile `diff.external`/textconv that must not run, the three merge strategies, every refusal, conflicts with a clean abort for each strategy), `crates/cli/tests/it/worktree_review.rs`, golden fixtures `*worktree_diff*`, `*worktree_file_diff*`, `*worktree_merge*`, `*worktree_merged*`.
- **Scope of a merge** (protocol 0.25): `worktree.diff` also answers `commits` (the commits of the branch since the merge base, newest first, at most 200) and flags each file `committed` and/or `uncommitted`. A merge integrates the commits only; staged, unstaged and untracked changes in the worktree stay where they are (`source_dirty` in the answer). `worktree.commit {path, message}` (CLI `hutan wt commit <branch> -m MSG`) stages everything and commits it so the merge takes it; it is refused for the main checkout, a detached HEAD, an operation in progress and a clean worktree, runs no hooks and leaves nothing staged when git refuses.
- **Finish** (PR-FINISH, protocol 0.35, capability `finish`, ADR 0020 — amends "never pushes"): `worktree.finish {checkout, message, push?, into?, strategy?}` is the one way Hutan delivers, for **both placements**. A main checkout: commit everything (`git add -A`, hooks off) on its branch, then push that branch. A worktree: commit, merge into the main checkout's branch with the merge modes above (a squash takes the Finish message), then push the target. Every refusal that does not depend on the commit (dirty main checkout, target not checked out, operation in progress, detached HEAD, an empty message with something to commit) is made before anything changes. The push is `git push <remote> refs/heads/<b>:<upstream>` in the user's login environment (their credential helper and SSH agent; Hutan stores nothing), never forced, after a read-only `git fetch` that says how far the branch is ahead and behind: a branch behind its upstream is reported `rejected` and not pushed (Hutan does not pull, merge or rebase for you); no upstream, a remote refusal (hook, protected branch) and credentials (`auth`) are reported with git's words, and the commit stays. `[finish] push = true` in daemon.toml (live; `false` keeps it local; a request's own `push` wins). **User-only** (ADR 0016): an agent-originated `worktree.finish` is `forbidden` whatever `[control]` says; `worktree.commit` stays refused for the main checkout (Finish is how the user commits there). CLI: `hutan finish [path|branch] [-m MSG] [--no-push] [--squash|--rebase] [--into BRANCH]` (one line per step, exit 1 when a step failed). Desktop: the Changes header's **Finish…** (it replaces *Merge into …*): message prefilled from the title of the task whose turn changed files in the checkout most recently (FX-REVIEW; never a chat that changed nothing — with several, a line under the message names the others, *Also changed here: …*; with none, the task the view was opened for, else the title of an agent session in the checkout that ran no task), merge modes for a worktree, *Push* starting as `[finish] push`, then one line per step (failures in red with their reason) and, after a merge, the worktree cleanup offer. Tests: `crates/daemon/tests/it/finish.rs` (temporary repositories with a local bare `origin`, its reflog checked for fast-forwards only), `crates/cli/tests/it/worktree_review.rs`, `crates/desktop/tests/it/tasks_gpui.rs`.
- **Delivery follows the worktree**: a successful `worktree.merge` of a task's branch marks that task `merged` (merge commit and strategy recorded); `worktree.remove` of the branch's worktree without a merge marks its open work `discarded`; a Finish that landed marks the open work of the tasks that ran in its checkout `merged` (FX-REVIEW). See § Delivery.

## Tasks panel

The `tasks` panel (default: the Tasks page of the left sidebar's nav; movable; settings namespace `tasks`) draws the daemon's tasks (`task.list`, `task.updated`, `task.removed`; the store lists once per connection and follows the events) as a dependency tree: see `docs/design.md` § Tasks panel for rows, actions, the new-task form and filters. The Changes view is a center tab (`ItemRef::Changes`, one per checkout) reached from a task row's **Changes** button, the placement badge's menu of a session row (*Review Changes…*, *Copy Checkout Path*), a session's context menu, or ⌘K *Worktree: Review Changes…*; its header has *Finish…* (commit, merge with a strategy for a worktree, push; a refusal stays in the form) and, after a success, *Remove worktree and branch*. Tests: `crates/desktop/tests/it/tasks_gpui.rs`, `crates/desktop/src/sessions/tasks.rs`.

The **Changes** tab of the right sidebar (`changes` panel, no settings of its own) lists the checkouts of the workspace you are in — the main checkout and every worktree, from `worktree.list` (the same listing as ⌘K *Worktree: Review Changes…*) — with the ones that have uncommitted changes first (a dot, "uncommitted changes", and how many sessions are live in it). It lists again when it is drawn after 15 s, when the workspace or the connection changes, and from its ↻ button. A click opens that checkout's full Changes view as a tab of the center (`ReviewChangesAt`). It never reads a repository itself.

### Delivery in the panel and the Changes view (DL-1)

Code: `crates/desktop/src/workbench/changes/delivery.rs`, `crates/desktop/src/sessions/{tasks,store}.rs`, `crates/desktop/src/workbench/panels/tasks.rs`. Only drawn when the daemon has capability `task.review`.

- **Pill**: a task row shows a delivery pill next to its run state — `Awaiting review` (accent), `Accepted` and `Merged` (success), `Changes requested` (warning; the note is the row's last detail), `Discarded` (muted); none while the delivery is `none`. A finished (`done`) task that waits for review or whose changes were requested stays listed when *Show done* is off and is not dimmed.
- **Needs you**: the session of a task that is `done` and `awaiting_review` is a soft item of the sidebar's *Needs you* (label `review`, accent tone, filled dot) until the user has **seen** it: its chat or the Changes view of its checkout was on screen after the work started waiting (also *Mark as read*). Seen work is the quiet state word *ready for review* (*Ready for review* on the Agents page; muted, hollow dot, not in *Needs you*, not counted); the Tasks panel keeps the `Awaiting review` pill. Work that waits again after another changing turn needs the user again. A turn that runs (or is stopping) is *working*, never review. None of it is counted by the menu bar item and the Dock badge — those are for what blocks someone or went wrong (`classify` leaves accent alone). It goes when the task is accepted, sent back, merged (also by a Finish of its checkout) or discarded, or the user sends the chat another message. A task whose session is gone from the list has the pill only.
- **Changes view header**: the delivery pill of the task whose work the checkout holds — the task the view was opened for (a task row's *Changes*), else the worktree-placed task on the checkout's branch (the one waiting for its delivery, else the latest) — then **Accept**, **Request changes…** and **Finish…**. *Accept* and *Request changes…* appear while the task is `done` and its work is neither merged nor discarded (*Accept* is dimmed once accepted). *Request changes…* opens a note form (⌘↩ sends, Esc cancels): the note is sent to the task's chat when its session lives and the task runs again, else it stays on the task; the result is a notice, a refusal stays in the form.
- **Merge scope**: for a worktree the view shows a card with two sections. *Committed on <branch>* — the commits (hash and subject, newest first, eight listed) and the number of files: exactly what *Merge into …* takes. *Uncommitted in the worktree* — the files with changes in no commit (or, with *With uncommitted* off, a line saying there are some): what a merge would not take, with **Commit all…** (a message form; `worktree.commit`; the view reloads and the commit joins the first section). The merge form repeats the commits it will integrate and warns about uncommitted changes.
- **After a merge** the card says what was merged. When the worktree still has uncommitted changes it says removing the worktree would discard them, *Keep* is the primary button and *Remove worktree and branch (discard its changes)* is secondary; with nothing left, *Remove worktree and branch* is primary as before. The task is `merged` as soon as the daemon has merged; the header pill follows.
- **Tests**: `crates/desktop/tests/it/tasks_gpui.rs` (pills, Needs you without a badge, Accept, Request changes, the scope sections, Commit all…, the merge preview, the cleanup default, the merged task).

## Review comments (RC-1)

No protocol change: a review is an ordinary user message, so the chat journal keeps it. Code: `crates/desktop/src/workbench/changes/{comments,tray}.rs`; the message goes out through `SessionsStore::chat_send` / `paste_into_terminal`.

- **Selecting**: click a line number in the Changes view's diff (drag over several, shift-click to extend); the selection stays inside one hunk, hunk headers select nothing. A **+ Comment** button appears at the last selected line; so does `c`. ⌘↩ in the box adds the comment, Esc cancels. A comment is shown under its last line (author *you*, age, *Edit*, *Delete*, *Send now*, *Resolve*) and in the **Review** tray under the header (`3 comments · 1 sent · 1 resolved`, *Send to agent*, ▾). A tray row jumps to its comment. `]c` / `[c` walk the open comments over every file; ⌘↩ with the view focused sends the review.
- **Anchors**: a comment keeps its lines as they were (kind, text, old/new numbers) and an excerpt of its hunk (the selection with three lines around it; at most 200 lines each). After every listing the patch is read again and the comment is looked for as the closest run of equal lines in one hunk: found it follows the lines to their new numbers; not found it is **outdated** and shows its original lines. Comments of files that are no longer changed are outdated too. Nothing is resolved or called outdated while the diff leaves out the uncommitted changes (the agent's edits may be there).
- **Send to agent**: all drafts of the diff become one message — `Please address these review comments:` and each comment numbered with `path:lines` — with, per comment, a `file` attachment (the checkout's file with the line range; none for removed lines) and a `pasted_text` of the excerpt; at most 16 attachments (the excerpts of comments past the limit go into the text) and 256 KiB of text. The default target is the live agent chat of the checkout that a task of it ran, else the newest chat, else a terminal with an agent; ▾ lists the others, and *Start a new agent with these comments* opens the new-agent dialog on the checkout with the review as its first message (plain text with the excerpts inline). A terminal agent gets the same plain text as a bracketed paste (when its terminal turned that mode on) followed by Enter. Sent comments move to *Sent · <time> UTC · n comments → agent* (collapsed list); after a refresh a sent comment whose lines changed is **resolved**, one whose lines did not stays open. *Resolve* / *Unresolve* are manual (a reopened comment is not resolved by a refresh again).
- **State**: comments are desktop view state, saved with the layout in `desktop-state.json` under `review_comments` (checkout directory → comments, at most 200 per diff, the *outdated* flag is computed and not saved) and dropped when the worktree is removed from its Changes view.
- **Tests**: `crates/desktop/src/workbench/changes/comments.rs` (anchoring, excerpts, composing), `crates/desktop/tests/it/review_comments_gpui.rs` (real clicks and drags, the in-process daemon with a replayed Codex for chat targets and a recording terminal for the paste, outdated and resolved after a refresh, persistence).

## Not here

Remote repositories, fetching and pushing are never done by these requests; resolving conflicts (the merge is aborted and the files listed, the user resolves them in a checkout), a worktrees panel.
