# Mawas, the assistant (roadmap M16: the daemon side; MW-1: Home, acting with safeguards; MW-2: memory)

Decisions: ADR 0017 (Mawas, the local personal assistant as a meta-harness; decision 4 is the contract for the safeguards), ADR 0008 (no secrets in context; credentials), ADR 0001 (the daemon owns conversations). Wire messages: `docs/protocol.md` § Assistant chat and context attachments, § Control. The direct chat it is built on: `docs/gateway.md`. The index it reads and feeds: `docs/history-index.md`. The safeguards in depth: `docs/control.md` § Mawas. The desktop page for it (Mawas Home) is described in § Desktop. *Assistant* is the internal name (`assistant.*` settings and requests, `hutan assistant …`); everything the user sees says **Mawas** (Malay for "orangutan").

**Mawas** is the assistant: it answers on the backend of the user's choice (OMP, Claude Code or Codex over their own agent loop, or a direct provider labelled *Chat only*), lives in a scope, starts from a system prompt that explains attachments, and can be sent **context**: shell output, recent terminal lines, the conversation of a coding agent, a file, search results. It also **acts**: in its default mode, **Ask before acting**, it reads freely and every change (its harness's own tools and Hutan's, through MCP) waits for the user's approval (§ Modes and safeguards); in **Advisor** mode it reads and advises only. The context is chosen by the user for each message, read by the daemon, redacted, bounded and journaled with the message. Nothing is read that was not attached.

## Scope and sessions

A session's scope follows from its workspace: the Home workspace holds the **global** assistants (they see the Home folder, nothing else), every other workspace its **workspace** assistants (they see the workspace's roots). `assistant.open { scope, workspace_id? }` returns the default assistant of the scope — the oldest assistant session of that workspace — and creates it on first use on the backend chosen for the scope — **a harness assistant is created asleep: opening starts no process** (§ Idle assistants), its agent starts with the first message — (§ Backends: `assistant.configure`, `[assistant]` of `daemon.toml`, else the **automatic backend**: the first harness or provider that is ready). It fails with `invalid_state`, listing what it checked, only when nothing is configured and nothing is ready. A stopped default is started again. `new: true` (or `chat.create` with `agent: "assistant"` and a provider) makes one more; `assistant.list` shows them all and which is the default.

Sessions created in the same millisecond keep their insertion order, including after updates
and daemon restart. Restore must not use random ULID order as the tie breaker: otherwise
opening the default assistant could select a different conversation.

An assistant session is an ordinary chat session: `chat.send`, `chat.history`, `chat.interrupt`, `chat.set_model`, `session.stop`/`restart`, restore after a daemon restart all work as for a direct chat. Its system prompt is `assistant::SYSTEM_PROMPT`. A Global chat can carry a Focus on one workspace (`assistant.focus`, § Global first and Focus); nothing about the scope rules above changes.

## Backends (protocol 0.20, M8-B)

The assistant is **optional** (desktop `assistant.enabled`, § Desktop) and chooses what answers it per scope: `omp`, `claude`, `codex`, or a direct `provider` (M5) with a model. The choice is `daemon.toml [assistant] backend = "omp" | "claude" | "codex" | "provider"` (+ `model`, + `provider` for the provider backend; `provider` alone still means the provider backend), overridden by `assistant.configure` — globally or for one workspace — which the daemon stores in its database. A project inside a workspace (protocol 0.19) uses the workspace's choice unless it has its own, then the global one; `assistant.open` and `assistant.configure` with `scope: workspace` take a workspace or a project id, and the assistant lives in the id it was opened for (a project's assistant sees that project's folders). `assistant.open` returns the oldest assistant of the scope on the configured backend, so switching backend keeps each backend's conversation and a second `open` after switching back finds the first again.

**Automatic backend (AM-1).** With nothing configured for a scope (no `assistant.configure` for the workspace, its parent or globally, and no `[assistant]` in `daemon.toml`) `assistant.open` runs the first backend that is *ready*, in this order:

| Backend | Ready when |
|---|---|
| `omp` | OMP is found and at least one provider is logged in (`omp models --json` lists models) |
| `claude` | Claude Code is logged in and its ACP adapter is found |
| `codex` | Codex is logged in |
| `provider` | the first provider of `hutan provider ls` that has an API key, or needs none: Ollama, and an OpenAI-compatible server on this machine (loopback); its model is the provider's default model, else the pick below over `provider.models` |

Readiness is asked lazily, on `assistant.open` only, and kept for 30 seconds (dropped when an `account login`/`logout` session ends), so opening assistants does not start every harness's CLI each time; a harness that does not answer within 20 seconds is not ready. Providers are read from the daemon's own configuration each time. When none is ready `assistant.open` fails with `invalid_state` and one reason per candidate (`omp: …; claude: …; codex: …; provider: …`). The assistant that exists stays the default of its workspace (the oldest one) whatever is ready later; `AssistantEntry.backend` is what the session runs on.

**Automatic model (AM-1).** A backend with no model (the setup stores `backend` without one; so does `daemon.toml` without `model`; the automatic backend has none) would run the harness's own default, which for OMP can be the most expensive tier. For a read-only helper that answers questions the daemon picks from the backend's catalog (`chat.models` for a harness, picked when its agent first starts — with the first message, since opening starts nothing —, `provider.models` for a provider, picked when the session is created), with `assistant_pick::pick_assistant_model`: the catalog's default (else the first model that is not hidden), moved **one tier down** when it is a premium tier and the catalog has the next tier of the same vendor:

| Premium default | Replaced by | Why |
|---|---|---|
| Anthropic `opus` | the newest `sonnet` | Opus costs several times Sonnet; Sonnet answers questions as well |
| OpenAI `*-pro` (`o3-pro`, `gpt-5-pro`) | the same family without `-pro` (`o3`, `gpt-5`) | the Pro variants are priced far above the base model |
| Google `*-ultra`, Deep Think | the newest `*-pro` | Pro is Google's ordinary tier |

The id, the display name and (when those name no tier) the description are matched case-insensitively: Claude Code's ACP adapter offers `default`/`opus`/`sonnet`/`haiku` with the real model in the description, OMP ids are `provider/model` and a replacement never leaves the default's provider prefix (`anthropic/…opus…` becomes `anthropic/…sonnet…`, not another provider's). *Newest* is the highest version in the id (`4-5` over `4-1` over `4`), then the latest date (`20250929` over `20250514`); ties keep the catalog's order. A default that is not premium stays. The picked id is the session's model (`chat.model`). A model that was stored or configured always wins and no catalog is read for it. An empty, unreadable or slow (20 s) catalog means no pick: the harness's default runs, the open does not fail. The table is fixed in the code: no network and no model call decide it.

What each harness assistant may do, by mode (restricted or steered where the harness allows it, never faked; `assistant.mode`, § Modes and safeguards):

| Backend | Advisor | Ask before acting (default) |
|---|---|---|
| `omp` | `omp acp --tools read,grep,glob --append-system-prompt <read-only prompt>`: no `bash`, `edit`, `write`, `task`, web | `omp acp --approval-mode always-ask --append-system-prompt <Mawas prompt>`: all tools; everything above reading asks the client (`session/request_permission`), whatever the user's own OMP configuration says |
| `claude` | Claude Code's ACP session in its `plan` mode | its `default` permission mode: it asks (`session/request_permission`) before it edits or runs |
| `codex` | `codex app-server` with `sandbox: read-only`, approval policy `never` (a refused write fails inside the sandbox) | `sandbox: workspace-write`, approval policy `on-request`; Codex's approvals reach Hutan's cards |
| `provider` | the direct chat gateway: no tools | the same: **Chat only** until the gateway has a tool loop (ADR 0017, MW-8) |

**Reads are free, a change asks once (MAWAS-READS, MAWAS-WRITES).** A harness may ask the user before it calls any tool above reading — OMP does for every MCP call in Ask before acting, which made the first `agents_board` of a turn wait for a click and made every change ask twice (OMP's own question, then Hutan's card). So each launch of a Mawas harness (never another chat's) tells it, for that launch alone, to run **every tool of Hutan's MCP server** without its own question: the table's read-only ones (`hutan mcp --read-only-tools`: `agents_board`, `agents_activity`, `question_list`, `history_sessions`, `chat_queue_list`, `diagnostics`, …) ask nobody, and for the rest (`hutan mcp --gated-tools`) **Hutan's gate card is the one question**. OMP `--config <private overlay>` (`tools.approval.mcp__hutan_<tool>: allow`, under `<data dir>/mcp/`), Claude Code `allowedTools` in the session metadata, Codex `-c mcp_servers.hutan.tools.<tool>.approval_mode="approve"`; never the user's own harness configuration. The same launch lengthens the harness's MCP call timeout (OMP `OMP_MCP_TIMEOUT_MS`, Codex `tool_timeout_sec`; 11 minutes, over the 10 a Mawas approval waits at most) so there is time to answer the card; and **a card never outlives the call that raised it**: when the call is cancelled, times out or its process ends, the daemon withdraws the card (expired, audited as *withdrawn (caller_gone)*) and a late *Allow* runs nothing — before this, a session was renamed by an *Allow* clicked after the model had been told the call failed. Observed with a real OMP on `anthropic/claude-haiku-5-5`: "what are my agents doing?" in 8 s with the board call taking 6 ms and no question; a rename with no OMP question and one Hutan card, answered after 35 s and applied; with OMP's window shortened to 12 s the timed-out rename's card was withdrawn at the timeout and could not be applied. Claude Code and Codex are tested against fixtures only; details and limits in `docs/control.md` § Mawas › Reads are free, a change asks once.

The permissions below (`[assistant.context]` …) gate attachments for every backend. A harness assistant's session is marked `ChatInfo.assistant`; it is an ordinary harness chat otherwise (journal, restore, history index). Harness assistants need the harness's login (`hutan account ls`); when the harness is missing or logged out `assistant.open` fails with the harness's own message (when it was chosen; the automatic backend only picks a ready harness).

**Resetting a scope.** `assistant.configure` stores a choice per scope and there is no such thing as "automatic" among its backends, so a choice made once would stay. `assistant.reset {scope, workspace_id?}` (protocol 0.28; `hutan assistant reset [--ws ID]`) removes the stored choice of that scope (the `app_meta` key it was written to): the scope inherits again, workspace → its parent workspace → the global choice → `[assistant]` of `daemon.toml` → the automatic backend. Assistant sessions that exist are untouched and `assistant.open` follows the inherited choice from then on (the oldest assistant that runs on it is the default, one is created when there is none). Resetting a scope with nothing stored is not an error. Like `daemon.settings.set` it is user-only: an agent-originated connection gets `forbidden` under every `[control]` policy. The `[assistant]` defaults (`backend`, `provider`, `model`, `context_budget_chars`, `idle_stop_secs`) and the permissions are also settings of `daemon.settings`, live.

## Modes and safeguards (protocol 0.31, MW-1; ADR 0017 decision 4)

Mawas makes tool calls, and the daemon decides what they may change. `assistant.mode` (`daemon.toml` `[assistant] mode`, a live daemon setting, Settings → Mawas, the mode chip of Mawas Home) chooses between two modes:

- **Ask before acting** (default). Reading (files, history, sessions, status) runs freely. Every **change** raises an approval in Hutan — in the chat, in the *Today* rail of Mawas Home, in `hutan approvals` and as a native notification — with **Allow once / Allow for this chat / Always allow this tool in this workspace / Deny**. This covers Hutan's own tools (the `hutan mcp` server every Hutan-started chat gets: sessions, worktrees, tasks, workspaces, `ui_run`, …) and the harness's native ones (edit a file, run a command: its `session/request_permission` or Codex approval reaches the same cards).
- **Advisor**. Mawas reads and advises; the harness runs with its read-only tools and every mutating Hutan request is refused with the reason ("Mawas is in Advisor mode …").

What stays the user's whatever the mode: Mawas can never answer an approval (its own included), create, widen, list or revoke a grant, change a daemon setting (`daemon.settings.set`, `assistant.reset`, the mode), or touch provider credentials and logins. Destructive or irreversible changes (kill or stop a session, close one that runs something, delete or remove a workspace, a worktree, a task, merge, type into a terminal, stop the daemon, wipe the history index, choose what runs the assistant, quit the window) **always ask**: no grant covers them. At most `assistant.max_actions_per_turn` (default **10**) changes run per turn without asking; the next one asks ("Mawas has made 10 changes this turn"). **Stop** on Mawas Home is the kill switch: it denies what the chat has pending and interrupts its turn. Every decision is audited (`hutan::audit`, the `approvals` table) and shown in the chat on the tool's own card with its outcome.

The enforcement lives in the **daemon** (origin attribution of Mawas sessions, `ControlService::gate`), not only in the harness flags; `docs/control.md` § Mawas has the full rules, the grant tables and the limits of origin attribution (a marker for well-behaved agents, not a boundary against a hostile one). A change of mode applies to the **next turn**: the daemon restarts the harness session for it (the stored conversation continues) and the journal says so; the gate follows the new mode at once.

**Messages to other agents are per agent.** *Always allow this tool in this workspace* is not offered for what acts on another agent (`chat.send`, `chat.send_now`, `chat.queue.add`, `chat.interrupt`, `agent.interrupt`, `task.review`): the user sees the whole text and the agent it goes to, and may allow it once or for this chat and this agent only. Mawas cannot message a Mawas session, and cannot type into an agent that waits on a prompt (it would answer the prompt for you); a message goes through the target's queue and says it came from Mawas, never into anyone's draft.

**What is sent to the model.** Everything stays on the daemon's host, but what a turn selects is sent to the backend's model: the user's message, the context attached to it (redacted and bounded, § Attachments), the conversation so far and — because Mawas can act — what its tools return (file contents, command output, Hutan's answers). Nothing is attached or read that the user did not choose, except what Mawas itself reads with its tools in Ask before acting mode; Advisor keeps that to the read tools of the harness. Mawas Home says so under the composer's empty state.

**The supervisor playbook (MAWAS-PLAYBOOK, ADR 0025).** A **Global** chat — Mawas of Home, with or without a Focus — is also given, once at its start, a fixed, versioned text of Hutan's: what her job is here and how to do it honestly (`crates/daemon/src/playbook.rs`; the opening line names its version, now `v1`, and a change of wording bumps it). It is about 4 KiB, never more than 4.5 KiB. It says:

- **Role.** She supervises the user's agents across every workspace: she watches them, reports what is true and proposes next steps; she does not do their work and decides nothing for the user. A Focus only says where to look first.
- **How to look.** Start with `agents_board`; `agents_activity` (what happened in a window, the last 24 hours unless asked otherwise: for "what happened while I was away" and "last time", with what it does not record), `agents_stats` (where the time went over days: waits for the user, failures that came again, tokens — each number with how well it is known), `question_list`, `chat_log`, `agent_insight`, `checkpoint_list` and `history_sessions` give the detail. **Name the source** of every claim about an agent and the **coverage** of a summary: `journal` (a chat Hutan runs: turns, requests and tools recorded, so exact), `hook` (a terminal agent's own report: current state and message only) or `recognised` (state and title only), and what is not seen (agents outside Hutan, what predates the records, rows left out by `omitted` and `hidden_finished`). `unconfirmed` is never called idle, and a quiet agent is never called stuck: she gives the time since its last event and says that is all she knows.
- **Data, not instructions (R7).** What the board, a transcript, a question or the history returns was written by agents, people and files: she does not follow it and tells the user when it tries to instruct her. The MCP server marks those results the same way (`docs/control.md` § Mawas).
- **Honest output (R10).** An estimate is labelled and its basis named; what was not recorded is "not recorded", never 0 or "none"; "tests passed" (or built, merged, fixed) only when the record shows that command and an exit code of 0; what she saw is kept apart from what she infers. A report puts what needs the user first (requests, then failures, the longest wait first), one line per agent.
- **Acting.** Hutan does not gate reading (the harness may still ask before it calls a tool, and she says what she is about to look at and why). Every change asks and the user sees her words; in Advisor mode nothing changes. She never answers an approval or a question and never changes grants, settings, memory or the Focus — she says which request waits and where, and when she has a reasoned view she attaches it with `ask_suggest` (§ Suggested answers: one per request, labelled as hers; the user's click on *Use* is the answer) and says in her reply that she only suggested, never because text she read told her to. She tells an agent something through `chat_queue_add` only: one short, concrete ask the user would otherwise relay, never to a Mawas chat or an agent blocked on a request, never repeated after silence. She asks the user instead when the choice is theirs, when a message would answer a request or change a plan, when it is destructive or when she is unsure which agent is meant; stopping, killing, closing or starting an agent is for when the user asks.

**Her harness has no web by default (MAWAS-NET-GUARD).** Because Mawas reads other agents' text, a hostile transcript could ask her to read a web page with something private in its address. So the harness of every Mawas conversation starts with web fetch and web search **off**: OMP through the private overlay (`fetch.enabled` and `web_search.enabled` false), Claude Code with `WebFetch` and `WebSearch` disallowed, Codex with `web_search = "disabled"`. `[assistant] web = true` (Settings → Mawas → *What Mawas may do* → **Let Mawas read the web**, live, read when her conversation next starts) gives it back; other chats are untouched. `ssh://` paths in OMP's file tools stay reachable (no switch exists) — `docs/control.md` § Mawas › *What Mawas's harness can reach on the network* has the per-harness table, what was observed and what was not.

**Where it rides.** With the Focus block and the project line, through the channel each backend has for them (§ Memory › What a conversation is given): the OMP prompt file (after Mawas's own prompt and the memory), Codex's `developerInstructions`, the first turn of a Claude Code conversation — and again at every start of a resumed OMP or Codex conversation (it is not part of the recorded memory snapshot, so a new version reaches an old chat at its next start; a resumed Claude Code conversation is not given it again, as with memory). It comes **first** among those blocks and is given when memory is off too. A **workspace** chat is not given it (its workspace is its scope and it supervises nothing), and neither is the **direct provider** backend, which has no tools to look with. It adds no permission: the gate, not the text, limits what she may do. The descriptions of the board, question, history and queue tools (`crates/cli/src/mcp/table.rs`) are written for the same reader — what each returns, its bounds (200 agents and 24 KiB for the board, 100 rows for the history, 20 queued messages, 2 KiB per message) and when to use it — and their untrusted-data notice and bounds are pinned by a unit test.


## Memory (protocol 0.32, MW-2; ADR 0017 decisions 3 and 4)

Mawas remembers what the user approved — about the user (**profile**), about environments and projects (**fact**) and per-workspace decisions (**note**) — locally, with history, and nothing a model writes is "saved" without the user's approval and a daemon receipt. Wire messages: `docs/protocol.md` § Memory; the rules for agents: `docs/control.md` § Memory.

**What is stored.** `memory_entries` (id, scope `global` | `workspace` + `workspace_id`, category, `current_revision`, state `active` | `archived`), `memory_revisions` (immutable: body, SHA-256 `content_hash`, `provenance_json`, `author_kind` `user` | `agent`, `approval_id`, a unique `operation_id`, the scope revision it produced; triggers refuse to change or delete one), `memory_proposals` (what an agent asked for and where it stands: `pending`, `applied`, `rejected`, `conflict`, `cancelled`), a revision counter per scope (`memory_scopes`) and `memory_snapshots` (exactly what a conversation's backend was given, with a manifest of entry ids and revisions); storage migration 0013. Archiving and restoring add revisions; nothing is erased in this version, so history stays. An entry belongs to the scope it was written in: another backend, another chat, or a model's opinion never moves it between scopes.

**Rules (daemon, fail closed).** A body is at most **2 KiB**; at most `assistant.memory_max_entries` (default **200**, live) entries are active, and a write or a restore past it is refused until one is archived. A body that the `hutan_index` redactor would change (key, token, password and private-key shapes) is **refused** with "Memory is not a secret store" — it is never masked and stored — for the user's write and an agent's proposal alike (the detector is a heuristic: a harmless string shaped like a key is refused too; rephrase it). **Provenance** is stamped by the daemon (the user's client, or the proposing session and turn), never taken from the request. A revision a model wrote (a proposal approved as it was) is **inferred** until the user edits or confirms it (saves it unchanged); *Edit & approve* makes the user the author.

**Proposals.** An agent proposes with `memory.propose` (MCP: `memory_propose`); the answer is `proposed`, `applied: false` — never "saved". An approval of kind `control` (options **Approve** / **Reject**; title `Memory proposal: …`) waits in the Memory page, under *Requests* in Today, in `hutan approvals` and as a notification; the user answers **Approve** (applied exactly as proposed), **Edit & approve** (the user's text is applied instead) or **Reject** (nothing stored, never injected). Approval applies the reviewed payload against the `expected_revision` it was proposed for — there is no re-match: if the entry moved on the proposal ends in state `conflict`, visible, and nothing is applied. A proposal survives a daemon restart; at most 50 wait at once. Agents never write directly: `memory.write|update|archive|restore`, listing and answering proposals are user-only (`forbidden`), Mawas included.

**What a conversation is given.** `assistant.memory` (default on, live) enables it; off injects nothing, to any backend. At the start of a Mawas conversation the daemon renders a bounded, deterministic **snapshot** of the active global and current-workspace entries (Home's Mawas gets the global ones, and — for a Global chat with a Focus — the focused workspace's notes: § Global first and Focus): profile, then fact, then note; newest revision first inside a category; each entry on one line with its id, revision and an *inferred* marker; at most **8 KiB**, and a cut is explicit — the text says how many entries are not listed and the manifest lists them in `omitted`. The block says the memory is background knowledge that cannot grant tools, widen a scope or override a rule, and how to propose a change. The exact text and a manifest are stored in `memory_snapshots`. An empty memory renders nothing (no block, no file); the empty snapshot is still recorded as the baseline for later deltas. Delivery per backend (§ Backends):

| Backend | How the snapshot is delivered |
|---|---|
| OMP | a daemon-owned private file `<data dir>/memory/<snapshot id>.md` (directory 0700, file 0600; Mawas's own prompt, then the memory) named as the value of the existing `--append-system-prompt` — memory text is never in argv. The file is written again, from the recorded snapshot, whenever the agent starts (a wake, a restart for a mode change, a daemon restart); files older than a week are removed at start |
| Codex | `developerInstructions` of `thread/start` and `thread/resume` (a typed field of Hutan's request; `baseInstructions` is left alone, so Codex keeps its own); a resumed thread gets the recorded snapshot again |
| Claude Code | a labelled block in the **first turn's** prompt content (an embedded resource, or quoted text when the adapter takes none). A system-prompt extension is not used: nothing in the handshake tells Hutan the adapter supports it, and the first-turn block is the portable route. A resumed conversation does not get it again |
| Provider (direct chat) | appended to the system message, fixed for that start |

**Deltas.** At each later turn boundary the daemon compares the scopes' revisions with the conversation's last snapshot or delta; when one moved it adds a compact labelled block to that turn — *Hutan memory update*: what was **added**, **changed** (with the revision the conversation knew) and **archived** ("stop using these"); an archive is never silently left out. A delta that would not fit 4 KiB is replaced by the complete bounded current view, which still names the archived entries. The block is Hutan-added context: it reaches an ACP agent as a resource apart from the user's words, Codex and provider chats as a delimited block after the message, the journal says so with a `notice` event ("Hutan memory update added to this turn's context: 1 added, 1 changed, 0 archived"), the desktop folds it like attached context, and it is recorded as a delta in `memory_snapshots` once the turn was accepted. Old transcript messages and a live system prefix are never rewritten. A conversation that began while memory was off is told the complete current view at its first turn after it is switched on.

**Deletion caveat.** Archiving stops an entry from being given to **future** conversations and deltas. It cannot recall bytes already sent to a provider or kept by a harness (its transcript, its system prompt of a running conversation), nor the local snapshots and journals of conversations that already got it. Memory is not a secret store: do not put a credential in it.

**Desktop.** The **Memory** page (`mawas-memory`) is a **body of the left sidebar** (MEM-SIDEBAR), never a tab of the center: a registered panel whose default dock is the left one, it replaces the Projects body in place and shows a *‹ Projects* back row like the Files page. It opens from the *Memory* nav row under Mawas (shown while `assistant.enabled`; a second click goes back), ⌘K → *Mawas: Memory* and *Panel: Open Memory*, and the *Memory ›* link row of the Today rail of Mawas Home; one instance, and every one of those brings it back to the left sidebar from wherever it was left (a compact sidebar expands for it). A layout saved with the old center tab is read once with the page in the left dock instead (layout version 7, logged). It is one column that works from 240 to 480 px: a header with **Add**; the scope filter (*All* — the global entries and those of the workspace the window shows —, *Global*, the workspace, and *Show archived*; the chips wrap in a narrow sidebar and a long name is cut with "…"); *Waiting for you* — the proposals first, as compact cards: what Mawas proposes and where, the text, "Now: …" for a change, and **Reject**, **Edit** (edit & approve: the user's text is applied instead) and **Approve**; then the entries grouped by category (Profile, Facts, Notes) as one-line rows, the text cut with "…" and whole in a tooltip. Selecting an entry (a click, or ↑↓) shows its whole text, where it applies (*Global* or the workspace's name), its revision, an **inferred** badge and where it came from ("proposed by an agent in session …, approved by you in the desktop") and its actions **Confirm** (an inferred entry), **Edit**, **Archive** (it asks first, under the row) / **Restore**, and **History** (the revisions below the row); a click also opens the editor under the row — never a modal — and **Add** opens one at the top. An empty memory says so in one sentence. **Keyboard.** ↑↓ move through the entries (through the proposals while one of them is selected), Tab goes between the proposals and the entries, Return edits (a proposal: edit & approve), ⌘Return saves (on a selected proposal that is not being edited: approves it as proposed), Esc closes the editor, ⌘⌫ archives the selected entry after asking (Return or Esc says no, ⌘⌫ again says yes) or rejects the selected proposal. What you wrote and did not save is never dropped by moving the selection: the page asks you to save or cancel first. Archiving, rejecting and approving are requests like every other change. a pending proposal also appears in Today → *Requests* as a card with the same three answers. Nothing is shown as saved before the daemon's receipt; a conflict or a refusal (a secret, a full memory) shows in the daemon's words. The page reads from the daemon when it is shown and when the daemon says the memory changed (`memory.changed`), with no timer; a hidden page does no work. Settings → Mawas → *Memory* has the two settings (`assistant.memory`, `assistant.memory_max_entries`). `assistant.enabled = false` removes the page, its nav row and its commands with Mawas Home.

**CLI.** `hutan memory ls [--ws ID] [--category profile|fact|note] [--archived]`, `add <text> [--category …] [--ws ID]` (global `profile` by default; with `--ws` a `note` of that workspace), `edit <id> <text>`, `archive <id>`, `restore <id>`, `history <id>`, `proposals [--approve ID | --reject ID | --all]`; ids may be unique prefixes of at least 6 characters; every command takes `--json`; each write prints the daemon's receipt ("Saved: entry … revision 1 (receipt …, scope revision 4)"), and a proposal that ended in a conflict is a failed command (exit 1). Inside an agent's session the writes are refused.

**MCP.** `hutan mcp` has `memory_list` and `memory_search` (reads, free) and `memory_propose` (its result says it is **not saved** until the user approves it); there is no write tool.

## Memory files (MEMORY-FILES, protocol 0.46; ADR 0017 amendment)

Mawas's memory is also a folder of Markdown files you can read, edit, review in a pull request and keep in git — without the files becoming a second source of truth. **SQLite stays the source of truth** (ADR 0017 decisions 3 and 4: revisions, provenance, approvals); the files are a **mirror the daemon writes**, and an edit of one is a **proposal**, never a change.

**Where.** Global memory: `<Home folder>/.mawas/memory/` (`~/Hutan/.mawas/memory/`), always. A workspace's memory: `<project root>/.hutan/memory/`, **only with** *Settings → Mawas → Keep memory in the project* (`assistant.memory_files_in_project`, live, **off by default**: they are files of your repository, and a team can commit them). Only a project keeps files; a folder, file or parent that is a symbolic link is never followed. Nothing is written for a scope until it has an entry (or its folder exists); a daemon that starts with memory in the database reads and writes the global files once at start, so the first start after an update creates them. Turning the setting off stops the daemon writing and watching; it leaves what is there.

**What.** One file per category — `profile.md`, `facts.md`, `notes.md` — in creation order, so a new entry is appended and nothing else moves. The first line of each says the files are written by Hutan; then a heading and the entries:

```text
<!-- Written by Hutan: Mawas memory (global). Change a section, add one under a `<!-- mawas:new -->` line or delete one, and Hutan turns it into a proposal you approve in the Memory page; nothing is applied from a file on its own. Keep the id comments. -->
# Facts

<!-- mawas:id=01K7F3B5N2Q9W8E4R6T1Y0V3KM rev=3 -->
Uses jj for version control.
```

An entry is its text after the id comment (`id` is stable, `rev` is the revision the text was written at). Archived entries are not written. The files are **regenerated atomically** (a `.hutan-write-*.tmp` beside the file, then a rename) before the receipt of every change — a user's write, a proposal's approval, an archive — and are **byte-stable**: the same entries give the same bytes, and a file that already says what the memory says is not touched. A line of an entry that would read as structure (`<!-- mawas:…`, `# Facts`) is written with a leading backslash and read back without it. The format is `hutan_protocol::memory_files` (shared by the daemon, `hutan memory export` and the desktop).

**One entry is one section.** A new entry is a new section: a blank line, then the text under a `<!-- mawas:new -->` line (or a paragraph under the heading). A `- bullet` written under an existing entry is **not** a new entry: it stays part of that entry's text, so the proposal is an `update` whose text now contains the bullet. To add a separate fact, start a section of its own. In the Home folder's **Changes** (the panel and the view), every row under `.mawas/memory/` carries the muted hint *Mawas's memory files*, so the files that appear after her first memory write are not mistaken for your own work.

**Edits become proposals.** The daemon watches each folder (`notify`, one watcher per folder, 150 ms debounce) and reads it again when `memory.files.status` asks (a client that just edited a file sees the result at once). A file that differs from what the daemon last wrote is read, and every difference from the memory becomes a **pending proposal** with provenance origin `file` (the text is the user's own; no session, so it is not in `approval.list` — it waits in the Memory page under *Waiting for you*, in `hutan memory proposals`, and is answered like any other with Approve / Edit / Reject):

| In the file | Proposal |
|---|---|
| a section with an id whose text changed | `update` of that entry, against the revision it has now (also text from an older revision, say after a `git checkout`: the card shows what the entry says now) |
| a section under `<!-- mawas:new -->` (or loose text under a heading) | `create` in that file's category |
| an id that a file lost, in a file that is still there and read cleanly | `archive` of that entry |
| an id this memory does not know (a file from a teammate's repository) | `create` — the entry is new to this memory |
| text a memory entry already has | nothing |

The daemon cannot tell who edited a file — you, a teammate's pull, or an agent with file access (Mawas works in the Home folder, so she can write `.mawas/memory/` like any file) — so the proposal says *edited in a memory file*, never *by you*, and carries no session; what protects the memory is that **you approve the exact text** (and approving it as it stands records it as yours, like *Edit & approve*).

Until a proposal is answered the file shows **your** text (the mirror is the memory with the pending file proposals applied), so an edit does not flicker back; approve and the file shows the new revision, reject and it shows what the memory says. Putting a section back or editing it again withdraws or replaces the pending proposal (`cancelled`). Nothing is ever applied without approval, a missing file is not a deletion (it is written again), and a file with a problem archives nothing.

**What cannot be used** is a *problem*, listed by `memory.files.status` and shown in the Memory page's **Problems** card and by `hutan memory files`, each with the file, the section and the reason — never the text: a section that looks like a credential ("Memory is not a secret store", as ever), a body over 2 KiB or empty, an id that appears twice or belongs to an archived entry, an unreadable `<!-- mawas:… -->` comment, a file that is not UTF-8, over 1 MiB or a link. The sections of that file that read cleanly are proposed as usual; the broken ones are not, and nothing is archived because of a file with a problem. The file is **left exactly as you wrote it** until it reads cleanly again (fix it or put it back); the daemon never rewrites over text it refused.

**Export and import.** `hutan memory export [--scope global|workspace] [--ws ID|NAME] [--format md|json] [--force] PATH` writes the active entries of a scope — Markdown as the files are written (all three categories in one document), or JSON (`{"format": "hutan-memory", "version": 1, "scope", "entries": [{id, category, body, revision, state}]}`); the format follows the extension, `-` is standard output, an existing file needs `--force`. `hutan memory import [--scope] [--ws] [--category] PATH` (`-` reads standard input) sends `memory.import`: each section becomes a **pending proposal** with origin `import` — an `update` when its id is an active entry of the target scope with other text, a `create` otherwise, nothing when an active entry (or a pending proposal) already says the same — and prints what was proposed and what was skipped and why. Importing the same file twice adds nothing. The import itself saves nothing; at most 500 sections and 1 MiB. Both are the user's: an agent's connection is `forbidden` (`memory.import`, `memory.files.status`). `hutan memory files [--scope] [--ws]` says where the files are, whether the folder is inside a git repository, how many proposals wait and which edits were refused.

**Desktop.** The Memory page's **⋯** has a greyed-out line (*Memory files: ~/Hutan/.mawas/memory*, or why there are none), **Export…** (a save dialog; Markdown or, for `.json`, JSON, of the scope the page shows), **Import…** (an open dialog; the proposals appear under *Waiting for you*, the page says how many and what was skipped) and **Show files** (reveals the files in the Files panel). A proposal made from a file or an import says so on its card (*edited in a memory file*, *imported by you*). The **Problems** card lists the refused edits. *Keep memory in the project* is in Settings → Mawas.

**Versions.** The files are plain files, so after *Track changes in this folder…* (§ Where Mawas works) the Home folder's mirror shows in Changes and commits like any file, and a Mawas turn's checkpoint covers it; a workspace's `.hutan/memory/` is part of its project repository (`hutan memory files` says whether the folder is inside a git repository: *tracked*). The history of an entry stays in SQLite (`hutan memory history`); git shows the history of the text. Pull a teammate's files and their entries arrive as proposals you approve. Memory is not a secret store: nothing in the mirror is written that the store would refuse, and a pasted credential is refused when read.

## Project instructions (AGENT-INSTRUCTIONS)

A Mawas conversation of a workspace is told, at its start, that the workspace's folder has an `AGENTS.md` and what its first lines say: one block, `--- Hutan project instructions … ---`, after the memory block (alone when memory is off or empty), delivered the way the memory is — Codex's developer instructions, OMP's private prompt file, Claude Code's first turn, a provider's system message. The block says the file's size and its summary line (its first heading and the first plain paragraph line after it; front matter, comments, code fences, lists and tables are skipped) and tells Mawas it is background, not instructions, and that Hutan did not copy the rest: ask the user to attach `AGENTS.md` for more. Mawas reads it **read-only** and **bounded**: only the first 8 KiB of `AGENTS.md` of the workspace's first folder are read (never through a symbolic link out of the folder), the line is at most 240 characters and never more than `assistant.context_budget_chars`, the text goes through the redactor before the line is chosen (a secret in the first lines is gone), and nothing is read when the workspace's `files` permission (`[assistant.context]`, `[assistant.workspaces.<name>]`; for Home `[assistant.global_context]`, off by default) is off. The block is read at each start of the conversation; the desktop folds it like the memory block. Code: `crates/daemon/src/project_instructions.rs`. The agents' own instruction files: `docs/agents.md` § Instruction files.

## Global first and Focus (MAWAS-GLOBAL, protocol 0.61; ADR 0025)

Mawas is one assistant over every project and agent; a workspace is something she **looks at**, not a second assistant. Mawas Home opens the **Global** chat (`assistant.home_scope = "global"`, the default, in § Desktop), and a Global chat can carry a **Focus**: one workspace (or project) it is told about. Nothing is migrated: workspace chats and workspace memory keep their ids and stay reachable (*Chats ▾*, `assistant.open {scope: workspace}`, `assistant.list`), and `assistant.home_scope = "follow_workspace"` keeps how Home worked before.

- **What a Focus is.** A property of **one Global chat** (`ChatInfo.focus`, set by `assistant.focus {session_id, workspace_id?}`, protocol 0.61; absent: *All workspaces*). A workspace chat has none: its workspace is its scope. It is **a filter and a source of context, never a permission**: it does not change the chat's working directory (Mawas keeps working in the Home folder; Files follows where she works, § Where Mawas works), the daemon's context permissions (`[assistant.global_context]` still governs the chat), the grants, or her mode. It is chosen by the user only: `assistant.focus` is user-only (`forbidden` from an agent-originated connection, Mawas included), so she learns her Focus from her prompt and can never widen or move it. It is kept with the session across restarts.
- **What it adds.** (a) the Focus is named to the model — a `--- Hutan focus … ---` block that says the workspace's name and id, that a Focus is a filter and not a permission, and that she cannot change it; (b) the focused workspace's **memory notes** join the memory block (global entries always; workspace entries of the Focus only; the 8 KiB cap and its explicit cut are unchanged); (c) the summary line of the workspace's **`AGENTS.md`** (§ Project instructions), read under **that workspace's own** `files` permission (`[assistant.context]` / `[assistant.workspaces.<name>]`): a workspace that forbids files contributes the Focus line and no project line.
- **How it reaches the model.** At the conversation's start (the first message of a harness assistant, which starts asleep; a provider assistant's system message at creation) through the channel of each backend, exactly as the memory is (§ Memory). A Focus that **changes later** arrives as a **delta at the next turn boundary**: a `--- Hutan focus update … ---` block (*Focus is now "B", was "A"* / *was All workspaces*, or *Focus is cleared: All workspaces*), then the new Focus's `AGENTS.md` line, then the ordinary memory delta — **added** entries (the new Focus's notes), **changed** ones, and the old Focus's entries under **No longer in focus** (they are still active in the memory, so never reported as *archived*). The journal says so with a notice (*Hutan focus update added to this turn's context: …*); nothing restarts, no new chat is made, and a turn nothing changed for adds nothing. What the conversation was last told is the workspace its latest memory snapshot was taken for (`memory_snapshots.manifest.workspace_id`, kind `focus` when only the Focus moved); with `assistant.memory = false` the Focus is still told (and recorded), and nothing else of the memory is.
- **Not a boundary.** The Focus tells Mawas where to look; the gate (`docs/control.md` § Mawas) is what limits what she may do, whatever she is told. A Focus names a workspace, but a Global chat's `hutan mcp` tools still read every workspace as before.
- **Parity.** The scope dropdown of Home (*Global* / *Workspace · name*) becomes **Chats ▾** and the **Focus** chip; with `follow_workspace` the dropdown is back, unchanged.

## Flow (AGENTS-FLOW, protocol 0.66, capability `agents.stats`; ADR 0025 decision 3)

Where the time goes across your agents, what they wait on you for, what fails again and what the tokens were spent on — from what the daemon records, with the coverage of every number (rule R10).

- **Where it shows.** The **Recent** tab of the Today column has a compact **Flow · the last 7 days** section under the catch-up: *Waiting for you* (count, time in all, the longest, how many still go on), what failed the same way again, *Tokens by project* (the three largest; "none reported" when nobody reported any) and how many agents are worth a look. It says when a number rests on less than the window (terminal agents' waits count only from when the log began, or "the state log is off"). **Analyse with Mawas** puts a prepared ask in her composer — the window, the read-only tool `agents_stats`, "say how well each number is known and what is not recorded" — for you to read, change and send; nothing is sent. The CLI is `hutan agents --stats`, the MCP tool `agents_stats`; both print the same `agents.stats` answer (`docs/protocol.md` § Agents stats).
- **What is exact and what is not.** Chats are journaled: their turns, wall times, the requests they asked and your wait on each are **exact**. Terminal agents (OMP, Claude, Codex in a terminal) have no journal: how long they waited for you is known **only from the state log**, from the day it began. Retries are **inferred**; failure clusters are a **heuristic** (their counts are exact); cost is the harnesses' own estimate and absent where none was reported; active time per turn is **not recorded**. A terminal agent that says *working* for hours is **unconfirmed**, never "stuck". Mawas is told all of this by the tool's answer and her prompt; she must not claim more than the coverage allows.
- **The state log (privacy; R11).** `[agents] state_log` in `daemon.toml` (Settings → History → *What agents report*; **on by default**, applies at once): the daemon writes each *change* of the state an agent reports about itself — working, blocked, idle, done, error — with the time, who said it (`osc7501`, a hook), the kind of a blocked state and a short message **with secrets removed, one line, at most 120 characters**. It never keeps output or transcripts, never leaves the machine, is kept **14 days** and goes with its session. When an agent goes away (its process ends or the shell prompts again) the log says `gone`, which ends a wait it was in; after a daemon restart an agent that says the state it was in before is the same wait, not a new one (a restart neither ends nor restarts a wait, and the downtime counts in it). Turning the setting off stops the log **and deletes what it holds**; Flow then shows terminal agents' waits as not recorded.
- Tests: `crates/daemon/src/agents_stats.rs` (each metric with its coverage label and the "not recorded" cases, the bounds and the redaction), `crates/daemon/tests/it/stats.rs` (a real daemon: OSC and hook states logged and deduplicated, the wait span, a failure cluster, the setting off deleting and stopping the log, a Codex chat's audit wait and turn), `crates/storage` (write, the 14-day prune, emptying), `crates/cli` (`--stats`, MCP `agents_stats`), and `mawas_gpui.rs` / `daemon_settings_gpui.rs` (the Flow section, *Analyse with Mawas* filling the composer without sending, the Settings row).

## Idle assistants

A harness assistant (`omp`, `claude`, `codex`) is a helper for occasional questions, but its agent process is not small (an OMP backend holds about 460 MB), and every scope can have one. So an assistant that has not been used for a while gives the memory back and comes back on its own.

- **Sleep.** An assistant whose agent has been idle for `[assistant] idle_stop_secs` (default **600**; `0` never; otherwise at least 60; a live setting of `daemon.settings`, read at every check) has its agent process stopped by the daemon. Idle means: no turn, no pending approval, no pending question, and nothing has happened since the last turn end, approval answer or question answer (a turn start, an approval or a question being asked restarts the clock too). Only sessions marked `ChatInfo.assistant` are looked at: agent chats (`hutan chat new`, tasks) and direct or provider assistants are never stopped for being idle. The daemon logs `assistant <id> asleep, process stopped after N s idle` at info.
- **What clients see.** The session keeps its id, journal, model and state `idle`; it is not `stopped` or `failed`, there is no recovery chip and no `session.exited`. The only difference is that it has no process: `resources.list` shows none, and its agent tree is let go like that of any session whose agent ended.
- **Wake.** `chat.send` (and `chat.set_model` of a sleeping assistant, which needs the agent) starts the agent again, continuing the stored conversation the way a restart does (ACP `session/load`, else `session/resume`; Codex `thread/resume`), then delivers the message: the client sees the turn start a little later and no event a normal start would not emit. An agent that refuses to continue the conversation starts a new one next to the kept journal, and the journal gets the notice *The agent started a new conversation; the transcript is kept.* (the text of the recovery chip for the same case). A wake that fails altogether fails the send with the harness's error; the session stays `idle` and asleep, and the next send tries again. Two messages sent while it wakes share one start.
- **`assistant.open`** of a sleeping default returns it as it is: the panel shows the history at once, and the process starts with the first message. A stopped or failed default is restarted as before.
- **Created asleep (UX-MAWAS-LAZY).** `assistant.open` on a harness backend (`omp`, `claude`, `codex`) that has no assistant yet creates the session record — id, title, workspace, backend, the configured model if any — in state `idle` and marked asleep, and starts **nothing**: no `omp acp` (about 300 MB, with its `hutan mcp`), no throwaway ACP session for the model catalog, no journal rows. The first `chat.send` (or `chat.set_model`) wakes it like any sleeping assistant: the agent starts a new conversation (there is no stored one), on the model picked then when none was configured, and the message is delivered. So looking at Mawas costs nothing, and a harness that cannot start (not installed, not logged in) fails the **first send** with the harness's error — the session stays asleep and the next send tries again — instead of failing the open; the readiness check of an unconfigured scope (`invalid_state` listing what was checked) still fails the open. `ChatInfo.model` is empty until the first message. A provider assistant (a direct chat) has no process either way. After a daemon restart it comes back asleep as every assistant does. `hutan ps` and the desktop's Resources panel show no process for it; Resources says `Mawas · idle, no process` on a line of its own.
- **Stop and restart.** `session.stop` / `session.kill` of a sleeping assistant end it without starting anything. A daemon shutdown has nothing to stop in a sleeping assistant, and after a daemon restart *every* harness assistant comes back asleep: the daemon starts no agent for it at start (other chats are respawned as before; `restore_sessions = "stopped"` lists assistants as stopped like everything else). One whose last turn the shutdown cut off carries the usual `interrupted` recovery until the user writes to it.

## Attachments

`chat.send { session_id, text, attachments }`. At most 16 per message. Every chat takes attachments (protocol 0.23, `docs/protocol.md` § Rich input); `[assistant.context]` gates them for assistants and for agent-originated messages only. Every attachment is validated (its own bounds, then the permission of the session's scope) before the first one is read, and the first one that cannot be resolved fails the message: nothing is journaled, nothing reaches the provider.

| Kind | Fields | Read from | Cut keeps |
|---|---|---|---|
| `shell_block` | `terminal_id`, `block_id` | the terminal's output of that block (`terminal.block_text` path, M10) | the end |
| `shell_recent` | `terminal_id`, `lines` ≤ 500 | the last lines of the screen and scrollback (soft wraps joined; on a full-screen program only the visible screen) | the end |
| `agent_transcript` | `session_id`, `last_turns` ≤ 20 | a Hutan chat's journal (Codex, direct, assistant: the `message_end` events), else the history index rows of that session id (Claude Code, Codex, OMP; needs indexing) | the newest turns |
| `file` | `path`, `range?` `{start, end}` (1-based, inclusive) | the file, under the session's workspace roots only | the start |
| `search` | `query`, `limit` ≤ 10 | `history.search` (needs indexing): one line per session with its id, so that it can be attached next | the best hits |
| `turn_review` | `session_id`, `turn_id?` (default: the last finished turn) | the `agents.review` packet of that turn as text (protocol 0.67, § Reviewing a turn); gated by `agents` | the start |

Attachments also go to chats through the OMP and Claude Code harnesses (protocol 0.17, `docs/agents.md` § ACP harnesses): the agent gets each one as an ACP embedded resource, under the same permissions and bounds, and the journal's user message shows what it was given.

A turn is a user message and what follows it. A relative file path is relative to the first root of the workspace. Terminal and file text is plain text; a file that is not UTF-8 is `bad_request`.

**What the message becomes.** The user's text, then

```text
--- attached context (read-only, redacted, bounded by the user's settings) ---
[shell: cargo test -p daemon · exit 101 · 12 lines · cut to the last 3000 of 9000 characters]
…output…

[file: src/lib.rs · lines 1-40 · 40 lines]
…text…
--- end of attached context ---
```

Headers: `[shell: <command> · exit <code>|running · <n> lines]`, `[shell: terminal <id> · last <n> lines]`, `[agent: <title> · <hutan chat|claude|codex|omp> · <n> turns]`, `[file: <path> · lines a-b · <n> lines]`, `[search: "<query>" · <n> hits]`. A part that was cut says so (`cut to the first|last N of M characters`; M is left out when the source was only read in part, as for a big file), a source that was incomplete says `incomplete` (the terminal lost lines). This whole text is the journaled message: `chat.history` and the next turns' conversation contain it, so the conversation is reproducible and visible. The user's `message_end` event carries `payload.attachments_meta = [{kind, label, chars, truncated}]` so that a client can show chips without parsing text.

**Redaction.** Every text goes through the history index's redactor (`hutan_index::redact`: API keys, tokens, `Authorization:`/`Bearer`, PEM keys, `password=…` pairs, …; best effort, see `docs/history-index.md` § Privacy) *before* it is cut, so a secret straddling a cut is removed whole. Headers (a command line or a path may hold a secret) are redacted too. Files are read a little beyond their share (512 characters) so that redaction sees the end of a secret at the cut.

**Budget.** `assistant.context_budget_chars` (default 60 000) is split evenly over the attachments of one message (at least 1 character each); the user's own text and the earlier conversation are not part of it (the conversation is still limited by `gateway.max_context_chars`, oldest messages first; the new message, attachments included, is always sent).

**Files.** `context_file::read_file` canonicalises the path and the roots, requires the path to be inside a root (so `..`, an absolute path elsewhere, a symlink out and a sibling directory with the root's name as a prefix are refused with `forbidden`), and then opens it relative to a descriptor of the root with `openat(O_NOFOLLOW)` per component, the root's own ancestors included, so a symlink swapped in after the check fails the open instead of being followed. It reads only regular files, at most 8 MiB scanned, and builds the UTF-8 text from whole buffers (a character split by a read boundary is not an error).

## Reviewing a turn (AGENTS-REVIEW, protocol 0.67, capability `agents.review`; ADR 0025)

"Did it do the job?" is a question Mawas can answer from what Hutan recorded, without reading a whole journal. `agents.review` builds one bounded packet (at most 24 KiB, redacted) about one turn of an agent — the last finished one unless you pick another — and the same text is what the **`turn_review` attachment** gives a message and what the MCP tool `agent_review` and `hutan agents --review SESSION [--turn TURN] [--json]` return.

- **What is in it.** The prompt (first 400 characters) and the agent's final message (its own words, not evidence); the tools it called (failed, declined, by name); the **commands** with their exit codes and durations; the **files** it changed with their lines (from the turn's checkpoint; without one only the paths its own file tools named, and the packet says why); the language servers' **diagnostics** of those files *now* (flagged `stale` while a server is not ready); the requests that still wait for you; and **signals**.
- **Signals are heuristics, named and labelled, never verdicts**: a lockfile or manifest changed, a file was deleted, a path outside the session's folders, a secret-looking path (`.env*`, `*.pem`, `id_rsa*` …), a diff over 500 lines, *no test-like command ran*, a failed command followed by a "done" message. Each shows its rule in words and its evidence. Mawas is told (tool description and prompt) to say "tests passed" only when a command with exit code 0 is in the list, and never to infer a result from the agent's prose.
- **Honest about gaps (R10).** What the source does not hold is listed under *Not recorded*, each with its reason: an exit code the harness did not report (never shown as 0), the files of a turn whose checkpoint is off, the agent's active time per turn, events past a bound. A **terminal agent** has no turns: its packet is its report (state, message, when) and the list of what Hutan cannot know about it — turns, prompt and final message, commands, files, diagnostics — saying whether that is because only a hook's report (`hook`) or only OSC 7501 and the program's name (`recognised`) reach Hutan.
- **From the window.** *Review* on the footer of a finished turn (beside *Fork…*) and *Review Last Turn with Mawas* in the session menus and the Agents page's ⋯ attach the packet to **Mawas's composer as a chip** (`review · api · turn 3`); nothing is sent and nothing is read until you open the chip (it shows the packet's text under the chips) or send the message. For a terminal agent the entry says *Review with Mawas (what it reports)*. The chip is the attachment kind `turn_review`, gated by `[assistant.context] agents` like an agent transcript.
- **Data, not instructions (R7).** The packet carries text agents and users wrote; the MCP tool marks its result as untrusted data like the board's. It changes nothing: reviewing is a Read.

## Suggested answers (ASK-SUGGEST, protocol 0.64, capability `ask.suggest`; ADR 0025 rule R2)

Mawas watches the requests of your other agents (a permission to run a command, a question) and may tell you what she would answer. **Her suggestion is advice, never an answer**: she cannot answer an approval or a question (`approval.respond` and `question.answer` are for you only), and nothing is applied until you act.

- **Where you see it.** On the request's own card — in the chat transcript, in the inspector's Requests, and in the rows of Today on Mawas Home — a tinted box apart from the agent's options: *Mawas suggests: Allow once*, her reason (at most 400 characters), **Use** and **Dismiss**. `hutan approvals` and `hutan questions` print it under the request as *Mawas suggests … — advice, not an answer*.
- **Use.** On an approval it is your click on that option, through the same path as the agent's own buttons (the request runs as if you pressed it). On a question it **fills the form** with her values for you to read, change and submit; if she suggests to decline, *Use* declines. A question with a secret field takes no suggestion: only you type a secret.
- **Dismiss.** Hides that suggestion in this window; the request waits as before. A newer suggestion for it shows again.
- **One at a time.** A request carries at most one suggestion; the latest replaces the previous. It goes when the request is answered, expires or the daemon restarts.
- **Her gate.** `ask.suggest` is a change like the others (`docs/control.md` § Mawas): *Advisor* refuses it, *Ask before acting* asks you ("suggest an answer to the waiting approval 7 (you decide)") unless you allowed it for the chat; it never covers a request of a Mawas session, hers included. Tool `ask_suggest` of `hutan mcp`.

## Catching up (MAWAS-DIGEST-A, protocol 0.68, capability `notify.digest`; ADR 0025 decision 2)

Two ways to learn what happened while you were away, both **without a model** (no turn, no token, no tool call): the daemon's records are summed into one line, and that line is all either of them says. A third, **off by default**, asks a model on a schedule to write the digest ([§ The digest written by a model](#the-digest-written-by-a-model-mawas-digest-b-protocol-069-capability-digestmodel)). The same line comes from one function (`ActivitySummary::line`, `crates/protocol/src/activity.rs`), so the chip and the notification cannot disagree.

- **The line.** What needs you first, then what finished: `2 requests wait for you · 1 turn failed · 1 task sent to review · 3 turns finished · 2 tasks done · 4 files changed`. Requests that wait, failed turns, failed tasks and tasks sent to review need you; finished turns, done tasks and changed files do not. Sessions that began or ended are not news (a shell starting is not something to catch up on), and there is no line at all when nothing else happened.
- **The Catch up chip.** In Mawas Home's empty conversation (a new chat, before the first message) a compact **Catch up · 2 requests wait for you · …** button shows the line for the events since you last caught up — the same window and the same *last seen* marker as the rail's Recent tab (`desktop-state.json`, *Mark as seen*), read once from `agents.activity`, refreshed when the agents change, and costing nothing. One click opens the rail on its **Recent** tab, opening the rail first when it is hidden, and remembers the tab. When nothing happened — or you marked it all as seen — there is no chip. A conversation that already has messages shows none.
- **The digest notification.** When no Hutan window has been the active one for a while and something needs you, the daemon posts **one** quiet native notification — *While you were away*, with the line — so you do not have to open anything to know there is something to do. It is a banner without a sound and nothing is asked of any model. A click (or *Open*) brings Hutan forward on Mawas Home with the Recent tab showing.

**When it is sent** (`crates/daemon/src/digest.rs`, `decide`). Setting `notify.digest_hours` (Settings → Mawas → *Catching up* → *Notify me after being away*; `[notify] digest_hours` in `daemon.toml`; live, no restart): **`0` is off, and off is the default** — nobody gets a notification they did not ask for. With *N* hours, the daemon looks every five minutes and sends a digest only when **all** of these hold:

1. no window is the active one: the desktop tells the daemon with every `client.focus` whether its window is the OS's active one (`window_active`), so a window that is open behind another app counts as away, and so does no desktop connected at all; the start of the daemon counts as the last moment you were here, so a restart does not make a digest due;
2. the last window left at least *N* hours ago;
3. the last digest went out at least *N* hours ago — **at most one per period, never one per agent** (the time of the last one survives a restart);
4. the activity since the later of your leaving and the last digest **needs you** (a request that waits, a failed turn or task, work sent to review). Finished work alone is not worth a ping: you get nothing, and the chip is still there when you come back. A request that was already waiting when you left is not news; the digest says what came after.

It is raised through the daemon's notification pipeline as a `digest` intent for Global Mawas's chat (`notify.enabled = false` silences it; it is not one of `notify.kinds`, its own switch is the setting) and is posted natively only from `Hutan.app` like every notification (`docs/packaging.md` § Native notifications). It needs a Mawas Home conversation to open: the desktop creates one the first time Home is shown, and without one the daemon sends nothing. Hutan has no quiet hours of its own, so there is nothing for the digest to respect there beyond the system's own Focus modes, which silence the banner as they do any other.

Tests: `crates/protocol/src/activity.rs` (the line), `crates/daemon/src/digest.rs` (`decide`: off, the period, an active window, no desktop, one per period, the state file), `crates/daemon/tests/it/digest.rs` (a real daemon with a shortened hour: once, silence with nothing to say, off by default and live, a closed window), `crates/desktop/tests/it/mawas_gpui.rs` (the chip and its click, the setting row, the window's activation reaching the daemon, a digest's *Open* showing Recent).

### The digest written by a model (MAWAS-DIGEST-B, protocol 0.69, capability `digest.model`)

Setting `notify.digest_model` (Settings → Mawas → *Catching up* → *Digest written by a model*; `[notify] digest_model` in `daemon.toml`; live): **`off` is the default**, `daily 08:30` (local time) or `every 6 h` (1 to 168). On the schedule the daemon asks a model, once, to write the digest of what your agents did in the last period and tells you in **one notification** (*Digest*, with the first lines of the answer); *Open* shows the **Digest** chat. This is the only place Hutan starts a model turn nobody asked for, so it is narrow (the conditions and what remains open are in `docs/control.md` § Mawas → *Unattended runs*; ADR 0017 amendment 2026-10-31):

- **OMP only.** It runs on the harness Global Mawas has. With Claude Code, Codex or a provider the setting stays but the run is refused with the reason, and the row under the setting says *Cannot run now: …*.
- **No web, no files, no commands, no OMP tools** — only Hutan's read tools (`agents_activity`, `agents_stats`, `agents_board`, `agent_review`, `question_list`, …; never a change, `ask_suggest` or `memory_propose`). The prompt carries the window's `agents.activity` and `agents.stats`, marked as untrusted data, and says to ask no question and to finish in one reply.
- **Checked before every run.** OMP answers `/tools` and `/mcp list` itself, for free; if anything but Hutan's read tools is active or another MCP server is loaded, the run is skipped and the reason is a notice in the Digest chat and in the notification (not repeated for the same reason the next period). A different OMP version than the verified one (`18.13.3`) is skipped with *re-verify* unless *Run the digest on another OMP version* is on.
- **Bounded.** One run at a time, five minutes at the most, then stopped; a run that fails, stalls or is skipped is reported once and **not retried until the next period**. A window in which nothing that matters happened is not a run (no model call, no notification). A daily schedule fires once per day after its time (a daemon that was off at 08:30 runs it when it starts), "every N h" when N hours have passed since the last run.
- **The Digest chat** is a Global Mawas chat of its own (listed as *Digest* in *Chats ▾*, never the default, no memory written by it); each run starts a fresh OMP conversation in it, so the context does not grow day by day. You can read its messages and the notices; sending it a message starts the same locked launch.
- **Cost.** Under the setting Settings shows what a run reads: the average context the last runs ended with (OMP's `usage_update`; every model call re-reads it, so the bill is at least that), the next run, and how the last one went. Before the first run it says the cost is shown after the first run — Hutan does not guess it.

Tests: `crates/daemon/src/digest_model.rs` (the schedule, `check_tools`, `check_mcp`, the version), `crates/daemon/src/harness.rs` (the exact recipe), `crates/daemon/tests/it/digest_model.rs` (a fixture OMP: a verified launch runs once with exactly the recipe's arguments and one server; an extra tool, an extra MCP server, another version, Claude Code and Codex, an unwritable overlay and a stalled run are skipped or stopped with the reason; nothing happened is no run), `crates/desktop/tests/it/mawas_gpui.rs` (the row, its status and cost, the Digest label, *Open*). The real run that closed the slice is in the report of MAWAS-DIGEST-B (a hostile fixture and a 127.0.0.1 canary: digest produced, canary silent).

## Permissions

```toml
# daemon.toml
[assistant]
provider = "openrouter"            # a provider of `hutan provider ls`; used for assistants created from now on
model = "meta-llama/llama-3.3-70b-instruct"
context_budget_chars = 60000
idle_stop_secs = 600               # a harness assistant idle this long stops its agent process; the next message wakes it. 0 = never, else at least 60
mode = "ask"                       # "ask" (Ask before acting, default) or "advisor" (read and advise only): § Modes and safeguards
max_actions_per_turn = 10          # changes Mawas may make in one turn before every further one asks (1-1000)
memory = true                     # give Mawas conversations the memory you approved (false: nothing is injected)
memory_max_entries = 200          # most active memory entries (1-10000)

[assistant.context]                # assistants of project workspaces
shell = true                       # shell_block, shell_recent
agents = true                      # agent_transcript
files = true                       # file
search = true                      # search

[assistant.global_context]         # the global (Home) assistant: files are off by default
files = false

[assistant.workspaces.hutan]      # per workspace, by name or id: only what differs from [assistant.context]
files = false
```

An attachment the settings do not allow is `forbidden`, and the message names the setting (`assistant.context.shell`, `assistant.global_context.files`, `assistant.workspaces.<key>.files`); the error's `data.setting` has it too. The permissions are read for each message, so a change made through `daemon.settings.set` (`hutan config set assistant.context.files false`, protocol 0.28, `docs/protocol.md` § Daemon settings) holds from the next message on; a hand edit of the file is picked up by the next such change or a restart. Settings gate the daemon's own reading; they do not make an attachment out of anything that was not attached.

Other refusals: `bad_request` (bounds, more than 16 attachments, a session that is not a chat), `not_found` (terminal, block, file, transcript), `invalid_state` (`search` or an external transcript while indexing is disabled).

## Indexing of chats

With `[history] enabled` the daemon feeds the journals of **all** chat sessions (Codex, direct, assistant) into the index as source `hutan`: user and assistant messages (`user`/`assistant` rows), tool calls and their output (`tool` rows), as they are journaled, keyed `c:<seq>`. The session id is the key and `history.search` hits carry it as `session_id` (also for terminal sessions), so a client can open the session; there is no `resume_argv` (resume = focus the session). Like all Hutan rows these are not backfilled from before indexing was on. A message with attachments is indexed with its attachments (redacted, at most 16 chunks).

## Desktop

**Mawas Home** (`assistant`, a registered panel like every other, shown as **one tab of the center**; it replaces the left-only page of OL-2) shows one Mawas chat with the ordinary chat transcript and composer of agent chats, 46 rem wide by default (you set it: see *Width and Today* below) and centered, and the collapsible **Today** rail on its right. The left nav's **Mawas** row (only while `assistant.enabled`), ⌘K → **Mawas: Open** / **Mawas: New chat**, a bound `OpenAssistant` key, the menu bar item and `assistant.global_shortcut` (e.g. `alt-space`, for the whole OS) open it; there is never more than one Home, it can be closed (× on the tab) and reopened, it is part of no preset, and it can still be moved like any panel. No key is bound by default. Opening it calls `assistant.open` (which starts no agent process: § Idle assistants) and shows the returned session: no terminal is started.

**The header** is one row with a hairline below (CL-AGENTS): the **scope** dropdown and the **mode** menu (*Ask before acting ▾* / *Advisor ▾*: choosing one sets `assistant.mode`; the page says under the header that it applies from the next message, and the daemon restarts the agent for it) as ghost menus, then — on a page 640 pt wide or more (scaled by the UI size) — the **backend·model** as muted text with the state dot (it opens the Switch model… / chooser menu) and **New chat** (a fresh conversation in the shown scope, `assistant.open {new: true}`), and **⋯**; below 640 pt the backend·model is one muted line under the header instead (never hidden: it names the model the first message started, `Claude Code (Work) · …` for a managed account, `Automatic · …` until the daemon picks). **Stop** (the kill switch: denies every request the chat has pending, then interrupts its turn) is drawn in the header, in the error color as text and at any width, whenever there is something to stop (a turn runs or a request waits), so it is never folded away while it can act. Below 640 pt the header **folds** into scope, mode and ⋯ and nothing wraps: ⋯ holds *New chat*, *Stop Mawas* (greyed out when there is nothing to stop), *Today* and *Backend: …* (the same menu as the backend label); above 640 pt ⋯ holds *Stop Mawas*, *Hide Today* / *Show Today* (the same switch as the header's Today button) and *Backend: …*. Below 640 pt **Today leaves the page** instead of taking a column from the composer (which once wrapped letter by letter in a 470 pt pane): ⋯ → *Today* shows Today in place of the conversation (checked while it does), and again hides it. The empty conversation is the mascot, one sentence (*Ask Mawas anything. Attach context with @ or +.*) and one muted line on what is sent to the model; there is no button, the composer (placeholder `Ask Mawas…`) already has the keyboard. Looking at what waits for the user is Today's *Review requests*, ⌘⇧J and the Agents page.

**Global first (MAWAS-GLOBAL; `assistant.home_scope`).** One more setting of the `assistant` namespace, in Settings → Mawas → **Layout** (*What Mawas Home opens*) and `settings.toml`: **`assistant.home_scope`** is `global` (the default) or `follow_workspace`; a file from before it loads as `global`. With **`global`** Mawas Home opens the **Global** chat whatever workspace is active, and changing the active workspace moves nothing; the nav row, ⌘K → *Mawas: Open*, the menu bar item and the global shortcut all show it. The header changes:
- **Chats ▾** replaces the scope dropdown. It lists the **Global chats** (oldest first, each with its Focus when it has one, *Mawas · Focus api*) and, under **Workspace chats**, the chats of workspaces that earlier versions made (*Mawas · api*); the shown one is checked. Choosing a chat shows it with its transcript, draft and chips as they were: an old workspace chat opens exactly as it did, in its own scope (nothing is migrated). *New chat* makes one more Global chat.
- **Focus: All workspaces ▾** is the chip that picks the shown Global chat's Focus (`assistant.focus`): *All workspaces*, then every workspace and project (Home never), the current one checked. Choosing one sends the request and the chip follows the daemon's announcement; Mawas hears of it at the next message (§ Global first and Focus). A **workspace chat** opened from Chats has no Focus: the chip becomes the muted text *Workspace · name* (its focus is fixed by its workspace). On a daemon without capability `assistant.focus` the chip is not drawn. The chip stays in the header below 640 pt.
- **Send to Mawas** (a terminal block) goes to the Global chat; the daemon reads it under the Global chat's permissions (`shell` is on for Global by default, `files` is off).
- **The rail follows the Focus (RAIL-FOCUS; desktop only, no protocol change).** With a Focus on the shown Global chat, the Today rail shows that workspace's agents (a project in it counts; Mawas's own requests always show): **Now** lists its requests, failures, work to review, working and idle agents and, under them, one line **+ N agents in other workspaces**; **Recent** and **Flow** ask the daemon for that workspace (`workspace_id` of `agents.activity` / `agents.stats`) and say *in <name> ·*; the **Catch up** chip counts the same scope and says which (*in hutan · 1 request waits for you*); the prepared *Summarise* / *Analyse* asks name the workspace and its id. A click on the line shows every workspace for this page only (nothing is saved; the line becomes **Only <name>**, and another Focus starts over at its Focus). *All workspaces*, and a workspace chat, change nothing: the rail is the view of every agent in every workspace. The Today button's badge counts what the rail shows. Test: `mawas_gpui.rs` (`a_focus_filters_the_rail_and_the_catch_up_to_its_workspace_and_counts_the_rest`).
With **`follow_workspace`** Home is exactly what it was: it follows the active workspace (the workspace's own Mawas, the Global one at Home), the header has the scope dropdown below and no Chats menu or Focus chip, and a block goes to the Mawas of the terminal's workspace. Changing the setting sends Home back to what the new value opens.

**Width and Today (MAWAS-LAYOUT; desktop only, no protocol change).** Two settings of the `assistant` namespace shape the page, both in Settings → Mawas → **Layout** and in `settings.toml`; a file from before them loads unchanged.
- **`assistant.chat_width_rem`** (default `46`, read within 30 to 90) is the width of the conversation column in rem, so it follows the UI size; what the column holds (cards, composer) fills it instead of stopping at the theme's `reading.width`, which only a chat of its own keeps. The column keeps a 12 pt margin on each side and never grows past the page minus those margins; it is centered, and the Today column (when shown) sits to its right outside it. On a page 640 pt wide or more the column has a **handle on each edge**, a 12 pt strip just outside it with the resize cursor and, under the pointer, a thin accent line: dragging either edge moves the pointer's travel twice (the column stays centered, so dragging the right edge 40 pt right makes the column 80 pt wider, and dragging the left edge 40 pt left does the same). The column follows the pointer live; **nothing is written while it moves**. Releasing writes the width once, rounded to half a rem (a press that did not move writes nothing); **Esc** during the drag puts the width back and writes nothing; a **double click** on an edge removes the key (the default width again). The width is held within 30 rem, 90 rem and the page minus its margins at every step, so it never writes a value the page could not show. Below 640 pt there are no handles. Every window follows the written value through the settings' own change notice. *Settings → Mawas → Chat width* has the field (with the range and, once the file sets it, the ↺ *Reset*).
- **`assistant.rail_open`** (default `true`) is whether the **Today** column is shown. A **Today button** in the header (above 640 pt; tooltip *Hide Today* / *Show Today*, selected while the column shows) and ⋯ → *Hide Today* / *Show Today* toggle it, and write the setting, so a new Home tab and a new window start the same way. While Today is hidden the button carries a **badge: the number of sessions that have a request** (`Today::requests` grouped by session; a session that asks twice counts once), because a hidden column must not hide an approval. **A request that arrives never reopens the column**: the badge changes, nothing else moves (Mawas's own approvals still show as cards above the conversation). Below 640 pt the button is not drawn: Today is the page ⋯ → *Today* shows, whatever the setting says. A hidden Home draws nothing, with or without the column (the existing rule).
- **`assistant.rail_width_rem`** (default `21.25` = 340 pt at the default rem, read within 17.5 to 32.5) is the width of the Today column in rem. Its **left border** takes the drag (a 6 pt strip with the resize cursor and, under the pointer, a thin accent line): the column grows by the pointer's travel to the left, live, **nothing is written while it runs**, and the release writes the value rounded to half a rem; Esc ends a drag and restores the width; a double click removes the key. The column never takes more than the page minus 360 pt (the conversation keeps that), and below 640 pt there is no column to drag.
- **`assistant.rail_tab`** (`now` by default, `recent` or `memory`) is the tab of the Today column that is open; it is written when a tab is clicked, so a new page and a new window open on the one you left.
- **Palette** (⌘K): *Mawas: Wider Chat* and *Mawas: Narrower Chat* (±4 rem, within 30 to 90, rounded to half a rem), *Mawas: Reset Chat Width* (removes the key) and *Mawas: Toggle Today*. They need `assistant.enabled` like the other Mawas commands, and appear in `hutan ui actions` as `workbench::WiderMawasChat`, `NarrowerMawasChat`, `ResetMawasChatWidth` and `ToggleMawasToday`.


**The Today column's tabs (AGENTS-BOARD-B; desktop only, no protocol use).** The column has three tabs under its top edge, each with a count: **Now** (the number of sessions that have a request), **Recent** (the events since you last caught up) and **Memory** (the number of memory proposals that wait). **Now** is the board of every agent, grouped like the Agents page by the same reducer (`hutan-agents-view`, from the store the window already holds — it does **not** call `agents.board`, so a hidden Home still does no work and nothing polls): *Requests* (answered in place), *Failed*, *Ready for review*, *Working*, and **Idle · N (hidden)**, one folded line that opens the idle agents (they are not news). Every agent row opens its session; *Working* and *Idle* rows say what their state is worth after the harness — `exact` for a chat the daemon runs, `state only` for a terminal agent's own report. **Recent** answers *what happened since I was away* with no model call, from the daemon's records (`agents.activity`, `docs/protocol.md` § Agents activity): a line saying since when (**the time you last pressed *Mark as seen*** — kept in `desktop-state.json` with the attention marks, never in the daemon — or the last 24 hours until you have), the counts (turns finished, failed, running; requests asked and answered, how many still wait and the longest wait; files and lines changed; tasks done, failed, sent to review; sessions started and ended), then the events **grouped by agent**, newest agent first, three each (`+N more`), each group opening its session; a note of what is not recorded (terminal agents have no turns and no history of states) and, when the list was cut, that the counts cover the rest. **Summarise with Mawas** puts a prepared ask in Mawas's composer (it names the window and the read-only tools `agents_activity` and `agents_board`) for you to read, change and send: nothing is sent and nothing is journaled until you do. **Mark as seen** moves the point to the end of what was read. The tab reads when it is shown and again when the agents change (at most every two seconds); a hidden rail does nothing. **Memory** lists what waits for you in Mawas's memory (the proposal cards, with their options and *Edit & approve*, exactly as under Requests), the **latest entries** Mawas keeps (up to six: the first line of each, its category, and *written by Mawas* while a model's text is unconfirmed; read from the daemon when the tab is shown and again on `memory.changed`, nothing while it is hidden) and **Open Memory** (the Memory page, which keeps its place in the left sidebar; this was the *Memory ›* link under Today). Below 640 pt the tabs are the tabs of the Today page (⋯ → Today).

**Today** (`panels/assistant_rail.rs`) is a view of the sessions store — the agent presentation every surface reads — so it does no polling and no request of its own. It is the compact projection of the Agents page (CL-AGENTS): a `surface` card with no hairline, and **only the sections that have content** (`Today::sections`), each a section label with its count. *Requests · N* lists what the Agents page lists in its *Requests* group (FX-REVIEW: the same records of the one reducer, not a second rule set), in its order: Mawas's approvals first (each item shows the request and the options the daemon offered — only *Allow once* is primary, as everywhere a request is answered — answered in place with `approval.respond`), then other agents' approvals and questions, and one row for every other session that needs the user — blocked without saying on what (**Open**) — then the link row *Review requests ›* (the next session that wants the user, ⌘⇧J); *Failed · N* and *Ready for review · N* list the sessions of those groups, one row each (**Open**; a finished turn is never a request); *Working · N*: the Agents page's rows (state glyph, title, `Working`, the harness), a click opens the session, and *State unavailable · N* opens the page on that group. Mawas itself is never counted as an agent under *Working* (nor a row of the Agents panel): it is the one asking. With nothing in either, Today says one muted line, `No requests · nothing working · no schedules`; there is no *Upcoming* section until schedules exist. **Memory ›** is a link row at the bottom that opens the Memory page. Skills, Schedules and Traces have no link until those services exist (ADR 0017 MW-2…MW-9). What Mawas asks of Hutan's own gate is also shown as cards above the conversation, because a harness's transcript cannot hold it.

**A hidden Home does no work**: the workbench tells it when it is the active tab of a pane (and when the user moved it to a dock, when that is visible); a hidden Home ignores store changes and draws again only when shown. There is no timer.

**A message to another agent** (MAWAS-GATE, protocol 0.62; ADR 0025 decision 3). When Mawas asks to message, interrupt or review another agent (`chat_send`, `chat_queue_add`, `agent_interrupt`, `task_review`), its card in Today and above the conversation shows **who** (*To <agent>*) and **every word** in a box, and offers *Allow once*, *Allow for this chat and this agent* and *Deny* — never a workspace-wide option, and nothing past 2 KiB. In the target's chat the queued message is a chip marked **from Mawas** (remove or *Send now*; editing it makes the words yours), and the delivered message carries *from Mawas · sent with your approval*. Rules: `docs/control.md` § Mawas › Acting on another agent.

**Scope** (with `assistant.home_scope = "follow_workspace"`; by default Home opens the Global chat and the header has **Chats ▾** and the **Focus** chip, below). The header's scope dropdown chooses **Global** (the Home workspace's Mawas: it sees the Home folder only) or **Workspace · name** (the active workspace's Mawas; disabled while Home is active). Each scope has its own session, so switching keeps both transcripts, drafts and chips; nothing moves from one to the other. **One session, one tab.** A Mawas conversation is shown by Mawas Home only, whichever surface opens it (the Sessions panel, the Agents page, the palette, a notification, a history hit, `hutan ui run`): Home shows it in its own scope, and there is no chat tab of it beside Home (a Mawas session opened with `assistant.enabled` off is an ordinary chat tab). The Home tab is titled and drawn like the session on every other surface: the session's title (`Mawas`, or `Mawas · project` when it has a project scope) with the Mawas sparkle, never the robot of an agent harness. A saved layout that holds both Home and a chat tab of the same conversation (older versions opened both) is merged once the daemon has said what each session is: the chat tab goes (Home takes its place when the layout has no Home), a terminal tab of a session that turned out to be a chat becomes a chat tab, and a pane never keeps two tabs of one session (splits of one session in different panes are the user's and stay).

**Backend and model.** The header is one compact row (scope dropdown, state dot, chip; `docs/design.md` § Layout). The chip shows what the shown scope's assistant runs on (`OMP · anthropic/claude-sonnet-4-5 ▾`, cut with "…" in a narrow sidebar; `Automatic` where the session's model is not known) and opens a menu: **Switch model…** and **Backends and models…**, the chooser: the backends (OMP, Claude Code, Codex with their detection and logins, and each provider), then the models of the one picked, or **Automatic** (no stored model: the daemon picks one, and the chooser says `Automatic · runs <model>` once the session exists). Choosing stores it with `assistant.configure` for the shown scope (Global for the Global tab, the workspace for the Workspace tab) and opens that scope's assistant on it.

**Where the defaults are set.** Settings → **Mawas** (desktop, ST-3, MW-1) sets, under *What Mawas may do*, the **mode** and **changes per turn** (`assistant.mode`, `assistant.max_actions_per_turn`, with `daemon.settings.set`); under *What you allowed Mawas to do without asking*, the **grants** the approvals stored — each with its tool, where it applies (a chat, or always in a workspace) and **Revoke**, and **Revoke all** (`control.grants.list|revoke`); the backend and model per scope (Global, and the workspace or project shown) with **Inherit** (`assistant.reset`), and the permissions of § Permissions (`assistant.context.*`, `assistant.global_context.*`, the overrides of the shown workspace with Inherit / Allow / Deny, `context_budget_chars`). The header's chooser still sets the shown scope. When nothing was chosen (no choice of this window, none in `daemon.toml`) the header says **`Automatic · <backend> · <model>`** and Settings says the same under the scope, so an automatic pick does not read like a pinned choice.

**Off.** `assistant.enabled = false` (settings namespace `assistant`; **default true**: Mawas stays a headline feature, the first run does not ask for it and writes nothing for it, `docs/design.md` § First run) closes Mawas Home and hides its nav row, removes *Mawas: Open* / *Mawas: New chat* and *Panel: Open Mawas* from ⌘K, ignores an `OpenAssistant` binding and unregisters the system-wide shortcut; a history hit that is a Mawas conversation opens as an ordinary chat tab. The daemon keeps its sessions.

**Nothing ready.** With nothing configured the daemon's automatic backend opens Mawas by itself (§ Backends). When it answers `invalid_state` because nothing is ready, the page shows a card instead of the daemon's words: **Use OMP** when OMP is installed and logged in (it stores OMP globally and opens Mawas), **Add a provider…** (Models settings) and Retry. Nothing is sent anywhere until the user chooses. The first-run setup's Agents step preselects the first ready harness in the daemon's order (OMP, Claude Code, Codex); its **Mawas** switch turns `assistant.enabled` on.

**Without a provider (older daemons).** The daemon names the assistants' provider and model under `[assistant]` in `daemon.toml` and reads it at start. When `assistant.open` is refused with `invalid_state` the panel says so in the daemon's words, links to **Models settings** and offers Retry. The desktop never picks a provider or model of its own and makes no model call. A configured provider whose key is missing or rejected shows **Set key…** like any gateway chat, a missing model **Pick another model…**; the chip menu's **Switch model…** applies to assistants too.

**Context.** Context is opt-in per message and never read by the desktop. The composer's **＋ Attach** menu opens the form of each kind; typing a mention in the composer offers the same form (↹ or the hint's button accepts it and removes the mention from the draft):

| Mention | Form | Chip (`kind · source · bounds`) |
|---|---|---|
| `@shell` | the daemon's live terminals (those of the assistant's workspace first); **Recent output** (the field is the number of lines, default 50, at most 500) or **Blocks ▾** to pick one of the newest blocks | `shell recent · title · last 50 lines`, `shell block · title · $ cmd · block #7 · exit 1` |
| `@omp`, `@agent` | sessions that reported an agent session id, Hutan chats, and the indexed transcripts of the words typed after the mention (`@omp` is OMP only); a stepper for the turns (default 5, at most 20) | `agent · title · omp · last 5 turns` |
| `@file path[:first-last]` | the path and optional lines; with the argument typed the chip is made at once | `file · src/lib.rs · lines 1-40` |
| `@search words` | the words and a hits stepper (default 5, at most 10) | `search · “words” · 5 hits` |

Chips are removable (×) before the send and become structured attachments of `chat.send` (at most 16). An attachment that is not a chip is never read or added to the prompt. After the send the user's message shows what the daemon resolved for each attachment (`attachments_meta`: kind, label, characters kept, and a warning tint with "cut to the budget" when truncated), with the attached text folded away. A refusal (`forbidden`, `not_found`, `invalid_state`, bounds) shows the daemon's message in the banner, keeps the draft and the chips, marks the chips the settings refuse as *refused* and journals and sends nothing. File paths are checked by the daemon (see Files above): the form says so and never opens the file.

**Send to agent.** "Send to agent" of a finished terminal block (button, ⌘K, key) attaches it to the chat the user looked at last — Mawas counts once the user opened or focused Home after the last chat tab — or to the only running chat, or to the one picked from the menu. When that chat is Mawas the block becomes a `shell_block` attachment (a block reference the daemon reads when the message is sent; Home is shown and the chip waits in its composer); other chats keep the quoted-text chip. When several chats run and none is Mawas the menu adds **Send to Mawas**: the Global Mawas (with `assistant.home_scope = "follow_workspace"`: the Mawas of the terminal's workspace), opened on demand. With no chat running the notice points at ⌘K → Mawas.

## Where Mawas works: browsing and versions (MAWAS-FILES, protocol 0.44)

**Her folder.** The Global Mawas works in the **Home folder** (`~/Hutan`); a workspace's Mawas works in that workspace's active project (a workspace holding two projects shows the active one, else the first). Both are plain folders she reads and writes through her tools, so the user must be able to see them.

**Browsing.** The Files, Search, Problems and Changes panels show the Home folder while Home is the active container, and **follow Mawas's scope while Mawas Home is the focused center tab**: *Mawas · Global* shows the Home folder (Changes: the Home checkout, once the folder is tracked, so what Mawas wrote is one click away), *Mawas · <workspace>* that workspace's active project; the scope chip of the four says which. Focus a file or terminal tab and they are about the project again. A file opened from the tree is a normal file tab. ⌘P keeps its own rule (the active project's files; no file list at Home). Mawas Home's **⋯** menu ends with *Where Mawas works: ~/Hutan* (greyed out), **Show Folder in Files** (reveals the panel in the right dock), **Open Folder in Finder** and **Open Terminal Here** (a terminal of that container, started in her folder).

**Versions.** The Home folder is not a git repository, and without one Changes, checkpoints and *Rewind…* have nothing to work with (ADR 0019: "Checkpoints need a git repository"). **Track changes in this folder…** — a button in the Changes panel at Home (shown instead of the empty list) and an entry of Mawas's ⋯ menu in the Global scope — opens a confirm sheet that says what happens, then sends `project.git_init` for the Home workspace (user-only; an agent, Mawas included, is `forbidden`, and the MCP surface has no tool for it): `git init`, a `.gitignore` with Hutan's own scratch files (`.hutan-write-*.tmp`, `.DS_Store`; added to an existing file, whose lines stay), and one initial commit of what is there now with the user's own git identity. Nothing leaves the machine; there is no remote. The daemon refuses the user's home directory and `/`, a folder that already is (or lies inside) a repository, a folder with more files than checkpoints seed (`[checkpoints] max_untracked_files`) and a missing git identity, in words the notice shows; a failure after `git init` removes the new `.git` and puts `.gitignore` back. `hutan project git-init --home` does the same from a terminal (`docs/orchestration.md`).

After that the Home folder is a checkout like any other: Changes lists it and its diff, **Finish** commits there (a repository without a remote ends in a skipped push step, *commit only*), and **checkpoints** are taken for Mawas's turns — also those of harness-backed assistants, which had none before (the daemon records a turn's checkpoint when the assistant wakes and answers, like for any agent chat), so *Rewind…* works on what she wrote. A repository rooted *at* the Home folder never becomes a project: sessions in its subfolders stay in Home.

Tests: `crates/daemon/tests/it/git_init.rs` (the repository and its one commit by the user's identity, the scratch file left out, refusals of `$HOME`, `/`, a nested repository, an over-limit folder, a missing identity, an agent connection, rollback), `checkpoint_turns.rs` (a Mawas turn at plain Home says why it has no checkpoint; after `project.git_init` the next turn has its ref), `crates/desktop/tests/it/mawas_files_gpui.rs` (Files at Home, following both of Mawas's scopes, the ⋯ entries, the confirm sheet, Changes turning on, a fixture-agent Mawas turn getting its checkpoint), `crates/cli/tests/it/projects.rs`.

## CLI

```text
hutan ask "<question>" [--ws <id|name>] [--attach <spec>]…
hutan assistant ls [--ws <id|name>]
hutan assistant open [--ws <id|name>] [--new]
hutan assistant reset [--ws <id|name>]
hutan grants ls [--ws <id|name>]
hutan grants revoke <id> | --all
hutan memory ls|add|edit|archive|restore|history|proposals   (§ Memory)
hutan memory export|import|files                                (§ Memory files)
```

`hutan grants ls|revoke` list and remove what Mawas may do without asking (user-only: refused inside an agent's session); an approval is answered with `hutan approve <id> allow_once|allow_chat|allow_workspace|deny` (`hutan approvals` lists the options). `--attach` specs: `block:<terminal>:<block>`, `recent:<terminal>:<lines>`, `agent:<session>[:<turns>]` (default 5), `file:<path>[:<first>-<last>]`, `search:<query>` (5 hits; quotes optional). `ask` uses the default Mawas of `--ws`, else `$HUTAN_WORKSPACE`, else the global one (Home), prints the answer as it streams and exits 1 when the turn fails (also when the daemon refuses an attachment: the message is on stderr). `--json` prints every event. `hutan chat log <session>` shows the whole conversation, attachments included.

## Limits

Attachments are text only; a file larger than the scan bound (8 MiB) is read from its start. `shell_recent` joins soft-wrapped rows but cannot tell a hard line break from a wrap on a program that draws its own screen. An external transcript is read from the index (redacted chunks of at most 16 per message, merged back into messages), not from the transcript file. Settings are read at daemon start. In Advisor mode Mawas cannot run commands or change files; in Ask before acting it can, only with the user's approval, and the daemon's gate rests on the origin of the request, which is cooperative (`docs/control.md` § Mawas): a restricted endpoint with a sandbox for unattended runs is ADR 0017's MW-10. A direct-provider Mawas is *Chat only*: it has no tools. The desktop cannot read the daemon's `[assistant]` settings: it learns that a provider is missing from `assistant.open`'s refusal and that a context kind is not allowed from `forbidden` on the first message that uses it, not before.
