## LSP client (E-11a)

`hutan-lsp-client` runs one language server as a child process; the daemon's `LspHub` (E-11b, `docs/lsp.md`) owns one `Server` per `(server, workspace root)`. No GPUI, no daemon types; types from `ls-types` (the maintained fork of `lsp-types 0.97`; the API is the same except that `ReferencesOptions` is now `ReferenceOptions`).

- **Lifecycle:** `initialize` (offers `positionEncodings: [utf-8, utf-16]`) → `initialized` … `shutdown` → `exit` → stdin closed → the process group is killed after a grace. States: `starting → indexing ⇄ ready → failed | stopped`; `indexing` while work-done `$/progress` runs.
- **Restarts:** a crash restarts after a backoff that doubles per failure (1 s … 30 s); 5 failures in 3 minutes make it `failed`. A missing executable is `failed` at once ("not installed", never downloaded). Open documents are sent again to the new process.
- **Documents:** `open` / `change` (an applied transaction's changes) / `replace` / `save` / `close`. Changes coalesce for 50 ms or until the next request: a burst of edits is one `didChange` per document, a single range replacement for incremental servers, the whole text for full-sync ones.
- **Requests:** hover, definition, references, completion, document symbols, formatting, prepare rename, rename, code action; refused unsent when the server did not announce them; 5 s (completion 2 s) timeouts; a request that times out or is dropped is cancelled with `$/cancelRequest`. Server requests (`workspace/configuration`, progress creation, registrations, …) are answered; `workspace/applyEdit` is refused (the client never writes files).
- **Bounds:** 64 MiB frames (larger incoming ones are skipped unbuffered); ≤ 64 messages / 16 MiB queued for the server, senders wait within their deadline; ≤ 1024 requests in flight; diagnostics ≤ 4096 files × 500 entries, messages ≤ 4 KiB; the last 256 log lines; 256 queued events per subscriber, a slow subscriber is told it lagged. The crate-level docs state the overflow policy in full.
- **Processes:** the server runs in its own process group; dropping the `Server` kills the group (rust-analyzer's proc-macro servers included). `ServerStatus::pid` is the root of the tree Resources read RSS from.

## Language servers in file tabs (E-12a)

The desktop is a client of the daemon's `LspHub` (`docs/lsp.md`); it never runs a server. Code: `workbench/lsp.rs` (`LspStore`: documents, diagnostics, servers, jumps; one per window), `workbench/lsp_nav.rs` (hover, go to definition, *Go Back*, the status item's data), `workbench/lsp_bar.rs` (the trust / install bar), `panels/problems.rs`, and in `hutan-code-view` `diagnostics.rs` and `hover.rs`. `Connection` (`crates/client`) carries the `doc.*` / `lsp.*` calls and turns the `lsp.state` / `lsp.diagnostics` events into notices.

- **Document sync.** A file tab's buffer is opened as a daemon document (`doc.open`, no language: the daemon names it by extension) once its text is in, only while the daemon offers `doc.sync`, never in large-file mode or above 3 MiB. A file whose language has no server is answered with no servers: it is closed at once and no file with that extension is offered again on the connection, so a window without servers sends one `doc.open` per language and then nothing (the protocol cannot be asked first). Edits are gathered for 50 ms (`CHANGE_DEBOUNCE`) and sent as one `doc.change` replacing the one span they touched (the whole text when 16 calls are already queued, or when that is simpler), in order, one call at a time; ⌘S is `doc.save` after them; closing the last tab of a file is `doc.close`. After a reconnect (the daemon closed the connection's documents) every document is opened again. Hover and go to definition first wait for the edits on their way.
- **Diagnostics.** `lsp.diagnostics` events replace the buffer's set (`FileBuffer::set_diagnostics`, LSP positions in UTF-16); the set already published is read once after `doc.open` (an older answer loses to a newer event). Until the next publish every edit maps the ranges through its transaction (anchors: typing at a start pushes it, at an end does not grow it, a deleted range becomes a point). A diagnostic without a severity counts as an error. Each frame records what it drew per line (`CodeView::drawn_diagnostics`: line, severity, underline style, glyph shape) and the first frame that drew a new set (`ViewStats::diagnostics_drawn`, the B16b budget).
- **Navigation.** `]d` / `[d` (Vim Normal) and F8 / ⇧F8 move the caret to the next / previous diagnostic, wrapping. Go to definition (`gd`, ⌘-click, F12) asks `lsp.definition` and goes to the first location: in the same file Vim's jumplist takes it (its `⌃O`), without Vim *Go Back* does; in another file the tab opens (or is focused) with the caret there and the place left is pushed on the window's list (100 entries), which `⌃O` in the arriving tab (Vim or not) and *Editor: Go Back* pop. `hutan-vim` has two hooks for it: `Vim::push_jump` (the host's own jump becomes a jumplist entry) and `Vim::jump_count` (whether Vim jumped since).
- **Hover.** The pointer resting 500 ms on a word (`HOVER_DELAY`), `K` (Vim) or ⌘⌥I (*Editor: Show Hover*; the Zed base's ⌘K ⌘I chord is gone, ⌘K opens the palette) opens the popover with the diagnostics there and asks `lsp.hover`; the markdown answer is drawn as plain text blocks (paragraphs, headings in semibold, code blocks monospaced; the first 8 192 characters). It closes when the pointer leaves the word, on Escape, a caret move or an edit.
- **Servers.** `lsp.state` events and `lsp.status` keep each server's state, root, languages, reason, install command and `trust_pending`: the trust bar (*Trust* is `lsp.trust {folder, trusted}`, user-only; it names every server waiting at or below the folder and what each may run, since trust is per folder; *Not now* is remembered per folder for the window, `LspStore::not_now`; one bar per window for a folder, § Language server bar, EDITOR-POLISH), the install bar (the command is copied, never run), the status item.
- **Problems panel.** Reads `lsp.diagnostics {min_severity?}` — every server, the same items `hutan diagnostics` prints — when it is made, when the connection comes back, after each `lsp.state` / `lsp.diagnostics` notice (one read at a time, one more after it when a notice came meanwhile), and on Refresh: the events of a file only another connection has open go to that connection, hence the button. With each read it asks `lsp.status` for the reasons, languages and install commands of the servers the answer names (`ServerLine`): the footer has a line per server and *Restart* (`Connection::lsp_restart`) for a failed or stopped one; "still starting" depends on those states (`starting`, `indexing`), not on the answer's `stale`, which is also set by a failed server.
- **Fake server.** `hutan-fake-lsp` (`crates/lsp_client/src/bin/fake_lsp.rs`) publishes one error per `error` in the text and, with `"warnings": true`, one warning per `warning`; the GPUI tests configure it in `daemon.toml` for `*.fake` files. Since E-12b it also scripts completion items (`completion.items`, `incomplete`, `filter`), what `completionItem/resolve` adds per label (`resolve`), signature help with the active parameter counted from the commas (`signature_help`), a request kind left unanswered once (`hang_once`) and a journal file of every message it received (`journal`: `<method> <id>`, `cancelled <id>`).

## Completion and signature help (E-12b)

Code: `hutan-code-view`'s `completion.rs` (the popup, filtering, accepting, tab stops, signature help) and `snippet.rs` (the snippet subset); `workbench/lsp_complete.rs` and `LspStore::{completion, completion_resolve, signature_help, completion_triggers}` in the desktop; `LspHub::{completion, completion_resolve, signature_help}` in the daemon (protocol 0.41, capability `lsp.completion`, `docs/protocol.md` § LSP). Look: `docs/design.md` § File tabs.

- **When.** The view asks only for a file whose server announced completion (`CompletionTriggers`, from `LspServerInfo.completion_triggers` / `signature_triggers` and `capabilities`, set by the workbench at every `lsp.state`), with one caret, no composition in progress, and in Vim only in Insert. A trigger character asks at once; a word character asks after `COMPLETION_DEBOUNCE` (20 ms) when no popup shows; ⌃Space (and ⌃N / ⌃P in Vim's Insert mode) asks at the caret.
- **Filtering and ranking.** The word from its start to the caret is matched as a case-insensitive subsequence of each item's `filter_text` (else its label); the server's `sort_text` (else the label) orders the matches, then the fuzzy score (runs and word starts count more), then the server's order. The list is filtered here while typing; an `incomplete` answer is asked again (`incomplete: true`) with the old list shown filtered meanwhile. With nothing typed, a `preselect` item is selected.
- **Requests in order.** A request waits for the edits on their way (`doc.change`) like hover does; if a newer request of the same kind was made meanwhile, it is not sent at all (requests that wait together would otherwise reach the daemon in any order). In the daemon these three requests run on a task of their own and a newer one of the connection supersedes the older: the server gets `$/cancelRequest` and the older answers `conflict` (`reason: superseded`), which the desktop ignores.
- **Accepting** replaces from the item's edit start (else the word start) to the caret with the item's text (its edit's, else `insert_text`, else the label) and applies its `additional_edits` (an import) — edits that overlap the completion are dropped — as one transaction, one undo step of its own. Snippets: `$1`, `${1}`, `${1:placeholder}`, `$0`, escapes `\$ \} \\`; everything else (choices, variables, nesting) is inserted as written. The first stop's occurrences are selected (several carets for a repeated stop); Tab / ⇧Tab move between stops, which grow with what is typed into them; the last stop (`$0`, else the end) ends the snippet, as do Escape and a caret outside every stop. An inserted call (`(` in the text) asks for signature help.
- **Documentation.** The selected item is resolved once (`lsp.completion_resolve`, the daemon keeps the 16 newest lists) when the server offers it; the detail and documentation then show beside the list (markdown drawn as hover does).
- **Signature help** is asked after a signature trigger and again at every keystroke while it shows (`retrigger`); an answer with no signature closes it, as do Escape and a caret on another line.
- **Escape** (TI-1): an input method's composition ends first; then the completion popup and signature help close (one Escape for both); only the next one leaves Vim's Insert mode (without Vim, collapses the carets).
- **B16** (keystroke → items on screen with a local fake server ≤ 100 ms, of which protocol + daemon ≤ 5 ms): `docs/perf.md` § Editor: completion.

## Finding and opening files (E-13a)

- **⌘P** (both keymap bases; in the Hutan base ⌘J keeps the jump palette alone) is one palette: a **Files** section, then **Sessions** (the rows of ⌘J: workspaces, projects, sessions). Files are those of the active project's folder (the active project, else the first project of the active workspace; none at Home): every key sends one `fs.find` (`docs/protocol.md` § Files; the daemon's fuzzy, path-segment scoring over its index) and drops the one before; the daemon's 100 best are ranked again so that the files opened most recently here gain up to 1.5 points (one word start), and the 20 best are shown, matched characters in the accent color. With nothing typed the Files section is the 10 files opened last below that folder (`recent_files` in `desktop-state.json`, at most 100, most recent first; a file found missing when opened is dropped), and one empty `fs.find` builds the daemon's index meanwhile. While a new answer is on its way the rows that still match stay, so the list does not flicker; Return on the top row before the answer waits for it.
- **Words in ⌘P** (FX-WORK-1): words separated by spaces are AND-matched, in any order, as in Zed and VS Code — `searcher glue` finds `crates/searcher/src/searcher/glue.rs`. The daemon scores every word as its own fuzzy subsequence of the path (smart case per word), adds the scores up and marks the characters of every word; one word behaves as before.
- `path:line[:col]` (`src/main.rs:16:5`, also `main.rs:16`) opens the file at that line and column. **Return** opens in the focused pane, **⌘Return** in a new split to the right (a session row opens its session there). `?` + words still searches the session history.
- While ⌘P is open its root is watched (`fs.watch`), so the daemon keeps its index until something changes; an `fs.generation` of the root asks the query again, so a file created or removed while the palette is open appears or goes.
- **Stale entries**: a recent file outside the active project's folder is never offered; the Sessions section (and ⌘J) leaves out projects that never had a session unless they are pinned, in a workspace or the active one — a folder opened by mistake and replaced is not offered (⌘O's recent projects still list it).
- **Files panel** (`files`, the first icon of the right sidebar's rail in every built-in preset, before Changes (SB-ATTACH; it was a page of the left sidebar); ⌘⇧E, *Files: Show Files Panel*, View → Files; settings `panels.files.*`): the folder of the project the window works in — or of the worktree picked in the sidebar — as a tree read through the daemon (`fs.list`, a folder when it is opened); its header chip names that project or worktree (`docs/design.md` § The active container), and a switch of container keeps drawing the old tree until the new root's first listing arrives. A file with uncommitted changes shows a letter (`M` `A` `U` `D` `R`) and a tint, and a folder that holds changes a dot; the marks are the file list of `worktree.diff`, read when the root is set, on `fs.changed` and when a checkout's activity ends (`panels/files_git.rs`; a root outside git has none; the read happens at most once in 2 s and never overlaps another). Files have an icon by kind (`item.file.rust`, `.markdown`, `.image`, … — the icon pack's semantic ids, `docs/themes.md`; any other file `item.file`). **EX-1, tree polish** (`panels/files_tree.rs` is the model, `panels/files.rs` the view): entries are in *natural* order, folders first (`file2` before `file10`, case-insensitive); what `.gitignore` / `.ignore` match (and `.git`) is hidden unless the header's ⋯ shows it dimmed (`panels.files.show_ignored`), dotfiles show unless `panels.files.show_hidden` is off (⋯ → *Show Hidden Files*); a folder that holds only one folder shares its row with it (`src/utils/helpers`, the folders in front muted, the last name whole; one click opens or closes the chain; opening a folder that holds one folder opens that one too; `panels.files.compact_folders`); indentation is 12 px per level down to level 6, then 6 px, never more than 100 px, and one guide line per open level is drawn on hover (`panels.files.indent_guides` = `hover` · `always` · `off`); the row's tooltip is its whole path. The header has *Refresh* (lists the open folders again and reads the git marks now) and *Collapse all* buttons, a ⋯ menu (*Show Hidden Files*, *Show Ignored Files*, *Fold Single-Folder Chains*, the three indent-guide choices, *Expand All*, *Collapse All*, *Refresh*) and the panel gear; the palette has *Files: Collapse All* and *Files: Refresh*. The rows are one flat list drawn with `uniform_list` and a scrollbar: a frame builds only the rows in view, 20 000 open entries included, and a listing that arrives for a folder replaces only that folder's rows (spliced, not rebuilt; none at all when its entries look the same), so 101 100 open rows cost 0.2 ms per listing instead of 9 ms (`just bench --only BEX`, `docs/perf.md` § Files tree). A listing cut at 5 000 entries ends in the row *Showing the first 5 000 — filter in this folder* (the filter itself is EX-3). Open folders are watched (at most 64; `fs.changed` lists the folder it happened in again — at most four times a second per folder, a burst of changes is one listing now and one a quarter second later —, an overflow every open folder, the root's `fs.generation` the open folders beyond the 64). **Per root:** the tree of a root the window leaves (listings, open folders, selection, scroll) is kept for eight roots and drawn at once when the window comes back to it (the open folders are listed again); the open folders of every root are also saved in `desktop-state.json` (`files_expanded`, eight roots, 500 folders each) and opened again after a restart — one that is gone is closed without a word. Keys: ↑↓ move, Home / End / PgUp / PgDn jump, → opens a folder or steps into it, ← closes it or steps to its parent, ⌘→ opens every folder in view (not when that would show more than 2 000 rows or list more than ten folders first: it says so), ⌘← closes every folder, Return opens the file and moves the keyboard to it, Space shows it and keeps the keyboard in the tree, Esc hands the keyboard back to the focused tab (the panel stays), ⌘⇧E does the same while the keyboard is already in the tree (it opens and focuses the panel otherwise), ⌘W closes the focused tab (never the panel); a click shows a file, a double click opens it. The focused tab's file is selected and scrolled to, its folders opened (`panels.files.auto_reveal`, default on; *Files: Reveal Active File*; *Reveal in Files Panel* in a file tab's menu). Files opened from the panel and from ⌘P are read as picked.
- **Files panel: file operations (EX-7)** (`panels/files/{edit,ops,drag}.rs`, `workbench/file_ops.rs`; every one a request to the daemon, `docs/protocol.md` § File operations, which never overwrites; every one also a ⌘K command *Files: New File · New Folder · Rename · Duplicate · Move to Trash · Copy · Cut · Paste · Undo · Redo*, and the row menu has them).
  - **Name field.** *New File* / *New Folder* (the header's two buttons, ⌘N / ⌥⌘N, the row menu) open the selected folder (the folder of a selected file, else the root) and put a row first inside it whose name is a field; **F2** turns the name of the selected row into the field with the stem selected (`main` of `main.rs`; a folder, a dotfile and a name without an extension whole). Return asks `fs.create` / `fs.rename`, Escape drops the edit, and so does moving the keyboard away when the name cannot be made (it makes the one that can). A name that is empty, has a `/`, is `.` or `..`, is longer than 255 bytes or collides with a sibling in any case (`readme.md` with `README.md`, but a rename to the case of its own name is fine) stays in the field with the reason in a line under the tree; the daemon decides the same when the listing was stale. A new file opens in a tab; the new row is selected.
  - **Move to Trash** (⌘⌫) always asks (`panels.files.confirm_delete`, on): a sheet names what goes (up to five names and "N more"), says how many tabs have unsaved changes (their text stays in the tab, which then shows the deleted bar) and that an agent is working in the checkout (*Codex is working in this checkout*); Return cancels. Files only ever go to the system Trash (`NSFileManager trashItem`), never to deletion. Open tabs of what was trashed show the deleted bar; undo brings the file back (`fs.restore` with the ticket) and the bar goes.
  - **Duplicate** (⌘D) copies next to the row as `name copy.ext`, `name copy 2.ext` … and opens the name field on the copy; **⌘C / ⌘X / ⌘V** remember rows (a cut row is dimmed; the path is also put on the system clipboard as text) and paste into the selected folder, a name that is taken becoming the next `copy` name; a paste of **files Finder copied** (the pasteboard's file URLs) copies them in from wherever they are (`fs.copy` with `picked_from`), one step for the lot. A paste with nothing to paste says so.
  - **Drag** a row onto a folder (or onto a file's row, meaning its folder, or the empty part of the tree, meaning the root) to move it; **⌥** held at the drop copies. The first drop of a session asks (`panels.files.confirm_drag`); a closed folder under the pointer opens after 0.7 s; near the top or bottom edge of the tree it scrolls by itself, faster the closer to the edge. Moves into the row's own folder, or a folder into itself, do nothing; a name that is taken is told and nothing is overwritten.
  - **Tabs follow.** After a rename or a move the buffer of every open file at (or below) the old path is kept — text, unsaved changes and undo history included — and belongs to the new path: the tab, its views and recent-file entry, the language server's document (closed under the old path and opened under the new one with the buffer's text, so unsaved text is what the server sees; its old diagnostics go), the watch. A read of the file at its new place follows, so a write that raced the move (an agent's) is found: a clean buffer reloads, one with unsaved text gets the usual bar and keeps its text. ## Searching and replacing across files (E-13b)

How it looks: `docs/design.md` § Search panel. Code: `panels/search.rs` (the panel: fields, the search, the list, the replace preview), `workbench/search_replace.rs` (the query as `fs.search` takes it, the client's copy of the daemon's expression, *Replace All*).

- **The search** is the daemon's `fs.search` below the active project's folder (`docs/protocol.md` § Files: `.gitignore` honoured, `.git` / `target` / `node_modules` left out, binary files and files above 4 MiB skipped, lines cut at 512 characters). Literal text unless *Regular expression*; smart case unless *Match case*; *Whole word* sends a regular expression with `\b` at each end of the query that is a word character. The include field's globs restrict, the exclude field's are sent with `!`. Every change cancels the running search (`fs.search.cancel`, sent at once) and starts the next after `panels.search.debounce_ms` (150); Return starts it at once. The daemon answers when a search ends: while it runs, `fs.search.progress` (counts only) is all that streams, so the status line counts files and hits and the rows arrive with the answer. `Connection` (`crates/client`) has `fs_search` / `fs_search_cancel` and turns the progress events into `Notice::FsSearchProgress`.
- **Bounds.** At most `panels.search.max_results` matching lines (default and ceiling 1 000, the daemon's); a search that reached it says "stopped at N results". The list is a `uniform_list` (one row per match, a header per file): a frame builds only the rows in view.
- **Never blocking input.** Nothing of the search runs on the main thread: requests, progress and the `fs.stat` of the listed files are background tasks, the answer is grouped in one pass, and the panel is drawn again only when its state changes (a key, a progress report, the answer) — the GPUI test types while a search streams over 100 000 files and counts both the key → frame time and the panel's drawings.
- **The version the search saw.** `fs.search` has no file versions, so the panel asks `fs.stat` of every listed file as soon as the answer comes (in the background; *Replace All* waits for it) and keeps `{mtime_ns, size, ino}` with the canonical path. A file changed between the daemon reading it and that `fs.stat` is still caught: every line is checked again before it is changed (below).
- **Replace All** (`ReplaceInFiles`, handled by the workbench): per file, one `FileBuffer::edit` with `Coalesce::Step` — one undo step in that file's tab, whatever the number of matches. A file without a tab gets one in the background (the active tab and the keyboard stay), read through the buffer store; a tab opened for a file that is then skipped is closed again. Each chosen match is found again on the line as the buffer has it now with the same expression (`Regex::captures_at` at the match's offset: the same match, `\b` and look-behind context included); `$1` / `${name}` expand only for a regular-expression query, literal text is inserted as is.
  - A **clean** buffer must hold the version the search saw (`Stored::disk`), else the file is skipped as *changed since the search*; it is then saved through the normal path (`fs.write` expecting the buffer's version), so a change on disk between the read and the write is refused by the daemon and shows the tab's conflict bar instead of being overwritten (listed as *changed on disk while saving*).
  - An **unsaved** buffer takes the replacements in the buffer and stays unsaved; nothing is written.
  - A matched line that is not the line the search showed (a cut line is compared by its start) skips the **whole file** as *changed since the search*: no file gets half of its replacements.
  - The outcome (`ReplaceOutcome`) goes back to the panel: replaced matches leave the list, skipped files say why on their row and in the summary under the fields, and the notice area says it in one line.
- **CLI parity.** `hutan fs search` runs the same search; there is no CLI replace (out of scope).

## Git blame and file history (GIT-HISTORY)

Read-only history in the editor, for what Zed, Helix and Orca users ask for most (`docs/spikes/2026-10-25-user-needs/editors.md`). The daemon runs git (`docs/protocol.md` § Git history); the editor draws.

- **Toggle Blame** (*Editor: Toggle Blame* in ⌘K, *Toggle Blame* in the file tab's menu) adds a column to the gutter, between the marks of agents and diagnostics and the line numbers: on the first line of each run of one commit, `author · 3 days ago · subject` in the muted gutter color, one line, cut with an ellipsis; every other line of the run repeats `author · date` in a fainter color, so no row of the column is blank (FX-WORK-2). The column is as wide as the longest of those lines needs, between 14 and 32 cells and never more than 30 % of the view (EDITOR-POLISH, F-09): the line is the short form `Ada · 3d · subject` (a name over 14 characters becomes its first name and the initial of the last, `Robert T.`, else its initials, the date is `now` `5m` `3h` `2d` `3w` `4mo` `2y`), cut with an ellipsis, never wrapped; the first line in view says its run too when the run began above the view, so a long run never leaves the column blank; in a view too narrow for 10 cells of it the column is left out. The hover has the whole commit; inline blame keeps the full line. Hovering a line's blame shows the commit (short hash, subject, author and email, date); clicking it opens the file's history at that commit (below) and never moves the caret. The toggle is per tab.
- **Inline blame.** `editor.inline_blame = true` (off by default) draws the same text after the end of the caret's line, muted, and asks for the blame by itself when a tab opens; a diagnostic's message on that line wins the place. It needs no column.
- **How it follows the text.** The workbench sends the buffer's text (what a save would write: line endings and byte-order mark as the file has them) as `contents` of `git.blame`, so unsaved edits are blamed as what they are. The buffer keeps the answer's text and matches each line of its current text to a line of it after every edit (whole lines, `hutan_buffer::line_map`): a line that is typed or changed is **Uncommitted**, a line that only moved keeps its commit, and undoing brings the commit back, because the match is made against the text, not accumulated from edits. The blame is asked again after a save, when the file is reloaded and when a tab turns it on; a file that git does not track says so in the notice, and a text over 2 MiB is not blamed. A blame the daemon cannot give leaves the tab as it was.
- **Show File History** (*Git: Show File History* in ⌘K, the file tab's menu, the Files panel's context menu for a file) opens a tab `History · name`: left, the commits that changed the file, newest first (subject, then relative time with the absolute time in its tooltip, author and short hash; renames are followed), 100 at a time (*Older commits*); right, the selected commit's subject, hash, author and absolute time, its message body, the old name when it renamed the file, and its diff **for that file**, drawn as the Changes view draws one (the chat's diff rows under hunk headers). ↑ ↓ (or j k) move through the list; **Open at this revision** opens the file as it was in a read-only tab `name @ 1a2b3c4` (a code view of a buffer of its own: not in the window's buffer store, so nothing watches, saves or hands it to a language server); **Copy hash**. A binary file or a revision over 2 MiB says so instead of showing text.
- **Repo history** is a *History* segment of the Changes view (see `docs/design.md` § Changes view): the recent commits of the checkout and each one's files and diff.
- **CLI and MCP.** `hutan git log|blame|show`, MCP `git_log`, `git_blame` (read-only; an agent calls them without asking).
- **Tests.** `crates/daemon/tests/it/git_history.rs` (log paging by hash, a file's history across a rename, blame mapping lines to commits and marking uncommitted ones and unsaved `contents`, show, file at a revision, bounds and refusals, a linked worktree), `crates/code_view/tests/it/blame.rs` and `src/blame.rs` (the blame follows typing and undo, the gutter column, hover and click), `crates/buffer/src/diff.rs` (`line_map`), `crates/desktop/tests/it/git_history_gpui.rs` over a real daemon (the column toggles and follows edits and is asked again after a save, inline blame, the history tab, *Open at this revision*, a click on a blame, the menus, the Changes History segment), `crates/cli/tests/it/{git,mcp}.rs`.

## Git change marks (EDITOR-POLISH)

What changed since the last commit or `git add`, in the gutter, for the cheapest "what did I do" signal (workability F-11). Code: `crates/code_view/src/{git_gutter,git_peek}.rs` (the base, the diff, the peek and the step keys; GPUI-free in `git_gutter.rs`), `crates/desktop/src/workbench/git_gutter.rs` (fetching the base, *Stage hunk*). No wire change: it reads through `git.file`, `worktree.hunks` and `worktree.stage`.

- **Against what.** The file as the **index** holds it. The workbench asks `git.file {path, rev: "HEAD"}` once, then `worktree.hunks` for the file's *staged* hunks and applies them to that text (`git_gutter::apply_hunks`): the result is the index. A file with nothing staged is compared with `HEAD`, which is then the index; the peek says which one it is (*against the index* / *against HEAD*). The peek is as wide as its text but never wider than the room right of the gutter, so in a split it stays inside its own pane. CRLF and a byte-order mark in git's text are normalized as the buffer's own are. A file git does not hold (outside a checkout, untracked, not in `HEAD`, binary, over `git.file`'s 2 MiB bound) has no base and no marks. The base is fetched again when the file loads or is saved, when its tab is shown again (the index may have moved while it was behind another), after *Stage hunk*, and when `editor.git_gutter` is turned on; it is dropped when the setting turns off.
- **The diff.** The buffer's text against the base, by lines (the same Myers line diff as an agent's hunks, `agent::hunks_between`, with the 250 ms deadline), in the background: at once after a load, 150 ms after the last edit while typing (1.5 s for a large or minified file), carried across the edits in between. Unsaved text counts: the marks follow the buffer, and undo clears them.
- **Drawing.** A 3 px bar (`editor.diff-gutter.added` / `.modified`) at the right edge of the gutter, beside the numbers, for added and changed lines; lines removed are `editor.diff-gutter.removed` on the edge above the line that followed them. A wrapped line has its bar on every row. The agent's own bar stays at the gutter's left edge, so both can show.
- **The peek.** A click on a mark (the strip at the gutter's right edge) opens a popup below the change (and never moves the caret): *Added 3 lines* / *Changed 2 lines* / *Removed 1 line*, *against the index · 2 of 5*, the lines the base had (up to 12, `- ` before each), and the buttons **Stage hunk**, **Revert hunk** and ✕. *Revert hunk* puts the base's lines back through the buffer, so it is one undo step with the carets restored (⌘Z brings the change back); it is not offered in a read-only tab. *Stage hunk* is offered while the daemon stages (`worktree.stage`, capability from protocol 0.53) and the file's checkout is known: with unsaved changes the file is **saved first** (`worktree.stage` works on what the disk holds; a save the conflict bar refuses stages nothing), then the unstaged hunks are read again and the change blocks that overlap the clicked lines are staged **by their lines** (`HunkRef::lines`, `git_gutter::match_change`), so a neighbouring change that git put in the same hunk stays unstaged; the answer is a line in the notice area and the marks are drawn against the new index. Escape, a click in the text, an edit or a click on the same mark closes the peek.
- **Keys.** ⌥F5 / ⇧⌥F5 (*Editor: Next Change* / *Previous Change*) go to the start of the next / previous change, wrapping, and open its peek; in Vim's Normal mode `]c` / `[c` do the same. *Editor: Show Change at Caret*, *Revert Change at Caret* and *Stage Change at Caret* are in ⌘K for the keyboard.
- **Tests.** `crates/code_view/src/git_gutter.rs` (the diff: insert, modify and remove at the start, the middle and the end, an emptied or filled file, CRLF and a byte-order mark, a missing final newline; staged hunks applied to `HEAD`, with `\ No newline`; the change blocks of a git hunk and `match_change`), `crates/code_view/tests/it/git_gutter.rs` (GPUI: marks appear after typing and clear after undo, a wrapped line's bar on every row, a click opens the peek and leaves the caret, Revert is one undo step, Stage asks the owner for the lines, the step keys and Vim's, the setting off, no base), `crates/desktop/tests/it/git_gutter_gpui.rs` over a real daemon and git repositories (the base is `HEAD`, or the index when something is staged; an untracked file has none; the setting is live; *Stage hunk* saves an unsaved file and stages only that change, and one of two changes in one git hunk).

## Scrolling past the end (EDITOR-POLISH)

A view stops with the last line at the bottom plus `editor.scroll_beyond_last_line` of its height (0.5: half a screen, as VS Code's `scrollBeyondLastLine` but a smaller room; 0: the last line stops at the bottom; 1: a whole screen), never on a blank view or with one line left at the top (workability F-19). The extent is `rows × line height + fraction × view height − view height`, floored at 0 (a file that fits does not scroll), in display rows while wrapping. It is applied by `clamp_scroll` at every frame, so a tab shown again after its file got shorter, or after the window got taller, is inside the new extent at its first frame; changing the setting takes effect at once. Tests: `crates/code_view/tests/it/scroll.rs`, `crates/desktop/tests/it/scroll_gpui.rs`.

## Scrollbars (SCROLLBARS)

A file tab has a scrollbar (`hutan_ui::Scrollbar`; when it shows, how it drags and pages, the setting `appearance.scrollbars` and the `ui.scrollbar.*` colors: `docs/design.md` § Scrolling). The **vertical thumb** is over the *display rows*, so with soft wrap it counts wrapped rows, and the room `editor.scroll_beyond_last_line` allows is part of the track; dragging it to the end reaches the position that setting stops at. The **horizontal thumb** runs along the text area (not the gutter) while the view does not wrap and a line is wider than the text area; its extent is the widest line drawn so far, so it can grow as the file scrolls. A click on either track pages and never moves the caret.

**Ticks on the vertical track** (a lite overview ruler, drawn while the bar is): a tick for each diagnostic (its severity's color; the worse severity of a spot wins), for each git hunk (`editor.diff-gutter.added|modified|removed`, spanning the hunk's rows) and for each find match (`editor.search-match`, the current match in `editor.search-match.active`), at its row's share of the document. At most 512 ticks per kind are drawn (a 10 000-match search is a few hundred quads). They are computed when the text, the diagnostics, the git hunks, the find result, the wrapping or the colors change — the view keeps the last answer and the key it was computed for — never per frame.

Tests: `crates/code_view/tests/it/scrollbars.rs`.

## Language server bar (EDITOR-POLISH)

How it looks: `docs/design.md` § File tabs (trust bar); the daemon's half: `docs/lsp.md` § Trust.

- **One bar per window.** The window shows one trust bar for a folder (and one install bar for a server), not one per pane or split: `Workbench::sync_lsp_bars` gives it to the first pane, in layout order, whose shown file needs it, and the tabs of the same folder in the other panes show none. It is decided again whenever the layout, the shown tabs or the servers change.
- **What it says.** It names each server waiting for the folder (its id in `daemon.toml`, the file's own first) with its languages and what it may run there: rust-analyzer *can run build scripts and procedural macros*, typescript-language-server *the project's TypeScript plugins*, pyright and basedpyright *the project's Python interpreter*, gopls *the go command on the project*, bash-language-server *shellcheck on the scripts*, and clangd, taplo, marksman and the JSON server *only read the files*; a server of your own *runs the program you set for it in daemon.toml*. The wire has the server's name, not its command line; the name is the built-in's command.
- **Only for a server that exists.** The daemon says `not_installed` (with the install command) for a server whose program is not found, also in a folder nobody has decided about; the bar is then the install hint, never a request to trust something that cannot run.
- **Not now and the way back.** *Not now* is remembered for the window, per folder. The `editor.diagnostics` status item reads `untrusted` while the file's server waits (or the folder was denied); clicking it (*Editor: Review Language Server Trust* in ⌘K) shows the same bar again, with the same *Trust* and *Not now* — also for a denied folder, which a *Trust* then overrules (the user's decision wins).
- **Tests.** `crates/desktop/tests/it/lsp_gpui.rs` (the new wording; one bar in a split and a third pane; *Not now*, the way back and *Trust*; a missing server asks no trust), `crates/desktop/src/workbench/{lsp_bar,panels/status}.rs` (the texts, the status item's click), `crates/daemon/tests/it/lsp.rs` (a missing server in an undecided folder is `not_installed`).

## Agents' edits (E-10)

Agents write files themselves (direct writes; there is no approve-before-write gate in the editor). The editor's job is to show what the current turn changed, never lose the user's text, and let the user take changes back one at a time. Evidence: `docs/spikes/2026-10-22-editor-research/agent-edits.md`.

- **No silent overwrite.** An agent's write to an open file arrives as `fs.changed` with origin `agent {session}`. A clean buffer takes it with `apply_external`: one undo step, carets in unchanged text stay. A buffer with unsaved changes gets the conflict bar (E-6) and never loses text; the write still enters the ledger, and its hunks appear once the buffer takes the file (*Reload*).
- **Hunks.** A file's turn has a **base** (the file before the turn's first write) and the **agent text** (after its last write). The hunks shown are the base, with the user's own later edits outside the agent's hunks carried into it (`agent::rebase`), diffed by lines against the buffer (`agent::agent_hunks`, Myers via `similar` with a 250 ms deadline). So the user's typing is never called the agent's, an edit inside a hunk stays part of it, and a rejected hunk (text equal to the base again) disappears; undo brings it back.
- **Drawing.** Changed lines get the `editor.agent-changed` tint and a gutter bar (`editor.diff-gutter.added` / `.modified`); removed lines a `editor.diff-gutter.removed` mark on the edge where they were. Only the lines in view are looked at.
- **Throttling.** The diff runs on a background thread: at once after a reload, a Reject or a new turn's changes; 150 ms after the last edit while typing; 1.5 s for a large (over 1 MiB) or minified (a line over 4 KiB) file. Between an edit and the next diff the hunks are carried across the edit. Large-file mode has none. `editor.agent_highlight = false` turns it all off: nothing is diffed or drawn.
- **The agent bar** over the file: "*Codex* changed *n* places in this file, on disk", ↑ ↓ (⌘⌥[ ⌘⌥]) between the changes, **Reject** (⌘⌥Z) the change at the caret, **Accept All**, **Follow**. Reject puts the base's lines back as one undo step (⌘Z undoes it), never deletes a file (a file the agent created rejects to empty) and saves a file that had no other unsaved changes, so the disk and the agent's next read have it. Accept All drops the file from the ledger.
- **Follow agent** (per tab, off by default): at every write of the agent, once its hunks are known, the view moves the caret to the newest change and scrolls it a third from the top.
- **The pending ledger** (`agent_edits.rs`): per file, the session, its turn, the base, the agent text and the last text seen on disk; saved next to the layout as `agent-edits.json` (owner-only, 0600) and loaded at start, so the hunks survive switching chats or models and a restart of the desktop. It learns from `fs.changed` (origin `agent`) for open files (the text before is the one last read or saved) and for files it watches itself (files in the ledger, and files a recent `file_diff` named, whose base is the patch taken back, or empty for a created file); from `turn_started` (a write of a new turn starts a new base); and from other writers (`external`, a rescan), which only move its idea of the disk. A Bash write by the agent therefore shows like an edit-tool write as long as the file is watched. Bounds: 64 files (the oldest go first), texts up to 2 MiB, `file_diff` hints for 10 minutes. The checkpoint of the turn's start (CK-2) is not reachable through the protocol yet, so a write to a file that is neither open, nor in the ledger, nor named by a `file_diff` has no base and is not tracked.
- **Open.** A file row of a chat's file-change card has *Open* (the file at its first change); a Changes view row has *Open* (at its first hunk once the patch is read) and so has every hunk header (at that hunk). ⌘-click on `src/lib.rs:42:7` in a terminal opens the file at the line: `terminal.open_files_with` is `editor` by default now. Agents use the MCP tool `open_file {path, line?, column?}` (`ui.run workbench::OpenFile`, `docs/control.md`).

**Parity:** `terminal.open_files_with` defaults to `editor` (it was `system`); set it to `system` for the old behaviour. Nothing was removed.

## File tabs (E-5)

How the tab looks and how to open one: `docs/design.md` § File tabs. Under the hood:

- **One buffer per file.** The workbench's `BufferStore` keys buffers by canonical path (what `fs.stat` returns), so the same file opened twice, or shown in two panes (a file tab's **Open in Split Right / Down**), is one `FileBuffer` with two `CodeView`s. Each view has its own scroll, selection and find. The buffer is dropped when the last tab that shows it closes; the Agents overview's stash counts as a tab.
- **Reads go through the daemon.** A file is looked up with `fs.stat`, which gives its canonical path, kind and size. It is then read with `fs.read` in chunks of up to 1 MiB (`Connection::fs_read_all`). The daemon refuses what the window may not read, along with binary, non-UTF-8 and files over 64 MiB, and the tab shows why. When the user chose the file (the Finder dialog, a ⌘-click in a terminal, a restored tab), it is read with `picked`, so from anywhere. When an agent may be asking (`ui.run workbench::OpenFile`, `hutan open`), it is read without `picked`, so only below the workspace roots.
- **Line endings and BOM.** The text is normalized for drawing: `\r\n` becomes `\n` and the BOM is dropped (`hutan_buffer::Buffer::from_content`). What the file had is kept on the buffer and written back on save (`Buffer::to_bytes`), so a CRLF file stays CRLF; pasted `\r\n` is normalized.
- **Syntax only while shown.** A tree-sitter tree of token-dense code takes about 37 bytes per byte of source (`docs/perf.md` § Editor: syntax). So a buffer holds a `Syntax` only while some pane shows it as its active tab. The rope stays; the tree is parsed again, in the background, when the tab is shown again. The parser's worker wakes the views through a one-slot channel when a tree lands. Until then the text is drawn uncolored, never blocked.
- **Large-file mode.** Above `editor.large_file_bytes` (default 16 MiB) nothing is read until the user confirms. The file then opens read-only without syntax.
- **Drawing.** `CodeElement` lays out only the lines that intersect the view (`OVERSCAN_LINES` = 0), and only the columns in view plus a margin of 8, so a 5 MB line costs a window, not the line. Code is drawn on a cell grid, one glyph per cell (GPUI's `force_width`, ligatures off):
  - a tab runs to the next stop of 4;
  - a wide character takes two cells;
  - a control character is one replacement glyph;
  - a combining mark rides on its base.

  Hit testing and the selection and match fills are therefore arithmetic (`layout.rs`). Shaped lines are cached by line, text version, column window, style generation and tree version. A frame that changes nothing shapes nothing, and scrolling a line shapes one line.
- **Theme.** `CodeStyle` is the pack's `editor()` colors, its monospace family, `editor.font_size` and `editor.line_height`. A theme or appearance change restyles the open tabs: the lines in view are shaped again in the new colors, and nothing is parsed again.
- **Find.** The search runs on a background thread over an `O(1)` snapshot of the rope (`hutan_buffer::Text::search_all`). It is literal or regex, case-insensitive unless **Aa** is on, and keeps at most 10 000 matches. A newer query drops the answer of an older one.

## Editing (E-6)

How it looks and which keys do what: `docs/design.md` § File tabs. Under the hood:

- **One transaction per command.** Every command runs on every caret and becomes one `hutan_buffer::Transaction` with the selections before and after it (`code_view/src/editing.rs`), so a multi-caret edit, a line move or a Replace All is one undo step and undo puts the selections back. Typing (and an input method's composition) joins the typing of the same view that came less than a second before (`Coalesce::Typing`, an open undo group in the buffer); a caret move, a command, a save or a pause ends the step. Undo is per buffer, shared by its views.
- **Other views follow.** The buffer announces every change (`BufferEdited`, with the transaction); the other views of the file map their carets, marked text and find matches through it.
- **The parser follows incrementally.** Each edit is fed to the syntax worker as tree-sitter edits (`edits_of_transaction`) and a reparse of the new rope snapshot, never a parse from scratch (`SyntaxStats::incremental` counts them); highlights are carried across edits until the new tree lands.
- **What a keystroke draws.** Shaped lines are cached twice: by line and text version (a frame without changes shapes nothing) and by what a line shows (its text and colors), so an edit reshapes the lines it changed, not every line in view.
- **Input methods.** `CodeView` implements GPUI's `EntityInputHandler` over UTF-16 offsets of the whole file (the rope's UTF-16 metric, `O(log n)`). Plain typing gets the auto-pair rules; a composition is applied to the text as marked ranges (one per caret), its candidate window goes under `bounds_for_range`, and the commit is one step with the typing around it. A replacement range (press-and-hold accents) replaces the letter before the caret. Return and Escape during a composition only end it.
- **Auto-indent** uses `Snapshot::indent_level_after` when the tree is of the current text, else the line's own indentation plus one level after an opening bracket (Python and YAML: also `:`); the unit (tab or 2/3/4/8 spaces) is read from the file when it loads.
- **Saving** (`desktop/src/workbench/file_sync.rs`): `fs.write` with `expect` = the version the file was read or last saved as. A `conflict` answer shows the conflict bar with the file's text as it is now; **Keep Mine** writes with `expect` = that newer version, so a third change is still refused; a deleted file is created again (`create`). While a save is on its way, typing goes on in a new undo step; the buffer is clean afterwards only if it was not edited meanwhile.
- **Watching.** Every open file is watched (`fs.watch`; the connection watches again after a reconnect and then checks every file). On `fs.changed`: origin `self` (our own save) is ignored; a change of anybody else is read with `fs.read`, and a clean buffer takes it with `apply_external` (one undo step, carets in unchanged text stay, clean afterwards), a changed one gets the bar. A removed file gets the *deleted* bar.

## Soft wrap (EDITOR-WRAP)

Markdown, TOML and prose were unreadable in a docked editor (`docs/spikes/2026-10-27-workability.md` F-06): a line wider than the pane was cut at its edge. Code: `crates/code_view/src/{wrap,soft_wrap}.rs` (the display map and the view's use of it), the rows in `element.rs`, `view.rs`, `motion.rs`; settings, the toggle and the status item in `crates/desktop` (`settings.rs`, `workbench/file_view.rs`, `panels/status.rs`).

- **Display map** (`wrap.rs`). A buffer line is drawn as one or more *rows* of at most `cols` cells. Columns stay the line's own (a tab runs to the next stop of the line, a wide character takes two cells, a combining mark rides on its base), so a row is a window `start_col..end_col` of the line and `layout.rs` works on it with a base column. A row breaks **after** a space or tab, after `, ; ) ] } ? !` and after `- / \ |` that follow a letter or digit (`src/main/` breaks after each slash, `--flag` never in the middle), and after any wide character (CJK breaks anywhere, except before closing punctuation such as `。` `）`); a row never starts with `) ] } , . ; : ! ?`. Trailing whitespace hangs at the end of its row instead of starting one, a token wider than a row is cut at the edge, and a row always holds a character. Rows after the first are drawn indented by the line's leading whitespace (more than half of the row: flush left). `WrapMap` keeps only the number of rows of every line and the first display row of every line (4 bytes each); the breaks of the lines in view are computed from the text when asked and cached (256 lines). An edit re-wraps only the lines it touched (`FileBuffer::edits_since` hands the view the transactions since its map's version, so the origin view and the others take it the same way; the log holds 256 edits, a load or a longer gap builds the map again), a new width re-wraps every line, and above 4 MiB (`MAX_WRAP_BYTES`) a buffer does not wrap.
- **Width.** `viewport`: the text area's width in cells less one (the caret at the end of a row has room); `column`: `editor.wrap_column` cells or the view's width when that is narrower. The view's first row stays at the top when the mode or the width changes.
- **Drawing.** `CodeElement` takes the display rows in view from the map (a frame still shapes only those). The gutter shows a line's number, blame and diagnostic glyph on its first row only; the agent's tint and bar, the current-line tint, selections, find matches, bracket matches, composition underlines and diagnostic underlines are cut to the row they fall on (a range that continues past a row's end stops there; the line break's extra selected cell and the caret line's diagnostic message and inline blame go after the *last* row). A caret at the byte where a row breaks is drawn at the start of the next row, unless it stands at the end of the row before (below). `ViewStats::last_rows` records the rows of the last frame (line, row of the line, number shown, carets, selected cells) for tests.
- **Scroll and hit testing.** `scroll_y` counts rows; the extent is the number of rows, `top_line` is the line of the first row, and there is no sideways scroll while wrapping. The pointer maps to a row, then to a byte of that row (`WrapMap::byte_at_x`); a click past the end of a row that another follows puts the caret at that row's end and draws it there. `point_of` (the input method's window, hover, completion, signature help), the blame hover, `reveal_line` and find all work in rows.
- **Movement.** ↑ ↓ and Page Up / Page Down move by display row and keep the cell they started at (the goal column is a cell of the row, indent included); a line shorter than the goal clamps, and the goal comes back on the next long one. Home goes to the start of the row, then (on a row after the first) to the line's first non-blank character, then to its start; End goes to the end of the row (drawn there, with its caret kept at the end of that row), then to the end of the line; on a line's first or last row they are what they were. ⇧ extends. Word motions, Delete to line start / end and the line commands stay on logical lines.
- **Vim.** `j` `k` stay on lines. `gj` `gk` move by display row keeping the column inside the row (`want_screen`), `g0` `g^` `g$` go to the row's start, first non-blank and last character (`g$` with a count: `n - 1` rows down), all characterwise and exclusive as in Vim (`g$` inclusive); `VimHost::display_row` (default `None`) gives `hutan-vim` the rows, `BufferHost` computes them from the line's text with the view's width. Where the tab does not wrap (or the host has no rows) they are `j k 0 ^ $`, so the 508 differential fixtures are unchanged.
- **Settings.** `editor.soft_wrap` = `auto` (default: on at the view's width for Markdown and plain text, off for code) · `off` · `viewport` · `column`, `editor.wrap_column` (100; 20–1000) and `languages.<name>.soft_wrap` (the language's name as `Language::name`: `markdown`, `rust`, `toml`, …, `plaintext` for files without a language; same values plus `auto`) which wins over `editor.soft_wrap`; the `languages` namespace may be set per workspace and has no page in the Settings sheet. All live. **View → Toggle Soft Wrap** (⌥Z in a file tab, *Editor: Toggle Soft Wrap* in ⌘K) flips the focused tab: wrapping again uses `editor.soft_wrap = column`'s width, else the view's; the choice belongs to the tab (not saved with the layout) and is dropped when it equals what settings say. The status item `editor.wrap` (`Wrap`, right side, before `editor.language`) shows while the tab wraps; a click toggles it.
- **Tests.** `crates/code_view/src/wrap.rs` (breaks: words, long tokens, wide characters and Cyrillic, tabs, indent, marks; the map: counts, lookups, edits at a wrap boundary, joined and split lines, multi-edit transactions, resize), `crates/code_view/tests/it/wrap.rs` (GPUI: rows drawn and numbered once, a wider window, caret rows, selection across a wrap, click on a continuation row and past a row's end, find and diagnostics on rows, scroll extent, edits, ↑/↓, Home/End, paging, Vim `gj` `gk` `g0` `g$`, one wrapped line and one shaped row per keystroke in a 10 000-line file), `crates/vim/tests/it/screen.rs`, `crates/desktop/tests/it/wrap_gpui.rs` (Markdown and plain text wrap and code does not, settings and `languages` decide and are live, the toggle per tab, the status item). Cost of a keystroke: `docs/perf.md` § Editor: soft wrap (B12w).

## Vim (E-8)

With `editor.vim_mode` on (live; ⌘K → *Editor: Toggle Vim Mode*), a file tab edits like Vim. Everything `hutan-vim` supports (`docs/design.md` § Vim mode) works on the file's rope.

- **Rope-native host.** `BufferHost` (`code_view/src/vim_host.rs`) implements `VimHost` on `hutan_buffer::Buffer`: reads are `O(log n)` on the rope, and every Vim transaction is one `hutan_buffer::Transaction` carrying the caret before and after it. For one key the view lends the buffer's text model to the host (`FileBuffer::lend`) and takes it back with the steps the key made (`FileBuffer::restore`), which reach the parser and the other views like any edit. A Normal command is one undo step; an Insert session is one step with the command that started it; `:s`, `:g` and `:normal` are one step each.
- **Modes.** A file opens in Normal mode with a block caret; Insert has a bar caret and types through the editor's own path (auto-pairs, auto-indent, input methods); Visual draws its selection from the Vim state. A mouse selection made in Normal mode becomes a Visual one at the next key; a click past the end of a line in Normal mode puts the caret on its last character, as in Vim. Vim state is per view, so two panes of one file can be in different modes.
- **Keys and input methods.** In Normal and Visual the view refuses text input (`accepts_text_input` is false, and `replace_text_in_range` drops anything a platform still sends), so printable keys arrive as key presses and never insert text, with or without an input method. A key is matched by the character it produces (a Dvorak layout types its own letters as commands); when that character is not ASCII (Russian, Greek, …) by its place on the keyboard instead, the US character macOS names the key by (`hutan_code_view::vim_key_of`), so `вв` on a Russian layout is `dd` and `:` is the key of `Ж` with ⇧. The character itself is kept where Vim waits for text: after `f t F T r`, on the `/` `?` line, and in Insert (`hutan_vim::Vim::takes_text`). Text fields read keys the same way. In Insert, Escape first ends a composition (the marked text stays); the next Escape leaves Insert.
- **Keymap contexts.** The code view's context is `CodeView Editor` plus `vim_mode = normal | insert | visual` while Vim is on. The editor's keys that Vim answers in Normal and Visual (arrows, Home/End, Return, Tab, Backspace/Delete, ⌥/⇧ motions, ⌃K, line moves) are bound in `CodeView && vim_mode != normal && vim_mode != visual`; its Escape (back to one caret) only in `CodeView && !vim_mode`. ⌃A / ⌃E (line start / end) and ⌃O (*Go Back*) are bound only with Vim off (`CodeView && !vim_mode`): with Vim on they are Vim's in every mode. Vim's own ⌃ keys are read before the window's other keys (`workbench/vim_keys.rs`, `docs/design.md` § Vim's keys and the keymap); a `keymap.toml` binding on such a key still wins.
- **Status items.** `editor.mode` shows `NORMAL` / `INSERT` / `VISUAL` and the keys of a command in progress (`2d`); `editor.position` shows `Ln, Col`. Both are cached views that read the focused code view (`editor_status.rs`); each observes the code view it read and the workbench, so every key, caret move and tab switch draws them again (a cached view is drawn again only when it is notified itself).
- **The `:` line** opens under the code (`'<,'>` after a Visual selection), with ↑ ↓ history; Escape or Backspace on an empty line closes it. Answers and errors show on the same line until the next key. The **`/` and `?` line** shows on the same line while it is typed (`/foo`, with a caret); Return searches, Escape or Backspace on an empty line ends it.

| Command | Does |
|---|---|
| `:w` `:w!` | saves through `fs.write` with the version it was read as (E-6: a file changed on disk is never overwritten; the conflict bar asks) |
| `:q` `:q!` | closes the tab; refuses (E37) when it is the last tab of a file with unsaved changes, unless `!` |
| `:wq` `:x` | saves and closes (`:x` writes only a changed file) |
| `:e <path>` `:e` `:e!` | opens a path (relative to the file's folder, `~` allowed); `:e` reads the clean file again; `:e!` drops the changes (⌘Z brings them back) |
| `:sp` `:vs` | splits the pane below / right with a second view of the same buffer; the new view starts at the caret and scroll of the one it was split from and has the keyboard (its own `:` line, `:q` closes it); the caret stays in view in both |
| `:b <n or name>` `:ls` | goes to an open file by Vim buffer number or a unique part of its path; lists them (`%` this one, `+` unsaved) |
| `:s/pat/rep/[gine]` with ranges `%` `.` `$` `N` `'<` `'>` `±N` | substitutes; searched in the background over a rope snapshot, applied as one step if the text did not change meanwhile |
| `:g/pat/cmd` `:g!` `:v` | runs `d`, `s/…/…/` or `normal …` on matching lines |
| `:normal keys` | runs Normal-mode keys on each line of the range |
| `:noh` | clears the find highlights |
| `:set number` `ignorecase` `smartcase` (with `no`, `inv`, `!`, `?`) | the gutter's numbers; the case rules of `:s` / `:g` |
| `:N` | goes to line N |
| `:term` | starts a Hutan terminal in the file's folder, in a split below |

Anything else answers `Not supported: :…`. Patterns are Vim patterns (E-7b, `hutan_vim::Pattern`; see the matrix below); a replacement knows `&`, `~`, `\0`–`\9`, `\u \l \U \L \E`, `\r`/`\n` (a line break; Vim's `\n` inserts a NUL) and `\\`. Every other text command (`:d :y :pu :m :t :j :> :< :k :u :red`, `:g` with them) runs through the Vim state; `:s` and `:g` with `d`, `s` or `normal` keep running on a background thread.

- **Registers** follow `editor.vim_use_system_clipboard`: on, yanks and deletes also write the system clipboard and `p` pastes from it (lines stay lines); off, the register is private.
- **Live toggle.** Turning `editor.vim_mode` off drops a pending command and closes an Insert session's undo step; turning it on puts every file tab in Normal mode.

**Parity** (what changes in a file tab with Vim on): in Normal and Visual the unmodified arrows, Home/End, Return, Tab, Backspace/Delete, ⇧/⌥ arrow selections and motions, ⌥↑/⌥↓ line moves, ⌥⇧↑/↓ duplicates and ⌃K are Vim's (or do nothing) instead of the editor's; ⌃A / ⌃E are Vim's in every mode (Insert: the last insert, the character below; Normal: increment, scroll) and bind line start / end only with Vim off (`keymap.toml` can bind them back, `docs/design.md` § Vim's keys and the keymap); ⌃O is Vim's jump list instead of *Go Back*; Escape leaves Insert/Visual instead of reducing to one caret. ⌘ shortcuts (⌘Z, ⌘C/⌘V/⌘X, ⌘A, ⌘D, ⌘S, ⌘F, ⌘/) keep their meaning in every mode. Without Vim nothing changes.

## Vim command matrix (E-7b)

`hutan-vim` is checked against Vim 9.1 (`/usr/bin/vim -Nu NONE -i NONE -es`, patches 1-1752) by 508 differential fixtures in `crates/vim/tests/fixtures/*.json`: each case gives a text, a caret and keys; the recorder (`cargo run -p hutan-vim --example record [file…]`, dev only, never in the gate) types the keys into the real Vim with `feedkeys(…, 'tx')` and stores the text, the caret and every non-empty register; `tests/it/fixtures.rs` replays every case on the reference host and fails on any difference. Every case replays twice: as its lines alone and as the file Vim read, ending in a newline (FX-SMALL-1). A text that ends in `\n` is the file's lines with a final newline, as in Vim (`'eol'`), not an empty line after them: `G`, `j`, `:$`, `}`, `]]` stop on the last real line, and `dd`, `dG`, `p`, `:m$`, `J` there keep the final newline. Behaviour is specified from Vim's documentation; no editor's Vim code was read.

| Area | Supported | Not supported (answers "Not supported: …") |
|---|---|---|
| Motions | `h j k l` (arrows, Space, Backspace), `w b e ge W B E gE`, `0 ^ $ g_ \|`, `gg G` with a count, `N%`, `+ - _`, `f t F T ; ,`, `%` (brackets), `( )` sentences, `{ }` paragraphs, `[[ ]] [] ][` sections, `gj gk g0 g^ g$` (by display row when the tab wraps long lines, § Soft wrap; else `j k 0 ^ $`); columns are display columns (tabs, CJK) | `H M L`, `zz`/`z…`, `gm go`, `[(` `])` and other `[`/`]` pairs, forced motions (`dv`, `dV`) |

| Text objects | `iw aw iW aW`, `is as`, `ip ap`, `i( a( ib ab`, `i{ a{ iB aB`, `i[ a[`, `i< a<`, `i" a" i' a' i\` a\``, with counts | `it at` (tags; tree-sitter objects are E-9) |

| Registers | unnamed, `"a`–`"z`, `"A`–`"Z` append, `"0`–`"9` (Vim 9.1 rules: a named delete also goes to `"1`; `%` `(` `)` `` ` `` `/` `?` `n` `N` `{` `}` deletes go to `"1` and `"-`), `"-`, `"_`, read-only `". ": "/`, `"+ "*` the system clipboard; `editor.vim_use_system_clipboard` makes the unnamed register mirror the clipboard | `"=` expression, `"#` `"%` |

| Macros | `q{a-z0-9"}` (`qA` appends), `@x @@ @:` with counts; a failing command stops the macro; a macro is one undo step; in a file tab the text typed through the editor is recorded too | — |
| Search | `/ ? n N * # g* g#`, offsets `e s b ±N` and line offsets, `'wrapscan' 'ignorecase' 'smartcase'`, `\c \C`, the magic levels `\v \m \M \V`, `\( \) \%( \|`, `\+ \= \? \{n,m} \{-}`, `\< \>`, `\zs \ze`, collections and the `\s \d \w \a \l \u \x \h \k …` classes; patterns match within a line | look-around `\@`, back references in a pattern, `\_x`, `\%` items other than `\%(`, matches across lines |
| `:` line | ranges `% . $ N 'x /pat/ ?pat? \/ \?` with `±N`, `,` and `;`; `:s` (flags `g i I n e &`, a count, `~`), `:&` `:&&` `&`, `:g :g! :v` with any of these, `:normal`, `:d :y` (register, count), `:pu[!]`, `:m :t :co`, `:j[!]`, `:> :<`, `:k :mark`, `:u :red`, `:N`, `:noh`, `:set` (`number ignorecase smartcase wrapscan hlsearch incsearch expandtab shiftround joinspaces shiftwidth tabstop`, with `no inv ! ? =`) | everything else (`:w` and the other file and window commands are the file tab's, see above) |

In text fields (composer, palette, forms) the same layer runs, except that `:`, `/` and `?` answer "Not supported here" (a field has no line to show them in); `n`, `*`, registers, marks, macros and the rest work. Differences from Vim kept on purpose: Return and Tab in Normal mode stay the field's (`+` moves down), Visual-mode changes are not repeated by `.`, and a typed line break in a `:s` replacement is a line break.
