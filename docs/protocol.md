# Hutan IPC Protocol — v0.28

Normative decisions: ADR 0002 (transport, framing, sequencing) and ADR 0004 (terminal render stream). This file is the message catalog; the `protocol` crate (`PROTOCOL_VERSION`) is the source of truth and this document must match it.

Latest: 0.30 — closing sessions (capability `session.close`): `session.close {session_id, stop_running?}` stops (when live) and removes a session from `session.list`, the restore set and the attention state while keeping its journal, blocks and history-index records; a busy session (foreground command per OSC 133, an agent `working`/`blocked`, a chat turn, a pending approval or question) is refused with `invalid_state` and `data: {"busy": {command?, agent?, state: working|blocked|turn|approval}}` unless `stop_running`; `session.reopen {session_id}` brings it back the way restart recovery does (terminal: saved command or the agent's resume command in the last directory; chat: `session/load`; assistant: asleep); event `session.closed {session_id}`; `HistorySessionRow.closed` (see § Sessions). 0.29 — session catalog (capability `history.sessions`): `history.sessions`, one row per agent session (Hutan, Claude Code, Codex, OMP) with title, latest turns, message count, model, attributed project, resume command, and the scan state; Workspace / Project / All scopes, `repo:`/`path:` filter, sorted by last update or creation. The DTOs are in `crates/protocol/src/history.rs`, the daemon side in `crates/daemon/src/history_catalog.rs` (see § Session catalog). 0.28 — daemon settings (capability `daemon.settings`): `daemon.settings.get`, `daemon.settings.set`, `assistant.reset` (see § Daemon settings). The history below starts at 0.27.

## Frames

| kind | Direction | Payload |
|---|---|---|
| 0 | both | UTF-8 JSON envelope |
| 1 | daemon → client | `u64 terminal_id` + postcard `TerminalRender` (`Snapshot` or `Frame`) |
| 2 | client → daemon | `u64 terminal_id` + raw input bytes |

Header: `u32 length (big-endian, excludes header) | u8 kind`. Max payload 4 MiB.

## Envelope

```json
{"id": 1, "method": "session.create", "params": {"workspace_id": "01J…", "kind": "terminal", "command": ["omp"], "cwd": "/repo"}}
{"id": 1, "result": {"session_id": "01J…", "terminal_id": 7}}
{"id": 2, "error": {"code": "not_found", "message": "session 01J… not found"}}
{"event": "session.updated", "epoch": "6f1c…", "seq": 1042, "data": {"session": {…}}}
```

## Handshake

```json
{"id": 0, "method": "hello", "params": {"protocol": {"major": 0, "minor": 1}, "client": {"kind": "desktop", "version": "0.1.0"}, "capabilities": ["terminal.render.v1"], "resume": {"epoch": "6f1c…", "seq": 1042}}}
{"id": 0, "result": {"protocol": {"major": 0, "minor": 1}, "daemon_version": "0.1.0", "epoch": "6f1c…", "capabilities": ["terminal.render.v1"], "resume": "replayed"}}
```

`resume` is `replayed` (events after `seq` follow immediately) or `snapshot_required`.

## Terminal render types (ADR 0004)

```text
TerminalSnapshot { frame, cols, rows, cursor, modes, palette, title?, lines: [Row; rows], links: [Link], history_len, viewport_top }
TerminalFrame    { frame, scrolled: i32, dirty: [(row, Row)], cursor, modes?, title??, links: [Link], history_len, viewport_top }
Row              { runs: [Run], wrapped }
Run              { text, fg: Color, bg: Color, flags: CellFlags, underline_color: Color?, link: u32? }
Color            default | indexed(u8) | rgb(u8, u8, u8)
CellFlags        bold, dim, italic, underline, double_underline, undercurl, dotted_underline, dashed_underline, inverse, hidden, strikethrough, wide
Cursor           { col, row, shape: block|underline|bar|hollow_block, visible, blinking }
Modes            { alt_screen, app_cursor, app_keypad, bracketed_paste, mouse: none|click|drag|motion, mouse_sgr, focus_events, alternate_scroll, kitty_keyboard: u8 }
Palette          { indexed: [(u8, rgb)], foreground?, background?, cursor? }   # OSC 4/10/11/12 overrides only
```

Semantics produced by the `terminal` crate (what clients can rely on):
- Rows list runs left to right; a wide character is one run character and spans two columns (spacer cells omitted), combining characters are appended to their base. Trailing default-style blanks are trimmed, so a row's runs may cover fewer columns than `cols`; the rest is blank.
- `Run.link` is an index into the terminal's link table (`Link.id == index`, stable for the terminal's lifetime, capped at 16 384 entries; later links render unlinked). A snapshot carries the whole table, a frame the entries added since the last snapshot/frame sent to that client.
- `scrolled` is always 0: a scrolling viewport is reported as the rows that differ.
- Frames carry neither dimensions nor palette. After a resize or a palette change (OSC 4/10/11/12) the daemon sends a fresh `TerminalSnapshot` instead of a frame (`Terminal::render`).
- `terminal.history`: `from_line` 0 is the line directly above the viewport, rows are newest first; the alternate screen has no history (`history_len` = 0 while it is active).
- `viewport_top` (0.7): the absolute line number of viewport row 0, as in `terminal.blocks` (see § Terminal blocks), counted over the primary screen only, so it keeps its last primary value while the alternate screen shows. A frame carries it after every change; a render whose only change is a new `viewport_top` (the screen scrolled and every row looks the same) is still sent. Clients map block lines to rows with `row = line - viewport_top` and never derive it from scroll counts (`scrolled` stays 0).  Render frames are postcard (field order is the format), so this field is a wire change the version number does not negotiate away: client and daemon of one build speak it, a 0.5 peer cannot decode 0.6 render frames.
- Scrollback storage (ADR 0013, no wire change): the daemon keeps the newest ≤ 256 history rows in the engine and older ones in a compact store; `terminal.history` reads across both with the semantics above, and the retained history is exactly `scrollback_lines` rows. Consequences clients may observe: after a resize only rows within the newest ~256 history rows are reflowed to the new width — older history rows keep the width they had when they scrolled out (a row of any width is valid; paint it as is, `wrapped` still marks soft wraps); `ESC[3J` and `ESC c` erase all of it; link ids of history rows are assigned when a row leaves that window, not when it is first read (ids stay stable, and the link table in a snapshot may therefore list links of history rows no client has fetched).
- Terminal queries answered by the daemon (through the terminal's single PTY writer, in query order, echoing the terminator the query used): OSC 10/11/12 `?` → `OSC 1x ; rgb:RRRR/GGGG/BBBB` (the application's override, else the configured default colours: foreground `#d4d4d4`, background `#1e1e1e`, cursor `#d4d4d4`); OSC 4 `;N;?` → override, else the standard xterm 256-colour table; CSI 18 t → `CSI 8 ; rows ; cols t`; CSI 14 t → `CSI 4 ; height_px ; width_px t`; CSI 16 t → `CSI 6 ; cell_h ; cell_w t` (pixel values from the last `TerminalSize`, `0` when unknown). Clients do not answer these queries.

Semantics implemented by the daemon (M1-D1; `crates/daemon/src/{registry,terminals}.rs`):
- `session.create`, `session.stop`, `.restart` and `.rename` answer `SessionResult { session }`; `create` does so even when the spawn failed (`state: failed`, reason inside). `stop` answers once the session is `stopped` (SIGHUP, SIGKILL after 3 s); `restart` is only valid from `exited`/`failed`/`stopped` and yields a new `terminal_id`. Process exit publishes `session.updated` and then `session.exited`.
- `terminal.attach` queues the snapshot frame before its response. Credit is one frame: after any render (the snapshot included) the daemon renders again only after `terminal.ack { frame }` for exactly that frame, at most once per ~8 ms, and never queues a render while credit is 0. Attaching twice from one connection replaces the first attachment; `terminal.detach`, closing the connection, and `session.restart` drop attachments.
- Terminals of ended sessions stay attachable (final screen) until restart or workspace close. Unknown `terminal_id` → `not_found` (acks for a missing attachment are ignored). Input (kind=2) for unknown or ended terminals is dropped; a full per-terminal input queue stalls only the sending connection's reader.
- `terminal.history` answers at most 5 000 rows per call (`count` is clamped) and stops adding rows once the JSON encoding of the rows would exceed 2 MiB (the first row is always included). The response may be shorter than requested although more history exists: page with `from_line += rows.len()` until `rows` is empty. Any response that still would not fit in one frame becomes an `internal` error instead of closing the connection.
- `session.exited` carries the raw signal number (e.g. 15 for SIGTERM) in `signal`, `code` is absent for a signal death.
- `session.restart` starts the process in the last directory the program reported with OSC 7 when that directory still exists, else in the spec `cwd`; `SessionInfo.cwd` reflects the directory used.
- A connection that has not sent `hello` within 5 s of being accepted is closed (logged at debug); the timeout covers the handshake only.
- `workspace.close`: Home and workspaces with live sessions → `invalid_state`; ended sessions leave with their workspace, and the project stays in `workspace.recent`. `daemon.shutdown { stop_sessions: false }` with live sessions → `invalid_state`; every shutdown (request, SIGTERM, SIGINT) hangs up all sessions concurrently and reaps them before the socket is removed.

Persistence and restore (M3-A; capability `session.restore`, protocol 0.3; `crates/daemon/src/{registry,restore,config}.rs`, `crates/storage`):
- Workspaces and sessions are written through to SQLite (`$HUTAN_HOME/hutan.db`) on every change: workspace create/rename/close, session create/rename/stop/restart/exit. Title and cwd changes (OSC 0/2, OSC 7) are coalesced: a session is rewritten at most once per second because of them. Writes go to the storage writer thread and never block request handling.
- At start the daemon loads the stored state before it listens, under the same ids: workspaces (and which one is `default`), sessions with title, workspace, creation time. A new epoch begins; clients treat it as "everything may have restarted" and re-snapshot.
- Sessions that were live when the previous daemon stopped (or died) are spawned again as **new terminals** (new `terminal_id`, same `SessionId`) in their last known cwd (falling back to the spec `cwd`, then the shell default, when the directory is gone): `starting` → `running`, title and workspace kept, `restored: false`. A stored `resume_ref` (`{"argv": [...], "source", "agent", "agent_session_id"}`, written by `agent.report`; only `argv` is read) replaces the spec command for this spawn; a restart afterwards uses the spec again. A stored session whose spec cannot be read comes back `failed`.
- Sessions that had ended (`exited`, `failed`, `stopped`) stay listed in that state with `restored: true`: the process and its final screen are gone, so there is no terminal to attach (`terminal_id` is absent). `session.restart` yields a live, unrestored session with the same id. `restored` is `false` and omitted from the wire for every other session.
- `daemon.toml` in the daemon's home directory: `[daemon] restore_sessions = "respawn" | "stopped"` (default `respawn`). `stopped` lists sessions that were live as `stopped` + `restored` instead of spawning them; the file is optional, an unreadable or invalid one stops the daemon from starting.
- Stopping the daemon does not forget its sessions. `daemon.shutdown { stop_sessions: true }` (and SIGTERM/SIGINT) hang the sessions up as always but leave them in the restore set, so the next daemon respawns them; clients still see them become `stopped` before the connection closes. `forget: true` (`hutan daemon stop --stop-sessions --forget`) records them as stopped instead, so the next start lists them as ended and does not respawn them. Sessions the user stopped or that exited earlier were never in the restore set.
- Storage is mandatory: a database that cannot be opened or migrated (including one written by a newer Hutan) stops the daemon with an error naming the file; the file is left unchanged. Before migrating an existing database the daemon copies it to `backups/hutan-<unix ms>-v<version>.db` (newest 5 kept). Environment variables in a session spec whose names look like secrets (`*TOKEN*`, `*SECRET*`, `*PASSWORD*`, `*API_KEY*`, …) are not stored; restored sessions start without them.

Agent reporting (M3-B; capability `agent.report`, protocol 0.4; `crates/daemon/src/{agent,registry}.rs`, `docs/integrations.md`):
- Every session process gets `HUTAN_ENV=1`, `HUTAN_SESSION_ID`, `HUTAN_WORKSPACE_ID`, `HUTAN_SOCKET`, and `HUTAN_BIN` (absolute path of the `hutan` CLI next to `hutand`, else the first `hutan` on the daemon's `PATH`, else the bare name). The daemon sets them after the spec's environment, so they win. The rest of a terminal session's environment is the login environment (`daemon.toml` `[terminal] env_inherit`, default `login`) under the spec's: `docs/architecture.md` § Session environment.
- `agent.report` sets `SessionInfo.agent = {source, agent, state, message?, agent_session_id?, updated_at_ms}` and publishes `session.updated`; a report that changes nothing visible (same source, agent, state, message, id) is applied silently. A new state drops the old `message`; `agent_session_id` carries over from the previous report of the same agent when absent. Unknown session → `not_found`; an empty or over-long (256 bytes) `source`/`agent`/`agent_session_id`, or a bad `resume_argv` → `bad_request` (the report is not applied and its `seq` is not consumed). Messages are cut at 512 characters.
- `seq` is per `(session, source)` (at most 16 sources per session): a request whose `seq` is not greater than the highest accepted for that pair is ignored and answers `{applied: false}`, as is a report for a session that is not live. The counters are memory only and start over when the session's process does (restart, respawn after a daemon restart). Hooks use the clock in nanoseconds; the OMP extension a counter in microseconds.
- `resume_argv`, when present, replaces the stored resume reference of the session (`resume_ref_json`, written through to SQLite at once). Rules: non-empty, at most 64 words and 8 KiB in total, `argv[0]` a plain command name (`[A-Za-z0-9._+@-]`, no `/`, not starting with `-`, looked up on `PATH`), no apostrophe or control character in any word. Absent leaves the stored reference alone. After a daemon restart the session is respawned running that argv instead of its spec command (`SessionInfo.command` keeps showing the spec); the agent starts without a report, which it is expected to send again.
- `agent.release` clears the report if it came from `source`, and the resume reference if it was stored by `source`; `applied` says whether anything was cleared. It consumes `seq` like a report.
- The agent is forgotten without a release when the session's process ends (report and resume reference are dropped; a daemon shutdown keeps the reference for the next start), when a restart begins, and — safety net for agents that die without saying so — when the shell prompts again (OSC 133 `A` from the shell integration) while a report is set.
- `SessionInfo.agent` is absent from the wire when no agent has reported; after a daemon restart it is absent until the resumed agent reports again.

## Terminal blocks (protocol 0.5, capability `terminal.blocks`)

The daemon turns the shell's OSC 133 marks (`docs/shell-integration.md`) into **blocks**: one prompt, its command and its output. Code: `crates/terminal/src/{blocks,emulator}.rs` (index), `crates/daemon/src/terminals.rs` (requests), `crates/protocol/src/blocks.rs` (DTOs), `crates/client/src/blocks.rs` (`BlockList`).

```
Block { id, prompt_line, command_line?, output_start?, end_line?, command?, exit_code?,
        started_at_ms, finished_at_ms?, cwd?, state: prompt | running | finished | truncated }
```

- **Lines are absolute**: line 0 is the first row the terminal ever scrolled into its history; numbers only grow, never change when older lines are evicted or erased, and are counted over the primary screen only. `viewport_top` in the `terminal.blocks` answer is the number of the viewport's first row; the row `n` above it (`terminal.history` `from_line = n - 1`) has the number `viewport_top - n`. Numbers are exact as long as the engine runs the stream in order: an `ESC[3J`/`ESC c` inside a DEC 2026 batch, a `CSI n S` flood of more than ~4 000 scrolled rows in one 2 KiB slice, and a column change while the alternate screen is shown (the affected blocks become `truncated`) are the exceptions.
- `prompt_line` = row of `A`; `command_line` = row of `B`; `output_start` = row of `C`; `end_line` is exclusive: the output is the rows `output_start..end_line` (`end_line` is the row after the cursor's when the output ended without a newline). `command` is the text between `B` and `C` read from the screen (soft wraps joined, hard breaks as `\n`, ≤ 4 KiB). `started_at_ms` is the prompt's start (`A`) and becomes the command's start at `C`; `finished_at_ms` is `D`. `cwd` is the shell's last OSC 7 before the prompt (an OSC 7 after `A` but before `C` replaces it).
- States: `prompt` (A seen), `running` (C seen), `finished` (D seen, or the next prompt started without one: no `exit_code`), `truncated` (the prompt line was evicted from the scrollback or erased by `ESC[3J`/`ESC c`; the fields keep what was known and a later `D` still fills exit code and times). A prompt that is drawn again (resize, Ctrl-L) or abandoned with an empty Enter reuses its block. Marks while the alternate screen is active are ignored, so a block's output ends where the program left it. Marks inside a DEC 2026 synchronized batch are applied when the batch ends, at the cursor it left.
- At most 2 000 blocks per terminal are kept; the oldest are dropped (ids stay monotonic per terminal, starting at 1). A terminal restart creates a new terminal with its own blocks.
- `terminal.blocks` answers newest first, ids below `before_id` when given (page with the last id), `limit` clamped to 500, and stops early before the block that would take the JSON encoding past 2 MiB (the first block is always included).
- `terminal.block_text` answers plain text: soft-wrapped rows joined, trailing spaces and trailing empty lines removed, lines separated by `\n`, the first `max_bytes` bytes (clamped to 512 KiB, cut on a character boundary). `truncated` is true when the text was cut or its first lines were evicted/erased. `command` is the stored text; `output` of a running block reaches the cursor's row. Unknown block (or dropped from the 2 000) → `not_found`; `output` while the alternate screen shows → `invalid_state` (the primary rows are out of reach; `command` still works).
- `terminal.block` carries the whole block after every change, in the order the changes happened, once for: the prompt start (`A`), its input line becoming known (`B`), the command starting (`C`), finishing (`D` or the next `A`), and each block that became `truncated`. Delivery is the usual bus (seq, replay ring); a client that missed events refetches with `terminal.blocks`.

## Projects and workspaces (protocol 0.6, capability `workspace.projects`)

M12-A; `crates/daemon/src/{registry,projects,config}.rs`, `crates/storage` (schema v2: `workspaces.kind|pinned|created_by|last_active_ms`, table `recent_projects`).

- `WorkspaceInfo` = `{id, name, roots, kind: home|project, pinned, position, created_by: user|cli|agent, last_active_ms, live_sessions, total_sessions}`. Every field is additive and defaults when absent (a 0.6 daemon's workspaces decode as unpinned projects). `workspace.list`, `session.snapshot`, and the client store order workspaces by `position`; pins, sort modes (manual, recent activity, attention, name) and filters are client concerns that read these fields.
- **Home**: exactly one workspace has `kind: home`; it is created at the first start (named `Home`) and bound to the folder of `daemon.toml` `[workspaces] home_folder` (absolute, or `~/...`; default `~/Hutan`, or `Hutan` inside `$HUTAN_HOME` when that is set). A missing folder is created with mode `0700` (with missing parents); an existing one is used as is and nothing is created inside it; a path that is not a directory stops the daemon from starting. Home's only root is that folder, rewritten at start when the setting changed. Home cannot be closed (`invalid_state`), cannot have roots added or removed (`invalid_state`), can be renamed and pinned and moved, and is where a session goes whose folder is the home directory, `/`, or Home's own folder (protocol 0.19; before, every session without `workspace_id`). A v1 database's `default` workspace becomes Home with its id, sessions, and (unless renamed) name `Home`.
- **`workspace.open { path }`**: `path` must be an absolute existing directory (`bad_request` / `not_found`); it is canonicalised (symlinks resolved). Since 0.19 the answer is the *project* of the folder (§ Projects and workspaces, 0.19): the project with the folder's repository identity, else the project whose folder it is, returned with `created: false`; otherwise a project is created at the end of the list (name = the folder's name, or the name the project had when it was closed). The home directory, `/` and Home's folder have no project: Home is returned. `created_by` (default `user`) is recorded for new projects only. The daemon records what the request claims; `agent` is meant for programmatic callers acting for a coding agent.
- **Roots**: a project has one root (its folder); a workspace shows the roots of its member projects as its own `roots` (derived, in list order, never stored twice). `workspace.add_root` resolves its path like `open` and puts that project into the workspace (a project that is in another workspace moves; idempotent); `workspace.remove_root` takes the member project whose folder is `path` (or the same place through symlinks) out of the workspace and answers `not_found` for anything else. Both are `invalid_state` for a project or Home.
- **Recent projects**: opening, creating, adding to a workspace, and closing a project record it by its folder in `recent_projects` (path, name, newest `last_opened_ms`; the newest 200 are kept). `workspace.recent` lists the open project workspaces (with `workspace_id`; time = the newer of last opened and `last_active_ms`) and the remembered closed ones (without), newest first, `limit` clamped to 50. Home is never listed.
- **Order**: `workspace.move` places a workspace before another (`before` unknown → `not_found`) or last, and renumbers `position` as `0..n`; one `workspace.updated` per workspace whose position changed. Moving a workspace before itself or to where it already is changes nothing. New workspaces take the next position. `workspace.pin` sets `pinned` (idempotent). Order and pins are stored.
- **Activity and counts**: `live_sessions` / `total_sessions` count the workspace's sessions (live states / all, ended and restored ones included). `last_active_ms` moves when a session is created, when input reaches one of its live terminals, and when one produces output; it changes at most once per 10 s per workspace (session creation excepted) and carries the time of the announcement when an update was held back. It is stored.
- **Events**: `workspace.updated` carries the whole `WorkspaceInfo` after every change of any field — rename, roots, pin, position, activity, and the session counts (published right after the `session.updated` that changed them). Creation is announced the same way; `workspace.closed` stays as it was.
- **CLI**: `hutan ws` and `hutan project`, see § Projects and workspaces (0.19). `hutan new` creates its session in `--ws <id|name>` (a workspace or a project), else `$HUTAN_WORKSPACE`, else the project of its folder (Home with `[projects] auto = false`); `hutan ls --ws` takes an id or a name too. A workspace target is a full id, an exact name (then ignoring case), or an id prefix of at least 4 characters; several matches are a usage error (exit 2), none a failure (exit 1). `ws new` and `project open` send `created_by: cli`.


## Projects and workspaces (protocol 0.19, capability `projects.auto`)

M18-A, ADR 0014; `crates/daemon/src/{registry,projects,placement,project_migration}.rs`, `crates/protocol/src/project.rs`, `crates/storage` (schema v8: `workspaces.common_dir|parent_id`, `kind` gains `workspace`), `crates/cli/src/commands/{workspaces,projects}.rs`. Orchestration view: `docs/orchestration.md` § Projects.

- **Two kinds of container, both `WorkspaceInfo`.** A **project** (`kind: project`) is a repository or a folder, made by the daemon; `WorkspaceInfo.project = {common_dir?, root}` identifies it. A **workspace** (`kind: workspace`) is the user's own: a name, a pin, an order, a settings layer and a layout, containing projects (`parent_id` on the project; a project is in at most one workspace). `home` is as before. New fields default when absent (`parent_id` and `project` to none), so a 0.17 daemon's workspaces decode as before.
- **Identity.** The project of a folder is the deepest enclosing git repository's *common directory* (`.git`, or `.git` file → `gitdir:` → `commondir`; read from disk, no git process), canonical; its `root` is the repository's main checkout. The main checkout and every linked worktree of a repository are one project; a submodule and a nested repository have their own; a folder outside any repository is its own project (`common_dir` absent, `root` the folder). A worktree whose repository is gone is a folder project. The home directory, `/` and Home's folder are not projects (a repository rooted in the home directory — a dotfiles repository — does not count, and does not swallow the folders below it); they belong to Home, and so does what lies below Home's folder outside any repository.
- **Where a session goes.** `session.create`, `chat.create`, `task.start` and a restored session whose project needs re-deriving: an explicit `workspace_id` wins (a project, a workspace, Home); otherwise, with `[projects] auto = true` (`daemon.toml`, default), the project of the session's folder, which the daemon creates (announced with `workspace.updated`, `created_by: user`) when it is new; a folder that does not exist, or none, goes to Home. With `auto = false` it goes to Home, as before 0.19. A session keeps the project it started in (it is not moved when its shell changes directory); `SessionInfo.folder` is where it is *now* — the shell's OSC 7 directory, else the start directory — and `placement` stays as in 0.14. A task of a *workspace* starts its session without `workspace_id` (so the session lands in the project of its folder, which the workspace holds); a task of a project names it. A client takes the session's workspace for settings and layout from `parent_id` of its project, else the project itself.
- **Workspaces.** `workspace.create {name, paths?, project_ids?}` makes a workspace holding the projects of the folders `paths` (a project that exists is reused, a new one made; a path that is no directory is `bad_request`/`not_found`) and the existing projects `project_ids` (`invalid_state` for an id that is not a project; one that is in another workspace moves). The workspace is created before its projects move in: `workspace.updated` for it, then one per project and per workspace whose members changed. `workspace.assign {project_id, workspace_id?}` puts a project into a workspace or out of it. `workspace.delete {workspace_id}` removes a workspace: its projects stay, ungrouped (`workspace.updated` each), `workspace.closed` follows; ended sessions and tasks of the workspace go with it, live sessions of its own refuse (`invalid_state`). `workspace.close` on a workspace is `workspace.delete`; on a project it closes it, which also removes it from its workspace. `workspace.rename`, `.pin` and `.move` work on every kind; order is one list over all kinds (`position` `0..n`), and a client groups by `parent_id` itself.
- **Derived fields of a workspace.** `roots` are the roots of its projects; `live_sessions` / `total_sessions` and `last_active_ms` include its projects' sessions and activity (announced right after the project's own change).
- **Settings layering** (client side; the daemon only exposes the roots): user < workspace (`<first project root>/.hutan/settings.toml` of the workspace) < project (`<project root>/.hutan/settings.toml`); a project outside any workspace layers only its own.
- **Migration** (daemon, once, at the first start on schema 8; `app_meta.projects_auto`): every existing workspace stays a workspace (id, name, pin, order and everything keyed by its id — layout, tasks, worktrees, sessions — are untouched) and each of its folders becomes a member project (identity computed from disk, named after the repository's main checkout; a folder that is gone keeps a folder project under its stored path; two workspaces with folders of one repository: the first keeps the project). Projects follow their workspace in the list; positions are renumbered. Home stays Home. No session moves.
- **Restore.** Sessions come back in the workspace they were stored in. Only when that workspace is a project whose folder is gone and the folder the session started in still exists does the session follow its folder to the project there (made if new); a missing folder keeps the stored project.
- **Compatibility.** A 0.17 client sees projects and workspaces as workspaces: it lists them all and can name any of them as `workspace_id`. `workspace.create` with `roots` (a 0.17 client) creates a workspace with member projects. `session.snapshot`, `workspace.list` and `workspace.updated` carry every kind.
- **CLI.** `hutan ws ls|new NAME [PATH…]|add WS PATH|PROJECT|remove WS PROJECT|rename|rm|move|pin|unpin|use` and `hutan project ls|open PATH|rename|pin|unpin|close|recent`; `ws ls` prints the tree (workspaces → their projects, then projects in no workspace, then Home; empty loose projects hidden without `--all`), `hutan ls` has PROJECT and FOLDER columns. `hutan wt` and `hutan task` find the project of the current directory through `workspace.open`, so a linked worktree belongs to its repository's project.

## Session history search (protocol 0.8, capability `history.search`)

Code: `crates/index` (index), `crates/daemon/src/history.rs` (requests, Hutan feed), `crates/protocol/src/history.rs` (DTOs). Sources, ranking, privacy, formats: `docs/history-index.md`.

- `query` is words and `"quoted phrases"`; every one must match, and quotes, `AND`/`OR`, `*`, `:` have no special meaning. A query with no letter or digit → `bad_request`, as do `limit` outside 1–100 and `since_ms > until_ms`.
- Hits are grouped by session: the best row (BM25 over the text and identifier columns, times a role weight: command 1.4, user 1.3, assistant 1.0, tool 0.7, output 0.6) with `matches` = rows of that session that match. `score` is higher-is-better and only comparable inside one response. `snippet` wraps matched words in `«` `»`.
- `session_key` is the agent's own session id (`claude`: file name; `codex`: `session_meta.id`; `omp`: `session.id`, a sub-agent's hits carry its parent's id) or the Hutan session id. `resume_argv` (`claude --resume <id>`, `codex resume <id>`, `omp --resume=<id>`) passes the `agent.report` resume validation or is absent; `hutan` hits have none.
- `project` matches sessions whose cwd is that directory or inside it. `since_ms`/`until_ms` compare the row's timestamp (rows without one carry their file's mtime).
- Indexing is opt-in. While disabled, `history.status` says `enabled: false` with no sources, `history.search`/`rebuild` answer `invalid_state`, and no transcript file is read.

## Session catalog (protocol 0.29, capability `history.sessions`)

Code: `crates/index/src/summary.rs` (the per-session summary), `crates/daemon/src/history_catalog.rs` (attribution, scopes, filter, sort), `crates/protocol/src/history.rs` (DTOs). Fields, title precedence and performance: `docs/history-index.md` § The session catalog.

- One row per session of the enabled sources (`[history]` per-source switches), sub-agent transcripts excluded, a session with neither message nor title not listed. `loaded` is the row count of the enabled sources before scope, `sources` and `filter`; `matched` is what is left after them; `sessions` is the first `limit` of those (`limit` above 1000 is cut to 1000, 0 is `bad_request`).
- `scope: workspace` keeps sessions whose `cwd` is inside a root of `workspace_id` or of one of its member projects (or in a linked git worktree of one of their repositories); `scope: project` keeps those attributed to `workspace_id`. `workspace_id` of a row is the project (or Home, or workspace) with the longest root containing the `cwd`, a project winning over Home over a workspace on equal roots; a linked worktree belongs to the project of its repository; a live Hutan session belongs to the workspace it runs in. Absent when nothing owns the folder.
- `filter`: case-insensitive substrings, every term required, over title, first prompt, latest turns, agent (`claude`, `codex`, `omp`, `hutan`), model, branch, `cwd` and session key; `repo:<text>` the attributed project's name or folder name, `path:<text>` the `cwd` or the transcript path; `"double"` or `'single'` quotes keep a value with spaces together. A filter over 2 KiB matches nothing.
- Order: `updated` (the last message, else when the transcript was last read) or `created` (the first message), newest first, ties by `session_key`. `updated_ms` falls back to when the transcript was last read.
- `resume_argv` passes the `agent.report` resume validation or is absent; OMP resumes by the absolute transcript path (`omp --resume=<path>`), Claude Code and Codex by session id. Hutan rows have `session_id` and no `path`/`resume_argv`.
- `scan`: transcript files found per source (`files`), looked at so far in a running scan (`done`), `scanning`, when the last scan finished. `refresh: true` looks at the files again and answers when that is done, at most 10 s: then the answer has `scanning: true` and the rescan finishes on its own.

## Agent chat and approvals (protocol 0.9, capability `chat.codex`)

Code: `crates/core/src/agent.rs` (the event model), `crates/agents` (adapter), `crates/daemon/src/chat.rs` (sessions, approvals, journal), `crates/protocol/src/chat.rs` (DTOs). How it works and how to re-record the test transcripts: `docs/agents.md`.

- A chat session is an ordinary session of kind `harness` with `SessionInfo.chat = {agent, model, approval_policy, sandbox, turn_active, pending_approvals}` and no terminal. State: `starting` → `idle`; `running` during a turn; `waiting_approval` while any approval is pending; `failed` (reason) when the agent cannot start or exits on its own; `stopped` after `session.stop`. `session.restart` starts the agent again and resumes the conversation.
- `AgentEvent` is one flat JSON object: `{session_id, seq, ts_ms, delivery: live|replay, turn_id?, item_id?, provider: {thread_id?, turn_id?, item_id?, request_id?}, type, …kind fields…, payload?}`. `type` is one of `turn_started`, `message_start|delta|end|partial`, `reasoning_start|delta|end|partial`, `tool_start|update|end`, `command_output`, `file_diff`, `permission_requested|resolved`, `plan`, `usage`, `turn_completed|failed|cancelled`, `resume_locator`, `notice`, `opaque`. Usage numbers a provider did not report are absent, never `0`. `payload` is the provider's own message for the kinds where it adds information (tool items, permission requests, `opaque`). A client that meets a `type` it does not know ignores that event.
- Local ids (`turn_id`, `item_id`, `approval_id`) are ULIDs the daemon assigns; the provider's are in `provider`. `seq` is strictly increasing per session across daemon restarts. Streaming events (`message_delta`, `reasoning_delta`, `command_output`) consume a `seq` and are delivered live only; the journal (`chat.history`) holds everything else, so its `seq` has gaps and the `*_end` events carry the complete text.
- Following a session: subscribe (`events.subscribe`), then page `chat.history` (the newest page first, `limit` 200; older pages with `before_seq` = the first `seq` of the page before, until `has_more` is false: the desktop's "Load earlier"); apply a live `chat.event` only when its `seq` is greater than the history's `last_seq` (the CLI's `chat attach` does this). `chat.event`s travel on the daemon-wide event stream like every other event (replayed after a reconnect while they are in the ring, see ADR 0002).
- Approvals: `permission_requested` lists the provider's offered `options` (`id` = the provider's own name for the decision, `label`, `kind` allow_once|allow_always|reject_once|reject_always|cancel|other); a request that offers none beyond the schema's defaults gets Codex's four (`accept`, `acceptForSession`, `decline`, `cancel`). `approval.respond` accepts only an `option_id` that was offered. Pending approvals live in the daemon, survive client disconnects, and end as `approval.resolved`: `selected` (with the option) or `expired` when the turn ends, the agent withdraws the request, the agent exits, or the daemon restarts. Every request and its outcome (who answered: the client kind) is stored in the `approvals` table.
- Provenance (0.15, capability `chat.provenance`): `approval.resolved` and the journaled `permission_resolved` event carry `decided_by: {client_kind, client_name?}` for a `selected` outcome: `client_kind` is the answering connection's `hello` kind (`desktop`, `cli`, `notifier`, `other`; a newer daemon may add more, clients treat an unknown one as "another client"), `client_name` the name it gave (no client names itself yet). The first answer the agent accepts is the one credited: a refused attempt (wrong option, already answered) takes no credit. `expired` carries none. Events journaled before 0.15 have none either, and `chat.history` replays what was journaled.
- Mid-stream text (0.15): a running turn keeps the text of every open assistant message and reasoning block; the daemon journals `message_partial {message_id, phase?, text}` / `reasoning_partial {reasoning_id, summary, content}` for the ones that changed at most every 500 ms (and for what is left when a turn ends without its `*_end` events). A snapshot is **replaced in place** (one per open item, the journal does not grow with the deltas) and is deleted when the item's `message_end` / `reasoning_end` arrives. It is never delivered live. A snapshot includes every delta of its item with a **smaller `seq`** than its own. `chat.history` answers an item that is still streaming with a fresh snapshot of it taken at that moment, stamped with a `seq` it takes from the session's counter (so it is no greater than `last_seq` and every live delta after the reply is greater): a client that joins mid-stream applies the snapshot as the text so far, then every live delta with a greater `seq`; a delta with a smaller one is already in the text. Text of an item beyond 1 MiB is not kept in a snapshot (the end event has all of it).
- A message of the provider Hutan has no model for becomes an `opaque` event with its method and payload; a request of the provider Hutan cannot serve (user-input questions, MCP elicitations) is declined towards the provider and noted as a `notice`.

## Direct model chat and providers (protocol 0.11, capability `chat.direct`)

Code: `crates/gateway` (providers), `crates/daemon/src/{providers,direct}.rs`, `crates/protocol/src/provider.rs` (DTOs). How it works: `docs/gateway.md`.

- `chat.create { agent: "direct", provider_id, model?, system_prompt?, cwd }` opens a chat session exactly like a Codex one (kind `harness`, no terminal, `SessionInfo.chat.agent = "direct"`, `SessionInfo.chat.provider_id`, `model`; `approval_policy` and `sandbox` are the defaults and mean nothing). `model` defaults to the provider's `default_model`; without either, `bad_request`. `cwd` only places the session in a workspace.
- `chat.send` streams the reply as the same `AgentEvent`s as a Codex turn: `turn_started` (its `payload` is `{provider_id, model}` of the turn), `message_start|end` for the user message, `message_start`, `message_delta`…, `message_end` for the assistant (nothing precedes the first delta, so a failure before any text has no assistant message), `usage` (`last` = this request, `total` = the conversation; fields the provider did not report are absent), `turn_completed`. A failure ends with `turn_failed` (the provider's own message, credentials scrubbed, `details` names provider and model), `chat.interrupt` with `turn_cancelled` after closing the HTTP stream; text streamed before a failure or an interrupt is kept (`message_end`). A provider that needs a key and has none, or a removed provider, fails `chat.send` itself (`provider_error` / `not_found`) before anything is journaled.
- The conversation sent with a turn is the user and assistant text of the session's journal. At most `gateway.max_context_chars` (daemon.toml, default 200000) characters of it are sent: the oldest messages that do not fit are left out (an assistant message is never first), and the turn carries a `notice` saying how many.
- `chat.set_model` changes provider and/or model between turns; it works on a running chat only. The notice `model switched from <provider> / <model> to <provider> / <model>` is journaled. Approvals do not exist for direct chats: `approval.*` never mention them.
- Providers are configuration in SQLite (`providers`: id, kind, name, base_url, default_model, keychain_ref, created_at) and a credential in the Keychain (service `dev.hutan.provider`, account = the provider id). `has_credential` is the only trace of the secret in any message.

## Agent observation tree (protocol 0.10, capability `agent.tree`)

Code: `crates/core/src/observation.rs` (model and reducer), `crates/protocol/src/tree.rs` (DTOs), `crates/daemon/src/tree.rs` (events, rollup, storage), `docs/integrations.md` § Observation tree.

- `agent.tree {session_id?}` → `{observations: [{session_id, root, nodes: {node_id: AgentNode}}]}` (one session, or every session that has agents, in creation order; unknown `session_id` is `not_found`). `AgentNode = {node_id, parent?, kind: main|sub, source, agent, name?, agent_type?, state: working|blocked|idle|unknown, outcome?: completed|failed|interrupted|disconnected, liveness: alive|gone|unknown, model?, started_at_ms?, ended_at_ms?, last_activity_ms, activity?, usage?, transcript_path?}`. Every number of `usage` (`input`, `output`, `cache_read`, `cache_write`, `reasoning`, `context_tokens`, `context_window`, `cost_usd`) is optional and never zero-filled; `usage.kind` (`omp.tokens`, `claude.context`, `codex.total`, …) says what the numbers mean.
- `agent.report` gains `node {id, parent?, kind, name?, agent_type?, outcome?, model?, activity?, usage?, transcript_path?}`; without it the report is about the main agent (the node `root`), as in 0.4. `state` is optional: absent leaves the node's state alone (a report that carries only a model). A report with a state replaces the node's `activity`. `seq` must increase per `(session, source, node)`. `agent.release` with `node` ends that node (`outcome`, default `completed`); a release of the main agent also disconnects every subagent still running.
- Three things are kept apart: `state` (what it does), `outcome` (how a finished node ended; its `state` is then `idle`) and `liveness`. Nodes the daemon has no evidence for are `unknown`/`disconnected`: after a daemon restart the main agent is `state: unknown, liveness: unknown` until it reports again, its subagents are `outcome: disconnected`. Bounds: 256 nodes per session (the oldest finished are dropped first), finished subtrees leave 30 minutes after they ended.
- `SessionInfo.agent` stays as the summary for older clients: the main agent's state, `blocked` while any subagent is blocked (then `blocked_sub` names it). `hutan ls` shows `blocked (sub: <name>)`.
- Following: `agent.tree`, then apply `agent.tree_updated` events (whole nodes; the root is the one node without a `parent`).

## Notification intents (protocol 0.13, capability `notify.intents`)

Code: `crates/daemon/src/notify.rs`, `crates/protocol/src/notify.rs` (DTOs). The daemon decides *that* something needs the user; whoever can show a notification (a Notifier, the desktop, `hutan notify watch`) renders it and sends the choice back. Native delivery (macOS notifications) is posted by the daemon itself, only from the signed app bundle, see § Native delivery below; a daemon outside the bundle posts nothing and the intents stay in `notify.list`.

- `NotificationIntent {id, kind, session_id, workspace_id?, title, body, actions: [{id, label}], created_at_ms, expires_at_ms?}`. `title` (≤ 120 characters) and `body` (≤ 240) are redacted like assistant context (secrets masked over the whole source text first, then one line, then cut; a cut ends in `…`, but text that exactly fits keeps its last character; a quoted `name="value` that an upstream bound — the tree keeps 200 characters of an activity — left without its closing quote is masked to the end of the text, including line breaks). `actions` are the approval's options for `approval_required`, else the single `{id: "open", label: "Open"}`.
- Redaction is idempotent: a previously masked assignment retains its complete `[REDACTED]` marker when a journal, attachment or intent passes through another redaction boundary.
- Kinds and what raises them: `approval_required` (`approval.required`); `agent_blocked` (a node of the session's agent tree becomes `blocked` and is not gone); `agent_finished` (the main agent goes `working` → `idle` with no outcome or outcome `completed`, and the turn, blocked stretches included, took at least `min_turn_secs`, measured from when the daemon saw it start; `failed`, `interrupted`, `disconnected` and subagents do not count); `session_exited_with_error` (a session's process exits with a non-zero code; a signal, such as a stop, does not count); `chat_turn_finished` (a live `turn_completed` while no connection has the session focused; the body is the assistant's last reply); `task_done` / `task_failed` (0.16: a task changes into `done` / `failed`, see § Tasks; exempt from the per-session rate limit).
- A normal stop is a finish: the Claude/Codex `Stop` hooks and OMP's main `agent_end` report a plain idle, and that, like an explicit `completed` (`agent.release`, or a report with `--outcome completed`), raises `agent_finished` after a long enough turn. Claude's `StopFailure` reports outcome `failed` and raises nothing. Hutan's own Codex chats (tree source `codex-app-server`) never raise `agent_finished`: their turns are `chat_turn_finished`. Blocked-agent and non-zero session-exit intents apply to every session.
- The gate, in this order: `[notify]` in `daemon.toml` (`enabled`, `kinds`; others dropped); focus suppression (only `chat_turn_finished`); dedup by `(kind, session, node)` where the node part is the approval, node or turn id — an identical intent that is still pending is not raised again; a rate limit of one intent per session per 10 s (approvals are exempt and do not count). A dropped candidate is gone; nothing is queued.
- Pending intents live in the daemon's memory (at most 100, oldest dropped first) and are lost with it. They leave the list on `notify.ack`, `notify.act`, when their approval resolves (answered anywhere, or expired with its turn), or when they expire: `expires_at_ms` is `created_at_ms + notify.expire_secs` (default one hour); an approval's intent has none and lives as long as the approval. Expiry is lazy: `notify.list` omits expired intents and ack/act on one is `not_found`.
- `notify.act` with an approval action calls `approval.respond` with the action's id as `option_id`; the approval audit trail's `decided_by` is the kind of the acting client (`cli`, `desktop`, `notifier`). `open` publishes `ui.open {session_id, workspace_id?, at_ms}` on the event bus and answers how many subscribed desktop clients it reached (`0`: nobody can show the session).
- `client.focus` is per connection; the desktop reports the session of its focused tab while its window is active, `none` otherwise, and again after every reconnect.
- Settings (`daemon.toml`): `[notify] enabled = true`, `min_turn_secs = 20`, `kinds = [...]`, `expire_secs = 3600`, `native = true` (`false` keeps intents off the system's notification centre; they are still raised and listed).
- CLI: `hutan notify ls|ack|act|watch`.

### Native delivery (M6-B, no wire change)

Code: `crates/daemon/src/notify_native.rs` (mapping, `NativePoster`, authorization state, delivery task), `notify_native/cocoa.rs` (`UNUserNotificationCenter` through objc2, the main-thread run loop), `notify_native/fake.rs` (test poster). Design: ADR 0007, `docs/packaging.md` § Native notifications.

- **Who posts.** `hutand` posts every raised intent itself, under the app identifier `dev.hutan.Hutan`; there is no helper process. It does so only when its executable is `<x>.app/Contents/MacOS/hutand` and `NSBundle.mainBundle.bundleIdentifier` is `dev.hutan.Hutan` (a pure check, `notify_native::runs_from_hutan_app`). Anywhere else (`cargo run`, tests, a bundle with another identifier) the daemon logs once at info level and uses no poster.
- **Mapping.** One category per intent kind (`hutan.<kind>`, so `hutan.task_done` and `hutan.task_failed` too, each with just *Open*; approvals add a hash of their buttons because the options are the provider's). Notification identifier = intent id, thread identifier = session id, title and body = the intent's (already redacted and bounded). An approval shows its first three options as actions (destructive style for the `reject_once`, `reject_always` and `cancel` kinds) plus *Open* (foreground); every other kind shows *Open* only. The *Open* action id is `hutan.open`, so a provider's own option called `open` stays an option.
- **Responses** reach the daemon's delegate and are routed like `notify.act` from a client of kind `notifier`: an option → `approval.respond` (`decided_by` = `notifier`); *Open* or a click on the body → `ui.open` (an approval's intent stays pending: it is answered where the session opens; any other intent is acknowledged); dismissing → acknowledge. A response for an intent that is gone is ignored.
- **Authorization** is requested (alert and sound) lazily before the first post, once per daemon run; posts wait for the answer, in order and bounded. Denied → no further posts, one warning, the intents stay in `notify.list` and `hutan notify watch`.
- **Removal.** An intent that is acknowledged, acted on, expired (swept every `min(expire_secs, 30)` s while a poster exists) or whose approval resolved elsewhere removes its delivered notification. A daemon restart re-posts nothing (intents are in memory). A click while the daemon is not running is lost (`usernoted` drops it); an approval then stays pending.
- **Threads.** `hutand` runs tokio on a dedicated thread and, inside the bundle, runs the Cocoa run loop (`NSRunLoop`, default mode) on the **main thread**, the only thread that receives the notification centre's callbacks (spike fact 5). All Objective-C calls are queued (bounded) to it and run in one drain block on the main dispatch queue; no Cocoa call waits for tokio and the tokio side never waits for Cocoa. Shutdown (SIGTERM/SIGINT, `daemon.shutdown`) ends the runtime thread, whose drop stops the main loop through the main queue, so the process exits cleanly.

## Worktrees and placement (protocol 0.14, capability `worktree`)

Code: `crates/daemon/src/{worktrees,placement}.rs`, `crates/protocol/src/worktree.rs` (DTOs), storage migration 6. Concepts, CLI and desktop: `docs/orchestration.md`.

- **git is the source of truth.** `worktree.list` runs `git worktree list --porcelain -z` in the main checkout of every repository the workspace's roots belong to (a root that is itself a linked worktree finds its repository; a repository reached from several roots or workspaces is listed once). Every git call runs with `GIT_TERMINAL_PROMPT=0` and `GIT_OPTIONAL_LOCKS=0`, a timeout (20 s for reads, 180 s for `worktree add`/`remove`), and never touches the network. Hutan remembers only which worktrees it created (`worktrees(path PK, workspace_id, repo_root, branch, base, created_at_ms)`); `created_by_hutan` is that memory and survives daemon restarts. A repository that cannot be listed (deleted) is skipped.
- `WorktreeInfo.dirty`: tracked changes or untracked files that are not ignored (`git status --porcelain`); `live_sessions`: live sessions whose placement root is the worktree; `locked`, `prunable`: git's flags (prunable: the directory is gone). `head` is the full commit id; `branch` is absent for a detached HEAD.
- `worktree.create`: `repo` is any directory in the repository (default: the first root of the workspace that is in a git repository). The default `path` is `<parent of the main checkout>/<repo name>-wt/<branch with / → ->` and must not exist (`conflict`; there is no automatic suffix). `base` only applies to a branch that does not exist yet and is ignored otherwise. The branch name must pass `git check-ref-format --branch`; names starting with `-` or containing `@{` are refused. Answers after `git worktree add` finished; `worktree.changed` follows for every workspace that has the repository.
- `worktree.remove`: refuses (`invalid_state`) the main worktree, any live session inside (placement root equal, or its directory below the worktree, even with `force`), a locked worktree, and uncommitted changes unless `force`. `delete_branch` runs `git branch -d` afterwards (never `-D`): an unmerged branch stays and its git message comes back as `branch_kept`; the worktree is removed regardless. A prunable worktree (directory gone) is removed from git's records.
- **Placement**: `SessionInfo.placement {kind: main|worktree, root, branch?, shared_with: [SessionId]}` (absent outside git, or while the directory is unknown or gone). It is derived from the session's live cwd (OSC 7, else the spec cwd): the nearest ancestor holding `.git` is the checkout root (canonical path); a `.git` directory is `main`, a `.git` file whose private directory has a `commondir` is a linked `worktree` (a submodule counts as `main`). No git process runs for it: the checkout of a directory is cached (60 s, 512 directories, cleared by every `worktree.*` request that changed something) and `HEAD` is read again at each derivation, so a branch switch shows up with the next change to the session.
- `shared_with` lists the other **live sessions whose agent is reported** (`SessionInfo.agent` present: not gone, any state) in the same checkout root, and only while the session has an agent itself: a shell next to an agent shares nothing. It changes with `agent.report`/`agent.release`, a cwd change, and a session ending, and is announced with `session.updated` for every session whose list changed. `worktree.create`/`remove` derive every placement again (a stopped session in a removed worktree loses its placement).
- Merging and diff review: § Worktree review and merge (0.22).

## Worktree review and merge (protocol 0.22, capability `worktree.review`)

Code: `crates/daemon/src/worktrees/review.rs`, `crates/protocol/src/worktree.rs` (DTOs). Concepts, CLI and desktop: `docs/orchestration.md` § Review and merge.

- **Git invocation.** Diffs run `git --no-pager --literal-pathspecs -c core.fsmonitor=false diff --no-ext-diff --no-textconv --no-color --src-prefix=a/ --dst-prefix=b/ --submodule=short -M` with the same environment as the other `worktree.*` calls (`GIT_TERMINAL_PROMPT=0`, `GIT_OPTIONAL_LOCKS=0`, `GIT_PAGER=cat`, no editor, English messages, closed stdin) under a 60 s timeout; a repository's `diff.external` or textconv configuration never runs, and nothing is written to the repository (untracked files are read from the file system and diffed with `--no-index`, never staged). Merges run under 180 s and never run hooks (`--no-verify`).
- **The comparison** is `git diff <merge base of base and HEAD>`: the commits of the checkout's branch since it left `base`, and (with `include_uncommitted`) the working tree. `base` defaults to the repository's default branch: the local branch `origin/HEAD` points to, else `main`, else `master`. Renames are detected (`-M`); a copy counts as a new file.
- **Bounds.** A file's patch is cut at 2 MiB (`worktree.file_diff.truncated`), all patches of one diff are read to 20 MiB at most and the list holds at most 5000 files; when any bound was hit `worktree.diff.patch_truncated` is set. Line counts of the list stay exact for text files; a binary file (git's NUL heuristic) has `binary: true`, no counts, and `Binary files … differ` as its patch.
- **Merge.** Refusals are decided before the first change; the main checkout is dirty when `git status --porcelain` is not empty (untracked files count). `merge` is `git merge --no-ff` (git's message unless `message`), `squash` is `git merge --squash` and one commit (message default `Squash merge branch '<branch>'`), `rebase` rebases the branch onto the target in its own worktree and moves the target with `git merge --ff-only` (linear history; `message` is `bad_request`). A conflict (or any failure half way) aborts: `git merge --abort`, `git reset --merge` after a squash, `git rebase --abort`; the `conflict` error's message names the files and `data.conflicts` lists them. After a success `worktree.changed` is published for every workspace of the repository, `source_dirty` says the worktree still has uncommitted changes that are not part of the merge, and removing the worktree and its branch is a separate `worktree.remove {delete_branch: true}` (the client offers it).

## Tasks (protocol 0.16, capability `task`)

*0.27, capability `task.chat_model`:* a `chat` run may name a `model` (one of `chat.models` for its agent); the chat is created with it, so the first turn already runs on it. A model the agent does not offer fails `task.start` with the `chat.create` error naming the choices; an empty one is `bad_request` at `task.create`. Absent: the agent's own default. Daemons without the capability ignore the field.

Code: `crates/core/src/task.rs` (model, state machine, graph rules, scheduler), `crates/daemon/src/tasks.rs`, `crates/protocol/src/task.rs` (DTOs), storage migration 7. Concepts and CLI: `docs/orchestration.md` § Tasks.

- `Task {id, workspace_id, title, prompt?, state, depends_on: [TaskId], placement: {kind: main|worktree, branch?, base?}, run?: {kind: terminal, argv} | {kind: chat, agent}, auto_start, sessions: [SessionId], created_at_ms, started_at_ms?, ended_at_ms?, outcome?}`. `title` is one line of 1–200 characters (trimmed), `prompt` at most 64 KiB, at most 64 dependencies, all of the task's workspace. `run` absent: starting opens the login shell. A `chat` run needs a `prompt` (its first message) and knows `codex`, `omp` and `claude` (0.17).
- **States**: stored `todo`, `running`, `done`, `failed`, `cancelled`; shown also `ready` (a `todo` task whose dependencies are all `done`; none means ready at once) and `blocked` (a `running` task whose agent waits for the user: session `waiting_approval`, a reported agent `blocked`, a chat with pending approvals). A failed or cancelled dependency does not release its dependants. Transitions: `todo/ready → running` (start), `running ⇄ blocked`, `running/blocked → done | failed`, `todo/ready/running/blocked → cancelled`, `todo/ready/running/blocked/failed → done` (the user's word), `done/failed/cancelled → todo` (reset; earlier sessions stay in `sessions`).
- **Dependencies**: a cycle is `bad_request` and the message names it (``dependency cycle: `a` -> `c` -> `b` -> `a` ``); so is a dependency of another workspace and a task depending on itself. `task.delete` of a task others depend on is `conflict` unless `cascade`, which removes the dependants first.
- **Start**: `task.start` claims the task (`running`) and then sets it up: placement `main` works in the first folder of the workspace that is a git repository (else its first folder), and `warnings` says when other live agents (a reported agent, or a Codex chat) already work in that checkout; `worktree` uses the existing worktree of the branch (default `task/<slug of the title>`; a branch checked out in the main checkout is `invalid_state`) or creates one through `worktree.create` (`base` default `HEAD`). A `terminal` run starts `argv` there with `HUTAN_TASK_ID` in its environment and the task's title as the session title; a `chat` run creates a chat with the run's agent (Codex, or the `omp` / `claude` harnesses over ACP) and sends the prompt. A failed setup puts the task back as it was (`todo`) and answers with the error.
- **Finish detection** (task `running`): the session exits 0 → `done` (`exited 0`), non-zero → `failed` (`exited N`, `killed by signal N`), session `failed` → `failed`, session stopped → `cancelled` (`session stopped`); the main agent of a terminal session going `working` (or `blocked`) → `idle` with no outcome or `completed` → `done` (`agent finished`, no minimum duration), with outcome `failed` → `failed` (`agent failed`); a live chat turn `turn_completed` → `done`, `turn_failed` / `turn_cancelled` → `failed`. `task.update {state: done}` overrides. The session of a finished task is left alone. The daemon also looks at the sessions of running tasks every 5 s, so a dropped event delays a finish.
- **Auto start**: a ready task with `auto_start` waits in a FIFO queue (order of becoming ready, creation order among tasks that become ready together) and starts when fewer than `[tasks] max_parallel` (default 3) tasks are `running` or `blocked`; a task that cannot be started is `failed` (`start failed: …`). `task.start` ignores the limit.
- **Restart**: a task `running` when the daemon stopped stays `running` when one of its sessions was restored alive, else it is `failed` with outcome `interrupted`. Closing a workspace deletes its tasks (`task.removed` for each).
- **Events**: `task.updated {task}` carries the whole task as shown, once per change; `task.removed {id}`. Both are in the replay ring like every event.
- **Intents**: `task_done` / `task_failed` (`notify.intents`) are raised for the last session of the task when it changes into `done` / `failed` (a task seen for the first time counts when it ended less than a minute ago). They pass the `[notify]` gate and dedup but not the per-session rate limit. A task without a session raises none.
- `outcome` is free text for people: `exited 0`, `agent finished`, `turn completed`, `marked done`, `cancelled`, `session stopped`, `interrupted`, `start failed: …`.

## Task delivery and review (protocol 0.25, capability `task.review`)

Code: `crates/core/src/task.rs` (`DeliveryState`, `DeliveryRecord`, `AfterPolicy`, `Task::record_delivery`), `crates/daemon/src/tasks.rs` (`review`, `worktree_merged`, `worktree_removed`), `crates/daemon/src/worktrees/review.rs` (`commit`, the scope of `diff`), `crates/protocol/src/{task,worktree}.rs` (DTOs), storage migration 9. Concepts, CLI and desktop: `docs/orchestration.md` § Delivery.

A task's **run state** says what its agent did; its **delivery** says where the finished work is. They are independent: a `done` task has not been reviewed, and a reviewed one has not been merged.

- `Task` gains `delivery` (`none` when absent), `after_policy` (`done` when absent) and `delivery_history: [DeliveryRecord]` (empty when absent), all omitted when they have their default. `DeliveryRecord {state, by: desktop|cli|agent|daemon, at_ms, note?, commit?, strategy?}`: `note` on `changes_requested` (and an acceptance that carried one), `commit` (the new tip of the target, full hash) and `strategy` (`merge|squash|rebase`) on `merged`. The last 20 records are kept, oldest first; `delivery` is the state of the last one.
- **States and moves**: `none → awaiting_review` when a run finishes `done` (the session exits 0, an agent goes idle after working, a chat turn completes) and the task has a worktree, or an agent (a chat, or an agent reporting inside a terminal) worked in the main checkout; a plain command that exits 0 in the main checkout leaves `none`. `task.update {state: done}` (the user's word) records no delivery. `awaiting_review | accepted | changes_requested → accepted | changes_requested` through `task.review`. `awaiting_review | accepted | changes_requested → merged` when a `worktree.merge` of the task's branch succeeds (every `done` task of a workspace of the repository placed on that branch, whatever its delivery); `→ discarded` when `worktree.remove` removes that branch's worktree without a merge. A run that finishes again after a change request is `awaiting_review` again; `task.update {state: todo}` (reset) clears the delivery. `merged` and `discarded` are final: `task.review` on them is `invalid_state`. `by` is `desktop` or `cli` for the connection's `hello` kind, `agent` for an agent-originated request (ADR 0016) and `daemon` for the automatic `awaiting_review`. Every move is announced with `task.updated {task}` once.
- **`task.review {id, decision: accept|request_changes, note?}`** → `{task, session?}` (`TaskReviewed`). `accept` moves the delivery to `accepted` (and releases dependants with `after_policy` `accepted`), `request_changes` to `changes_requested`. `note` (trimmed, at most 16 KiB; `bad_request` above) is recorded. A `request_changes` note for a task that ran as a chat whose session is still live is sent to that session as a user message (`Changes requested on the work of this task:` and the note), the task goes back to `running` (outcome and end time cleared) and `session` names the chat; a terminal agent cannot be written to, so the note stays on the task (`delivery_history`, `hutan task show`). The decision is not recorded when the message cannot be sent (the error is the chat's: `invalid_state` while a turn runs). Repeating a verdict that changes nothing and has no note answers the task unchanged. Errors: `not_found`; `invalid_state` for a task that is not `done` (the message says what it is), or whose work is `merged` or `discarded`. An agent-originated call needs the user's approval like every mutation (ADR 0016, `[control]` policy `ask`).
- **`after_policy`** (`task.create`, `task.update`; default `done`): what each of the task's dependencies must have reached before it is `ready`. `done` — the dependency's run finished (the behaviour before 0.25); `accepted` — it is `done` and `accepted` or `merged`; `merged` — it is `done` and `merged`. A dependency that runs again (change request, reset) no longer satisfies `accepted` or `merged` until its new delivery does. Like the other fields it is refused by `task.update` while the task runs.
- **`worktree.diff`** says what a merge takes and what it does not. `commits: [{id, subject}]` (omitted when empty; newest first, at most 200, `commits_truncated` when more) are the commits of the checkout's branch since `merge_base` — exactly what `worktree.merge` integrates. Every file has `committed` (it changed in those commits) and `uncommitted` (it has staged, unstaged or untracked changes in no commit; only set when `include_uncommitted` is true); a file can be both. Without `include_uncommitted` every listed file is `committed`.
- **`worktree.commit {path, message}`** → `{commit, branch, files}` (`WorktreeCommitted`). Runs `git add -A` (tracked changes and untracked files that are not ignored) and `git commit --no-verify` in the worktree at `path`, so a following merge takes everything; nothing stays staged when the commit fails. Errors: `bad_request` (an empty message, `path` not absolute), `not_found` (git does not list `path`), `invalid_state` for the main checkout (commit there yourself), a detached HEAD, a merge or rebase in progress, nothing to commit, or git's own refusal (no author identity). An agent-originated call is a mutation (ADR 0016). `worktree.changed` is published.
- **Restart**: the delivery, its history and the policy are stored (SQLite migration 9: `tasks.delivery`, `tasks.after_policy`, `tasks.delivery_json`) and survive a daemon restart; tasks from before the migration have no delivery and policy `done`.
- **Compatibility**: a 0.24 client ignores the new fields (it still sees `done`). A 0.25 client against an older daemon finds no `task.review` capability and hides the review controls.

## Assistant chat and context attachments (protocol 0.12, capability `assistant`)

Code: `crates/daemon/src/{assistant,context,context_file}.rs`, `crates/protocol/src/assistant.rs` (DTOs). How it works, the settings, privacy: `docs/assistant.md`.

- An assistant is a direct chat (§ Direct model chat) with `SessionInfo.chat.agent = "assistant"`. Its scope follows from its workspace: the Home workspace holds the **global** assistants, every other workspace its own **workspace** ones. `assistant.open {scope: global|workspace, workspace_id?, new?}` → `{session}` returns the default assistant of the scope (the oldest of its workspace), creating it on first use with `[assistant] provider`/`model` of `daemon.toml`; a stopped default is started again; `new: true` creates one more. `invalid_state` (the message names `[assistant] provider`) when no provider is configured, `bad_request` for `workspace` without `workspace_id` or with the Home workspace, `not_found` for an unknown workspace. `assistant.list {scope?, workspace_id?}` → `{assistants: [{scope, workspace_id, default, session}]}` oldest first.

That whole text is the journaled and the sent user message; the user's `message_end` event carries `payload.attachments_meta = [{kind, label, chars, truncated}]` (never the text on its own).

## Assistant backends (protocol 0.20, capability `assistant.backend`)

Decision: ADR 0015. Code: `crates/daemon/src/assistant.rs`, `crates/protocol/src/assistant.rs`. How it works: `docs/assistant.md` § Backends.

- `assistant.configure {scope: global|workspace, workspace_id?, backend: omp|claude|codex|provider, model?, provider?}` → `{scope, workspace_id?, backend, model?, provider?}` stores which backend assistants of a scope are created with from now on (persisted in the daemon's database, `app_meta` keys `assistant.config.global` / `assistant.config.workspace.<id>`). A workspace's choice wins over the global one (a project inside a workspace, 0.19, uses its workspace's unless it has its own; `workspace_id` may name a project), which wins over `[assistant] backend` / `provider` of `daemon.toml`. `provider` is required for (and only allowed with) the `provider` backend and must exist (`bad_request` otherwise); `workspace` needs a `workspace_id` that is not the Home workspace.
- `assistant.open` returns the oldest assistant of the scope **that runs on the configured backend** (and provider), creating one with that backend and `model` when there is none; a stopped one is started again. Unconfigured it fails `invalid_state` naming `assistant.configure` and `[assistant]`; a harness that cannot start fails `provider_error`.
- `ChatInfo.assistant` (additive, default false) marks a harness-backed assistant (`agent` is `omp`, `claude` or `codex`); the provider-backed one keeps `agent: "assistant"`. `AssistantEntry.backend` says what each assistant runs on; `default` is the one `assistant.open` returns.
- Attachments reach harness assistants as in § Harness chats (ACP embedded resources; Codex has no such input, so its assistant gets the same text quoted after the message).

## Daemon settings (protocol 0.28, capability `daemon.settings`)

Code: `crates/protocol/src/daemon_settings.rs` (DTOs), `crates/daemon/src/daemon_settings.rs` (the table of settings, validation, the file edit, live apply). The daemon owns `daemon.toml`; clients show and change it through the daemon instead of editing the file (`hutan config`, the desktop's Settings pages).

- `daemon.settings.get {}` → `{file, entries: [{key, kind, value, default, set_in_file, applies, pending_restart}], restart_pending}`. `file` is the path of `daemon.toml`. `key` is the dotted TOML path: `notify.enabled`, `assistant.context.files`, `assistant.workspaces.<workspace>.files`, `harness.omp.bin`, `mcp.<name>`. `kind` is `{type: bool}`, `{type: int, min?, max?}`, `{type: string}`, `{type: path}` (a file or executable; empty means the default lookup), `{type: enum, choices}`, `{type: string_list, choices?}`, `{type: string_map}` (environment variables) or `{type: table}` (an MCP server: set and removed as a whole object). `value` is the JSON of what `daemon.toml` says, else `default`; an optional text or path that is not set is `""`. `set_in_file`: the key is in the file (a reset removes it). `applies` is `live` (the running daemon uses a change as soon as `set` answers) or `restart`. `pending_restart` is true when the running daemon uses something else than `value`: a `restart` key changed since start, or a file edited by hand since start. `restart_pending` is true when any entry is pending.
- The table covers every option of the config structs: `daemon.restore_sessions`, `workspaces.home_folder`, `history.{enabled,range_days,hutan,claude,codex,omp}` and `history.roots.{claude,codex,omp}`, `codex.{bin,args}`, `harness.{omp,claude}.{bin,args,env,cli}`, `gateway.max_context_chars`, `assistant.{backend,provider,model,context_budget_chars}`, `assistant.context.*` and `assistant.global_context.*` (`shell`, `agents`, `files`, `search`), `notify.{enabled,min_turn_secs,kinds,expire_secs,native}`, `terminal.env_inherit`, `tasks.max_parallel`, `projects.auto`, `control.{agents,mcp,approval_timeout_secs}`; plus one `assistant.workspaces.<workspace>.<permission>` entry per permission of each workspace override in the file (its `default` is the inherited `assistant.context` value) and one `mcp.<name>` entry (`kind: table`, `applies: restart`) per MCP server. A test pins that no config field is missing.
- `daemon.settings.set {key, value?}` → the `get` answer after the change. `value` absent or `null` removes the key (back to the default), and so does an empty string for text, path and choice settings. Validated against the table before anything is written: type, `min`/`max` (`history.range_days` is 0, 30 or 90), choices, a `path` of `bin` and `cli` keys must be absolute, exist and be executable, one of `history.roots.*` and `workspaces.home_folder` (`~/…` allowed) an existing folder; `assistant.workspaces.<workspace>.<permission>` needs a workspace with that id or name (setting a new one creates the table). `bad_request` for a key that is not in the table (including `mcp.*`), a value that does not fit and a file that would not load after the change; `invalid_state` when `daemon.toml` cannot be parsed (the message names the file, line and column; the file is never overwritten); `internal` when it cannot be written. `mcp.<name>` takes an object `{command, args?}` (a program Hutan starts) or `{url, transport?}` (a remote server, `transport` `http` (default) or `sse`) — exactly one of `command` and `url`, `args` only with `command`, `transport` only with `url`, a `url` starting with `http://` or `https://`, any other field refused — for a `name` of 1 to 32 lowercase letters, digits, `-` and `_`; it is written as a `[mcp.<name>]` table (an existing table keeps its place and the comments on it and on the keys that stay; the comments of a removed server go with it), `null` removes the server, and the change reaches harness sessions after the daemon restarts (`applies: restart`: the daemon hands the servers it started with to every session it starts).
- The file is edited in place with `toml_edit`: comments, order and keys the daemon does not know stay, and a comment after a changed value stays after it. It is written to a temporary file (mode 0600) and renamed over `daemon.toml`. A key that was removed takes the tables it leaves empty with it, unless a comment hangs on them.
- Live settings, applied to the running services when `set` answers: `notify.{enabled,min_turn_secs,kinds,expire_secs}`; `history.*` (indexing starts, stops or starts again with its new sources and range); `assistant.*` (the permissions are read for each message, backend defaults for each `assistant.open`); `control.agents` and `control.approval_timeout_secs`; `tasks.max_parallel`; `gateway.max_context_chars`. A change hands the daemon the whole fresh table of its group, so a hand edit of another key of that group is in use too. Everything else is `restart`: `pending_restart` stays true until the daemon restarts.
- **Security.** `daemon.settings.set` and `assistant.reset` are user-only (ADR 0016): from an agent-originated connection they answer `forbidden` under every `[control] agents` policy, so an agent can never widen its own permissions. `daemon.settings.get` is a read. Neither is a tool of `hutan mcp`. Values are never secrets (provider keys stay in the Keychain).
- `assistant.reset {scope: global|workspace, workspace_id?}` → `{}`: removes the choice `assistant.configure` stored for the scope, so it inherits again (workspace → its parent workspace → global → `[assistant]` of `daemon.toml` → the automatic backend). Existing assistant sessions are untouched; nothing stored is not an error; arguments are checked like `assistant.configure`'s (`bad_request`, `not_found`).
- Provider changes (`provider.add|update|remove`) answer `internal` when the database refuses the write, and leave the list as it was (0.28; before, the failure was only logged).
- CLI: `hutan config ls|get|set|reset` (`set` takes a TOML value: `true`, `30`, `"text"`, `["a", "b"]`, or bare text for a string) prints `restart the daemon to apply (`hutan daemon restart`)` when the key is pending; `hutan assistant reset [--ws ID]`.

## Error codes
`bad_request`, `unsupported_version`, `unauthorized`, `not_found`, `conflict`, `invalid_state`, `option_not_offered`, `slow_consumer`, `forbidden` (0.12: a setting or boundary refuses an assistant attachment; 0.21: the `[control]` policy refuses an agent, `error.data.control.decision` says why; 0.18: a pid that is not a process of the session; 0.28: `daemon.settings.set` and `assistant.reset` from an agent-originated connection, always), `provider_error`, `internal`.

## Compatibility rules
- Unknown fields are ignored; unknown events are ignored; unknown methods → `bad_request`.
- Additive change = minor bump + capability string; breaking = major bump + ADR.
- Golden fixtures for every message live in `crates/protocol/tests/fixtures/v{major}/`.

## Questions (protocol 0.24, capability `chat.questions`)

`QuestionInfo {id, session_id, turn_id?, title, prompt (markdown), fields: [{id, label, description?, kind, required, default?}], raw_schema?, source?, expires: turn|process, requested_at_ms}`; `kind` is `{type: text|multiline|boolean|secret}`, `{type: choice, options: [{value, label, description?}], multi?, allow_other?}` or `{type: number, integer?, min?, max?}`. Answer values are a string, a number, a boolean or (multi choice) an array of strings. Events: `question.required {question}` and `question.resolved {question_id, session_id, outcome: answered|declined|cancelled|expired, values?, withheld?, decided_by?}` (`values` never holds a secret field's answer; `withheld` names those fields); the same appear in the chat journal as `question_requested` / `question_resolved` agent events. `ChatInfo.pending_questions` counts the session's pending questions and a session with one is `waiting_approval`. Pending questions survive client disconnects and expire with their turn, the agent process or the daemon; every question and its outcome (never the answers) is in the `questions` table. Notification intent `question_required` carries the single action `open`. Provider shapes: `docs/agents.md` § Questions.

## Rich input (protocol 0.23, capability `chat.rich_input`)

Every chat (OMP, Claude Code, Codex, direct, assistant) takes `chat.send` attachments; `ChatSend.text` may be empty when there is one.

- `{kind: "image", path? | data_base64?, media_type}`: PNG, JPEG, GIF or WebP. A `path` is read by the daemon (at most 5 MiB, `IMAGE_MAX_BYTES`), a clipboard image goes inline as base64 (at most 3 000 000 decoded bytes, `IMAGE_INLINE_MAX_BYTES`: one frame is 4 MiB, so a 5 MiB inline image cannot be sent; larger images go by path). The daemon sniffs the bytes (`bad_request` for anything else) and uses what it finds.
- `{kind: "pasted_text", text}`: at most 256 KiB, redacted and bounded like any text attachment.
- `{kind: "file", path, range?, picked?}`: `picked: true` (set by the desktop and the CLI for what the user dropped, picked or typed) reads the file from anywhere; otherwise only below the workspace roots. A directory is `bad_request`.
- Origin (ADR 0016): an agent-originated request may not attach `image` or `pasted_text` (`forbidden`); its `picked` counts for nothing.
- Gates: `[assistant.context]` applies to assistants and to agent-originated messages; an `image` with a `path` needs `files`, inline images and pasted text are not gated.
- `AttachmentMeta` gains `size`, `media_type`, `path` and `sha256` for images; the journal keeps those, never the bytes. `ChatInfo.images` says whether an ACP harness takes images (`promptCapabilities.image`); absent for Codex and direct chats.
- `unsupported` (new `ErrorCode`): the backend or model takes no images (ACP without `promptCapabilities.image`; a provider whose model list does not say the model reads images).

## Recovery (protocol 0.26, capability `session.recovery`)

A daemon start says what it did to every session it found in the database, from facts it has and nothing else (ADR 0009: session processes die with the daemon; nothing "kept running"). `SessionInfo.recovery` is absent for a session the start did not touch (and from every session of a first start).

```
recovery: {
  kind: {type: "shell_respawned", cwd?, was_running?}      // new shell, same folder
       | {type: "agent_resumed", resume_argv}              // the terminal runs the agent's reported resume command
       | {type: "chat_resumed", thread_id?, last_turn: "completed" | "interrupted"}
       | {type: "not_restarted", reason}                   // listed, not running
       | {type: "ended_before"},                           // had ended during the previous run; history only
  previous_epoch?,                                         // the run that ended
  daemon_stop: {state: "clean", at_ms} | {state: "crashed"} | {state: "unknown"},
  restarted_at_ms,                                         // when this daemon started
  lost?: [{type: "approvals", count} | {type: "questions", count} | {type: "turn"} | {type: "task", task_id, title}]
}
```

- **Terminals.** `shell_respawned`: a terminal that was live (`restore_sessions = "respawn"`) is a new process in `cwd`, the last folder the shell reported, else the spec's; its previous command line is not run again. `was_running` is the command of the last *running* terminal block (`OSC 133` C without D), secrets removed (`hutan-index` redaction) and cut to 200 characters, as of the daemon's last write (at most about a second old); it is the command that was running when the previous daemon ended, and it is **not running now**. It is absent when the shell was at a prompt, when the shell has no integration, or when nothing was recorded. `agent_resumed`: the stored resume reference of an agent that reported one replaces the shell (`resume_argv`, as in § Persistence).
- **Chats.** `chat_resumed`: the agent is started again and continues its conversation (`thread/resume`, `session/load`; `thread_id` is what it was asked to continue, absent for a direct chat or when the session had none); the journal is the history. `last_turn: interrupted` says the previous run ended while a turn was open: the journal row never ended (crash), or the shutdown cancelled it (the turn row says `hutan stopped during the turn`; a turn the user cancelled before is `completed`, as is one that failed on its own). `lost` then lists `turn`. If the agent starts but is given a new conversation, `thread_id` is absent.
- **`not_restarted`.** `restore_sessions = "stopped"` (reason `restore_sessions is "stopped"`), a stored spec that cannot be read, a program that cannot be started (the spawn error), and a chat whose agent failed to resume (`resuming failed: …`). A respawned session that exits by itself afterwards is changed to `not_restarted` with the exit (`it exited with code N after the restart`): the recovery never says a session runs that does not. The session state says the rest (`failed`, `stopped`); `session.restart` starts it.
- **`ended_before`.** Sessions that had ended during the previous run only; older endings carry no recovery, only `restored: true`.
- **`daemon_stop`.** `clean`: the previous daemon noted its own shutdown (`hutan daemon stop`, SIGTERM, a deleted socket, `daemon.shutdown`) at `at_ms`, after it hung up on its sessions. `crashed`: its record shows no stop: it was killed, crashed or lost power. `unknown`: no earlier run is recorded, or a build before 0.26 wrote the record. `previous_epoch` is the epoch of that run, from the epoch history in `app_meta`.
- **`lost`.** `approvals`: permission requests of that session that expired with the run (left open by a crash, or expired by the shutdown); `questions`: the same for questions of the agent (`chat.questions`); `turn`: the interrupted turn; `task`: a running task whose session did not survive (it is `failed` with outcome `interrupted`, see § Tasks).
- **Lifetime.** Not stored; every start computes it again. It is cleared, with a `session.updated`, by `session.recovery_ack`, and by the session's next user action: terminal input from a user connection (not an agent's), a user's `chat.send`, `session.stop`, `session.restart`.

The desktop shows one summary per restart (`hutand restarted 3 min ago (it was killed or crashed). 5 sessions: 2 shells respawned, 1 agent resumed (claude --resume …), 1 chat turn interrupted, 1 not restarted (omp not found)`; the absolute local time is its tooltip, `docs/design.md` § Time), chips (`respawned`, `resumed`, `interrupted`, `not restarted`) on the sidebar rows and the terminal and chat headers until acknowledged, Restart for `not_restarted`, and Retry last message for an interrupted turn (the last user message of the journal is sent again; its attachments are not). The CLI has a `RECOVERY` column in `hutan ls`, `hutan recovery` (`hutand restarted at 2026-10-17 14:31 +0500, 3 min ago (it was stopped).`) and `hutan recovery ack [--all|<session>]`.

**Open terminals follow their session.** Terminal ids start over with every daemon, but a respawned session keeps its `SessionId`: after a reconnect to a new epoch the client's terminal handles end with `EpochChanged`, and a view that shows a session the new daemon respawned (its `terminal_id` of the new epoch) attaches to that terminal: a fresh snapshot, input goes to the live shell, the “session is gone” line clears. A view of a session that really ended (`stopped`, `exited`, `failed`, or missing) keeps the ended line, with the new daemon's reason (the desktop: `TerminalSession`, `crates/desktop/src/sessions/terminal.rs`).
